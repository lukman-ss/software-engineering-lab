Example-based tests check developer assumptions; property-based tests explore domain boundaries.

Ilusi Keamanan Example-Based Testing

Unit test berbasis contoh (example-based testing) bekerja dengan menegaskan bahwa f(x) == y untuk segelintir sampel statis. Masalah mendasarnya adalah bias konfirmasi: engineer cenderung hanya menguji kombinasi nilai yang telah mereka antisipasi dalam implementasi. Pada dataset kecil atau input tipikal, kode tampak sempurna dan seluruh baris assertions berstatus PASS. Namun, lolos pengujian statis tidak otomatis memvalidasi kondisi batas yang tidak terduga di lingkungan produksi.

Tiga Pilar Siklus Property-Based Testing

Siklus kerja Property-Based Testing membagi tugas antara komputasi mesin dan perancangan manusia secara terstruktur. Manusia bertanggung jawab mendefinisikan batasan domain serta relasi invariant matematika yang wajib bernilai benar. Mesin PBT kemudian bertindak sebagai musuh (adversary) yang mengeksekusi ratusan kombinasi data acak melalui generator, memverifikasi invariant pada setiap iterasi, dan mengisolasi kegagalan menggunakan algoritma shrinking. Meski demikian, pembuktian invariant di lab belum membuktikan kebalikan dari seluruh skenario konkurensi database nyata.

Empat Pola Invariant Kanonikal

Kunci keberhasilan PBT terletak pada pemilihan pola invariant yang tepat tanpa menulis ulang logika implementasi di dalam assertion test. Pola Roundtrip menguji integritas transformasi bolak-balik tanpa data corruption. Pola Idempotence memeriksa stabilitas state di mana pemanggilan berulang tidak memicu mutasi tambahan. Pola Test Oracle membandingkan algoritma teroptimasi terhadap implementasi referensi sederhana. Pola Easy-to-Verify memeriksa keabsahan properti hasil komputasi kompleks. Memenuhi pola ini bukan berarti menggantikan kebutuhan pengujian integrasi end-to-end.

Pola InvariantFormula FormalContoh Kasus Nyata
RoundtripDecode(Encode(x)) == xSerialisasi JSON, mata uang, kompresi

Kegagalan Presisi Float pada Mata Uang

Menyimpan nilai moneter dalam tipe floating-point float64 adalah anti-pattern klasik dalam rekayasa perangkat lunak. Pemformatan dengan sintaks pembulatan desimal string memotong digit pecahan sub-cent tanpa sinyal peringatan. Konversi string kembali ke float64 tunduk pada aproksimasi biner IEEE 754. Pada pengujian konvensional dengan nilai bulat rapi, kelemahan ini tidak terdeteksi, tetapi keberhasilan contoh statis bukan berarti representasi desimal bebas dari penyimpangan fraksional.

type NaiveCurrency struct{}

func (n NaiveCurrency) Format(dollars float64) string {
    return fmt.Sprintf("$%.2f", dollars)
}

func (n NaiveCurrency) Parse(s string) (float64, error) {
    s = strings.TrimPrefix(s, "$")
    return strconv.ParseFloat(s, 64)
}

PBT Mendeteksi Kebocoran Float 100%

Ketika properti roundtrip diuji menggunakan paket standar Go testing/quick, kelemahan implementasi float64 langsung terekspos. Dari 1.000 iterasi angka acak, seluruh 1.000 input mengalami kegagalan roundtrip karena nilai desimal asli terpotong oleh format dua angka di belakang koma. PBT membuktikan secara empiris bahwa fungsi Parse(Format(x)) bukanlah fungsi identitas bagi domain float64. Namun, temuan ini hanya pada jalur ini dan tidak otomatis mencakup tipe data khusus pada database eksternal.

func TestPropertyNaiveCurrencyFails(t *testing.T) {
    naive := NaiveCurrency{}
    prop := func(val NaiveFloat) bool {
        dollars := float64(val)
        formatted := naive.Format(dollars)
        parsed, err := naive.Parse(formatted)
        if err != nil { return false }
        return parsed == dollars // Gagal pada sub-cent!
    }
    err := quick.Check(prop, &quick.Config{MaxCount: 100})
    // quick.Check mengembalikan error counterexample
}

Desain Robust: Integer Cents Representation

Solusi rekayasa yang terbukti secara industri untuk domain mata uang adalah merepresentasikan nominal terkecil sebagai bilangan bulat utuh (integer cents bertipe int64). Format visual desimal hanyalah proyeksi tampilan pada lapisan presentasi string, sedangkan operasi aritmatika internal dan penyimpanan data tetap berada di ranah bilangan diskrit. Pendekatan ini mengeliminasi distorsi aproksimasi IEEE 754 di memori, tetapi production masih perlu batasan skema database guna menangkal risiko integer overflow.

type RobustAmount struct {
    Cents int64
}

func (r RobustAmount) Format() string {
    absCents := r.Cents; sign := ""
    if absCents < 0 { sign = "-"; absCents = -absCents }
    dollars := absCents / 100; cents := absCents % 100
    return fmt.Sprintf("%s$%d.%02d", sign, dollars, cents)
}

Custom Generator & Boundary Value Bias

Generator acak yang murni seragam (uniform distribution) sering kali melewatkan titik-titik krusial tempat bersarangnya cacat logika batas. Implementasi generator RobustAmount pada Lab 40 menyuntikkan bias probabilitas ke arah nilai rawan: batas nol, transisi bilangan negatif kecil di sekitar nol (-100 hingga +99 sen), serta nilai nominal raksasa multi-miliar sen. Menguji input ekstrem memperketat validasi parser, tetapi biased sampling belum membuktikan ketahanan terhadap string masukan yang cacat format.

func (RobustAmount) Generate(r *rand.Rand, size int) reflect.Value {
    switch r.Intn(5) {
    case 0: cents = 0                         // Boundary zero
    case 1: cents = int64(r.Intn(200) - 100)  // Near-zero negatives
    case 2: cents = int64(r.Intn(1000000))    // Normal positive
    case 3: cents = -int64(r.Intn(1000000))   // Normal negative
    default: cents = r.Int63n(1e12) - 5e11    // Multi-billion bounds
    }
    return reflect.ValueOf(RobustAmount{Cents: cents})
}

Kasus Interval Merge & Asumsi Tersembunyi

Kelemahan algoritma sering kali berakar pada prakondisi implisit yang tidak dinyatakan secara tegas dalam kontrak kode. Fungsi NaiveMerge dirancang untuk menggabungkan interval waktu yang saling tumpang tindih. Namun, loop perulangan langsung membandingkan elemen berjalan terhadap elemen terakhir dari slice output, mengasumsikan input sudah terurut berdasarkan titik awal (Start). Ketika dipanggil dengan contoh terurut, fungsi bekerja mulus, tetapi keberhasilan input terurut tidak otomatis membuktikan kebenaran pada data acak yang tidak terurut.

func NaiveMerge(intervals []Interval) []Interval {
    if len(intervals) == 0 { return nil }
    out := []Interval{intervals[0]}
    for _, iv := range intervals[1:] {
        last := &out[len(out)-1]
        if iv.Start <= last.End {
            if iv.End > last.End { last.End = iv.End }
        } else { out = append(out, iv) }
    }
    return out // BUG: Mengasumsikan input terurut!
}

Test Oracle: Membongkar 85% Discrepancy

Teknik Test Oracle memanfaatkan dua implementasi berbeda untuk input yang sama: f_naive(x) versus f_robust(x). RobustMerge secara eksplisit melakukan pengurutan sort.Slice sebelum proses penggabungan dilakukan. Ketika dievaluasi dengan generator irisan acak, pengujian membongkar bahwa 85 dari 100 input menghasilkan inkonsistensi keluaran antara NaiveMerge dan RobustMerge. Discrepancy ini mengidentifikasi kelemahan algoritma naif, tetapi pengujian oracle hanya valid sejauh implementasi referensinya akurat.

func TestPropertyNaiveMergeFails(t *testing.T) {
    prop := func(ivs IntervalSlice) bool {
        naive := NaiveMerge([]Interval(ivs))
        robust := RobustMerge([]Interval(ivs))
        return intervalsEqual(naive, robust)
    }
    err := quick.Check(prop, &quick.Config{MaxCount: 100})
    // 85 dari 100 input acak menghasilkan ketidaksesuaian!
}

Invariant Idempotence pada Penggabungan Data

Idempotensi adalah sifat matematika fundamental dalam arsitektur komputasi: f(f(x)) == f(x). Dalam konteks pemrosesan data, menjalankan fungsi penggabungan pada kumpulan interval yang sudah digabungkan menghasilkan output yang sama persis tanpa mutasi tambahan. Pengujian TestPropertyRobustMergeIdempotence memvalidasi 1.000 iterasi irisan acak, membuktikan stabilitas operasional pada fungsi murni. Meski demikian, cakupannya mengikuti test dan tidak otomatis membuktikan keamanan konkurensi tanpa sinkronisasi memori eksternal.

// Formula Teoretis: f(f(x)) == f(x)

func TestPropertyRobustMergeIdempotence(t *testing.T) {
    prop := func(ivs IntervalSlice) bool {
        once := RobustMerge([]Interval(ivs))
        twice := RobustMerge(once)
        return intervalsEqual(once, twice)
    }
    quick.Check(prop, &quick.Config{MaxCount: 1000})
}

Invariant Struktural: Non-Overlapping Slices

Selain relasi f(f(x)), kebenaran algoritma penggabungan interval harus memenuhi invariant struktural domain: untuk setiap indeks i dan i+1 pada irisan keluaran, titik akhir interval pertama harus lebih kecil dari titik awal interval berikutnya (out[i].End < out[i+1].Start). Pengujian 1.000 iterasi acak membuktikan tidak ada segmen bertumpuk yang tersisa. Memenuhi aturan struktural ini membatasi anomali partisi data, namun simulasi ini tidak mencakup batasan memori jika volume interval mencapai jutaan entri.

func TestPropertyRobustMergeNonOverlapping(t *testing.T) {
    prop := func(ivs IntervalSlice) bool {
        merged := RobustMerge([]Interval(ivs))
        for i := 0; i < len(merged)-1; i++ {
            if merged[i].End >= merged[i+1].Start {
                return false // Ada tumpang tindih!
            }
        }
        return true
    }
    quick.Check(prop, &quick.Config{MaxCount: 1000})
}

Anatomi Masalah: Kompleksitas Counterexample

Ketika mesin PBT mendeteksi pelanggaran invariant pada input acak berukuran besar, output mentahnya sering kali berupa struktur data raksasa yang membingungkan. Pada contoh demo, input yang memicu kegagalan predicate adalah array 10 elemen acak yang bercampur antara ratusan angka positif dan dua bilangan negatif (-27 dan -7). Tanpa mekanisme reduksi otomatis, engineer menghabiskan waktu signifikan memilah data mana yang sebenarnya memicu kegagalan sistem.

  • Array Awal (10 elemen acak): [137, 18, 100, -27, 95, 107, 126, 78, -7, 79]
  • Apakah kegagalan dipicu oleh magnitudo nilai 137 atau panjang array 10?
  • Apakah posisi urutan elemen saling mempengaruhi hasil evaluasi?
  • Apa pemicu batas minimal mutlak yang menyebabkan pelanggaran invariant?

Konsep dan Algoritma Shrinking

Algoritma counterexample shrinking dirancang untuk mentransformasikan input kegagalan mentah menjadi kasus reproduksi minimal deterministik. Algoritma bekerja dalam tiga fase bertingkat: pemotongan biner (halving) panjang array, penghapusan elemen individual satu per satu, dan pengecilan magnitudo nilai numerik mendekati nol. Setiap langkah yang mempertahankan status gagal (FAIL) diadopsi sebagai kandidat baru. Menemukan counterexample minimal mempercepat isolasi akar masalah, tetapi bukan berarti bug kode terselesaikan secara otomatis.

Fase AlgoritmaAksi ReduksiTarget Optimasi
1. Binary SectioningPotong separuh kiri / kanan arrayPangkas ukuran O(log N)
2. Element RemovalHapus elemen individual satu per satuEliminasi noise non-kritis
3. Value ReductionBagi dua nilai elemen menuju 0Minimalisasi magnitudo nilai

Binary Sectioning: Memangkas Panjang Array

Fase pertama dari shrinking adalah binary chunking. Algoritma membagi slice menjadi dua bagian (kiri dan kanan), lalu mengevaluasi predicate pada masing-masing belahan. Jika belahan kiri masih memicu kegagalan, separuh bagian kanan langsung dibuang secara permanen. Dalam demo, array 10 elemen terpotong menjadi 5 elemen, lalu menjadi 3 elemen dalam hitungan langkah awal. Pemotongan biner memangkas derau secara cepat, tetapi hanya pada jalur ini di mana predicate kegagalan bersifat independen terhadap panjang array.

if len(current) > 1 {
    mid := len(current) / 2
    left := current[:mid]
    if !predicate(left) {
        current = append([]int(nil), left...)
        changed = true; continue
    }
    right := current[mid:]
    if !predicate(right) {
        current = append([]int(nil), right...)
        changed = true; continue
    }
}

Reduksi Elemen & Magnitudo Menuju Nol

Setelah panjang array dipangkas hingga tersisa elemen tunggal [-27], algoritma melanjutkan ke strategi ketiga: reduksi nilai numerik. Nilai -27 secara bertahap dibagi dua mendekati nol: -27 -> -13 -> -6 -> -3 -> -1. Ketika mencapai -1, langkah berikutnya yaitu 0 menghasilkan PASS (karena 0 bukan negatif). Algoritma berhenti dan menetapkan [-1] sebagai nilai batas minimal. Reduksi nilai memperjelas batas numerik, tetapi heuristik ini perlu bukti tambahan untuk fungsi non-linear yang kompleks.

// Coba set elemen menjadi 0 atau bagi dua nilainya
candidates := []int{0, current[i] / 2}
for _, cand := range candidates {
    testSlice := append([]int(nil), current...)
    testSlice[i] = cand
    if !predicate(testSlice) {
        current = testSlice
        changed = true; break
    }
}

Log eksekusi demo memperlihatkan transparansi penuh proses reduksi data. Dari input awal acak 10 elemen, mesin hanya membutuhkan 21 evaluasi predikat untuk membuang 9 elemen tidak relevan serta mereduksi nilai -27 menjadi -1. Hasil akhir [-1] memberikan kejelasan diagnostik instan: masalah murni disebabkan oleh keberadaan bilangan negatif. Jejak 21 langkah ini membuktikan efisiensi algoritma pada kasus uji lab, tetapi jumlah langkah reduksi bervariasi bergantung pada struktur data input awal.

Integrasi Go Standard Library testing/quick

Salah satu keunggulan ekosistem Go adalah ketersediaan paket bawaan testing/quick di dalam standard library tanpa dependensi pihak ketiga. Fungsi quick.Check mengeksekusi properti hingga ribuan kali dengan konfigurasi MaxCount dan seed kustom. Generator bawaan secara otomatis menangani tipe data primitif, sedangkan interface quick.Generator memungkinkan engineer menyuntikkan generator buatan sendiri. Memakai testing/quick menghilangkan beban dependensi eksternal, namun testing/quick belum menyertakan shrinker bawaan secara terintegrasi.

cfg := &quick.Config{
    MaxCount: 1000, // Jumlah iterasi acak yang dieksekusi
    Rand:     rand.New(rand.NewSource(seed)), // Determinisme
}

err := quick.Check(func(a RobustAmount) bool {
    return ParseRobust(a.Format()) == a
}, cfg)
if err != nil {
    t.Fatalf("property violation: %v", err)
}

Determinisme, Seeding, & CI/CD Pipeline

Kritik yang kerap diarahkan pada PBT adalah risiko munculnya flaky tests jika seed acak berubah di setiap eksekusi CI. Pendekatan terstruktur membagi pengujian ke dua ranah: pada local test dan PR check, terapkan seed tetap dengan 100–500 iterasi agar eksekusi cepat dan konsisten; pada nightly build, jalankan seed dinamis dengan 50.000 iterasi untuk memperluas cakupan eksplorasi. Mencatat log failing seed memfasilitasi reproduksi lokal, tetapi determinisme seed tidak otomatis menyelesaikan flakiness yang dipicu oleh ketergantungan waktu sistem.

Matriks Komparasi Example vs PBT

Matriks perbandingan memperlihatkan pergeseran paradigma kualitas pengujian. Unit test konvensional sangat baik untuk memvalidasi alur bisnis spesifik dan skenario regresi tertentu. Namun, untuk sistem yang menangani kalkulasi finansial, protokol serialisasi, atau struktur data, PBT memberikan keyakinan yang lebih terkalibrasi melalui eksplorasi spektrum input kontinu dan reduksi kegagalan deterministik. Walaupun PBT memperluas cakupan batas domain, penggunaannya tidak otomatis meniadakan kebutuhan skenario pengujian fungsional.

Praktik Terbaik & Anti-Pattern PBT

Kesalahan umum saat mengadopsi PBT adalah kecenderungan developer menduplikasi logika fungsi yang diuji ke dalam assertion test. Praktik ini berisiko karena jika implementasi memiliki kecacatan logika, asersi duplikat akan ikut meloloskannya. Asersi harus berfokus murni pada sifat relasional independen seperti roundtrip dan idempotensi. Pastikan generator secara terencana menyertakan nilai batas ekstrem (nol, negatif, irisan kosong), dan simpan counterexample yang ditemukan sebagai unit test regresi permanen.
