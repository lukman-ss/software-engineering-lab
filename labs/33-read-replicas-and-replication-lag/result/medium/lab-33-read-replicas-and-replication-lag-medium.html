Masalah Nyata: Ilusi Freshness di Balik Read Replica

Skenario ini terjadi secara default di hampir semua database production yang menggunakan primary-replica topology. PostgreSQL streaming replication, MySQL async replication, AWS RDS read replicas, dan Azure Database for PostgreSQL semuanya menjalankan replikasi asinkron secara default tanpa konfigurasi khusus. Ketika client application melakukan pattern write-then-read pada session yang sama, ia tidak memiliki awareness bahwa data yang baru ditulis belum tersedia di replica target. Akibatnya, user mengalami anomali UX yang sulit dilacak karena log menunjukkan write sukses, tapi query berikutnya gagal membaca data yang sama.

Mengapa Read Naif ke Replica Selalu Berisiko?

Implementasi ReadNaive menunjukkan pendekatan paling sederhana dalam read splitting: arahkan setiap request ke replica berikutnya secara berputar. Namun pendekatan ini mengabaikan fakta fundamental bahwa setiap replica memiliki appliedLSN yang mungkin jauh di belakang currentLSN primary. Dalam kondisi write-heavy workload dengan replication lag 200 milidetik, probabilitas mendapatkan stale read bisa mendekati 100% untuk key yang baru ditulis. Bug ini termasuk subtle karena tidak menghasilkan panic atau crash — hanya mengembalikan data salah yang terasa aneh bagi pengguna akhir.

func (r *Router) ReadNaive(key string) (string, string, uint64, error) {
    replicas := r.cluster.Replicas()
    if len(replicas) == 0 {
        return r.cluster.Primary().Read(key)  // Fallback aman
    }
    idx := r.rrIndex.Add(1) % uint64(len(replicas))
    target := replicas[idx]
    return target.Read(key)  // Tanpa cek appliedLSN!
}

Mental Model: LSN sebagai Jangkar Konsistensi

Model mental ini memisahkan dua lapisan abstraction: lapisan konsistensi (LSN sequence) dan lapisan ketersediaan (data distribution). Primary bertindak sebagai single writer yang memberi nomor urut absolut pada setiap transaksi. Setiap replica secara independen consume dan apply entry WAL dengan latensi tertentu. Router membaca appliedLSN setiap replica untuk membuat keputusan routing yang informed. Tanpa LSN, kita tidak bisa membedakan replica yang fresh versus lagging secara terukur — routing menjadi guesswork belaka.

type WALEntry struct {
    LSN       uint64    // monotonik naik dari primary
    Key       string
    Value     string
    Timestamp time.Time
}

Pipeline Write-Read dengan Replication Lag

Pipeline ini menggambarkan perjalanan lengkap sebuah request dari penulisan hingga pembacaan dengan empat varian routing strategy. Jalur pertama menelusuri write path di mana primary mengincrement currentLSN secara atomik lalu broadcasting WAL entry ke channel setiap replica. Jalur kedua mensimulasikan replication lag melalui goroutine worker yang tidur sesuai duration sebelum apply. Empat jalur ketiga menunjukkan bagaimana router memilih target read: naive round-robin tanpa proteksi, sticky session berbasis waktu, token-based LSN wait dengan blocking, atau lag-aware dynamic filtering dengan threshold.

Implementasi Sticky Session Router

Potongan kode ini merupakan implementasi time-based sticky routing yang paling sederhana namun efektif. Method pertama-tama memeriksa apakah session ID memiliki state yang terekam di sync.Map. Jika state ditemukan dan waktu sejak lastWrite masih dalam batas StickyDuration, router secara deterministik mengarahkan read ke primary — bukan replica manapun. Ini memastikan read-your-own-writes dalam jendela sticky tanpa biaya LSN check. Setelah jendela habis, flow jatuh ke ReadLagAware yang menggunakan threshold filtering.

func (r *Router) ReadWithStickySession(sessionID, key string) (string, string, uint64, error) {
    if stateVal, ok := r.sessions.Load(sessionID); ok {
        state := stateVal.(SessionState)
        if time.Since(state.LastWriteTime) < r.config.StickyDuration {
            val, lsn, err := r.cluster.Primary().Read(key)
            return val, r.cluster.Primary().ID(), lsn, err
        }
    }
    return r.ReadLagAware(key)
}

Failure Path: Stale Read Anomali di Demo CLI

Failure path ini diambil langsung dari demo CLI ketika ReadNaive dipanggil tepat setelah write. Primary LSN meningkat ke 1, namun replica-2 masih berada di appliedLSN 0 karena worker goroutine belum menyelesaikan sleep 200 milidetik. Load balancer round-robin memilih replica-2 untuk read berikutnya, menyebabkan key not found karena data belum tersedia. Error ini berbeda dengan koneksi mati atau timeout — aplikasi merespons 200 dengan body kosong, membuat debugging menjadi nightmare bagi engineer yang tidak memahami replication topology.

Mekanisme vs Gejala: Evaluasi Strategi Read Routing

Tabel ini mengklasifikasikan empat strategi routing berdasarkan empat dimensi evaluasi. ReadNaive menghilangkan overhead komunikasi tetapi mengorbankan konsistensi sepenuhnya. Sticky session menawarkan jaminan session-level freshness dengan overhead minimal berupa time comparison dan session map lookup. Causal token memberikan jaminan kausal terukur tetapi memperkenalkan blocking wait yang dapat meningkatkan p99 latency. Lag-aware filtering menyeimbangkan throughput dan freshness melalui threshold predicate, degraded gracefully ke primary ketika tidak ada replica yang memenuhi syarat.

Output terminal ini menyajikan empat bukti eksekusi yang masing-masing mengonfirmasi perilaku strategi routing. YANG TIDAK DIBUKTIKAN

Klaim teknis laboratorium ini dibatasi oleh parameter lingkungan pengujian yang disederhanakan. Cluster yang digunakan berjalan in-memory tanpa persistence disk, sehingga tidak bisa membuktikan perilaku recovery setelah node crash. State router disimpan dalam sync.Map lokal single-process, berbeda dengan arsitektur stateless production yang memerlukan Redis atau shared session store. Simulasi replication lag menggunakan timer sleep 200 milidetik, bukan network latency riil yang bervariasi. Konstanta timing seperti sticky 500ms dipilih untuk deterministik demo, bukan sebagai guideline tuning produksi.

Trade-off Arsitektur: Freshness vs Throughput

Penerapan strategi replication lag mitigation menuntut kompromi arsitektural antara freshness guarantee dan read throughput. Sticky session menambahkan overhead berupa concentrated primary reads selama jendela waktu, tetapi eliminasi stale read sepenuhnya untuk session-bound operations. Causal token menawarkan presisi deterministik namun memperkenalkan blocking wait yang menggeser p99 latency read path. Lag-aware filtering menyeimbangkan keduanya dengan filtering threshold yang dapat dikonfigurasi, degraded gracefully ke primary ketika semua replica terlambat. Synchronous replication menghilangkan lag sama sekali dengan harga write latency ekstra yang proporsional dengan jumlah replica.

Validasi Konkurensi: 15 Goroutine × 20 Operasi Race-Free

Uji konkurensi ini membuktikan ketahanan implementasi saat 15 goroutine bersamaan mengeksekusi pattern write-then-read pada 20 iterasi per session. Setiap goroutine menggunakan session ID unik yang menjaga isolation state di Router sync.Map. Cluster dengan tiga replica worker memproses WAL entries secara paralel dengan gap 10 milidetik. Di bawah go race detector, tidak ada data race terdeteksi di seluruh memory accesses Router methods maupun Cluster nodes. Test ini mengonfirmasi bahwa concurrent access ke shared state tetap linearizable berkat mutex proteksi di setiap node.

func TestConcurrentAccess_RaceFree(t *testing.T) {
    c := cluster.NewCluster(3, 10*time.Millisecond, cluster.AsyncReplication)
    defer c.Close()
    r := router.NewRouter(c, router.DefaultConfig())

    var wg sync.WaitGroup
    for i := 0; i < 15; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            sid := fmt.Sprintf('s%d', id)
            _, _ = r.Write(sid, fmt.Sprintf('k%d', id), fmt.Sprintf('v%d', id))
            for j := 0; j < 20; j++ {
                _, _, _, _ = r.ReadWithStickySession(sid, fmt.Sprintf('k%d', id))
            }
        }(i)
    }
    wg.Wait()
}

Before vs After: Evolusi Read Routing Strategy

Perbandingan before-after ini menunjukkan evolusi arsitektur read routing dari pendekatan naif yang rentan stale read menuju sistem four-layer mitigation dengan fallback bertingkat. Sebelum penerapan strategi, setiap write-then-read cycle berisiko tinggi menghasilkan data usang karena tidak ada mekanisme penutupan replication gap. Setelah implementasi, sistem memiliki tiga lapis proteksi: sticky session untuk session-bound operations, causal token untuk critical reads, dan lag-aware filtering untuk bulk analytics. Setiap lapis memiliki fallback eksplisit ke primary dengan logging yang dapat diobservasi.

Test 1: Stale Read Terjadi Tanpa Proteksi

Unit test pertama membuktikan keberadaan stale read anomaly secara eksplisit. Setelah write ke primary dengan key 'key:A', panggilan ReadNaive seketika menghasilkan error ErrNotFound karena replica belum menerapkan WAL entry. Setelah menunggu 250 milidetik yang melampaui batas lag 200 milidetik, read yang sama berhasil mengembalikan value yang benar. Test ini mengonfirmasi bahwa anomali bersifat temporal — bukan permanen — dan dapat dicegah dengan menambahkan lapisan routing intelligence di antara write commit dan read dispatch.

func TestNaiveReplicationLag_StaleRead(t *testing.T) {
    c := cluster.NewCluster(2, 200*time.Millisecond, cluster.AsyncReplication)
    defer c.Close()
    r := router.NewRouter(c, router.DefaultConfig())

    _, err := r.Write("s1", "key:A", "value-A")
    if err != nil { t.Fatalf("Write failed: %v", err) }

    // Immediately read without any mitigation
    val, nodeID, lsn, err := r.ReadNaive("key:A")
    if err == nil {
        t.Fatalf("Expected stale read error, got val=%s node=%s lsn=%d", val, nodeID, lsn)
    }
    // After waiting for lag to expire, read should succeed
    time.Sleep(250 * time.Millisecond)
    val, nodeID, lsn, err = r.ReadNaive("key:A")
    if err != nil { t.Fatalf("Post-lag read failed: %v", err) }
}

Test 2: Sticky Session Menjamin Read-Your-Own-Writes

Unit test kedua mengonfirmasi bahwa sticky session routing berhasil mencegah stale read dalam jendela waktu yang ditentukan. Read yang dipanggil dalam 500 milidetik pasca-write secara konsisten diarahkan ke primary node, menjamin data fresh tersedia. Setelah jendela expire dengan sleep 600 milidetik, routing otomatis bergeser ke ReadLagAware yang menyeleksi replica berdasarkan threshold eligibility. Test ini membuktikan bahwa pendekatan time-based sederhana namun efektif untuk session-bound read patterns tanpa memerlukan LSN tracking di setiap request.

func TestStickySessionRouting(t *testing.T) {
    c := cluster.NewCluster(2, 200*time.Millisecond, cluster.AsyncReplication)
    defer c.Close()
    cfg := router.DefaultConfig()
    cfg.StickyDuration = 500 * time.Millisecond
    r := router.NewRouter(c, cfg)

    _, err := r.Write("s1", "key:B", "value-B")
    if err != nil { t.Fatalf("Write failed: %v", err) }

    // Read within sticky window — must hit primary
    val, nodeID, _, err := r.ReadWithStickySession("s1", "key:B")
    if err != nil || val != "value-B" || !strings.HasSuffix(nodeID, "primary") {
        t.Fatalf("Sticky read failed or hit wrong node: val=%s node=%s err=%v", val, nodeID, err)
    }

    time.Sleep(600 * time.Millisecond) // Expire sticky window
    val, nodeID, _, err = r.ReadWithStickySession("s1", "key:B")
    if err != nil || nodeID == "primary" {
        t.Fatalf("Post-sticky read should route to replica, got node=%s", nodeID)
    }
}

Test 3: Causal Token Tunggu Catch-Up Sebelum Serve Read

Unit test ketiga menguji implementasi causal token routing yang melibatkan blocking wait mechanism. Setelah write dengan LSN tertentu, ReadWithToken iterasi replica untuk menemukan yang sudah mencapai threshold LSN. Ketika tidak ada replica yang match, method memanggil WaitForLSN pada replica pertama dengan context timeout. Test ini memvalidasi bahwa read blocked selama sekitar 200 milidetik menunggu replica catch-up, kemudian melayani response dengan nilai fresh dan LSN yang sesuai. Blocking behavior ini merupakan bedanya dengan sticky session yang hanya mengandalkan waktu tanpa memeriksa LSN aktual.

func TestReadWithToken_LSN(t *testing.T) {
    c := cluster.NewCluster(1, 200*time.Millisecond, cluster.AsyncReplication)
    defer c.Close()
    r := router.NewRouter(c, router.DefaultConfig())

    lsn, err := r.Write("s1", "key:C", "value-C")
    if err != nil { t.Fatalf("Write failed: %v", err) }

    start := time.Now()
    val, nodeID, readLSN, err := r.ReadWithToken(context.Background(), lsn, "key:C")
    elapsed := time.Since(start)

    if err != nil { t.Fatalf("ReadWithToken failed: %v", err) }
    if val != "value-C" { t.Fatalf("Expected value-C, got %s", val) }
    if readLSN < lsn { t.Fatalf("Expected LSN >= %d, got %d", lsn, readLSN) }
    if elapsed < 150*time.Millisecond {
        t.Fatalf("Expected token read to wait ~200ms, finished in %v on node %s", elapsed, nodeID)
    }
}

Studi Kasus Industri: Replication Lag di Database Production

Studi kasus industri menunjukkan bahwa masalah replication lag bukan teoretis melainkan operasional sehari-hari di infrastruktur cloud modern. AWS RDS menyediakan metric ReplicaLag melalui CloudWatch yang memungkinkan tim SRE mendeteksi anomali sebelum user complaint muncul. PostgreSQL streaming replication memberikan kontrol granular melalui synchronous_commit parameter yang membedakan antara durability guarantee dan visibility guarantee. Aplikasi enterprise besar seperti Twitter dan Netflix mengimplementasikan custom session-affinity routing di layer client library untuk menutup gap readability tanpa menunggu perbaikan di database engine.

Bagaimana WaitForLSN Membedakan Blocking dan Timeout?

Implementasi WaitForLSN menunjukkan pola konkurensi Go yang elegan untuk menunggu kondisi berbasis channel dan condvar. Goroutine waiter mengakuisisi mutex node, loop until appliedLSN memenuhi target, dan memanggil cond.Wait() yang secara atomik melepaskan mutex sambil memblokir goroutine. Worker goroutine setelah apply WAL entry memanggil cond.Broadcast() untuk membangunkan semua waiter yang sedang blocked. Context cancellation memberikan jalur escape yang aman dengan menutup stop channel dan memicu broadcast ulang agar waiter tidak stuck selamanya.

func (n *Node) WaitForLSN(ctx context.Context, targetLSN uint64) error {
    ch := make(chan struct{})
    stop := make(chan struct{})
    go func() {
        n.mu.Lock()
        defer n.mu.Unlock()
        for n.appliedLSN < targetLSN {
            select {
            case <-stop:
                return
            default:
            }
            n.cond.Wait()  // Release lock, block until Broadcast
        }
        close(ch)
    }()
    select {
    case <-ctx.Done():
        close(stop); n.cond.Broadcast(); return ctx.Err()
    case <-ch:
        return nil
    }
}

Checklist Implementasi Read Replica Strategy

Daftar periksa ini merangkum sepuluh prinsip krusial yang wajib dipenuhi sebelum deploying read replica strategy ke production. Parameter timing seperti sticky duration dan wait timeout tidak boleh di-set berdasarkan feeling, melainkan harus dikalibrasi dari data historis replication lag percentile. Monitoring dan alerting menjadi mata telinga operator untuk mendeteksi degradation sebelum user complain. State management router perlu diverifikasi tidak menyebabkan memory leak pada session lifecycle yang panjang. Terakhir, dibedakan antara synchronous replication untuk critical path versus asynchronous dengan application-level fencing untuk read-heavy workload.

Anti-Pattern: Kesalahan Desain yang Harus Dihindari

Mengabaikan prinsip desain replication topology dapat berakibat fatal bagi availability dan consistency system. Anti-pattern yang paling sering terjadi adalah underestimate durasi sticky window dibanding actual replication lag, menghasilkan false sense of security bagi engineer. Tidak menyertakan fallback primary pada lag-aware routing berarti read operations akan total unavailable ketika semua replica mengalami lag spike simultan. Hardcoding sleep duration alih-alih menggunakan context timeout juga menyebabkan goroutine leakage yang dapat mematikan seluruh cluster worker.

Prinsip Arsitektur: Desain untuk Asinkronitas

Tiga prinsip arsitektur ini berlaku universal di luar implementasi lab Go ini. Pertama, sadari bahwa asinkronitas adalah default industri dan upaya menghilangkannya secara total akan mengorbankan skalabilitas tulis.
