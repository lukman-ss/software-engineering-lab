Read Replica dan Replication Lag: Menjaga Read-Your-Own-Writes Tanpa Mengorbankan Skalabilitas Baca

Menjaga Read-Your-Own-Writes Tanpa Mengorbankan Skalabilitas Baca

Lukman / lukman-ss · Software Engineering Lab 33

Laboratorium ini membahas masalah nyata yang dihadapi setiap backend engineer yang menggunakan read replica untuk scaling database: stale read. Ketika write baru commit ke primary, replica menerima aliran WAL secara asinkron dengan delay tertentu. Jika aplikasi langsung mengarahkan read user ke replica tanpa mekanisme penutupan jarak tersebut, user akan melihat data lama bahkan menerima not-found untuk key yang baru saja ditulis. Lab ini mengimplementasikan empat strategi mitigasi — time-based sticky routing, causal token dengan LSN wait, lag-aware dynamic filtering, dan synchronous remote_apply — dalam simulasi cluster in-memory Go yang utuh.

Masalah Nyata: Ilusi Freshness di Balik Read Replica

Skenario ini terjadi secara default di hampir semua database production yang menggunakan primary-replica topology. PostgreSQL streaming replication, MySQL async replication, AWS RDS read replicas, dan Azure Database for PostgreSQL semuanya menjalankan replikasi asinkron secara default. Ketika client application melakukan pattern write-then-read pada session yang sama, ia tidak memiliki awareness bahwa data yang baru ditulis belum tersedia di replica target.

  • Write Committed: User mengubah field 'tier' premium; request dialihkan ke primary; write berhasil 200;
  • Replica Lagging: WAL entry LSN 47 mengalir ke replica-1 namun belum di-apply; appliedLSN = 44;
  • Stale Read Terjadi: Load balancer round-robin mengalihkan read ke replica-1; query SELECT profile WHERE id=user mendapat ErrNotFound;

Mengapa Read Naif ke Replica Selalu Berisiko?

Implementasi ReadNaive menunjukkan pendekatan paling sederhana: arahkan setiap request ke replica berikutnya secara berputar. Namun pendekatan ini mengabaikan fakta fundamental bahwa setiap replica memiliki appliedLSN yang mungkin jauh di belakang primary. Dalam kondisi write-heavy workload dengan replication lag 200 milidetik, probabilitas mendapatkan stale read bisa mendekati 100% untuk key yang baru ditulis.

func (r *Router) ReadNaive(key string) (string, string, uint64, error) {
    replicas := r.cluster.Replicas()
    if len(replicas) == 0 {
        return r.cluster.Primary().Read(key)
    }
    idx := r.rrIndex.Add(1) % uint64(len(replicas))
    target := replicas[idx]
    return target.Read(key)
}
  • Tidak ada validasi AppliedLSN vs currentLSN sebelum melayani read;
  • Round-robin indifferent terhadap freshness state setiap replica;
  • Stale read probability berbanding lurus dengan throughput write;

Mental Model: LSN sebagai Jangkar Konsistensi

Model mental ini memisahkan dua lapisan abstraction: lapisan konsistensi (LSN sequence) dan lapisan ketersediaan (data distribution). Primary bertindak sebagai single writer yang memberi nomor urut absolut pada setiap transaksi. Setiap replica secara independen consume dan apply WAL entries dengan latensi tertentu. Router membaca appliedLSN setiap replica untuk membuat keputusan routing yang informed.

type WALEntry struct {
    LSN       uint64
    Key       string
    Value     string
    Timestamp time.Time
}
  • Primary: mengasign LSN atomic saat commit write; sumber kebenaran tunggal;
  • Replica: menyimpan map data KV + appliedLSN + goroutine worker consumption WAL;
  • Gap: currentLSN - appliedLSN = ukuran replication lag saat ini;

Pipeline Write-Read dengan Replication Lag

Pipeline ini menggambarkan perjalanan lengkap sebuah request dari penulisan hingga pembacaan dengan empat varian routing strategy. Setiap langkah menunjukkan bagaimana data ditulis ke primary lalu menyebar ke replica, serta bagaimana router membuat keputusan akhir berdasarkan LSN.

1. Client.Write → Primary commit, LSN increment, WAL broadcast ke replica channel
2. Replica worker sleep(lagDuration) → entry apply, appliedLSN = entry.LSN, cond.Broadcast
3a. ReadNaive: round-robin pilih replica → jika appliedLSN < lastWriteLSN → stale read
3b. ReadWithStickySession: cek waktu → redirect ke primary jika dalam sticky window
3c. ReadWithToken: iterasi replica untuk appliedLSN >= minLSN → blocking wait
3d. ReadLagAware: hitung diff = primaryLSN - appliedLSN → filter threshold

Implementasi Sticky Session Router

Potongan kode ini merupakan implementasi time-based sticky routing yang paling sederhana namun efektif. Method pertama-tama memeriksa apakah session ID memiliki state yang terekam di sync.Map. Jika state ditemukan dan waktu sejak lastWrite masih dalam batas StickyDuration, router secara deterministik mengarahkan read ke primary — bukan replica manapun.

func (r *Router) ReadWithStickySession(sessionID, key string) (string, string, uint64, error) {
    if stateVal, ok := r.sessions.Load(sessionID); ok {
        state := stateVal.(SessionState)
        if time.Since(state.LastWriteTime) < r.config.StickyDuration {
            val, lsn, err := r.cluster.Primary().Read(key)
            return val, r.cluster.Primary().ID(), lsn, err
        }
    }
    return r.ReadLagAware(key)
}

Trade-off Arsitektur: Freshness vs Throughput

Penerapan strategi replication lag mitigation menuntut kompromi arsitektural antara freshness guarantee dan read throughput. Sticky session menambahkan overhead berupa concentrated primary reads selama jendela waktu, tetapi eliminasi stale read sepenuhnya untuk session-bound operations. Causal token menawarkan presisi deterministik namun memperkenalkan blocking wait yang dapat meningkatkan p99 latency.

  • Manfaat: Read-Your-Own-Writes terjamin; Replica menanggung sebagian besar beban read; Fallback ke primary eksplisit; LSN metrics dapat dipantau;
  • Konsekuensi & Biaya: Sticky Window Overhead primary menambah traffic; Blocking Latency p99 read naik saat replica belum catch-up; Complexity cost router membutuhkan session state management dan LSN inspection;

Validasi Konkurensi: 15 Goroutine × 20 Operasi Race-Free

Uji konkurensi membuktikan ketahanan implementasi saat 15 goroutine bersamaan mengeksekusi pattern write-then-read pada 20 iterasi per session. Setiap goroutine menggunakan session ID unik yang menjaga isolation state di Router sync.Map. Cluster dengan tiga replica worker memproses WAL entries secara paralel. Di bawah go race detector, tidak ada data race terdeteksi.

func TestConcurrentAccess_RaceFree(t *testing.T) {
    c := cluster.NewCluster(3, 10*time.Millisecond, cluster.AsyncReplication)
    defer c.Close()
    r := router.NewRouter(c, router.DefaultConfig())

    var wg sync.WaitGroup
    for i := 0; i < 15; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            sid := fmt.Sprintf("s%d", id)
            _, _ = r.Write(sid, fmt.Sprintf("k%d", id), fmt.Sprintf("v%d", id))
            for j := 0; j < 20; j++ {
                _, _, _, _ = r.ReadWithStickySession(sid, fmt.Sprintf("k%d", id))
            }
        }(i)
    }
    wg.Wait()
}
  • Race Detector: PASS (zero data race, 3.98s);
  • Session Isolation: 15 session unik tidak saling mengganggu;
  • Write-Read Consistency: Setiap session melihat data yang ditulis sendiri;
  • Cluster Stability: 3 replica workers tetap stabil tanpa goroutine leak;

Test 1: Stale Read Terjadi Tanpa Proteksi

Unit test pertama membuktikan stale read anomaly secara eksplisit. Setelah write ke primary, ReadNaive mengembalikan ErrNotFound karena replica belum menerapkan WAL entry. Setelah menunggu 250ms yang melampaui batas lag 200ms, read yang sama berhasil mengembalikan value yang benar.

func TestNaiveReplicationLag_StaleRead(t *testing.T) {
    c := cluster.NewCluster(2, 200*time.Millisecond, cluster.AsyncReplication)
    defer c.Close()
    r := router.NewRouter(c, router.DefaultConfig())

    _, err := r.Write("s1", "key:A", "value-A")
    if err != nil { t.Fatalf("Write failed: %v", err) }

    val, nodeID, lsn, err := r.ReadNaive("key:A")
    if err == nil {
        t.Fatalf("Expected stale read error, got val=%s node=%s lsn=%d", val, nodeID, lsn)
    }
    time.Sleep(250 * time.Millisecond)
    val, nodeID, lsn, err = r.ReadNaive("key:A")
    if err != nil { t.Fatalf("Post-lag read failed: %v", err) }
}
  • Immediate Read: ReadNaive pasca-write menghasilkan ErrNotFound (stale read);
  • Post-Lag Read: Setelah sleep 250ms, read berhasil dengan nilai fresh;
  • Node Affinity: Setelah catch-up, read dapat berhasil dari replica manapun;

Test 2: Sticky Session Menjamin Read-Your-Own-Writes

Unit test kedua mengonfirmasi sticky session routing berhasil mencegah stale read dalam jendela waktu yang ditentukan. Read yang dipanggil dalam 500ms pasca-write secara konsisten diarahkan ke primary, menjamin data fresh. Setelah jendela expire, flow jatuh ke ReadLagAware.

func TestStickySessionRouting(t *testing.T) {
    c := cluster.NewCluster(2, 200*time.Millisecond, cluster.AsyncReplication)
    defer c.Close()
    cfg := router.DefaultConfig()
    cfg.StickyDuration = 500 * time.Millisecond
    r := router.NewRouter(c, cfg)

    _, err := r.Write("s1", "key:B", "value-B")
    if err != nil { t.Fatalf("Write failed: %v", err) }

    val, nodeID, _, err := r.ReadWithStickySession("s1", "key:B")
    if err != nil || val != "value-B" || !strings.HasSuffix(nodeID, "primary") {
        t.Fatalf("Sticky read failed or hit wrong node")
    }

    time.Sleep(600 * time.Millisecond)
    val, nodeID, _, err = r.ReadWithStickySession("s1", "key:B")
    if err != nil || nodeID == "primary" {
        t.Fatalf("Post-sticky read should route to replica")
    }
}
  • Pre-Expiration: Read dalam 500ms pertama selalu diarahkan ke primary;
  • Post-Expiration: Setelah 600ms, routing beralih ke read lag-aware;
  • Value Integrity: Payload 'value-B' konsisten di primary dan replica;

Test 3: Causal Token Tunggu Catch-Up Sebelum Serve Read

Unit test ketiga menguji implementasi causal token routing dengan blocking wait mechanism. Setelah write dengan LSN tertentu, ReadWithToken iterasi replica untuk menemukan yang sudah mencapai threshold LSN. Test ini memvalidasi bahwa read blocked selama sekitar 200ms menunggu replica catch-up.

func TestReadWithToken_LSN(t *testing.T) {
    c := cluster.NewCluster(1, 200*time.Millisecond, cluster.AsyncReplication)
    defer c.Close()
    r := router.NewRouter(c, router.DefaultConfig())

    lsn, err := r.Write("s1", "key:C", "value-C")
    if err != nil { t.Fatalf("Write failed: %v", err) }

    start := time.Now()
    val, nodeID, readLSN, err := r.ReadWithToken(context.Background(), lsn, "key:C")
    elapsed := time.Since(start)

    if err != nil { t.Fatalf("ReadWithToken failed: %v", err) }
    if val != "value-C" { t.Fatalf("Expected value-C, got %s", val) }
    if readLSN < lsn { t.Fatalf("Expected LSN >= %d, got %d", lsn, readLSN) }
    if elapsed < 150*time.Millisecond {
        t.Fatalf("Expected token read to wait ~200ms, finished in %v on node %s", elapsed, nodeID)
    }
}
  • Deterministic Wait: ReadWithToken blocking hingga appliedLSN >= minLSN;
  • Elapsed Timing: Test asserting elapsed >= 150ms mengkonfirmasi blocking behavior aktif;
  • LSN Guarantee: readLSN >= minLSN menjamin causal ordering terpenuhi;

Bagaimana WaitForLSN Membedakan Blocking dan Timeout

Implementasi WaitForLSN menunjukkan pola konkurensi Go yang elegan untuk condition-based waiting. Goroutine waiter mengakuisisi mutex node, loop sampai appliedLSN memenuhi target, dan memanggil cond.Wait(). Worker goroutine setelah apply WAL entry memanggil cond.Broadcast(). Context cancellation memberikan escape hatch yang aman.

func (n *Node) WaitForLSN(ctx context.Context, targetLSN uint64) error {
    ch := make(chan struct{})
    stop := make(chan struct{})
    go func() {
        n.mu.Lock()
        defer n.mu.Unlock()
        for n.appliedLSN < targetLSN {
            select {
            case <-stop:
                return
            default:
            }
            n.cond.Wait()
        }
        close(ch)
    }()
    select {
    case <-ctx.Done():
        close(stop); n.cond.Broadcast(); return ctx.Err()
    case <-ch:
        return nil
    }
}
  • cond.Wait() melepas mutex sementara goroutine block;
  • Worker goroutine memanggil cond.Broadcast() setelah apply entry;
  • Context deadline memicu close(stop) + Broadcast() untuk cleanup;

Anti-Pattern: Kesalahan Desain yang Harus Dihindari

Violasi princip desain replication topology dapat berakibat fatal bagi availability dan consistency system. Anti-pattern yang paling sering terjadi adalah underestimate durasi sticky window dibanding actual replication lag, menghasilkan false sense of security bagi engineer.

  • Anti-Pattern Umum: Mencampuradukkan semi-sync dengan synchronous; Sticky Duration Terlalu Pendek; Tidak Ada Fallback Primary; Ignore LSN pada Cached Reads; Hardcode Waiting Durasi;
  • Caranya Reproduksi Gagal di Lab: 1. Ubah ReadLagAware: hapus fallback primary → test fail; 2. Set MaxLSNDiff = 0 → throughput read drop drastis; 3. Hapus WaitForLSN context timeout → token reads hanging;

Prinsip Arsitektur: Desain untuk Asinkronitas

Tiga prinsip arsitektur ini berlaku universal di luar implementasi lab Go ini. Pertama, sadari bahwa asynchronicity adalah default industri dan upaya menghilangkannya secara total akan mengorbankan skalabilitas tulis. Kedua, tempatkan tanggung jawab penutupan replication gap di lapisan aplikasi karena hanya aplikasilah yang memahami konteks konsistensi setiap use case. Ketiga, prioritaskan degradasi eksplisit ke primary dengan observabilitas lengkap dibandingkan menyajikan data stale secara senyap.

  • Asynchronicity adalah kenormalan: Replication lag bukan bug yang harus dihapus, melainkan realitas yang harus dikelola;
  • Closing mechanism adalah hak klien: Aplikasi memilih mekanisme penutupan jarak (sticky, token, threshold). Database hanya menyediakan primitives (LSN, WAL);
  • Degrasi eksplisit lebih baik daripada silent failure: Fallback ke primary dengan logging terstruktur atau data stale yang tidak tercatat;

Replication scales reads; application routing safeguards consistency.
