Code Review: Checkout Sukses, Stok Tetap Bermasalah

Membaca risiko stok, retry, dan partial state dari checkout naive hingga batas implementasi improved.

Checkout mengembalikan success, tetapi stok sudah berkurang tanpa order yang tersimpan. Pada request lain, dua pembeli sama-sama berhasil membeli barang yang stoknya hanya satu. Lab 09 memakai kasus ini untuk membahas code review dari sisi behavior dan risiko bisnis.

Fokusnya bukan menghitung jumlah komentar reviewer. Yang perlu ditelusuri adalah requirement, perubahan behavior, failure mode, dampak, perbaikan paling sederhana yang cukup, dan bukti pengujian. CheckoutNaive dan CheckoutImproved memberi contoh konkret untuk mengikuti urutan tersebut.

Mulai dari invariant, lalu baca alurnya

Requirement utamanya sederhana: stock tidak boleh negatif; reservasi stok dan pembuatan order harus berhasil bersama; retry tidak boleh membuat order baru; dan user hanya boleh checkout cart miliknya. Keempatnya menjadi acuan saat membaca implementasi.

Versi naive memuat cart, mengambil product satu per satu, mengurangi stok, membuat order, mengirim notifikasi, lalu mengembalikan success. Masalah muncul karena hasil beberapa operasi penting diabaikan. Cuplikan berikut berasal dari checkout_naive.go; kode di sekitarnya dipersingkat.

_ = c.repo.CreateOrder(ctx, order)
_ = c.notify.SendOrderConfirmation(ctx, userID, orderID)
return &CheckoutResponse{Success: true, OrderID: orderID, Total: total}, nil

Jika CreateOrder gagal, pemotongan stok yang sudah berjalan tetap tertinggal. Notifikasi masih dicoba, dan caller menerima success. Dampaknya adalah partial state: inventory berubah tetapi order tidak ada. Perbaikannya harus menyatukan perubahan bisnis dan mengembalikan error, bukan sekadar mengganti pesan response.

Ada detail yang berbeda dari ringkasan README. Kode Go naive meneruskan error GetCart. Saat lookup product gagal, loop memakai continue, bukan melakukan dereference product nil. Namun order tetap memuat seluruh cart melalui toOrderItems, sementara total melewati item yang lookup-nya gagal. Ketidaksesuaian ini tetap merupakan masalah correctness.

Transaction boundary harus punya arti yang jelas

Improved menempatkan ReserveStock untuk setiap item dan CreateOrder dalam callback WithinTransaction. Jika salah satunya gagal, callback mengembalikan error. Pada mock, reservasi ditampung sementara; commit menerapkan pengurangan stok dan menyimpan order.

// checkout_improved.go; cuplikan, kode sekitar dipersingkat
for _, item := range cartItems {
    if reserveErr := tx.ReserveStock(ctx, item.ProductID, item.Quantity); reserveErr != nil {
        return reserveErr
    }
}
if createErr := tx.CreateOrder(ctx, order); createErr != nil {
    return createErr
}

Test IdempotencyFailureCanRetry menginjeksi kegagalan order creation, lalu memeriksa stok tetap utuh, tidak ada order, dan tidak ada notifikasi sebelum retry. MultiProductFailureRollsBackEverything memeriksa kedua stok kembali pada nilai awal. Nama lengkap test tersebut diawali TestImprovedCheckout_. Ini adalah assertion pada mock, bukan hasil pengujian database production.

Mutex tidak otomatis menjaga aturan bisnis

Pada naive, UpdateStock memang memakai mutex untuk mengubah map. Namun ia menerima pengurangan tanpa syarat stock cukup. Dua pengurangan dari stok satu tetap dapat menghasilkan stok negatif meskipun akses memory disinkronkan. Bahkan satu pembelian dengan quantity melebihi stok dapat merusak invariant.

Ini membedakan data race dari logical atau business race. Race detector memeriksa akses memory yang tidak aman; assertion bisnis memeriksa apakah jumlah pembelian dan stok akhir masih valid. Lulus go test -race saja tidak membuktikan bahwa overselling mustahil.

ConcurrentStockReservationPreservesInvariant mengharapkan satu sukses, satu gagal, satu order, dan stok akhir nol ketika dua pembeli memperebutkan satu unit. MockTransactionManager menahan satu mutex selama callback dan commit, sehingga transaksi melalui manager yang sama diserialkan. Mekanisme demonstrasi ini bukan concurrency control database production.

README memberi ilustrasi SQL UPDATE dengan kondisi stock >= quantity dan pemeriksaan affected rows. SQL itu belum menjadi adapter di lab. BEGIN/COMMIT sendiri juga tidak menetapkan kondisi stok. Test bernama DeterministicNoRace memasang read hook, tetapi improved menggunakan GetProducts yang tidak memanggil hook itu; ia tidak memaksakan interleaving yang sama seperti test naive.

Retry: claim, processing, dan replay berbeda

Improved membentuk key checkout:{userID}:{idempotencyKey}. Lookup awal mengembalikan response jika record sudah COMPLETED. Baru jika belum ada replay, service memuat cart, memvalidasi quantity, menghitung hash, dan melakukan Claim. Urutan aktual ini lebih spesifik daripada penjelasan README yang menyebut pemeriksaan sebelum cart dimuat.

Hash dibuat dari CheckoutCommand: CartOwnerID dan IdempotencyKey. Isi cart, harga, quantity, dan versi cart tidak masuk hash. Di repository mock, claim pertama menjadi PROCESSING; claim dengan hash sama selama proses mendapat ErrDuplicateRequest; hash berbeda mendapat ErrIdempotencyConflict; COMPLETED dengan hash sama mengembalikan response tersimpan.

Test StateMachineDirect menguji kontrak repository dengan dua hash buatan. Pada service, jalur replay awal tidak membandingkan RequestHash. Dengan command sekarang dan ownership check, key yang sama biasanya menunjuk field command yang sama. Namun mekanisme ini tidak mendeteksi perubahan isi cart dan perlu ditinjau jika payload command diperluas.

RetryAfterCartMutationReturnsOriginalResponse mengosongkan cart setelah checkout awal, lalu memeriksa order ID tetap sama dan stok hanya berkurang sekali. Claim atomik sendiri berjalan setelah cart loading, bukan sebelumnya. Tanpa record COMPLETED, cart yang berubah masih dapat memengaruhi validasi sebelum Claim dicapai.

Ownership dan harga harus dibaca terpisah

// checkout_improved.go; cuplikan
if principal.UserID != cmd.CartOwnerID {
    c.logger.Error(ctx, "authorization failed", "userID", principal.UserID, "cartOwnerID", cmd.CartOwnerID)
    return nil, ErrForbidden
}

CannotCheckoutAnotherUsersCart memeriksa ErrForbidden, stok tidak berubah, dan order tidak dibuat. Per-user scoping diuji terpisah agar dua user dengan string key sama tetap mendapatkan operasi masing-masing. Lab ini tidak mengimplementasikan middleware authentication; sumber principal tetap menjadi tanggung jawab integrasi di luar contoh.

Quantity nol atau negatif ditolak. Improved menghitung subtotal dari product.UnitPrice, bukan harga pada cart seperti naive. Tetapi tidak ada guard untuk harga negatif, perkalian overflow, atau penjumlahan total overflow. Mock product memakai harga tetap 1000. Mengganti sumber harga belum membuktikan seluruh validasi uang selesai.

Batch loading mengubah pola pemanggilan

Naive memanggil GetProduct di dalam loop. Improved mengumpulkan unique product ID lalu memanggil GetProducts sekali. Di sini N+1 merujuk lookup product berulang; banyak UPDATE adalah pola write lain.

Test NPlusOneProductLookups mengharapkan tiga single lookup untuk tiga item. BatchLoadsProducts mengharapkan satu batch dan nol single lookup; BatchLoadUsesUniqueProductIDs memeriksa deduplikasi ID. Counter ini menunjukkan jumlah panggilan repository, tanpa mengukur query database atau latency. Tidak ada hasil benchmark yang dapat disimpulkan.

Commit masih menyisakan failure window

Setelah transaksi bisnis selesai, improved menjalankan MarkCompleted. Jika operasi ini gagal, service mengembalikan ErrIdempotencyFinalize, padahal order sudah tersimpan dan stok sudah berkurang. FinalizeFailureAfterCommit memeriksa kondisi itu serta memastikan notifikasi belum dikirim. Error tersebut tidak berarti rollback.

Notifikasi berjalan synchronous setelah commit dan finalisasi berhasil. Kegagalannya dicatat tanpa membatalkan order. Crash sebelum pengiriman dapat menghilangkan notifikasi, dan replay COMPLETED tidak mengirimnya kembali. Outbox, reconciliation, dan unique business constraint disebut sebagai opsi dalam README, tetapi belum diimplementasikan.

Error handling juga belum seragam. Pada kegagalan transaksi, Release error digabung lewat errors.Join. Pada cabang product hilang dari batch, Release error hanya dicatat. MarkCompleted membungkus sentinel finalisasi, tetapi underlying error diformat dengan %v. Logger dipanggil dengan context, sementara MockLogger hanya menyimpan pesan sehingga field terstruktur belum dibuktikan oleh test.

Review yang baik menjelaskan batas buktinya

Prioritas review mengikuti impact, likelihood, dan blast radius. Stok negatif, akses lintas user, partial state, dan duplicate order lebih penting daripada saran penamaan. Performa batch lookup dinilai sesuai workload; jumlah pemanggilan saja tidak menetapkan severity universal.

Improved masih berupa contoh in-memory. atomic.Int64 menghasilkan ID dari counter milik satu instance service; instance lain, replica lain, atau restart dapat menghasilkan ID sama. Tidak ada mekanisme TTL/recovery untuk stale PROCESSING, adapter database, atau jaminan exactly-once umum. Mock notifikasi selalu sukses, sehingga failure pengiriman belum diuji.

Beberapa nama test dalam README juga berbeda dari file test aktual; referensi di atas mengikuti kode dan assertion yang tersedia.

Code review reduces risk by protecting behavior and business invariants. Temuan menjadi berguna ketika reviewer dapat menghubungkan kode, kegagalan, dampak, perbaikan, dan batas bukti pengujiannya.
