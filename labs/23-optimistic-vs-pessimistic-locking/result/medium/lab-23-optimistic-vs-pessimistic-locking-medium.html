Optimistic vs Pessimistic Locking & Atomic Updates

Lost Update Anomaly Mitigation, Version Guards, dan Operasi Atomik di Go

Lukman / lukman-ss · Software Engineering Lab 23

Sistem inventori konkuren dengan 50 goroutine yang mengurangi stok dari 100 seharusnya menghasilkan sisa 50 unit. Tanpa sinkronisasi, hasilnya adalah 99. Lost update adalah korupsi senyap, bukan galat yang terpapar kepada pemanggil. Lab 23 mendemonstrasikan tiga strategi — pessimistic locking, optimistic version guarding, dan atomic single-statement update — untuk mencegah korupsi ini pada simulasi Go tanpa dependensi eksternal.

Lost update adalah korupsi data senyap; transaksi SQL standar tidak mencegahnya secara otomatis.

Anomali Lost Update

Ketika dua transaksi konkuren membaca snapshot inventori bernilai 100, menghitung secara mandiri 100 - 1 = 99, lalu masing-masing menulis 99 kembali ke penyimpanan, pengurangan pertama lenyap tanpa jejak. Tidak ada exception yang merambat. Tidak ada permukaan galat database yang mengekspos korupsi tersebut. Invarian initial_stock == remaining_stock + total_deductions rusak secara senyap: 100 ≠ 99 + 50.

Ini bukan kasus tepi teoretis. Sistem produksi e-commerce, tiket, dan dompet digital Encounter pola ini ketika beberapa request memproses produk atau akun yang sama dalam jendela snapshot terkomit yang identik. Membungkus operasi ini dalam blok BEGIN TRANSACTION standar tidak secara otomatis mencegah tabrakan, karena batas transaksi mengendalikan urutan komit, bukan isolasi snapshot lintas-request.

Mengapa Isolasi Database Default Gagal

PostgreSQL dan Oracle menggunakan READ COMMITTED sebagai level isolasi default. Pada level ini, setiap query individual membaca snapshot terkomit terbaru yang tersedia pada saat permulaan pernyataan. Celah antara SELECT yang membaca stok saat ini dan UPDATE berikutnya yang menulis nilai berkurang menjadi jendela fragmentasi-write. Transaksi lain yang berkomit selama celah tersebut memperkenalkan versi baris baru yang tidak pernah diamati oleh transaksi pertama.

Level isolasi database mengisolasi pernyataan individual, bukan siklus kalkusi aplikasi multi-pernyataan. READ COMMITTED menjamin setiap query melihat snapshot yang konsisten, namun tidak menjamin snapshot yang diamati oleh SELECT masih valid ketika UPDATE dieksekusi. Celah inilah asal-usul lost update.

Pola Naif Read-Modify-Write yang Rentan

// internal/inventory/store.go
func (s *Store) NaiveDeduct(id int, qty int) error {
    p, err := s.Get(id) // 1. Baca snapshot tanpa lock apapun
    if err != nil { return err }
    if p.Stock < qty { return ErrInsufficientStock }
    time.Sleep(100 * time.Microsecond) // perlebar celah balapan
    s.mu.Lock()
    curr := s.products[id]
    curr.Stock = p.Stock - qty // 2. Tulis pakai snapshot usang
    s.mu.Unlock()
    atomic.AddInt64(&s.NaivelyDrawn, int64(qty))
    return nil
}

Penyisipan jeda microsecond tidak secara artifisial merusak kode yang valid — ini merefleksikan latensi komputasi aplikasi nyata dan jeda jaringan antar-layanan. Setiap goroutine menangkap snapshot lokalnya sendiri sebelum mengakuisisi mutex peta, memastikan setiap pekerja konkuren menulis kembali nilai usang yang identik.

Kompromi Rekayasa: Beban Tunggu vs Beban Retry

Pessimistic Locking — Menjamin konsistensi melalui serialisasi eksklusif. Kekurangan: lonjakan latensi di bawah kontensi tinggi saat transaksi bersaing mengantre di balik lock yang dipegang. Ideal untuk saldo keuangan bernilai tinggi dan reservasi tiket terbatas di mana hasil yang benar lebih penting daripada throughput.

Optimistic Locking — Mencapai throughput baca maksimum tanpa blocking. Kekurangan: siklus CPU dan round-trip jaringan terbuang saat tingkat konflik meningkat. Beban retry tidak otomatis efisien di bawah kontensi tanpa henti; starvation dapat terjadi pada loop retry ketat tanpa jitter backoff.

Atomic Update — Menghilangkan celah read-then-write sepenuhnya. Kekurangan: terbatas pada aritmatika satu kolom yang dapat diekspresikan dalam satu kondisi UPDATE ... WHERE. Tidak mampu enforcing invarian multi-tabel yang kompleks.

Memilih optimistic locking bukan berarti bebas dari penanganan error. Layer pemanggil wajib mengimplementasi exponential backoff dengan randomized jitter, selain itu retry konkuren akan tersinkronisasi dan mengamplifikasi tingkat tabrakan.

Pessimistic Locking: Mengunci Sebelum Membaca

// internal/inventory/store.go
func (s *Store) PessimisticDeduct(id int, qty int) error {
    rowLock := s.GetRowLock(id)
    rowLock.Lock()                  // akuisisi lock eksklusif baris
    defer rowLock.Unlock()
    s.mu.Lock()
    p, exists := s.products[id]
    if !exists { s.mu.Unlock(); return ErrNotFound }
    if p.Stock < qty { s.mu.Unlock(); return ErrInsufficientStock }
    p.Stock -= qty
    s.mu.Unlock()
    atomic.AddInt64(&s.Pessimistically, int64(qty))
    return nil
}

Logika pencegahan ini cakupannya mengikuti test konkurensi lab. Seluruh 50 goroutine berserialisasi melalui row-lock per-baris, mengurangi stok dari 100 tepat menjadi 50 tanpa mutasi hilang. Implementasi ini adalah model simulasi, bukan bukti perilaku lock manager database fisik SELECT FOR UPDATE.

Optimistic Locking: Version Guard Tanpa Mengunci Pembaca

// internal/inventory/store.go
func (s *Store) OptimisticDeduct(id int, qty int) error {
    p, err := s.Get(id)             // ambil snapshot beserta version
    if err != nil { return err }
    if p.Stock < qty { return ErrInsufficientStock }
    time.Sleep(50 * time.Microsecond)
    s.mu.Lock()
    defer s.mu.Unlock()
    curr, exists := s.products[id]
    if curr.Version != p.Version {  // validasi version guard
        atomic.AddInt64(&s.OptimisticFails, 1)
        return ErrOptimisticLock    // ekuivalen affected_rows == 0
    }
    curr.Stock -= qty
    curr.Version++
    atomic.AddInt64(&s.Optimistically, int64(qty))
    return nil
}

Pembacaan berjalan tanpa lock baris dipegang. Pada saat commit, version divalidasi terhadap version tersimpan saat ini. Jika divergen, update dibatalkan dengan ErrOptimisticLock. Mekanisme ini tidak otomatis menghasilkan sukses; kode pemanggil harus menangani konflik dan memutuskan apakah akan retry, eskalasi, atau mengembalikan error kepada pengguna.

Konvergensi Retry: Exponential Backoff dengan Jitter

// internal/inventory/service.go
func (svc *Service) DeductOptimisticWithRetry(id, qty, maxRetries int) error {
    for attempt := 0; attempt <= maxRetries; attempt++ {
        err := svc.store.OptimisticDeduct(id, qty)
        if err == nil { return nil }
        if err != ErrOptimisticLock { return err }
        if attempt == maxRetries { return ErrOptimisticLock }
        sleepDuration := time.Duration(1<<attempt)*time.Millisecond +
            time.Duration(rand.Intn(5))*time.Millisecond
        time.Sleep(sleepDuration)
    }
    return ErrOptimisticLock
}

Exponential backoff (1<<attempt ms) menjadwalkan ulang upaya retry secara bertingkat. Jitter acak (rand.Intn(5)) mencegah goroutine tersinkronisasi pada tick yang sama — masalah thundering herd. Tanpa jitter, semua 20 goroutine bersaing akan retry bersamaan, memproduksi tabrakan yang sama lagi, dan berputar kembali. Dengan jitter, retry terde-sinkronisasi hingga kontensi berkurang. Hanya pada jalur ini 20 request konkuren konvergen berhasil seluruhnya.

Atomic Update: Memangkas Celah Read-Modify-Write

// Ekuivalen SQL: UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?
func (s *Store) AtomicDeduct(id int, qty int) error {
    if qty <= 0 { return ErrInvalidQuantity }
    s.mu.Lock()
    defer s.mu.Unlock()
    curr, exists := s.products[id]
    if !exists { return ErrNotFound }
    if curr.Stock < qty { return ErrInsufficientStock }
    curr.Stock -= qty             // validasi + mutasi dalam satu seksi kritis
    atomic.AddInt64(&s.Atomically, int64(qty))
    return nil
}

Dengan mengikat pengecekan kondisi dan mutasi state dalam satu seksi kritis, celah temporal antara baca dan tulis hilang. Pola ini bukan peluru perak universal: atomicity single-statement tidak mampu enforcing invarian multi-tabel atau aturan konsistensi lintas-baris. Ini adalah pilihan optimal untuk pengurangan counter sederhana di mana seluruh aturan bisnis muat dalam satu kondisi WHERE stock >= N.

Urutan Keputusan Arsitektur

PertanyaanStrategi Direkomendasikan
Apakah mutasi adalah operasi aritmatika tunggal pada satu baris?Atomic Update (UPDATE ... WHERE stock >= N)
Apakah entitas menghadapi kontensi tinggi (flash sale, saldo)?Pessimistic Lock (SELECT FOR UPDATE)
Apakah baca dominan dan tabrakan tulis jarang?Optimistic Version Guard + retry jittered

Memilih optimistic locking bukan opsi gratis. Ia memerlukan infrastruktur retry, monitoring metrik konflik, dan strategi error面向-pengguna untuk retry yang habis. Setiap strategi mempertukarkan biaya operasional yang berbeda: waktu tunggu serial, bandwidth CPU retry, atau keterbatasan ekspresibilitas.

Checklist Implementasi Produksi

  • Identifikasi pola mutasi: single-statement atomik atau read-modify-write multi-langkah.
  • Gunakan UPDATE ... SET stock = stock - N WHERE stock >= N untuk counter numerik sederhana.
  • Terapkan SELECT ... FOR UPDATE pada entitas bernilai tinggi dengan kontensi padat.
  • Jangan pernah menahan row lock database saat melakukan panggilan jaringan eksternal (HTTP/RPC/webhook).
  • Tambahkan kolom version integer dan validasi affected_rows == 0 untuk optimistic lock.
  • Implementasi wrapper retry dengan randomized jittered backoff untuk konflik optimistik.
  • Jalankan go test -race ./... secara berkala pada pipeline CI/CD untuk mendeteksi race level memori.

Anti-Pattern yang Harus Dihindari

Mengabaikan affected rows. Update optimistik yang tidak memeriksa affected_rows (atau ekuivalennya) mengasumsikan kesuksesan, menerima secara senyap overwrite usang.

Lock menyeberang I/O. Menahan row lock database sambil menunggu respons webhook payment gateway menserialisasi seluruh connection pool di balik satu panggilan pihak ketiga yang lambat, menyebabkan antrean sistemik.

Redis locking prematur. Langsung memakai distributed Redis lock bukan berarti teknik superior. Database relasional sudah menyediakan primitif locking tingkat baris native dengan latensi rendah. Lock manager eksternal memperkenalkan mode kegagalan jaringan dan kompleksitas operasional yang tidak perlu ketika engine database sudah menangani persyaratan tersebut.

Prinsip Arsitektural Inti

Kunci rekayasa transaksional yang matang adalah menyesuaikan primitif sinkronisasi dengan profil kontensi domain. Baris-baris kritis dengan biaya kegagalan yang tidak dapat ditoleransi membutuhkan kepastian pessimistic. Beban kerja baca-dominan diskalakan melalui guard optimistik. Counter sederhana berkembang optimal pada update atomik. Merancang sistem konkuren tidak otomatis memerlukan infrastruktur rumit ketika statement atomik native cukup untuk mutasi yang dibutuhkan. Pengendalian konkurensi terbaik adalah yang paling sederhana yang tetap menjaga invarian.
