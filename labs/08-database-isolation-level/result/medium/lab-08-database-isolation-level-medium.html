Database Isolation Level: Transaksi Belum Menjamin Saldo Benar

Dua transfer bisa sama-sama berhasil di-commit, tetapi total uang justru bertambah. Di Lab 08, masalahnya muncul ketika aplikasi membaca saldo, memeriksa kecukupan dana, menghitung saldo baru di Go, lalu menulis hasil hitungan itu setelah transaksi lain juga mengambil keputusan dari saldo yang sama.

BEGIN dan COMMIT memberi batas operasi yang sukses atau gagal bersama. Untuk menjaga saldo saat transaksi saling overlap, kita juga perlu menentukan cara membaca state, mengoordinasikan penulisan, dan menangani conflict. Kasus wallet membuat perbedaan itu terlihat tanpa memerlukan skenario yang rumit.

Mulai dari aturan uangnya

Alice, Bob, dan Charlie masing-masing memiliki Rp1.000.000. Transfer boleh memindahkan uang di antara mereka, tetapi tidak boleh membuat saldo negatif atau mengubah total Rp3.000.000. Dua aturan ini adalah business invariant yang perlu diperiksa secara terpisah.

Schema sudah memakai CHECK untuk menolak saldo negatif. Namun constraint per baris tersebut tidak menghitung jumlah uang lintas akun. Karena itu, semua saldo bisa lolos constraint sementara sistem tetap salah.

balance BIGINT NOT NULL CHECK (balance >= 0)

Bagaimana Rp800.000 bisa muncul dari dua transfer

Transfer A mengirim Rp800.000 dari Alice ke Bob. Transfer B mengirim nominal yang sama dari Alice ke Charlie. Keduanya membaca saldo Alice Rp1.000.000 sebelum penulisan dimulai. Validasi dana cukup lalu lolos di dua transaksi.

Implementasi naive menghitung saldo pengirim di memori aplikasi. Masing-masing transaksi mendapat hasil Rp200.000, kemudian menulis nilai absolut itu ke row Alice. Penulisan kedua tidak tahu bahwa debit pertama harus ikut diperhitungkan.

// 4. Overwrite sender balance with calculated value (Lost Update vulnerability)
	_, err = tx.ExecContext(ctx, "UPDATE isolation_accounts SET balance = $1 WHERE id = $2", fromBalance-amount, fromID)
	if err != nil {
		return fmt.Errorf("update from balance: %w", err)
	}

Cuplikan dipersingkat dari transfer.go. Bagian debit ini berada di dalam transaksi READ COMMITTED bersama kredit penerima dan audit. Jadi masalahnya bukan karena debit dan kredit berada di luar transaction boundary.

Assertion TestNaiveTransfer_LostUpdate mengharapkan Alice Rp200.000, Bob Rp1.800.000, dan Charlie Rp1.800.000. Totalnya Rp3.800.000. Alice masih memiliki saldo positif sehingga CHECK tidak menolak apa pun, tetapi debit Rp800.000 telah hilang dari perhitungan total.

Apa yang benar-benar direproduksi test

Test menyusun transaksi secara eksplisit untuk mereproduksi pola naive; ia tidak memanggil TransferNaive secara langsung. Channel menahan kedua transaksi setelah membaca saldo. Coordinator baru melepas penulisan setelah keduanya siap. Dengan begitu, stale read bukan sekadar kemungkinan yang diharapkan terjadi karena timing.

Angka di atas adalah ekspektasi dalam kode test. Test lab tidak dijalankan pada sesi penyusunan artikel ini. Karena itu, angka tersebut tidak disajikan sebagai output eksekusi atau benchmark baru.

Isolation mengatur apa yang terlihat

Isolation menjelaskan bagaimana transaksi melihat perubahan transaksi lain. PostgreSQL memakai MVCC, sehingga ordinary SELECT membaca versi sesuai snapshot tanpa mengambil row lock FOR UPDATE. Snapshot yang konsisten dan hak eksklusif untuk mengubah row merupakan dua mekanisme berbeda.

Jangan menyalin tabel standar menjadi perilaku engine

Tabel standar SQL mengizinkan dirty read pada READ UNCOMMITTED dan phantom read pada REPEATABLE READ. PostgreSQL memiliki perilaku lebih kuat: READ UNCOMMITTED setara READ COMMITTED, sedangkan REPEATABLE READ mencegah phantom klasik melalui snapshot yang tetap.

Dirty read berarti membaca perubahan yang belum commit. Dalam test READ UNCOMMITTED PostgreSQL, penulis mengubah saldo menjadi Rp500.000 tanpa commit, sedangkan pembaca tetap diharapkan melihat saldo committed Rp1.000.000. Nama level tidak membuat PostgreSQL mengizinkan dirty read.

Satu transaksi belum tentu punya satu view

READ COMMITTED mengambil snapshot baru per statement. Test non-repeatable read membuat pembaca mengambil saldo Rp1.000.000, menunggu penulis menambah Rp500.000 dan commit, lalu membaca row yang sama lagi. Bacaan kedua diharapkan menjadi Rp1.500.000 walaupun transaksi pembaca belum selesai.

Perubahan yang terlihat sudah committed, sehingga ini bukan dirty read. Masalahnya adalah dua statement dalam boundary yang sama menggunakan view berbeda.

Phantom test menerapkan pola serupa pada kumpulan invoice PAID. Pembacaan awal menghitung dua invoice. Penulis memasukkan invoice PAID ketiga dan commit. READ COMMITTED diharapkan membaca tiga pada query berikutnya; REPEATABLE READ PostgreSQL tetap membaca dua.

SELECT COUNT(*) FROM isolation_invoices WHERE status = 'PAID'

Snapshot stabil bisa berakhir dengan conflict

REPEATABLE READ mengambil snapshot pada pembacaan pertama. Test snapshot isolation mengharapkan saldo tetap Rp1.000.000 pada dua bacaan meskipun penulis lain sudah commit. Ini berguna ketika beberapa query perlu memakai view yang konsisten.

Namun ketika dua transaksi mencoba meng-update row yang sama dari snapshot yang berbenturan, PostgreSQL dapat mengembalikan SQLSTATE 40001. Test concurrent update REPEATABLE READ mengharapkan tepat satu sukses dan satu serialization failure. Aplikasi masih harus menangani transaksi yang dibatalkan.

README membahas kemungkinan serialization anomaly seperti write skew. Eksperimen yang tersedia memperlihatkan same-row update conflict; tidak ada reproduksi write skew terpisah yang dapat diklaim dari test ini. Consistent snapshot juga tidak boleh diterjemahkan menjadi jaminan semua business invariant otomatis benar.

Pindahkan validasi ke belakang row lock

TransferWithLock tetap memakai READ COMMITTED. Perbedaannya adalah kedua akun dikunci terlebih dahulu melalui SELECT FOR UPDATE. Setelah lock didapat, aplikasi menentukan saldo pengirim dan memvalidasi kecukupan dana sebelum debit dan kredit.

firstID, secondID := DeterministicLockOrder(fromID, toID)

	// Lock both accounts deterministically
	var b1, b2 int64
	err = tx.QueryRowContext(ctx, "SELECT balance FROM isolation_accounts WHERE id = $1 FOR UPDATE", firstID).Scan(&b1)
	if err != nil {
		return fmt.Errorf("lock account %d: %w", firstID, err)
	}
	err = tx.QueryRowContext(ctx, "SELECT balance FROM isolation_accounts WHERE id = $1 FOR UPDATE", secondID).Scan(&b2)
	if err != nil {
		return fmt.Errorf("lock account %d: %w", secondID, err)
	}

Cuplikan dipersingkat dari transfer.go. Transaksi lain yang meminta FOR UPDATE atau mengubah row yang sama menunggu pemegang lock selesai. Ordinary SELECT tetap memakai MVCC. Setelah lock dilepas, transfer berikutnya dapat mengevaluasi saldo yang sudah berubah, lalu menolak transfer jika dana tidak cukup.

Urutan lock harus sama meskipun arah transfer berbalik

Transfer Alice ke Bob dan Bob ke Alice bisa saling menunggu jika masing-masing mengunci pengirim dahulu. Helper lab mengurutkan ID akun dari kecil ke besar sehingga kedua arah memakai urutan lock yang sama.

func DeterministicLockOrder(id1, id2 int) (firstID, secondID int) {
	if id1 < id2 {
		return id1, id2
	}
	return id2, id1
}

Bidirectional test menjalankan dua worker dengan 50 transfer per worker dan memeriksa error serta konservasi saldo. Urutan ini menghindari circular wait pada pola dua akun tersebut. Ia bukan jaminan universal jika jalur lain menambah lock dengan urutan yang berbeda.

Row locking juga membawa biaya menunggu. Implementasi tidak memberikan jaminan latency deterministik, meskipun tabel README memakai istilah itu. Durasi transaksi dan contention tetap memengaruhi waktu tunggu; lab tidak menyediakan pengukuran latency.

Serializable tetap berjalan concurrent

PostgreSQL SERIALIZABLE memakai SSI atau Serializable Snapshot Isolation. Hasil transaksi yang commit harus setara dengan suatu serial execution, tetapi transaksi tidak harus dijalankan satu per satu di belakang global lock.

Ketika conflict memerlukan abort, aplikasi menerima serialization failure 40001. Serializable test lab mengoordinasikan dua update pada row yang sama dan mengharapkan satu sukses serta satu 40001. Itu adalah bukti cakupan skenario conflict, bukan pengujian seluruh jenis anomaly.

Retry berarti memulai transaksi baru

Wrapper retry memanggil TransferSerializable sebagai satu operation. Setiap attempt mengulangi BeginTx, read, validasi, debit, kredit, audit, dan commit. Keputusan transfer dihitung ulang. Mengulang satu statement saja tidak sama dengan mekanisme ini.

func (r *PostgresWalletRepo) TransferSerializableWithRetryPolicy(ctx context.Context, fromID, toID int, amount int64, maxAttempts int, policy RetryPolicy) error {
	repo := r
	return RetryTransaction(ctx, maxAttempts, policy, func(ctx context.Context) error {
		return repo.TransferSerializable(ctx, fromID, toID, amount)
	})
}

Filter menerima 40001 untuk serialization failure dan 40P01 untuk deadlock, baik melalui pq.Error maupun sentinel yang sesuai. WrapTxError menjaga error chain sehingga errors.Is dan errors.As tetap dapat digunakan. Insufficient funds, constraint violation, dan generic error tidak diperlakukan sebagai alasan retry otomatis.

maxAttempts mencakup attempt pertama dan harus positif. Default base delay adalah 10 milidetik, batasnya satu detik. Helper memakai exponential backoff yang dibatasi, lalu full jitter untuk memilih delay. Context diperiksa sebelum attempt dan dapat menghentikan default sleep. Jika seluruh kesempatan habis, ErrMaxRetryExceeded membungkus error terakhir.

retry_test.go memeriksa filter, pemeliharaan error asli, sukses setelah conflict, exhaustion, pembatalan context, batas attempt yang tidak valid, dan perilaku delay. Kebijakan retry tetap terbatas; ia tidak menjanjikan semua transaksi akhirnya berhasil.

Ukur correctness dari state akhirnya

Stress test memakai fixture yang berbeda dari contoh awal: saldo Rp50.000 pada tiga akun, total Rp150.000. Seratus goroutine melakukan transfer Rp1.000 dengan TransferWithLock setelah start gate dilepas. Test memeriksa error, saldo akhir non-negatif, dan total yang tetap Rp150.000.

Start gate membuat pekerjaan bersaing bersama, tetapi tidak memaksa semua query terjadi persis pada saat yang sama. Naive test menggunakan barrier setelah pembacaan untuk mengatur overlap yang lebih spesifik. Deskripsi kedua mekanisme ini tidak boleh disamakan.

cd labs/08-database-isolation-level
go test -v ./...

Jalankan setelah PostgreSQL dari infrastruktur repository tersedia. Helper integration test dapat melakukan skip saat database tidak tersedia; REQUIRE_POSTGRES=1 membuat kondisi itu menjadi failure. Status test sukses dengan eksperimen yang di-skip belum membuktikan perilaku database.

Pilih strategi dari invariant yang harus dijaga

Untuk wallet dengan row akun yang diketahui, lock eksplisit dan urutan konsisten mengoordinasikan read-check-write. Untuk kebutuhan beberapa query dengan view tetap, REPEATABLE READ menyediakan snapshot. Untuk serial equivalence pada invariant yang lebih kompleks, SERIALIZABLE membutuhkan penanganan abort dan retry.

README menyebut atomic conditional update sebagai alternatif, tetapi implementasinya tidak tersedia dalam lab. Repository juga tidak memberi benchmark throughput atau latency untuk membandingkan strategi. Kesimpulan yang didukung sumber adalah menentukan invariant, memahami read/write set, memilih mekanisme concurrency, lalu memeriksa state akhirnya di bawah overlap.

Transaction boundary, snapshot, row lock, dan serial equivalence menjawab persoalan yang berbeda. Menggabungkan mekanisme yang sesuai beserta conflict handling membuat pengujian dapat menilai apakah sistem benar, bukan sekadar apakah request selesai tanpa error.
