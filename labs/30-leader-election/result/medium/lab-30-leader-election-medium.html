Masalah Nyata: Ilusi Otoritas Tunggal

Dalam arsitektur terdistribusi nyata, proses tidak pernah mati secara instan dan rapi. Fenomena runtime seperti stop-the-world garbage collection pause pada runtime modern atau network partition parsial dapat membekukan proses selama ratusan milidetik. Selama periode pause tersebut, lease TTL milik leader lama akan kedaluwarsa di coordinator, memicu failover otomatis ke kandidat baru. Ketika leader lama bangun dari pause, ia tidak menyadari waktu telah berlalu dan tetap mengeksekusi operasi tulis yang berpotensi merusak integritas data sistem.

Mengapa Lease Berbasis Waktu Saja Gagal?

Pendekatan naif mengasumsikan pengecekan status boolean lokal `if n.state == StateLeader` cukup menjamin mutual exclusion. Asumsi ini salah fatal dalam sistem asinkron karena adanya time-of-check to time-of-use (TOCTOU) gap. Tepat setelah pengecekan lokal berhasil, runtime thread dapat diinterupsi oleh GC pause atau penjadwalan OS selama ratusan milidetik. Saat thread kembali aktif, status kepemimpinan telah berpindah ke node lain, namun instruksi tulis tetap dikirim ke storage. Tanpa validasi di lapisan penyimpanan, write usang akan menimpa data terkini.

func (n *Node) DoWorkNaive(val string) error {
    if n.state != StateLeader { return ErrNotLeader }
    // GC pause terjadi tepat di sini selama 350ms!
    // Lease TTL 200ms kedaluwarsa di coordinator.
    // Node-B terpilih sebagai leader baru.
    return n.sharedStorage.Save(val) // Menimpa data Node-B!
}

Mental Model: Otoritas Temporal vs Validasi Monotonik

Mental model arsitektur ini memisahkan dua konsep: hak memimpin sementara (lease) dan hak menulis permanen (fencing token). Lease coordinator mengelola kepemimpinan dengan TTL berbatas waktu, menerbitkan nomor tiket revisi yang strictly monotonically increasing setiap kali pemimpin baru dilantik. Penyimpanan bersama tidak lagi mempercayai identitas klien secara buta, melainkan bertindak sebagai gerbang independen yang hanya menerima mutasi jika tiket yang dibawa strictly lebih besar dari tiket terakhir yang tercatat.

type Lease struct {
    Key          string
    HolderID     string
    FencingToken int64         // revision monotonik naik
    ExpiresAt    time.Time
    TTL          time.Duration
}

Alur Koordinasi & Penolakan Mutasi Basi

Pipeline koordinasi menunjukkan bagaimana kegagalan temporal ditangani secara deterministik. Tahap 1 hingga 2 memperlihatkan alur kerja normal di mana Node-A memenangkan election dan menulis sukses dengan token generasi 1. Pada tahap 3 hingga 5, Node-A mengalami pause melebihi batas TTL, memungkinkan coordinator melantik Node-B dengan token generasi 2 yang berhasil menulis ke storage. Saat Node-A tersadar di tahap 7 dan mencoba menulis dengan token 1, storage mengeksekusi fencing check dan menolak mutasi tersebut secara mutlak.

Implementasi Gerbang Fencing di Shared Storage

Potongan kode ini merupakan inti pertahanan terhadap split-brain di seluruh arsitektur sistem. Method Write pada struct FencedStorage mengunci mutex untuk menjamin operasi check-and-set berlangsung secara linier dan atomik. Aturan validasi mengevaluasi apakah token yang disertakan bernilai lebih kecil atau sama dengan lastSeenToken. Jika ya, storage langsung menolak operasi dengan mengembalikan ErrStaleFencingToken. Hanya token yang strictly lebih besar yang diizinkan memperbarui lastSeenToken dan mencatat data mutasi.

func (s *FencedStorage) Write(author string, token int64, value string) error {
    s.mu.Lock()
    defer s.mu.Unlock()

    if token <= s.lastSeenToken {
        return fmt.Errorf("%w: token %d <= last seen %d (author: %s)",
            ErrStaleFencingToken, token, s.lastSeenToken, author)
    }
    s.lastSeenToken = token
    s.records = append(s.records, Record{FencingToken: token, Author: author, Value: value, Timestamp: time.Now()})
    return nil
}

Failure Path: Penolakan Stale Write Pascajeda GC

Failure path konkret ini diambil langsung dari hasil eksekusi program demo lab. Pada langkah 4 hingga 5, Node-A dipause selama 350 milidetik, melampaui batas TTL 200 milidetik sehingga lease kedaluwarsa. Menariknya, sistem sempat berada pada kondisi transient dual-leader di mana kedua node menganggap dirinya sebagai LEADER aktif. Namun, saat Node-A terbangun dan mencoba menulis dengan token 1, lapisan penyimpanan menolak operasi tersebut secara seketika karena token 1 lebih kecil dari token 2 milik Node-B.

Mekanisme vs Gejala: Evaluasi Solusi Koordinasi

Tabel ini membandingkan empat pendekatan koordinasi terdistribusi dalam menghadapi kegagalan jaringan dan runtime pause. Heartbeat naif dan lease TTL murni gagal melindungi integritas data karena keduanya rentan terhadap jeda eksekusi dan kondisi split-brain. Penggunaan distributed lock tanpa token urutan hanya cocok untuk optimalisasi efisiensi seperti deduplikasi job. Hanya penggabungan antara lease berbatas waktu dengan fencing token monotonik yang memberikan garansi keamanan mutlak pada level resource.

3 Keputusan Desain Kritis Leader Election

Implementasi koordinasi yang aman bergantung pada tiga keputusan desain fundamental. Pertama, perhitungan masa berlaku lease harus menggunakan monotonic clock untuk menghindari disrupsi penyesuaian jam sistem via NTP. Kedua, setiap pergantian kepemimpinan wajib menerbitkan revision token yang monotonik naik; UUID acak dilarang karena tidak memiliki relasi urutan kausal. Ketiga, gerbang validasi di lapisan penyimpanan bersama harus mengimplementasikan check-and-set atomik yang menolak token yang tidak lebih besar.

Bukti Eksekusi: Siklus Lengkap Election & Fencing

Output terminal ini membuktikan bahwa seluruh siklus kepemimpinan berjalan sesuai spesifikasi desain. Node-A pertama kali dilantik dengan Token 1 dan berhasil menulis record pertama. YANG TIDAK DIBUKTIKAN

Klaim teknis dalam laboratorium ini dibatasi oleh parameter lingkungan pengujian yang disederhanakan. Coordinator yang digunakan berjalan in-memory di dalam satu proses Go, bukan kluster terdistribusi multi-node berbasis konsensus Raft seperti etcd atau Paxos. Nilai parameter waktu seperti TTL 200 milidetik hanya dirancang untuk kecepatan eksekusi demo dan tidak boleh langsung diaplikasikan ke lingkungan produksi tanpa benchmarking p99 latency.

Trade-off Arsitektur: Fencing vs Kompleksitas

Penerapan fencing tokens menuntut kompromi arsitektural antara keamanan data dan kompleksitas sistem. Keunggulan utamanya adalah eliminasi total terhadap korupsi data akibat split-brain serta kemampuan failover tanpa perlu menunggu konfirmasi kematian node lama. Namun, biaya penerapannya tidak kecil: lapisan penyimpanan harus dimodifikasi agar mampu mengevaluasi token, waktu failover dibatasi oleh durasi TTL lease, dan klien aplikasi harus memiliki logika fallback ketika transaksi ditolak akibat token kedaluwarsa.

Validasi Konkurensi: 5 Node Berlomba Rebut Lease

Uji konkurensi membuktikan ketahanan implementasi saat lima node kandidat mencoba mengakuisisi lease secara simultan. Coordinator memanfaatkan sync.Mutex internal untuk memastikan setiap pengecekan dan penetapan lease berjalan secara linearizable. Dalam pengujian TestConcurrentElectionRace, setelah 100 milidetik kompetisi intensif, tepat satu node berhasil dipromosikan menjadi LEADER sementara empat node lainnya tertahan sebagai FOLLOWER. Verifikasi dengan flag -race membuktikan tidak ada data race di seluruh memori proses.

func TestConcurrentElectionRace(t *testing.T) {
    coord := coordinator.New()
    store := storage.New()
    nodes := make([]*candidate.Node, 5)
    for i := 0; i < 5; i++ {
        nodes[i] = candidate.NewNode(string(rune('A'+i)), "leader-lock", 100*time.Millisecond, 20*time.Millisecond, coord, store)
        nodes[i].Start(ctx)
    }
    time.Sleep(100 * time.Millisecond)
    // Assert: leaderCount == 1 di antara 5 node yang berlomba
}

Before vs After: Evolusi Sistem Koordinasi

Perbandingan before-after ini menunjukkan pergeseran paradigma dalam menangani koordinasi terdistribusi. Sebelum menerapkan fencing tokens, sistem sangat rapuh terhadap jeda eksekusi karena penyimpanan mempercayai klaim kepemimpinan klien secara pasif. Akibatnya, jeda eksekusi leader lama dapat merusak data yang baru saja ditulis oleh leader pengganti. Setelah menerapkan arsitektur fencing, penyimpanan bersama bertindak sebagai filter aktif yang menjamin data tidak akan pernah tertimpa oleh mutasi yang berasal dari generasi kepemimpinan masa lalu.

Test 1: Akuisisi, Renewal, dan Kedaluwarsa Lease

Unit test pertama membuktikan kebenaran siklus hidup lease pada modul coordinator. Node-1 berhasil memperoleh lease pertama dengan fencing token bernilai 1. Selama lease masih aktif, permintaan akuisisi dari Node-2 langsung ditolak dengan error ErrLeaseHeld. Operasi pembaruan berkala (Renew) terbukti memperpanjang masa berlaku lease tanpa menaikkan nilai token. Setelah dilakukan sleep selama 250 milidetik yang melampaui batas TTL 200 milidetik, lease kedaluwarsa secara otomatis dan Node-2 berhasil mengakuisisi lease dengan token 2.

func TestCoordinatorLeaseAcquisitionAndRenewal(t *testing.T) {
    coord := coordinator.New()
    ttl := 200 * time.Millisecond
    lease1, err := coord.Acquire("leader-lock", "node-1", ttl)
    // Assert: lease1.FencingToken == 1
    _, err = coord.Acquire("leader-lock", "node-2", ttl)
    // Assert: errors.Is(err, coordinator.ErrLeaseHeld)
    time.Sleep(250 * time.Millisecond) // Lampaui TTL 200ms
    lease2, err := coord.Acquire("leader-lock", "node-2", ttl)
    // Assert: lease2.FencingToken == 2
}

Test 2: Storage Menolak Token Usang & Duplikat

Unit test kedua menguji ketatnya aturan validasi pada lapisan FencedStorage. Penyimpanan pertama kali menerima token 10, kemudian menerima token 11. Saat Node-1 mencoba menulis kembali dengan token 10, operasi ditolak karena 10 lebih kecil dari 11. Begitu pula saat Node-2 mencoba menulis ulang dengan token 11 yang identik, storage menolaknya karena aturan mensyaratkan token harus strictly lebih besar. Hasil pemeriksaan History() membuktikan riwayat penyimpanan hanya berisi tepat dua data yang sah dan menolak semua mutasi ilegal.

func TestFencedStorageRejectsStaleTokens(t *testing.T) {
    store := storage.New()
    _ = store.Write("node-1", 10, "state-1") // Sukses: 10 > 0
    _ = store.Write("node-2", 11, "state-2") // Sukses: 11 > 10
    err1 := store.Write("node-1", 10, "stale-state")
    // Assert: errors.Is(err1, storage.ErrStaleFencingToken)
    err2 := store.Write("node-2", 11, "duplicate-token")
    // Assert: errors.Is(err2, storage.ErrStaleFencingToken)
    // Assert: len(store.History()) == 2 (mutasi ilegal tidak dicatat)
}

Test 3: Failover Otomatis & Pertahanan Split-Brain

Test ketiga mendemonstrasikan skenario inti split-brain yang dipecahkan oleh lab ini. Node leader pertama disimulasikan mengalami stop-the-world pause selama 250 milidetik, melampaui batas lease TTL 150 milidetik. Kandidat kedua mendeteksi kekosongan lease, mengambil alih kepemimpinan, dan sukses menulis dengan token 2. Ketika leader pertama bangun dan mencoba menulis ke storage menggunakan token 1 yang dipegangnya, operasi ditolak mentah-mentah dengan ErrStaleFencingToken. Tes ini mengonfirmasi pertahanan split-brain bekerja sempurna.

// 1. Leader-1 terpilih dan menulis sukses dengan token1
leader1.SimulatePause(250 * time.Millisecond) // Lebih lama dari TTL 150ms
time.Sleep(200 * time.Millisecond)
// 2. Leader-2 mengambil alih kepemimpinan dengan token2 > token1
err = leader2.PerformFencedWrite("leader-2-write") // SUKSES
// 3. Leader-1 bangun dan mencoba menulis dengan token1 usang
err = store.Write(leader1.ID(), token1, "stale-write-after-gc-pause")
// Assert: errors.Is(err, storage.ErrStaleFencingToken)

Studi Kasus Industri: Mekanisme Fencing Nyata

Riset sistem terdistribusi menunjukkan kesepakatan luas tentang perlunya fencing tokens. etcd memanfaatkan nomor Raft Revision 64-bit yang selalu bertambah sebagai fencing token alami untuk setiap transaksi mutasi. Apache ZooKeeper menggunakan zxid dan urutan pembuatan ephemeral znode. Debat bersejarah antara Martin Kleppmann dan antirez mengenai algoritma Redis Redlock menegaskan prinsip utama: kunci terdistribusi tanpa fencing token monotonik hanya cukup untuk efisiensi sistem, bukan untuk keamanan data yang membutuhkan korektivitas mutlak.

Mengapa Lease Wajib Menggunakan Monotonic Clock?

Penggunaan tipe jam yang tepat merupakan detail implementasi yang membedakan sistem amatir dari sistem kelas produksi. Wall-clock (jam dinding) dirancang untuk mencatat waktu kalender manusia dan dapat melompat mundur atau maju secara drastis saat terjadi penyesuaian NTP. Jika perhitungan lease bergantung pada wall-clock, lompatan waktu dapat memicu kegagalan fatal: failover palsu atau lease yang terkunci abadi. Go standard library mengatasi ini dengan menyematkan pembacaan monotonic hardware clock pada fungsi time.Now(), menjamin perhitungan durasi TTL selalu linier.

Checklist Implementasi Leader Election & Fencing

Daftar periksa ini merangkum sembilan prinsip krusial yang wajib dipenuhi sebelum menerapkan sistem leader election di produksi. Penentuan batas waktu TTL dan laju renewal tidak boleh ditebak, melainkan harus diukur berdasarkan data empiris p99 latency jaringan dan durasi GC pause runtime. Coordinator wajib menyediakan nomor generasi monotonik, sementara shared storage wajib mengisolasi validasi token di balik operasi atomik. Setiap penolakan stale token harus dimonitor sebagai indikasi awal degradasi performa atau partisi jaringan.

Anti-Pattern: Kesalahan Desain yang Harus Dihindari

Mengabaikan prinsip dasar koordinasi dapat berakibat fatal bagi integritas data perusahaan. Anti-pattern yang paling sering dijumpai adalah memvalidasi status kepemimpinan di sisi klien aplikasi alih-alih di gerbang penyimpanan, membuka celah TOCTOU yang lebar. Mengizinkan token yang bernilai sama (menggunakan operator lebih besar atau sama dengan) juga merusak keunikan generasi pemimpin. Untuk membuktikannya di lab, kita cukup melonggarkan validasi di storage.go dan melihat unit test langsung mendeteksi pelanggaran keamanan.

Prinsip Arsitektur: Desain untuk Asinkronitas

Tiga prinsip arsitektur ini berlaku universal di luar implementasi lab Go ini. Pertama, pahami bahwa lease berbasis waktu hanya memberikan timed mutual exclusion yang cocok untuk optimalisasi efisiensi, bukan keselamatan mutlak. Kedua, tempatkan gerbang keamanan di lapisan resource bersama karena proses klien yang membeku tidak memiliki kesadaran akan berlalunya waktu. Ketiga, gantikan asumsi waktu dengan urutan generasi eksplisit; nomor token yang monotonik naik memberikan jaminan kausalitas yang kebal terhadap jeda sistem terdistribusi.
