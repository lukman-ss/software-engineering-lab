Circuit Breaker: Hentikan Panggilan Saat Dependency Gagal

Melindungi checkout melalui CLOSED, OPEN, HALF_OPEN, timeout, dan probe pemulihan yang dibatasi.

Lukman / lukman-ss · Software Engineering Lab 14

Payment service yang lambat dapat membuat checkout terus menunggu sampai timeout. Jika setiap request tetap dikirim ke dependency yang sedang bermasalah, caller terus membayar biaya penantian. Lab 14 menempatkan circuit breaker di depan payment client untuk menghentikan sebagian panggilan baru setelah kegagalan mencapai threshold.

Mental model-nya: A circuit breaker protects the caller; it does not repair the dependency. Ia menentukan apakah sebuah panggilan diizinkan, lalu memakai hasil panggilan yang diizinkan untuk memperbarui state. Payment server tetap perlu pulih melalui mekanisme di luar breaker.

Kenali jalur yang benar-benar dijalankan

Checkout memanggil payment client melalui Breaker.Execute. Client melakukan HTTP POST ke /pay pada FakeServer berbasis httptest. Server memiliki tiga mode: HEALTHY mengembalikan 200, DOWN mengembalikan 500, dan SLOW melakukan sleep sebelum mengembalikan 200. Jadi lab benar-benar memakai HTTP lokal, tetapi tidak melakukan pembayaran, perubahan saldo, atau integrasi gateway production.

README memakai cascade failure sebagai motivasi: dependency lambat dapat menahan resource caller dan mengganggu jalur lain. Test lab tidak mengukur kehabisan thread, socket, memory, atau outage seluruh platform. Bukti yang tersedia lebih spesifik: keputusan state, penolakan callback, jumlah HTTP request, timeout, dan recovery probe.

CLOSED menghitung kegagalan berurutan

State awal adalah CLOSED. Panggilan diizinkan; callback berjalan di luar mutex. Nilai error nonnil menambah failures, sedangkan sukses mengembalikan failures menjadi nol. Ketika failures mencapai FailureThreshold, breaker berpindah ke OPEN. Pada penggunaan concurrent, urutan yang memengaruhi counter adalah urutan penyelesaian callback yang masih berlaku pada generation tersebut.

// circuit_breaker.go: cuplikan onFailureLocked
b.failures++
if b.failures >= b.cfg.FailureThreshold {
    b.state = Open
    b.openedAt = now
    b.generation++
}

DefaultConfig memakai threshold tiga, cooldown 300 ms, dan satu panggilan HALF_OPEN. Nilai konfigurasi nonpositif diganti dengan default oleh New. Angka tersebut adalah pilihan lab, bukan rekomendasi universal production. Model ini tidak menghitung persentase error, minimum sample, atau sliding window.

OPEN menolak panggilan baru sebelum callback

// circuit_breaker.go: cabang Execute
case Open:
    b.mu.Unlock()
    return ErrCircuitOpen

Saat OPEN belum melewati cooldown, Execute mengembalikan ErrCircuitOpen sebelum memanggil fn. Jika fn membungkus payment client, request baru tersebut tidak dikirim ke network. TestOpenDoesNotCallDownstream memeriksa satu callback awal yang gagal dan lima penolakan berikutnya, dengan total callback tetap satu.

Perlindungan itu tidak membatalkan request yang sudah lolos sebelumnya. CLOSED tidak memiliki batas jumlah in-flight call, sehingga burst concurrent dapat mengirim lebih banyak panggilan daripada threshold sebelum kegagalan pertama selesai. Circuit breaker pada lab tidak sekaligus menjadi bulkhead atau batas concurrency umum.

Cooldown dievaluasi secara lazy

Tidak ada goroutine timer yang tidur lalu membuka probe otomatis. advanceLocked dipanggil dari State dan Execute. Ketika state OPEN dan selisih waktu sejak openedAt mencapai OpenTimeout, fungsi tersebut mengubah state menjadi HALF_OPEN, mereset halfOpenIn, dan menaikkan generation.

Konsekuensinya, memanggil State bukan pembacaan pasif sepenuhnya: ia dapat memicu transisi. Cooldown yang sudah berlalu juga belum berarti network probe sudah dikirim. Probe baru terjadi ketika Execute mengizinkan callback setelah evaluasi waktu.

HALF_OPEN membatasi percobaan pemulihan

// circuit_breaker.go: cabang HALF_OPEN
case HalfOpen:
    if b.halfOpenIn >= b.cfg.HalfOpenMaxCalls {
        b.mu.Unlock()
        return ErrCircuitOpen
    }
    b.halfOpenIn++

Saat jumlah panggilan yang masuk probe mencapai batas, panggilan tambahan ditolak dengan ErrCircuitOpen yang sama. Error ini tidak membedakan OPEN dari kapasitas HALF_OPEN penuh. Test memakai channel untuk menahan satu probe dan membuktikan panggilan kedua ditolak ketika batasnya satu.

Satu probe sukses langsung menutup breaker menjadi CLOSED. Satu probe gagal langsung membukanya lagi serta memperbarui openedAt. Jika HalfOpenMaxCalls lebih dari satu, implementasi tidak menunggu seluruh probe sukses: hasil pertama yang mengubah state menaikkan generation, sehingga hasil probe lama berikutnya dapat diabaikan. Jangan mengartikan batas probe sebagai syarat N sukses berturut-turut untuk recovery.

Generation mencegah hasil lama mengubah state baru

// circuit_breaker.go: guard pada pencatatan hasil
if b.generation != gen {
    return
}

Execute menyimpan generation saat callback diizinkan. Callback yang selesai setelah breaker memasuki generation lain tidak boleh mengubah counter atau state baru. TestTrailingInFlightRequestDoesNotCorruptNewState memulai request lambat saat CLOSED, membuka breaker melalui request lain, lalu memastikan failure lama tidak merusak HALF_OPEN.

Generation bukan cancellation. Callback lama tetap berjalan dan hasil errornya tetap kembali kepada caller; hanya pengaruhnya pada state breaker yang dilewati. Ini membantu memisahkan hasil request dari otoritas request tersebut untuk mengubah state saat ini.

Panic dicatat sebagai failure, lalu tetap diteruskan

Execute memakai deferred bookkeeping dengan penanda panicked. Jika fn panic, pencatatan failure tetap dijalankan dan mutex state dibersihkan. Panic tidak diubah menjadi error biasa dan tidak ditelan. Test HALF_OPEN memeriksa panic tetap dapat di-recover oleh caller, state kembali OPEN, dan probe berikutnya dapat dilakukan setelah cooldown.

Timeout, retry, dan breaker menjawab kebutuhan berbeda

HTTP client memiliki Timeout; Checkout(ctx) meneruskan context caller ke request. Dua helper demo memakai context.Background. Breaker.Execute sendiri tidak menerima context dan tidak membatasi durasi callback. Tanpa timeout pada dependency, callback yang diizinkan tetap bisa menunggu lama, termasuk ketika probe sedang memegang slot HALF_OPEN.

Retry dan exponential backoff dibahas di README, tetapi tidak diimplementasikan dalam client maupun checkout. Breaker tidak menjadwalkan retry dan tidak mematikan retry loop secara otomatis. Ia hanya menolak callback pada evaluasi yang tidak diizinkan. Kombinasi dengan queue, bulkhead, atau retry policy adalah rancangan lanjutan, bukan fitur runtime lab ini.

Klasifikasi failure masih luas

Payment client menganggap semua HTTP status selain 200 sebagai ErrPaymentFailed. Transport error, timeout, atau cancellation juga menjadi error yang dikembalikan callback. Breaker menghitung semua error nonnil tanpa memeriksa kategori. Karena itu, 4xx maupun cancellation dapat ikut memengaruhi threshold jika terjadi melalui jalur ini.

Pada respons 200, client tidak memvalidasi isi JSON sebagai hasil pembayaran bisnis. Probe sukses berarti callback mengembalikan nil menurut aturan client tersebut. Ini bukan bukti saldo terdebit dengan benar atau transaksi gateway selesai. FakeServer SLOW juga tidak memeriksa pembatalan context selama sleep; timeout caller belum berarti pekerjaan server sudah berhenti.

Baca empat skenario demo dengan kondisi yang tepat

Skenario pertama memakai server SLOW 200 ms dan HTTP timeout 100 ms, tanpa breaker. Tiga panggilan dilakukan berurutan. Perkiraan penantian N × timeout hanya menggambarkan rangkaian sequential semacam ini; bukan formula total latency semua workload concurrent.

Skenario kedua memakai server DOWN yang menjawab 500, threshold tiga, dan enam panggilan sequential. Tiga kegagalan awal membuka circuit, lalu panggilan berikutnya ditolak selama cooldown. Jadi dua skenario pertama memakai jenis failure berbeda; jangan menyajikannya sebagai benchmark latency satu workload yang identik.

Skenario ketiga mengganti server menjadi HEALTHY sebelum probe, yang kemudian menutup breaker. Skenario keempat membiarkan server DOWN, sehingga probe membuka breaker lagi. Angka nanosecond atau microsecond pada contoh README adalah contoh output, bukan jaminan latency dan bukan hasil pengukuran baru pada artikel ini.

Fallback perlu menjaga arti hasil bisnis

Checkout pada lab mengembalikan error saat payment gagal atau circuit menolak. Tidak ada cache fallback, antrean, atau status pembayaran palsu. README membahas pemisahan dependency kritis dan nonkritis melalui contoh CMMS dan PPOB, tetapi alur invoice, WhatsApp, provider pulsa, dan debit saldo belum diimplementasikan di folder ini.

Untuk dependency payment yang kritis, fast rejection tetap merupakan kegagalan checkout yang perlu ditangani caller. Circuit breaker mengurangi panggilan yang sia-sia; ia tidak boleh dipresentasikan sebagai mekanisme membuat pembayaran berhasil ketika gateway sedang gagal.

Test, observability, dan batas bukti

Unit test memeriksa threshold, reset sukses, OPEN tanpa callback, cooldown, dua hasil probe, limit HALF_OPEN, panic, trailing generation, dan beberapa akses concurrent. Integration test memakai HTTP fake server untuk 500, recovery 200, serta SLOW yang melewati timeout. Test concurrent umum hanya memeriksa state valid; test interleaved menunggu goroutine tanpa assertion semantik tambahan.

Gauge circuit_state, open count, rejected count, dan percentile dependency latency di README masih rekomendasi. Implementasi menyediakan State dan request counter FakeServer, bukan exporter atau stack observability production.

cd labs/14-circuit-breaker
go test -v ./...
go test -race ./...
go run ./cmd/demo

Modul lab menyatakan Go 1.22. Go belum tersedia di lingkungan penyusunan, sehingga source dan assertion test dibaca, belum dijalankan ulang. Materi ini tidak mengklaim passing test atau benchmark baru.

Pelajaran utamanya adalah memberi batas pada panggilan dependency sambil membaca detail recovery secara tepat. Timeout membatasi penantian yang diizinkan; circuit breaker mengendalikan panggilan berikutnya; probe menguji apakah jalur itu layak dibuka lagi. Ketiganya tetap perlu kriteria yang sesuai behavior dependency sebenarnya.
