## Core Design Decisions

### In-Memory Store Instead of Redis
No external Redis/PostgreSQL required. `MemoryCache` exposes TTL metadata (`ExpiresAt`, `ReadDelta`) needed by XFetch and SWR without requiring Redis TTL inspection commands. The implementation is self-contained and 100% reproducible.

### `GetRaw` Separate From `Get`
XFetch and SWR need access to items that have passed their TTL for comparison of `ExpiresAt`. A `GetRaw` method returns the raw item regardless of expiration, letting services decide to serve stale or recompute.

### `ReadDelta` Stored Per Item
Each item stores the measured DB fetch time (`ReadDelta`). XFetch reads this to parameterize the probabilistic early-expiration formula. This reflects the algorithm's dependency on measured compute time per key.

### XFetch Formula Guard
`ShouldRecompute` explicitly guards `u <= 0 || u >= 1` to prevent `-math.Log(0)` = `+Inf` and `u >= 1` = no-op. The formula is documented as `-Δ·β·ln(U) > TTL_remaining` matching the approved research correction.

### SWR Revalidation Guard
`triggerRevalidate` uses a `revalidating` map under a mutex to prevent multiple concurrent background revalidations for the same key (single-revalidation-in-flight per key). RFC 5861 §5 specifies request-triggered revalidation; the SWR implementation triggers one background goroutine per key, not an unbounded pool.

### Write-Behind Buffer Overflow
`Update` uses `select { case s.writeQueue <- req: default: }` to drop writes on full queue rather than blocking. This is an implementation decision, not a production recommendation.

## Implementation-Specific Choices
- Test concurrency: 20 goroutines with 20ms DB delay to reliably differentiate naive (20 queries) from singleflight (1 query).
- XFetch `beta = 1.0` (practical default per research Finding 6).
- SWR TTL 20ms / staleDelta 300ms gives enough window for test timing with 50ms sleep.
- `WriteBehindService.Close()` drains queue via graceful shutdown before exiting.

## Known Limitations
- **In-process single-flight only**: `SingleFlightService` uses `singleflight.Group` which coalesces within one process. Cross-process stampede (e.g., 10 pods) would require a distributed lock.
- **XFetch optimality proof not verified**: Paper proofs unavailable per research. Implementation follows algorithm from Wikipedia summary.
- **Write-Behind queue drop**: Queue overflow drops writes silently. Noted with `ponytail:` comment. Production requires persistent queue (Kafka, WAL).
- **No persistence**: Cache is in-memory; process restart loses all cached data.
- **SWR timing-sensitive**: SWR test uses `time.Sleep` which may be flaky under heavy system load.

## Trade-offs
| Concern | Decision | Alternative |
|---|---|---|
| No Redis | In-memory cache | Require Docker/Redis, add setup complexity |
| Test determinism | `SetRandFunc` injectable rand | Real random, non-deterministic test |
| Write-behind safety | Drop on overflow | Block on overflow or return error |
| SWR concurrency | Single goroutine per key | Worker pool for high write-update keys |

## What Is Demonstrated
- Cache-Aside read/write lifecycle with cache invalidation on update.
- Write-Through synchronous read-after-write consistency without extra DB query.
- Write-Behind async flush with immediate cache visibility and delayed persistence.
- Cache stampede (thundering herd) via naive concurrent cache miss.
- Single-flight reducing N concurrent DB queries to 1.
- XFetch probabilistic early expiration formula with correct sign `-Δ·β·ln(U)`.
- Stale-While-Revalidate serving stale data while asynchronously refreshing.
- TTL jitter desynchronizing multiple key expirations.

## What Is Not Demonstrated
- Distributed lock-based stampede protection (requires Redis/etcd).
- Write-behind with durable queue (WAL or Kafka).
- Cross-process singleflight (circuit breaker pattern).
- HTTP-layer `stale-while-revalidate` via Cache-Control headers (RFC 5861 applies at HTTP level; lab applies concept at application layer).
- XFetch optimality benchmark comparison vs. simple TTL.
