Dilema Terbesar Sistem Terdistribusi

Cache invalidation adalah salah satu dilema terbesar dalam arsitektur sistem terdistribusi skala modern. Cache dirancang sebagai lapisan memori kerja yang sangat cepat di depan database, bertujuan agar ribuan query per detik dapat dilayani tanpa membebani storage persisten. Namun, ketika record di database mengalami perubahan, cache harus segera diperbarui atau dihapus. Tanpa mekanisme invalidasi yang disiplin, cache akan terus menyimpan data basi, memicu inkonsistensi data di level aplikasi, serta dapat merusak integritas transaksi bisnis secara meluas.

Taksonomi Lab 37

Lab 37 mengklasifikasikan strategi pengelolaan cache ke dalam dua dimensi arsitektural utama: write patterns dan stampede mitigations. Tiga pola penulisan—Cache-Aside, Write-Through, dan Write-Behind—menentukan keseimbangan antara latensi baca-tulis serta jaminan konsistensi data. Di sisi lain, empat mitigasi stampede—Singleflight, XFetch, Stale-While-Revalidate, dan TTL Jitter—bekerja sama untuk mencegah kehancuran database saat kunci panas kedaluwarsa secara mendadak di bawah lonjakan konkurensi. Cache-Aside (Lazy Loading) - Mekanisme & Flow

Pola Cache-Aside atau lazy loading merupakan pendekatan paling populer pada sistem dengan beban baca tinggi. Pada alur pembacaan, aplikasi memeriksa cache terlebih dahulu; jika terjadi cache miss, aplikasi mengambil data langsung dari database lalu menyimpannya ke cache dengan TTL tertentu. Saat data diperbarui, aplikasi wajib menulis perubahan ke database terlebih dahulu sebelum menghapus kunci dari cache. Pola ini memastikan hanya data yang benar-benar dibaca yang menempati ruang memori cache.

func (s *CacheAsideService) Update(ctx, key, val) error {
    s.db.Write(ctx, key, val) // 1. DB dulu
    s.cache.Delete(key)      // 2. baru invalidate
    return nil
}

Cache-Aside - Anomali & Race Condition

Meskipun fleksibel, pola Cache-Aside memiliki celah race condition antara thread pembaca dan thread penulis yang berjalan bersamaan. Jika reader mengalami cache miss lalu memulai query database yang lambat, sementara writer secara bersamaan menulis data baru ke database dan menghapus cache, reader yang terlambat dapat menuliskan kembali data usang ke dalam cache. Akibatnya, nilai usang tersebut akan bertahan di cache hingga masa TTL berakhir, menghasilkan anomali data inkonsisten yang berbahaya.

Write-Through - Konsistensi Sinkron

Pola Write-Through menawarkan jaminan read-after-write consistency yang sangat kuat dengan memperlakukan cache sebagai penyimpanan utama yang sinkron. Setiap operasi pembaruan menulis data ke database persisten dan segera memperbarui kunci cache terkait dalam satu alur eksekusi aplikasi secara berurutan. Hasilnya, setiap request pembacaan berikutnya dijamin langsung memperoleh data terbaru dari cache tanpa perlu query database tambahan. Pola ini mengeliminasi celah data basi yang sering terjadi pada Cache-Aside.

func (s *WriteThroughService) Update(ctx, key, val) error {
    start := time.Now()
    if err := s.db.Write(ctx, key, val); err != nil {
        return fmt.Errorf("db write failed: %w", err)
    }
    delta := time.Since(start)
    s.cache.Set(key, val, s.ttl, delta)
    return nil
}

Write-Through - Biaya Latensi & Partial Failure

Kelemahan mendasar Write-Through terletak pada penalti latensi tulis dan risiko kegagalan parsial di lingkungan terdistribusi. Latensi setiap operasi update membengkak karena harus menunggu dua operasi I/O sinkron secara berturut-turut: penulisan database dan pembaruan cache. Selain itu, jika database commit berhasil namun penulisan cache gagal akibat kendala memori, status cache menjadi inkonsisten. Dalam skenario ini, TTL bertindak sebagai jaring pengaman agar data tidak terkunci dalam status usang selamanya.

Write-Behind (Write-Back) - Throughput Ekstrem

Write-Behind atau Write-Back memprioritaskan throughput penulisan ekstrem dengan memutus ketergantungan langsung terhadap latensi database persisten. Saat pembaruan terjadi, aplikasi langsung memperbarui cache di memori dan memasukkan tugas penulisan ke dalam antrean asinkron, lalu segera merespons pemanggil. Goroutine background secara berkala menguras antrean dan mengeksekusi penulisan ke database di latar belakang. Dengan mekanisme ini, latensi tulis ditekan hingga mendekati nol milidetik, sangat cocok untuk beban tulis masif.

func (s *WriteBehindService) Update(key, val string) {
    s.cache.Set(key, val, s.ttl, 1*time.Millisecond)
    select {
    case s.writeQueue <- WriteRequest{Key: key, Value: val}:
    default: // queue full — drop (demo limitation)
    }
}

Write-Behind - Risiko Durabilitas & Data Loss

Kecepatan luar biasa Write-Behind harus dibayar dengan kompromi serius pada aspek durabilitas data. Jika proses aplikasi mengalami crash, panic, atau kehabisan memori sebelum worker latar belakang sempat mengosongkan antrean, seluruh data pembaruan yang masih tertahan di antrean akan hilang permanen. Selain itu, jika antrean penuh di bawah beban tinggi, implementasi yang menggunakan select-default akan membuang request penulisan secara diam-diam. Sistem produksi wajib menggunakan antrean persisten seperti Kafka atau WAL.

Thundering Herd / Cache Stampede

Cache stampede atau thundering herd terjadi ketika kunci cache populer yang sering diakses kedaluwarsa secara mendadak. Puluhan hingga ribuan goroutine pembaca yang datang bersamaan akan mendapati cache miss, lalu serentak mengeksekusi query database yang identik. Fenomena ini melipatgandakan beban database sebesar perkalian laju kedatangan request dan durasi query. Akibatnya, connection pool terkuras habis, waktu tunggu melonjak tajam, dan sistem dapat mengalami kegagalan berantai hingga ketersediaan layanan runtuh sepenuhnya.

Singleflight - Request Coalescing

Mitigasi pertama terhadap cache stampede adalah request coalescing menggunakan paket resmi Go golang.org/x/sync/singleflight. Pola ini memastikan bahwa untuk kunci yang sama, fungsi pengambilan data ke database hanya dijalankan tepat satu kali oleh satu goroutine pemenang. Goroutine-goroutine lain yang datang bersamaan akan ditahan pada barrier internal dan menunggu selesainya eksekusi goroutine pertama. Setelah selesai, seluruh pemanggil menerima salinan hasil yang identik, memangkas puluhan query database menjadi satu panggilan tunggal.

import "golang.org/x/sync/singleflight"

type SingleFlightService struct {
    cache  *MemoryCache
    db     *MockDB
    ttl    time.Duration
    flight singleflight.Group
}

Singleflight - Kode & Mekanika Do()

Implementasi SingleFlightService menerapkan teknik double-check locking di dalam closure fungsi Do untuk efisiensi maksimal. Sebelum memulai query database yang mahal, goroutine memeriksa kembali isi cache untuk mengantisipasi kemungkinan kunci tersebut telah berhasil diisi oleh eksekusi paralel lain. Singleflight mengelola tabel pemetaan pemanggilan aktif secara internal dan membagikan return value melalui channel bersama. Namun, perlindungan ini terbatas pada level satu proses; sistem multi-pod tetap membutuhkan distributed lock seperti Redis SETNX.

func (s *SingleFlightService) Get(ctx, key) (string, error) {
    item, err := s.cache.Get(key) // outer cache check
    if err == nil { return item.Value, nil }
    res, err, _ := s.flight.Do(key, func() (interface{}, error) {
        // Double-check cache inside flight execution
        item, err := s.cache.Get(key)
        if err == nil { return item.Value, nil }
        start := time.Now()
        val, err := s.db.Query(ctx, key)
        if err != nil { return "", err }
        delta := time.Since(start)
        s.cache.Set(key, val, s.ttl, delta)
        return val, nil
    })
    if err != nil { return "", err }
    return res.(string), nil
}

XFetch - Probabilistic Early Expiration

XFetch adalah algoritma mitigasi stampede probabilistik berbasis riset akademis Vattani et al. Setiap kali request membaca cache, algoritma menghitung ambang batas kedaluwarsa dini berdasarkan biaya komputasi query database terakhir, parameter tuning beta, dan bilangan acak seragam. Jika nilai komputasi probabilistik melebihi sisa TTL, request tersebut akan berinisiatif merefresh cache secara proaktif sebelum waktu kedaluwarsa resmi tiba. Pola ini menyebarkan beban pembaruan cache ke sepanjang kurva eksponensial.

func ShouldRecompute(delta time.Duration, beta float64,
    ttlRemaining time.Duration, u float64) bool {
    if u <= 0 || u >= 1 { return false }
    deltaSec := delta.Seconds()
    ttlRemainingSec := ttlRemaining.Seconds()
    expiryCompute := -deltaSec * beta * math.Log(u)
    return expiryCompute > ttlRemainingSec
}

XFetch - Tanda Negatif Matematika

Penerapan matematis formula XFetch menuntut pemahaman mendalam terhadap tanda minus logaritma natural. Karena variabel U berada pada rentang nol hingga satu, nilai logaritma natural ln(U) selalu menghasilkan bilangan negatif. Penambahan tanda minus di depan rumus membuat hasil kalkulasi bernilai positif, sehingga memungkinkan perbandingan yang valid terhadap sisa TTL. Kesalahan umum dalam mengabaikan tanda minus akan menghasilkan nilai negatif permanen, menyebabkan kondisi penyegaran awal tidak pernah terpenuhi dan stampede tetap terjadi.

Stale-While-Revalidate (SWR) - Toleransi Data Basi

Stale-While-Revalidate yang diadaptasi dari RFC 5861 menawarkan solusi performa tinggi dengan memperluas toleransi terhadap data kedaluwarsa. Sistem membagi siklus hidup cache menjadi tiga jendela: fresh di mana data disajikan langsung, stale window di mana data usang segera disajikan ke klien sementara revalidasi dipicu di latar belakang, serta hard miss di mana query database harus dieksekusi secara sinkron. Pendekatan ini menjaga latensi pembacaan tetap berada di level sub-milidetik.

item, ok := s.cache.GetRaw(key)
now := time.Now()
if ok {
    if now.Before(item.ExpiresAt) { return item.Value, nil }       // Fresh
    staleUntil := item.ExpiresAt.Add(s.staleDelta)
    if now.Before(staleUntil) {
        s.triggerRevalidate(key)                                   // Stale-1
        return item.Value, nil
    }
}
// Hard miss / Stale-2 → synchronous fetch
val, err := s.db.Query(ctx, key)
s.cache.Set(key, val, ttl, delta)
return val, nil

SWR - Async Revalidation & Deduplikasi

Keberhasilan SWR sangat bergantung pada mekanisme deduplikasi revalidasi latar belakang agar tidak memicu badai permintaan baru ke database. Tanpa pembatas, ratusan request pada data basi akan masing-masing meluncurkan goroutine revalidasi baru. SWRService mengatasi ancaman ini dengan memelihara tabel penanda revalidasi berbasis mutex; hanya satu goroutine yang diizinkan memperbarui database untuk kunci yang sama pada satu waktu. Jika revalidasi gagal, klien tetap aman menerima nilai usang sebagai fallback.

func (s *SWRService) triggerRevalidate(key string) {
    s.mu.Lock()
    if s.revalidating[key] { s.mu.Unlock(); return }
    s.revalidating[key] = true
    s.mu.Unlock()
    s.revalCount.Add(1)
    go func() { // async fetch & set
        defer func() {
            s.mu.Lock()
            delete(s.revalidating, key)
            s.mu.Unlock()
        }()
        ...db.Query → s.cache.Set...
    }()
}

TTL Jitter - Anti-Sinkronisasi Expiry

TTL Jitter adalah teknik pertahanan sederhana namun ampuh untuk mencegah sinkronisasi waktu kedaluwarsa lintas kunci cache. Ketika ribuan kunci diisi secara bersamaan saat startup sistem atau deploy aplikasi, penggunaan TTL statis akan menyebabkan seluruh kunci tersebut kedaluwarsa pada detik yang sama persis. Dengan menambahkan offset acak pada rentang nol hingga batas maksimum jitter, masa kedaluwarsa tersebar merata, mengeliminasi lonjakan serentak pada database di masa mendatang.

func TTLWithJitter(base, maxJitter time.Duration) time.Duration {
    if maxJitter <= 0 { return base }
    jitter := time.Duration(rand.Int63n(int64(maxJitter)))
    return base + jitter
}

Pengujian: Cache-Aside vs Write-Through vs Write-Behind

Pengujian TestCachePatterns memvalidasi perilaku ketiga write pattern menggunakan MockDB dengan counter query atomik yang presisi. Pada Cache-Aside, query database hanya bertambah pada cache miss pertama dan tetap stabil pada hit kedua, lalu bertambah lagi setelah operasi update menghapus cache. Pada Write-Through, pembacaan pasca-update langsung mendapati cache hit tanpa query database. Pada Write-Behind, update cache terjadi seketika, dan penulisan database terbukti dieksekusi secara asinkron beberapa milidetik kemudian.

Pengujian: Naive Stampede vs Singleflight

Pengujian mitigasi stampede membuktikan efektivitas Singleflight secara empiris di bawah beban konkurensi tinggi. Ketika dua puluh goroutine diluncurkan secara simultan untuk mengakses kunci panas yang belum ada di cache, implementasi Naive menghasilkan dua puluh query database paralel—memperlihatkan stampede nyata. Sebaliknya, SingleFlightService berhasil menggabungkan seluruh dua puluh panggilan tersebut menjadi tepat satu query database tunggal, dan seluruh goroutine menerima nilai yang benar tanpa terjadi data race.

[Naive] 20 concurrent goroutines -> 20 DB queries (stampede!)
[SF]    20 concurrent goroutines -> 1 DB queries (singleflight), 20 correct results

Pengujian: XFetch Deterministic Simulation

Pengujian logika XFetch dirancang secara deterministik melalui injeksi fungsi pengacak randFunc tiruan untuk menguji kedua percabangan algoritma. Ketika generator acak menghasilkan nilai tinggi mendekati satu, formula matematis memutuskan tidak perlu recompute, sehingga data disajikan langsung dari cache. Sebaliknya, saat diinjeksi nilai acak yang sangat kecil, rumus menghasilkan nilai komputasi yang melampaui sisa TTL, memicu eksekusi query pembaruan dini ke database secara terbukti dan terukur.

Initial GET       -> DB queries: 1, val: initial-val
Low rand draw     -> DB queries: 2, val: refreshed-val (early proactive refresh)
High rand draw    -> DB queries: 1, val: fresh-data (served from cache, no early refresh)

Pengujian: SWR & Race Detection

Pengujian Stale-While-Revalidate memverifikasi bahwa data usang langsung dikembalikan kepada pemanggil tanpa jeda latensi begitu TTL kedaluwarsa namun masih dalam rentang toleransi stale. Sepuluh goroutine konkuren yang membaca kunci basi secara simultan terbukti hanya memicu tepat satu proses revalidasi latar belakang berkat mekanisme deduplikasi. Pengujian race detector Go dengan flag -race lulus sempurna tanpa kebocoran data, membuktikan keandalan thread-safety implementasi SWR di lingkungan produksi.

Matriks Komparasi 7 Strategi

Matriks komparasi tujuh strategi menyajikan panduan evaluasi menyeluruh berdasarkan profil latensi tulis, latensi baca, tingkat konsistensi, dan risiko arsitektural utama. Tidak ada satu strategi tunggal yang sempurna untuk semua skenario; setiap pilihan merupakan kompromi teknik yang sadar. Cache-Aside unggul pada efisiensi memori, Write-Through memberikan konsistensi tertinggi dengan mengorbankan kecepatan tulis, sementara Write-Behind menawarkan performa penulisan maksimum namun menuntut mitigasi khusus terhadap risiko hilangnya data saat kegagalan sistem.

Panduan Adopsi & Rekomendasi Lapangan

Panduan adopsi menetapkan pohon keputusan praktis untuk mengimplementasikan strategi cache di lingkungan produksi. Untuk sebagian besar API read-heavy, Cache-Aside yang dipadukan dengan TTL Jitter adalah pilihan default terbaik. Ketika beban lalu lintas tinggi memicu stampede pada kunci panas, pasang Singleflight untuk layanan monolitik atau kunci terdistribusi untuk arsitektur multi-pod. Terapkan SWR jika sistem menoleransi data usang demi latensi sub-milidetik, dan gunakan Write-Behind hanya jika kehilangan data non-kritis dapat diterima.
