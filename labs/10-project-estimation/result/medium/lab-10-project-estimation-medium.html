Estimasi Proyek: Delapan Fitur Bukan Delapan Hari

Membedakan effort dan duration lewat breakdown, spike, risk, serta asumsi aplikasi booking servis.

Delapan fitur tidak otomatis berarti delapan hari kerja. Pada aplikasi booking servis, halaman pembayaran bisa terlihat sederhana, tetapi pekerjaannya mencakup authentication vendor, pembuatan transaksi, webhook, retry, dan pengujian sandbox. Menghitung layar saja menyembunyikan bagian yang paling tidak pasti.

Lab 10 membahas estimasi proyek melalui kasus tersebut. Repository menyediakan model kalkulasi dan validasi dalam Go, bukan aplikasi booking yang sudah dibangun. Tujuannya adalah membuat effort, uncertainty, risk, dependency, dan asumsi terlihat sebelum sebuah angka diperlakukan sebagai deadline.

Hitung pekerjaan, bukan halaman

Scope kasusnya terdiri dari login, booking online, pilih cabang, pilih mekanik, payment gateway, notifikasi WhatsApp, dashboard admin, dan laporan Excel. Estimator naive mengembalikan satu hari untuk setiap halaman. Test-nya memang memeriksa perilaku itu, tetapi bukan bukti bahwa seluruh fitur dapat diselesaikan dengan produktivitas satu halaman per hari.

README memecah payment gateway menjadi pekerjaan konkret: membaca dokumentasi, memahami authentication, membuat transaksi, menerima webhook dan memverifikasi signature, menangani error, menjaga retry/idempotency, lalu menguji sandbox. Ini adalah breakdown perencanaan; tidak ada integrasi payment sungguhan yang dijalankan oleh lab.

Breakdown juga memisahkan booking schema dan business validation, relasi cabang-mekanik beserta availability, query dashboard, dan generator Excel. Task kecil membantu menjelaskan apa yang masuk scope. Ia tidak otomatis memastikan semua pekerjaan sudah terdaftar.

Known dan unknown memerlukan perlakuan berbeda

Pekerjaan familiar dapat diberi range berdasarkan scope dan pengalaman tim yang relevan. Vendor baru dengan flow webhook yang belum dipahami membutuhkan discovery. Unknown bukan nol hari dan bukan alasan untuk menghasilkan tebakan yang terlihat presisi.

Spike menghasilkan informasi, bukan integrasi siap rilis

Spike dibatasi waktu dan diarahkan pada pertanyaan tertentu: apakah authentication bekerja, transaksi sandbox dapat dibuat, signature webhook bisa diverifikasi, dan failure behavior dapat dipahami? Hasilnya berupa informasi untuk menyusun estimasi implementasi. Timebox discovery tidak sama dengan waktu menyelesaikan fitur production.

Ada perbedaan antara README dan kode. Task.Validate menolak RiskUnknown ketika SpikeDays bernilai nol, meskipun range implementasinya sudah nonzero. Test UnknownRiskWithoutSpikeRejected memang memakai range 1/2/3 tanpa spike dan mengharapkan error. Baris README yang menyebut kondisi itu diperbolehkan setelah spike tidak sesuai implementasi.

Model tidak memiliki flag spike selesai. Setelah discovery, risk dan range perlu ditinjau ulang; mempertahankan Unknown sambil mengosongkan spike masih ditolak. Sebaliknya, RequiredSpikes mengumpulkan semua task dengan spike positif, termasuk jika label risk-nya bukan Unknown.

Range bukan probabilitas deadline

// estimation.go; definisi lengkap
type EstimateRange struct {
    Min        float64
    MostLikely float64
    Max        float64
}

func (r EstimateRange) Expected() float64 {
    return (r.Min + 4.0*r.MostLikely + r.Max) / 6.0
}

Expected adalah hasil weighted calculation: MostLikely diberi bobot empat. Validasi memeriksa nilai nonnegatif dan urutan Min ≤ MostLikely ≤ Max. Model menjumlahkan minimum, expected, dan maksimum task secara terpisah.

Tidak ada distribusi probabilitas, percentile, simulasi, atau kalibrasi dari histori proyek. Angka Max bukan janji deadline terakhir. Confidence juga bukan persentase peluang proyek selesai tepat waktu.

Contingency mengikuti aturan model yang eksplisit

Unknown sekecil apa pun membuat overall risk menjadi High. Tanpa Unknown, proporsi task High minimal 30% juga menghasilkan High. Jika tidak, adanya task High atau Medium menghasilkan Medium; sisanya Low. Heuristik ini menghitung task, bukan memberi bobot berdasarkan effort.

AutoContingency memilih 25% untuk High, 15% untuk Medium, dan 10% untuk Low hanya ketika rate yang diberikan nol. Rate positif eksplisit tetap dipakai. Jika auto dimatikan dan rate nol, tidak ada contingency. Default ini adalah pilihan model lab, bukan aturan persentase yang wajib untuk semua proyek.

Buffer diterapkan ke seluruh endpoint

ContingencyEffort dihitung dari base expected × rate. Namun minimum dan maksimum masing-masing dikalikan 1 + rate; bukan ditambah satu angka buffer expected yang sama. Untuk fixture booking, rate 25% menghasilkan buffer expected 8,2075 dan final effort 24,38 / 41,04 / 64,38 engineer-days setelah pembulatan.

Angka tersebut merupakan perhitungan ulang dari input dan formula repository. Itu bukan output eksekusi test Go dan bukan quotation delivery proyek nyata.

Effort berbeda dari duration

// estimation.go; cuplikan Project.Estimate
effectiveDailyCapacity := float64(p.EngineerCount) * p.Availability

Duration diperoleh dengan membagi setiap final effort dengan kapasitas harian efektif. Satu engineer pada availability 70% memberikan kapasitas model 0,7 engineer-days per hari kerja. Fixture tadi menghasilkan 34,8 / 58,6 / 92,0 hari kerja setelah pembulatan satu desimal.

Weeks membaginya dengan lima: range endpoint sekitar 7,0–18,4 minggu dengan lima hari kerja. Nama CalendarDuration tidak membuat model mengenali tanggal, hari libur, critical path, atau waktu menunggu vendor. Itu masih working-day capacity calculation.

README menyebut contoh terpisah 15–23 engineer-days pada availability 70%, tetapi mengaitkannya dengan 3–4 minggu dan hanya menghitung endpoint bawah. Membagi kedua endpoint memberi sekitar 21,4–32,9 hari kerja, atau 4,3–6,6 minggu kerja. Jangan mencampur contoh itu dengan fixture test yang lebih besar.

Test MultipleEngineersReducesCalendar memeriksa durasi formula lebih kecil ketika engineer ditambah. Ia tidak membuktikan bahwa setiap task dapat dibagi rata atau bahwa dua engineer membuat delivery nyata dua kali lebih cepat. Urutan dependency dan overhead koordinasi tidak dimodelkan.

Assumptions dan confidence perlu dibaca apa adanya

Asumsi fixture mencakup desain UI final, sandbox dan dokumentasi vendor tersedia, API provider dapat diakses, satu engineer tersedia, serta tidak ada perubahan requirement besar. Dependency adalah hal yang dibutuhkan, seperti credential; risk adalah kemungkinan yang mengganggu, seperti dokumentasi berbeda dari sandbox atau aturan slot berubah.

calculateConfidence memberi Low jika masih ada Unknown atau overall risk High. Medium risk menghasilkan Medium; Low risk dengan asumsi menghasilkan High, sedangkan tanpa asumsi menghasilkan Low. Teks asumsi hanya dihitung, tidak diverifikasi. Parameter contingencyRate diterima tetapi tidak dipakai dalam kalkulasi confidence.

Karena itu, fixture booking tetap Low confidence meskipun asumsi dan contingency sudah dicantumkan. Menambah buffer tidak otomatis meningkatkan label tersebut.

Batas bukti dan komunikasi hasil

Test memeriksa range terbalik, nilai negatif, availability tidak valid, engineer count nol atau negatif, risk label salah, project kosong, serta task tanpa nama. Test case study memeriksa High risk dan minimal dua spike, kemudian mencetak nilai; ia tidak menetapkan assertion eksak untuk semua endpoint angka.

Model masih menerima nama task berisi whitespace dan tidak memiliki guard eksplisit NaN/infinity. Task dalam project dan feature dijumlahkan tanpa deduplikasi. Tidak ada dependency graph, waktu tunggu vendor, deteksi scope yang hilang, atau re-estimation otomatis setelah spike.

Seluruh pembahasan memakai README.md, estimation.go, estimation_test.go, dan go.mod pada commit 82af988b89439fa92b1200406c5afbd59ce72a56. Go tidak tersedia di lingkungan pembuatan konten ini; test dibaca, tidak dijalankan. Perhitungan fixture diperiksa secara terpisah tanpa mengklaim hasil test.

An estimate is a range with assumptions, not a promise without conditions. Hasil estimasi menjadi berguna ketika scope, spike, kapasitas, risiko, dan batas model tetap terlihat bersama angkanya.
