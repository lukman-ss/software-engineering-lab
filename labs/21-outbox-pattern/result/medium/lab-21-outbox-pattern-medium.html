Dual-Write Problem: Ketidakonsistenan Senyap

Dual-write problem muncul saat aplikasi menyimpan data ke database lalu menerbitkan event ke broker secara terpisah. Transaksi database tidak bisa me-rollback sistem eksternal seperti Kafka atau RabbitMQ. Jika commit database sukses tetapi publish gagal akibat timeout atau jaringan putus, order tersimpan namun event tidak pernah terkirim ke downstream.

Mengapa Pendekatan Naif Gagal?

Implementasi naif tampak intuitif namun kehilangan jaminan atomisitas lintas sistem. Kegagalan publish ke broker terjadi di luar batas transaksi commit, meninggalkan order persisten tanpa jejak event yang dapat di-retry secara otomatis.

func CreateOrderDualWriteNaive(broker, orderID, amount) error {
    tx := db.BeginTx()
    tx.SaveOrder(order)
    tx.Commit()          // DB berhasil
    broker.Publish(msg)  // Broker gagal → inkonsisten
}

Mental Model: Transactional Outbox

Pola Transactional Outbox memindahkan penulisan event ke dalam transaksi database yang sama dengan entitas bisnis. Layanan menyimpan order dan outbox message secara atomik. Proses terpisah berupa polling relay kemudian membaca record berstatus PENDING secara asinkron dan mengirimkannya ke broker.

type OutboxMessage struct {
    ID        string
    EventType string
    Payload   string
    Status    MessageStatus  // PENDING, PROCESSED
    CreatedAt time.Time
}

Alur Eksekusi: Dari Transaksi Hingga Consumer

Alur pipeline end-to-end menghubungkan komponen sistem:

Client → OrderService.CreateOrderWithOutbox
Service → DB.BeginTx() → SaveOrder + SaveOutbox (staged)
Service → DB.Commit() → flushed atomically
Relay (ticker) → GetPendingOutbox() → [PENDING]
Relay → Broker.Publish(msg) → success?
Relay → MarkOutboxProcessed(msg.ID) → PROCESSED
Consumer.Handle(msg) → idempotent check → accepted

Implementasi Atomic Outbox Write

Metode CreateOrderWithOutbox menampung mutasi order dan outbox message secara staged dalam satu transaksi, lalu melakukan commit secara atomik.

func (s *OrderService) CreateOrderWithOutbox(orderID string, customerID string, amount float64) error {
    tx := s.db.BeginTx()
    order := Order{ID: orderID, CustomerID: customerID, Amount: amount, Status: OrderStatusCreated}
    payload, _ := json.Marshal(order)
    msg := OutboxMessage{ID: fmt.Sprintf("evt-%s", orderID), EventType: "OrderCreated", Payload: string(payload), Status: MessageStatusPending, CreatedAt: time.Now()}
    tx.SaveOrder(order)
    tx.SaveOutbox(msg)
    return tx.Commit()
}

Mekanisme vs Gejala: Dual-Write vs Outbox

AspekDual-Write NaiveTransactional Outbox
Write BoundaryTerpisah (DB commit dulu, lalu broker)Sama (order + outbox dalam satu Tx)
AtomicityTidak atomik lintas sistemAtomik untuk write pertama
Broker Failure ImpactOrder persisten, event hilangOrder + event persisten, relay retry
Idempotency RequirementTidak diperlukan (karena konsisten)Diperlukan (at-least-once delivery)
Operational ComplexityRendah, tetapi risiko tinggiSedang, dengan relay dan cleanup

3 Keputusan Desain Kritis

1. Atomic Boundary: Satukan penulisan entitas bisnis dan pesan outbox dalam satu transaksi database lokal menggunakan pola staging.
2. Reliable Relay: Terapkan mekanisme retry pada relay dan hanya tandai record sebagai PROCESSED setelah menerima ACK broker.
3. Idempotent Consumer: Pasang verifikasi deduplikasi berbasis event ID di sisi consumer untuk menangani at-least-once delivery.

YANG TIDAK DIBUKTIKAN

Lab ini menggunakan database in-memory, bukan mesin RDBMS produksi seperti PostgreSQL atau MySQL. Hanya strategi Polling Publisher yang diuji; log-tailing berbasis CDC seperti Debezium tidak diimplementasikan. Belum ada antrean dead-letter queue untuk poison payload non-retryable. Nilai ambang SLA bersifat ilustratif untuk kebutuhan lab.

Trade-off Arsitektur: Outbox Pattern

Keuntungan: Menghilangkan risiko kehilangan event secara senyap, menjamin at-least-once delivery, dan mendekopel layanan bisnis dari ketersediaan broker.
Konsekuensi: Menambah latensi pengiriman pesan akibat interval polling, menambah beban kueri database berkala, serta menuntut mekanisme deduplikasi idempoten di sisi penerima.

Before vs After: Transformasi Arsitektur

Before (Dual-Write Naive): Service memanggil DB.Commit lalu Broker.Publish. Saat broker mati, order tersimpan tetapi event hilang permanen tanpa jejak recovery.
After (Transactional Outbox): Service menulis order dan outbox dalam satu transaksi atomik. Relay worker secara berkala mencoba ulang pengiriman hingga broker kembali pulih.

Test 1: Happy Path - Atomic Write + Relay Dispatch

TestTransactionalOutbox_HappyPath memvalidasi siklus penuh: pembuatan order atomik, polling relay pada interval 10ms, keberhasilan publish ke broker, dan perubahan status record menjadi PROCESSED.

func TestTransactionalOutbox_HappyPath(t *testing.T) {
    db := outbox.NewDB()
    broker := outbox.NewMockBroker()
    relay := outbox.NewRelay(db, broker, 10*time.Millisecond)
    service := outbox.NewOrderService(db)
    consumer := outbox.NewConsumer()
    relay.Start()
    err := service.CreateOrderWithOutbox("o-1", "c-1", 100.50)
    assert.NoError(t, err)
    time.Sleep(50 * time.Millisecond)
    published := broker.GetPublished()
    assert.Len(t, published, 1)
    assert.Equal(t, "OrderCreated", published[0].EventType)
    msg, _ := db.GetOutbox("evt-o-1")
    assert.Equal(t, outbox.MessageStatusProcessed, msg.Status)
}

Test 2: Rollback - Nothing Persists

TestTransactionalOutbox_Rollback membuktikan bahwa pemanggilan Rollback membuang mutasi staged pada order maupun outbox. Tidak ada rekaman yang tersisa di database dan broker tidak menerima pesan sama sekali.

func TestTransactionalOutbox_Rollback(t *testing.T) {
    db := outbox.NewDB()
    tx := db.BeginTx()
    tx.SaveOrder(outbox.Order{ID: "o-2", Amount: 50})
    tx.SaveOutbox(outbox.OutboxMessage{ID: "evt-o-2", Status: outbox.MessageStatusPending})
    tx.Rollback()
    _, ok := db.GetOrder("o-2")
    assert.False(t, ok, "order should not exist")
    _, ok = db.GetOutbox("evt-o-2")
    assert.False(t, ok, "outbox should not exist")
    time.Sleep(30 * time.Millisecond)
    assert.Len(t, broker.GetPublished(), 0, "no messages to broker")
}

Test 3: Idempotency - Duplicate Delivery Rejected

TestTransactionalOutbox_Idempotency_DuplicateDelivery menguji penolakan duplikasi pengiriman pesan pada consumer. Pengiriman pertama diterima (accepted=true), sedangkan pengiriman ulang ditolak (accepted=false) sehingga received count tetap bernilai 1.

func TestTransactionalOutbox_Idempotency_DuplicateDelivery(t *testing.T) {
    consumer := outbox.NewConsumer()
    msg := outbox.OutboxMessage{ID: "evt-duplicate", EventType: "OrderCreated", Payload: "data"}
    p1 := consumer.Handle(msg)
    assert.True(t, p1, "first delivery should be accepted")
    p2 := consumer.Handle(msg)
    assert.False(t, p2, "duplicate delivery should be rejected")
    assert.Equal(t, 1, consumer.GetReceivedCount(), "count stays 1")
}

Test 4: Relay Retry - Broker Failure Tolerated

TestTransactionalOutbox_RelayRetryAfterBrokerFailure membuktikan ketahanan relay saat broker gagal sementara. Pesan tetap berstatus PENDING pada poll pertama, lalu berhasil dipublish dan ditandai PROCESSED pada siklus berikutnya setelah broker pulih.

func TestTransactionalOutbox_RelayRetryAfterBrokerFailure(t *testing.T) {
    db := outbox.NewDB()
    broker := outbox.NewMockBroker()
    relay := outbox.NewRelay(db, broker, 10*time.Millisecond)
    service := outbox.NewOrderService(db)
    broker.SetFailNext(true)  // first publish fails
    service.CreateOrderWithOutbox("o-retry", "c-retry", 55.0)
    relay.Start()
    time.Sleep(25 * time.Millisecond)  // first poll fails
    msg, _ := db.GetOutbox("evt-o-retry")
    assert.Equal(t, outbox.MessageStatusPending, msg.Status)
    time.Sleep(50 * time.Millisecond)  // second poll succeeds
    published := broker.GetPublished()
    assert.Len(t, published, 1)
    msg, _ = db.GetOutbox("evt-o-retry")
    assert.Equal(t, outbox.MessageStatusProcessed, msg.Status)
}

Test 5: Purge Processed - Memory Leak Prevention

TestTransactionalOutbox_PurgeProcessed memastikan mekanisme pembersihan tabel outbox bekerja efektif. Record berstatus PROCESSED dihapus untuk mencegah ledakan ukuran tabel, sementara record PENDING tetap dipertahankan.

func TestTransactionalOutbox_PurgeProcessed(t *testing.T) {
    db := outbox.NewDB()
    tx := db.BeginTx()
    tx.SaveOutbox(outbox.OutboxMessage{ID: "m1", Status: outbox.MessageStatusPending})
    tx.SaveOutbox(outbox.OutboxMessage{ID: "m2", Status: outbox.MessageStatusProcessed})
    tx.Commit()
    purged := db.PurgeProcessedOutbox()
    assert.Equal(t, 1, purged)
    _, ok := db.GetOutbox("m1")
    assert.True(t, ok, "pending should remain")
    _, ok = db.GetOutbox("m2")
    assert.False(t, ok, "processed should be purged")
}

Checklist Implementasi Outbox Pattern

Daftar periksa implementasi produksi: siapkan skema tabel outbox_events dengan agregat terindeks, sertakan penulisan event dalam transaksi bisnis lokal, konfigurasi interval relay polling secara seimbang, tandai status processed hanya setelah ACK diterima, implementasikan consumer idempoten, jalankan cron job pembersihan record lawas, serta pantau metrik oldest-event age dan pending count.

Anti-Pattern: Apa yang Harus Dihindari

Hindari memanggil broker sebelum commit database, menggunakan event ID yang tidak deterministik atau non-unik, membiarkan consumer tanpa perlindungan deduplikasi, menonaktifkan proses penghapusan berkala tabel outbox, serta menyetel interval polling yang terlalu lama sehingga memicu penumpukan antrean.

Prinsip Arsitektural Jangka Panjang

Kembangkan sistem dengan mengasumsikan kegagalan jaringan adalah hal pasti. Pisahkan boundary penulisan data transaksional dari boundary pengiriman pesan jaringan. Konsistensi eventual yang ditopang oleh jaminan at-least-once dan konsumen idempoten memberikan ketahanan operasional yang jauh lebih realistis daripada koordinasi transaksi terdistribusi dua-fase.
