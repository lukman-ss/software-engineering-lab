Dual-Write Problem: Ketidakonsistenan Senyap

Dual-write problem muncul ketika aplikasi mencoba menulis ke database dan message broker secara terpisah dalam satu flow bisnis. Transaksi database hanya mengontrol operasi di dalam database itu sendiri; ia tidak dapat melakukan ROLLBACK pada sistem eksternal seperti Kafka atau RabbitMQ. Akibatnya, jika commit database sukses tetapi publish ke broker gagal, sistem masuk ke keadaan inkonsisten: order tersimpan tetapi event tidak pernah dikirim. Kondisi ini sulit dideteksi secara real-time dan memerlukan mekanisme rekonsiliasi manual yang kompleks.

Mengapa Pendekatan Naif Gagal?

Implementasi naive dual-write tampaknya intuitif: simpan order ke database, lalu publish event ke broker. Namun, karena kedua operasi berada di luar boundary transaksi yang sama, kegagalan publish tidak dapat di-rollback dari sisi database. Order tetap tersimpan sementara event hilang selamanya. Pendekatan ini juga memperkenalkan coupling yang kuat antara service pemesanan dan broker, sehingga setiap kegagalan broker akan menggagalkan seluruh flow bisnis.

func CreateOrderDualWriteNaive(broker, orderID, amount) error {
    tx := db.BeginTx()
    tx.SaveOrder(order)
    tx.Commit()          // DB berhasil
    broker.Publish(msg)  // Broker gagal → inkonsisten
}

Mental Model: Transactional Outbox

Mental model inti dari pola Transactional Outbox adalah memindahkan penulisan event ke dalam boundary transaksi yang sama dengan penulisan entitas bisnis. Alih-alih melakukan dua write terpisah, aplikasi menulis order dan outbox message secara bersamaan dalam satu transaksi database. Setelah commit berhasil, kedua rekaman tersebut persisten. Proses asynchronous yang disebut message relay kemudian secara periodik polling record PENDING dan mengirimkannya ke broker. Jika relay gagal, record tetap PENDING dan akan dicoba lagi pada siklus berikutnya.

type OutboxMessage struct {
    ID        string
    EventType string
    Payload   string
    Status    MessageStatus  // PENDING, PROCESSED
    CreatedAt time.Time
}

Alur Eksekusi: Dari Transaksi Hingga Consumer

Pipeline eksekusi Transactional Outbox terdiri dari lima tahap utama. Pertama, service menerima request pembuatan order dan memulai transaksi database. Kedua, service menyimpan order dan outbox message secara staged di dalam transaksi. Ketiga, service melakukan commit yang secara atomik flush kedua staged record ke database. Keempat, relay worker yang berjalan periodik polling record PENDING dan mencoba publish ke broker. Kelima, consumer menerima pesan dan melakukan idempotent check sebelum memproses lebih lanjut.

Implementasi Atomic Outbox Write

Implementasi atomic outbox write berada di method CreateOrderWithOutbox pada service.go. Method ini memulai transaksi baru, membuat entitas order dan outbox message, lalu menyimpan keduanya secara staged menggunakan SaveOrder dan SaveOutbox. Jika Marshalling JSON gagal atau salah satu save operation error, method akan rollback dan mengembalikan error. Hanya setelah kedua staged record tersimpan dengan sukses, method melakukan commit yang akan secara atomik flush semua perubahan ke database.

func (s *OrderService) CreateOrderWithOutbox(orderID string, customerID string, amount float64) error {
    tx := s.db.BeginTx()
    order := Order{ID: orderID, CustomerID: customerID, Amount: amount, Status: OrderStatusCreated}
    payload, _ := json.Marshal(order)
    msg := OutboxMessage{ID: fmt.Sprintf("evt-%s", orderID), EventType: "OrderCreated", Payload: string(payload), Status: MessageStatusPending, CreatedAt: time.Now()}
    tx.SaveOrder(order)
    tx.SaveOutbox(msg)
    return tx.Commit()
}

Failure Path: Dual-Write Naive Menghasilkan Dangling Order

Failure path ini membuktikan bagaimana dual-write naive menciptakan dangling reference: order yang persisten di database tanpa event yang sesuai di broker. Dalam demo, broker disimulasikan gagal melalui SetFailNext(true). Setelah commit database sukses, method CreateOrderDualWriteNaive mencoba publish ke broker yang gagal, menyebabkan error dikembalikan. Namun order sudah tersimpan permanen di database. Test Case TestDualWriteProblem_Failure mengassert kondisi ini: order ditemukan di DB, tetapi broker tidak menerima pesan apa pun.

Mekanisme vs Gejala: Dual-Write vs Outbox

Tabel perbandingan ini menyoroti perbedaan fundamental antara pendekatan dual-write naive dan transactional outbox. Pada dual-write naive, boundary write terpisah antara database commit dan broker publish, sehingga tidak ada atomisitas lintas sistem. Ketika broker gagal setelah commit, order tetap persisten sedangkan event hilang. Sebaliknya, pada transactional outbox, kedua write dilakukan dalam satu transaksi database, menjamin atomisitas untuk tahap pertama. Broker failure hanya menunda delivery, bukan menghapus event, karena relay akan retry hingga sukses.

Write BoundaryTerpisah (DB commit dulu, lalu broker)Sama (order + outbox dalam satu Tx)
AtomicityTidak atomik lintas sistemAtomik untuk write pertama
Broker Failure ImpactOrder persisten, event hilangOrder + event persisten, relay retry
Idempotency RequirementTidak diperlukan (karena konsisten)Diperlukan (at-least-once delivery)
Operational ComplexityRendah, tetapi risiko tinggiSedang, dengan relay dan cleanup

3 Keputusan Desain Kritis

Tiga keputusan desain kritis ini membentuk fondasi implementasi transactional outbox yang robust. Keputusan pertama menetapkan boundary transaksi yang atomik untuk write bisnis dan outbox. Keputusan kedua memilih mekanisme relay yang reliable dengan retry logic. Keputusan ketiga memastikan consumer dapat menangani duplicate delivery dengan aman melalui idempotency check. Ketiga keputusan ini saling bergantung dan harus diimplementasikan bersama untuk mencapai eventual consistency yang diinginkan.

Trade-off Arsitektur: Outbox Pattern

Implementasi Transactional Outbox membawa trade-off yang perlu dipertimbangkan. Di sisi keuntungan, pola ini menghilangkan silent event loss yang sering terjadi pada dual-write naive dan menjamin at-least-once delivery melalui mekanisme retry. Pola ini juga mendekopling service pemesanan dari implementasi broker tertentu. Namun, ada kerugian yang signifikan: latency tambahan karena event tidak langsung sampai ke broker tetapi perlu menunggu polling interval. Selain itu, ada operational overhead berupa monitoring oldest-event age dan pending count, serta kompleksitas tambahan untuk relay process, cleanup job, dan idempotency tracking.

Before vs After: Transformasi Arsitektur

Transformasi dari dual-write naive ke transactional outbox mengubah arsitektur secara fundamental. Sebelum menerapkan pola ini, service menulis ke database dan broker secara berurutan tanpa jaminan atomisitas. Jika broker gagal, order tetap tersimpan tetapi event hilang, menciptakan inconsistent state yang sulit dideteksi. Setelah menerapkan pola ini, kedua write dilakukan dalam satu transaksi database, sehingga baik order maupun event persisten bersama. Broker failure hanya menunda delivery, bukan menghapus event, karena relay akan terus retry hingga sukses.

Test 1: Happy Path - Atomic Write + Relay Dispatch

Test ini membuktikan happy path lengkap dari transactional outbox. Pertama, service membuat order dengan ID o-1 secara atomik bersama outbox message. Setelah transaksi commit, relay yang berjalan dengan interval 10ms akan polling dan menemukan message PENDING. Relay kemudian publish ke broker dan menandai message sebagai PROCESSED. Consumer menerima pesan dan memprosesnya. Test ini mengassert bahwa broker menerima tepat satu pesan dengan EventType OrderCreated, dan status outbox message berubah menjadi PROCESSED. Semua assertion lolos, membuktikan alur端到端 berfungsi dengan benar.

func TestTransactionalOutbox_HappyPath(t *testing.T) {
    db := outbox.NewDB()
    broker := outbox.NewMockBroker()
    relay := outbox.NewRelay(db, broker, 10*time.Millisecond)
    service := outbox.NewOrderService(db)
    consumer := outbox.NewConsumer()
    relay.Start()
    err := service.CreateOrderWithOutbox("o-1", "c-1", 100.50)
    assert.NoError(t, err)
    time.Sleep(50 * time.Millisecond)
    published := broker.GetPublished()
    assert.Len(t, published, 1)
    assert.Equal(t, "OrderCreated", published[0].EventType)
    msg, _ := db.GetOutbox("evt-o-1")
    assert.Equal(t, outbox.MessageStatusProcessed, msg.Status)
}

Test 2: Rollback - Nothing Persists

Test rollback membuktikan bahwa staged mutation dibuang sepenuhnya ketika transaksi di-rollback. Method SaveOrder dan SaveOutbox hanya menaruh data di map stagedOrders dan stagedOutbox, belum menulis ke database utama. Ketika Rollback dipanggil, kedua map staged tersebut dibuang tanpa pernah menyentuh database. Test mengassert bahwa order dan outbox message tidak dapat diambil dari database setelah rollback. Selain itu, setelah menunggu relay poll, broker tidak menerima pesan apa pun, membuktikan bahwa rollback mencegah event dispatch sama sekali.

func TestTransactionalOutbox_Rollback(t *testing.T) {
    db := outbox.NewDB()
    tx := db.BeginTx()
    tx.SaveOrder(outbox.Order{ID: "o-2", Amount: 50})
    tx.SaveOutbox(outbox.OutboxMessage{ID: "evt-o-2", Status: outbox.MessageStatusPending})
    tx.Rollback()
    _, ok := db.GetOrder("o-2")
    assert.False(t, ok, "order should not exist")
    _, ok = db.GetOutbox("evt-o-2")
    assert.False(t, ok, "outbox should not exist")
    time.Sleep(30 * time.Millisecond)
    assert.Len(t, broker.GetPublished(), 0, "no messages to broker")
}

Test 3: Idempotency - Duplicate Delivery Rejected

Test idempotensi membuktikan bahwa consumer dapat dengan aman menangani duplicate delivery. Pertama, Handle dipanggil dengan pesan unik dan mengembalikan true (accepted). Kedua, Handle dipanggil lagi dengan pesan yang sama dan mengembalikan false (rejected). Test mengassert bahwa received count tetap 1, membuktikan bahwa duplicate tidak menambah state konsumen. Skenario ini mensimulasikan kasus di mana relay crash setelah publish tetapi sebelum menandai message sebagai PROCESSED, menyebabkan pesan yang sama dipublish ulang oleh relay pada siklus berikutnya.

func TestTransactionalOutbox_Idempotency_DuplicateDelivery(t *testing.T) {
    consumer := outbox.NewConsumer()
    msg := outbox.OutboxMessage{ID: "evt-duplicate", EventType: "OrderCreated", Payload: "data"}
    p1 := consumer.Handle(msg)
    assert.True(t, p1, "first delivery should be accepted")
    p2 := consumer.Handle(msg)
    assert.False(t, p2, "duplicate delivery should be rejected")
    assert.Equal(t, 1, consumer.GetReceivedCount(), "count stays 1")
}

Test 4: Relay Retry - Broker Failure Tolerated

Test relay retry membuktikan mekanisme ketahanan terhadap kegagalan broker. Pertama, broker diatur untuk gagal pada publish berikutnya melalui SetFailNext(true). Service membuat order dengan outbox, kemudian relay dimulai. Pada poll pertama, publish gagal karena broker dalam mode fail, sehingga message tetap berstatus PENDING. Pada poll berikutnya (setelah interval ticker), broker kembali normal, publish sukses, dan message ditandai PROCESSED. Test ini mengassert bahwa setelah retry, broker menerima pesan dan status outbox berubah menjadi PROCESSED.

func TestTransactionalOutbox_RelayRetryAfterBrokerFailure(t *testing.T) {
    db := outbox.NewDB()
    broker := outbox.NewMockBroker()
    relay := outbox.NewRelay(db, broker, 10*time.Millisecond)
    service := outbox.NewOrderService(db)
    broker.SetFailNext(true)  // first publish fails
    service.CreateOrderWithOutbox("o-retry", "c-retry", 55.0)
    relay.Start()
    time.Sleep(25 * time.Millisecond)  // first poll fails
    msg, _ := db.GetOutbox("evt-o-retry")
    assert.Equal(t, outbox.MessageStatusPending, msg.Status)
    time.Sleep(50 * time.Millisecond)  // second poll succeeds
    published := broker.GetPublished()
    assert.Len(t, published, 1)
    msg, _ = db.GetOutbox("evt-o-retry")
    assert.Equal(t, outbox.MessageStatusProcessed, msg.Status)
}

Test 5: Purge Processed - Memory Leak Prevention

Test purge processed membuktikan mekanisme pembersihan tabel outbox untuk mencegah memory leak. Database awalnya berisi dua message: m1 dengan status PENDING dan m2 dengan status PROCESSED. Method PurgeProcessedOutbox akan menghapus semua record dengan status PROCESSED dan mengembalikan jumlah record yang dihapus. Test mengassert bahwa purged count = 1, message PENDING masih ada, dan message PROCESSED sudah dihapus. Tanpa cleanup mechanism seperti ini, tabel outbox akan tumbuh tak terbatas karena record PROCESSED tidak pernah dihapus.

func TestTransactionalOutbox_PurgeProcessed(t *testing.T) {
    db := outbox.NewDB()
    tx := db.BeginTx()
    tx.SaveOutbox(outbox.OutboxMessage{ID: "m1", Status: outbox.MessageStatusPending})
    tx.SaveOutbox(outbox.OutboxMessage{ID: "m2", Status: outbox.MessageStatusProcessed})
    tx.Commit()
    purged := db.PurgeProcessedOutbox()
    assert.Equal(t, 1, purged)
    _, ok := db.GetOutbox("m1")
    assert.True(t, ok, "pending should remain")
    _, ok = db.GetOutbox("m2")
    assert.False(t, ok, "processed should be purged")
}

Checklist Implementasi Outbox Pattern

Checklist implementasi ini mencakup langkah-langkah esensial untuk menerapkan transactional outbox pattern di production. Pertama, buat tabel outbox_events dengan skema yang memadai termasuk kolom agregat untuk partitioning Kafka. Kedua, pastikan setiap business transaction menyertakan INSERT ke outbox_events. Ketiga, implementasikan polling relay dengan interval yang seimbang antara latensi dan beban database. Keempat, relay hanya menandai message sebagai PROCESSED setelah broker memberikan ACK. Kelima, consumer harus memiliki idempotency check berbasis event ID. Keenam, tambahkan scheduled job untuk purge processed records guna mencegah table bloat.

Anti-Pattern: Apa yang Harus Dihindari

Anti-pattern dalam implementasi outbox pattern dapat merusak seluruh jaminan konsistensi yang dimaksudkan. Menulis ke broker sebelum commit database mengembalikan ke keadaan dual-write naive. Menggunakan ID event yang tidak unik menyebabkan deduplication gagal. Consumer tanpa idempotency check akan memproses duplicate message secara ganda. Tidak ada purge untuk processed records akan menyebabkan tabel outbox tumbuh tak terbatas. Relly dengan polling interval terlalu lama akan meningkatkan latency delivery secara signifikan.

Prinsip Arsitektural Jangka Panjang

Prinsip arsitektural jangka panjang ini melampaui implementasi spesifik transactional outbox. Pertama, eventual consistency seringkali lebih praktis daripada strong consistency yang memerlukan koordinasi terdistribusi mahal. Kedua, memisahkan boundary write dari boundary delivery memungkinkan masing-masing bagian dioptimalkan secara independen. Ketiga, at-least-once delivery lebih aman daripada at-most-once karena mencegah kehilangan data. Keempat, idempotency bukan fitur optional melainkan keharusan karena retry adalah hal yang wajar. Kelima, observable metrics seperti oldest-event age dan pending count harus diimplementasikan untuk deteksi dini degradasi.
