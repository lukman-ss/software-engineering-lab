# Core Concepts of Backward Compatibility

## 1. Definition of Backward Compatibility
Backward compatibility means that a newer component (system, API, library, or database) can accept inputs and execute workloads formatted according to older specifications without failing or corrupting data.
- **Consumer Perspective**: Existing clients can continue interacting with the system using old contracts without making code modifications.
- **Provider Perspective**: The system continues to interpret, parse, and process older request formats, schemas, and communication protocols.

## 2. Backward vs. Forward Compatibility
- **Backward Compatibility (Looking Back)**: A new system accepts input produced by an old system.
  - *Example*: An API v2 endpoint still accepts payloads that only supply v1 fields.
- **Forward Compatibility (Looking Forward)**: An old system gracefully accepts input generated by a newer system without crashing or malfunctioning.
  - *Example*: An older client ignores newly added JSON fields (Postel's Law / Robustness Principle: "Be conservative in what you send, be liberal in what you accept").

## 3. Breaking vs. Non-Breaking Changes

### Breaking Changes (Incompatible)
- Removing or renaming fields/columns/endpoints.
- Changing field data types (e.g., string to array, integer to UUID).
- Adding mandatory/required parameters to existing interfaces.
- Changing validation rules to be more restrictive (e.g., max string length reduced from 100 to 50).
- Altering semantic meanings (e.g., changing `status` code 1 from "Pending" to "Rejected").

### Non-Breaking Changes (Compatible)
- Adding optional fields with safe defaults.
- Adding new endpoints alongside old ones.
- Relaxing validation rules (e.g., allowing previously disallowed characters).
- Adding new enum values (if consumers are forward-compatible and use fallback handlers).

## 4. Contexts in Modern Distributed Systems
- **Database Schema**: Modifying tables and columns while running instances of application versions N and N+1 concurrently.
- **API Payloads**: Evolving JSON/gRPC contracts without breaking Web, Mobile (which update slowly or never), or third-party consumers.
- **Message Brokers / Event Schemas**: Evolving event streams (Kafka/RabbitMQ) where old worker instances consume new events or new workers consume old events in the log.
- **In-Memory Cache**: Upgrading cached serialization structures without causing deserialization errors on previous service versions.
