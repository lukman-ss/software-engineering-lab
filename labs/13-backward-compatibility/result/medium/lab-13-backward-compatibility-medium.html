Backward Compatibility: Ubah Sistem, Jaga Consumer Lama

Migrasi phone menjadi phones lewat Expand–Migrate–Contract, dual-write, backfill, dan batas rollback.

Lukman / lukman-ss · Software Engineering Lab 13

Sistem lama menyimpan satu nomor telepon pada users.phone. Kebutuhan baru meminta banyak nomor per user. Mengganti field phone dari string menjadi array terlihat sederhana, tetapi consumer lama masih mengharapkan string. Migrasi data dan perubahan API perlu memberi ruang bagi versi lama serta versi baru untuk hidup bersamaan.

Lab 13 memakai pola Expand → Migrate → Contract. Tambahkan representasi baru, pindahkan pemakaian dan data secara bertahap, lalu pensiunkan bentuk lama. Mental model-nya: Compatibility must survive the transition, not just the final state. Kondisi di tengah migrasi sama pentingnya dengan desain akhir.

Expand: tambahkan bentuk baru tanpa mengganti tipe lama

Representasi baru adalah daftar PhoneEntry yang menyimpan number dan is_primary. UserResponse memperkaya payload dengan phones, sambil mempertahankan phone sebagai string. LegacyConsumerDTO membaca string tersebut; ModernConsumerDTO membaca array baru.

// model.go: response aditif
type UserResponse struct {
    ID     int          `json:"id"`
    Name   string       `json:"name"`
    Phone  string       `json:"phone,omitempty"`
    Phones []PhoneEntry `json:"phones"`
}

TestSerializationBackwardCompatibility membuat user lewat dual-write, melakukan marshal, lalu decode payload yang sama dengan dua DTO. Test memeriksa nilai nomor legacy, dua entry modern, dan primary phone. Yang terbukti oleh assertion itu adalah kontrak dua consumer Go pada fixture tersebut; bukan jaminan semua SDK atau strict decoder menerima field tambahan.

Perhatikan bentuk kosong: phone memakai omitempty sehingga string kosong dapat hilang dari enriched payload. Response CreateUser pada mode legacy tidak mengisi slice Phones, sehingga serialisasi phones bisa berupa null. Sebaliknya, GetPhones membuat slice kosong sehingga hasil read tanpa entry dapat berupa []. Bentuk kosong juga bagian kontrak yang perlu diperiksa.

Pisahkan versi API dari pilihan storage

GetUserV1 memanggil GetLegacyUser dan mengirim LegacyConsumerDTO; GetUserV2 mengirim ModernConsumerDTO. Payload enriched yang dipakai test serialisasi bukan response identik dari kedua handler. Endpoint V1 hanya memiliki field DTO lama, sementara V2 hanya memiliki array DTO modern.

WriteMode dan ReadMode mengendalikan jalur storage secara terpisah. Nama ReadLegacyOnly tidak berarti enriched response menyembunyikan phones: GetUser tetap memuat daftar modern sebelum memilih sumber untuk nilai scalar phone. GetModernUser mengambil daftar tersebut dari response.

ModePerilaku
WriteLegacyOnlyMenyimpan scalar legacy; extraPhones tidak diproses.
WriteDualMenyimpan scalar dan entry primary modern; nomor tambahan masuk modern.
WriteNewOnlyMenyimpan daftar modern; User.Phone nil.
ReadLegacyOnlyNilai scalar phone berasal dari legacy.
ReadFallbackMemilih primary/entry pertama modern; jika kosong, memakai legacy.
ReadNewOnlyNilai scalar diturunkan dari entry modern.

Dual-write menjaga data yang masih dibutuhkan versi lama

CreateDual menulis user dan primary phone modern di bawah satu mutex MemoryStore. Pada fase ini, pembaca lama masih dapat melihat nomor utama untuk record yang dibuat oleh versi baru. Nomor tambahan hanya direpresentasikan di daftar modern: kompatibilitas tidak berarti versi lama tiba-tiba mendukung semua kemampuan baru.

Ada batas atomicity. CreateUser menambahkan extraPhones lewat pemanggilan SavePhoneEntry terpisah, sesudah CreateDual selesai, dan mengabaikan error dari pemanggilan tambahan itu. Jadi seluruh operasi multi-phone bukan satu transaksi database. Implementasi ini memakai map dalam memori; schema.sql adalah contoh evolusi schema, bukan migrasi yang dieksekusi oleh store.

Backfill memindahkan data historis dalam batch

Dual-write hanya menangani create yang lewat mode tersebut. User historis masih membutuhkan backfill. Worker membaca ID sesudah LastProcessedID, memproses batch, dan menambahkan nomor legacy jika nilainya tidak kosong serta daftar modern belum memiliki entry. Ia melewati daftar yang sudah terisi; backfill bukan mekanisme overwrite atau perbaikan semua drift.

// store.go: deduplikasi dalam SavePhoneEntry
for _, p := range s.userPhones[userID] {
    if p.Number == number {
        return p, nil
    }
}

Deduplikasi tersebut berlaku untuk pasangan user dan nomor. Ia tidak mengubah IsPrimary entry yang sudah ada. Worker menyimpan LastProcessedID, TotalMigrated, dan IsComplete dalam objek memori. Test menjalankan batch 3 + 3 lalu sisa 4 dari sepuluh user, kemudian mengharapkan nol pada pengulangan worker yang sudah selesai.

Resumable di sini berarti melanjutkan objek worker yang sama. Tidak ada checkpoint persisten atau pemulihan sesudah restart proses. Setelah IsComplete=true, worker itu langsung mengembalikan selesai; record legacy yang baru muncul sesudahnya tidak otomatis dipindai ulang. Karena itu, penyelesaian satu worker tidak membuktikan semua writer sudah berpindah.

Fallback read memiliki efek samping dan batas response

ReadFallback memilih nomor modern bila tersedia. Jika daftar modern kosong tetapi legacy ada, GetUser mengembalikan scalar legacy dan melakukan lazy backfill. Ini membantu jalur scalar selama migrasi, tetapi ada detail implementasi: variabel phones sudah dibaca sebelum lazy write dan tidak di-refresh sesudahnya.

Akibatnya, read pertama dapat mengembalikan phone yang benar tetapi phones masih kosong, walaupun store telah berisi satu entry setelah method selesai. GetModernUser pada kondisi itu juga dapat menerima array kosong pada request pertama. TestFallbackRead memeriksa scalar response dan isi store setelah read; ia tidak meng-assert array response pertama. Jangan menyebut fallback ini menjamin data modern langsung lengkap pada read yang sama.

Reconcile untuk mendeteksi, bukan otomatis memperbaiki

ReconcileData membandingkan legacy phone dengan primary number modern. Nomor modern yang tidak ada atau primary yang berbeda dihitung sebagai drift. Pemeriksaan melewati user dengan Phone=nil dan langsung berhenti setelah contract diterapkan. Ia tidak memperbaiki mismatch atau membuktikan bahwa seluruh data modern valid.

Return drifts adalah jumlah temuan pada pemanggilan itu. Counter DriftDetected bersifat kumulatif: scan ulang mismatch yang sama menambah counter lagi. Nilai nol pada return scan terbaru dan nilai nonzero pada counter historis tidak harus bertentangan. Tidak ada audit berkala otomatis yang dipicu oleh timer; demo dan test memanggil reconciliation secara eksplisit.

Rollback aman selama representasi lama tetap terisi

TestRollbackScenarios menunjukkan dua kondisi. Record yang dibuat saat WriteDual masih terbaca ketika mode dikembalikan ke legacy. Namun, record yang dibuat saat WriteNewOnly memiliki Phone=nil. Setelah mode baca kembali ke legacy, nomor yang dibaca menjadi string kosong tanpa read error.

Data modern belum tentu hilang; yang hilang adalah visibilitas nomor bagi pembaca lama. Mengembalikan binary atau mode aplikasi saja tidak mengisi representasi legacy yang sudah berhenti ditulis. Sebelum contract, rollback juga memiliki batas berdasarkan write history, bukan sekadar keberadaan kolom lama.

Contract adalah keputusan yang memerlukan bukti

// service.go: guard awal ApplyContract
if !force && s.obs.LegacyReadHits.Load() > 0 {
    return fmt.Errorf("%w: recorded %d legacy reads",
        ErrContractViolation, s.obs.LegacyReadHits.Load())
}

LegacyReadHits adalah counter kumulatif, bukan rate atau jendela observasi. Tidak ada mekanisme reset/window yang dikelola guard. GetLegacyUser menambah counter sebelum memeriksa error, sehingga request gagal juga tercatat. Demo memakai ApplyContract(true), yang melewati guard; itu bukan bukti bahwa traffic legacy benar-benar nol selama periode tertentu.

Guard tidak memeriksa checkpoint backfill, drift, atau writer lama. Bahkan tanpa force, counter nol dapat meloloskan contract meskipun data historis belum dimigrasi. ApplyContract mengganti read/write ke NewOnly, menandai contract, lalu mengosongkan Phone pada store. Tahapan itu tidak menjadi satu transisi atomik di seluruh service.

Setelah contract, GetLegacyUser mengembalikan error dan handler V1 menjawab 410 Gone. Namun UserResponse masih memiliki field Phone: ReadNewOnly dapat mengisinya dari nomor modern. Contract pada kode ini menonaktifkan jalur V1 dan storage legacy, bukan menghapus definisi field enriched dari source.

Schema contoh dan header bukan bukti operasi production

schema.sql mempertahankan users.phone TEXT NOT NULL pada tahap expand, sementara CreateModern dalam memori membuat Phone=nil. SQL itu belum memodelkan seluruh urutan write-new-only sebelum drop dengan constraint database yang nyata. Tidak ada eksekusi DDL, pengukuran lock, atau pembuktian zero downtime dalam test MemoryStore.

Handler V1 menambahkan Deprecation dan Sunset berupa nilai hardcoded. Test memeriksa Deprecation bernilai "true" dan Sunset tidak kosong; ia tidak memvalidasi format standar maupun menjalankan penutupan berdasarkan tanggal. Perubahan ke 410 dikendalikan ApplyContract, bukan scheduler sunset. Karena itu, materi ini tidak mengklaim kepatuhan header pada RFC tertentu.

Bukti test harus dibaca sesuai cakupannya

Test mencakup decode dua DTO, batch backfill, fallback, drift sebelum/sesudah backfill, handler 200/410, lifecycle, dan dua skenario rollback. Concurrency test menjalankan writer, reader, backfill, dan reconciliation, tetapi mengabaikan banyak error dan hanya meng-assert counter DualWriteErrors di akhir. Ia tidak membuktikan konsistensi semua record atau keamanan contract concurrent.
