Feature Flags: Deploy Kode, Kendalikan Release

Rollout online booking secara bertahap dengan deterministic bucketing, metrik, fallback, dan kill switch.

Lukman / lukman-ss · Software Engineering Lab 12

Fitur online booking sudah selesai dan kodenya siap masuk production. Apakah semua pelanggan bengkel harus langsung memakai flow baru? Lab 12 memisahkan dua keputusan itu: deploy menempatkan kode, sedangkan release menentukan siapa yang mulai menggunakan perilaku baru.

Deploy does not have to mean release. Feature flag online_booking menjadi batas pemilihan flow. Engineer dapat memulai dari OFF, membuka akses internal, menaikkan rollout, lalu mematikannya ketika hasil memburuk. Flag mengendalikan eksposur; ia tidak membuktikan bahwa fitur baru sudah benar.

Satu keputusan di batas business flow

Implementasi Go memakai FeatureService untuk menyimpan dan mengevaluasi konfigurasi. BookingService memanggilnya sekali di CreateBooking, lalu memilih newBookingFlow atau legacyBookingFlow. Keputusan targeting tidak disebar ke setiap bagian business logic.

// booking_service.go: CreateBooking
func (s *BookingService) CreateBooking(req BookingRequest) BookingResponse {
    if s.featureService.IsEnabled("online_booking", req.UserID) {
        return s.newBookingFlow(req)
    }
    return s.legacyBookingFlow(req)
}

Kedua flow masih berupa simulasi response. Tidak ada penyimpanan booking, reservasi mekanik, atau pemanggilan vendor sungguhan. Flow baru mengembalikan Success=true, kecuali simulateFail diaktifkan. Legacy selalu mengembalikan Success=true. Pesan "Vendor Error (Simulated)" adalah kegagalan buatan, bukan hasil integrasi eksternal.

Urutan evaluasi menentukan perilaku

UrutanKeputusan
1Flag tidak ditemukan: OFF.
2Enabled=false: OFF untuk semua user.
3UserID ada dalam InternalUsers: ON.
4Persentase <= 0: OFF untuk user biasa; >= 100: ON.
5Untuk 1–99, bandingkan bucket dengan persentase rollout.

Global OFF diperiksa sebelum daftar internal, sehingga kill switch juga mematikan akses internal. Sebaliknya, ketika Enabled=true dan persentase nol, anggota InternalUsers tetap mendapat flow baru. Inilah konfigurasi internal rollout: bukan ON untuk semua orang, tetapi ON bagi daftar ID yang eksplisit.

Struct User memiliki IsInternal, tetapi evaluator tidak membaca field itu. Penentuan internal memakai kecocokan UserID terhadap InternalUsers. Komentar persentase menyebut rentang 0–100, namun tidak ada validasi yang menolak nilai di luar rentang: evaluator memperlakukan nilai negatif seperti nol dan nilai di atas seratus seperti seratus.

Bucket konsisten untuk user dan feature yang sama

Random per request dapat membuat user berganti flow di request berikutnya. Implementasi ini membentuk input hash dari userID, tanda titik dua, dan featureKey. Ia menghitung SHA-256, membaca delapan byte pertama sebagai uint64 big-endian, lalu mengambil modulo 100.

// feature_service.go: cuplikan deterministic bucketing
hashInput := fmt.Sprintf("%s:%s", userID, featureKey)
hash := sha256.Sum256([]byte(hashInput))
bucketVal := binary.BigEndian.Uint64(hash[:8])
bucket := int(bucketVal % 100)
return bucket < flag.RolloutPercentage

Pada 10%, bucket 0–9 mendapat fitur. Pada 50%, bucket 0–49 mendapat fitur. Selama input hash, algoritma, dan aturan targeting tetap sama, cohort 10% tetap termasuk ketika threshold dinaikkan ke 50%. Stabil berarti evaluasi berulang pada konfigurasi yang sama konsisten; bukan berarti hasil tidak boleh berubah setelah konfigurasi diubah.

Sebagai contoh hasil perhitungan ulang, user-3 berada di bucket 25 untuk online_booking: OFF pada 10%, ON pada 50%. user-4 berada di bucket 83: masih OFF pada 50%, lalu ON pada 100%. Angka ini dihitung ulang dari formula sumber, bukan output eksekusi Go.

Rollout 10% bukan janji tepat sepuluh request

CLI membangun 100 user: internal-1 sampai internal-3, lalu user-3 sampai user-99. Setiap fase melakukan satu request per user secara berurutan. Tiga user internal di-allowlist pada fase internal, 10%, 50%, dan 100%. Mereka dapat mengakses fitur tanpa perlu lolos threshold bucket.

Pada fase 50%, ada 45 user biasa ditambah tiga internal. Sampel terbatas dan pengecualian internal menjelaskan mengapa angka aktual fixture berbeda dari label persentasenya.

Persentase pengguna juga tidak otomatis sama dengan persentase traffic: user dapat membuat jumlah request berbeda. Demo menyamakan keduanya dengan satu request per user per fase. Karena itu, klaim blast radius "hanya 10%" perlu dipahami sebagai sasaran eksposur cohort, bukan batas pasti semua dampak sistem.

Naikkan rollout berdasarkan bukti, bukan jadwal CLI

README menyarankan proses bertahap dengan observasi pada 10%, 50%, lalu 100%. CLI memang menampilkan fase tersebut, tetapi transisinya hardcoded. Tidak ada pengecekan threshold metrik yang memutuskan apakah rollout boleh naik, dan tidak ada jeda observasi production. Demo mengilustrasikan urutan, bukan controller rollout otomatis.

Metrik dicatat oleh runner

Runner phase mengukur durasi CreateBooking, lalu memanggil IncrementTotal, RecordFlow, RecordBooking, dan RecordResponseTime. BookingService menerima pointer Metrics tetapi tidak memperbarui counter di CreateBooking. Jika method tersebut dipanggil langsung, metrik tidak otomatis tercatat seperti pada CLI.

// metrics.go: formula ErrorRate pada Snapshot
ErrorRate: float64(m.BookingFailed) /
    float64(max(1, m.TotalRequests)) * 100,

ErrorRate memakai denominator seluruh request. Ketika hanya sebagian user memakai flow baru, error rate agregat dapat terlihat kecil walaupun kegagalan di cohort baru tinggi. Counter yang tersedia memisahkan jumlah request per flow, tetapi outcome sukses/gagal digabung. Breakdown error per flow merupakan usulan pengembangan, bukan metrik yang sudah tersedia.

Metrics di-reset setiap fase. AvgResponseTime adalah mean sampel fase, bukan p95 atau p99. Durasi mengukur method simulasi lokal, tanpa database atau network. Angka latency demo tidak dapat dipakai sebagai benchmark online booking production.

Kill switch mengubah keputusan berikutnya

Setelah 100% rollout, CLI mengaktifkan simulateFail=true. Semua request fase 6a masuk flow baru dan gagal. Berikutnya, SetFlag mengganti konfigurasi menjadi Enabled=false; request fase 6b masuk legacy dan sukses meskipun simulateFail masih aktif. Ini memperlihatkan bahwa gate menghindari jalur baru pada pemanggilan berikutnya.

// cmd/simulate/main.go: konfigurasi kill switch
service.SetFlag(featureflags.Flag{
    Key: "online_booking",
    Enabled: false,
})

Request yang sudah mendapat response gagal tidak diulang otomatis ke legacy. Evaluasi yang sudah membaca konfigurasi lama juga tidak dibatalkan oleh perubahan flag. Kill switch tidak mengembalikan side effect yang sudah terjadi dan tidak menghapus kode baru. Pada lab, ia hanya mengganti pilihan jalur untuk evaluasi yang membaca konfigurasi OFF.

Runtime update memiliki batas operasional

FeatureService memakai map lokal dan RWMutex. SetFlag mengganti satu nilai Flag secara utuh; ia bukan patch field. Jika pemanggil hanya mengisi Key dan Enabled, persentase kembali nol dan InternalUsers kosong. Saat ingin mempertahankan targeting, kirim konfigurasi lengkap seperti yang dilakukan fase rollout CLI.

Tidak ada penyimpanan konfigurasi persisten, sinkronisasi antar-replica, dashboard operator, atau endpoint administrasi. "Tanpa redeploy" di sini berarti objek dalam proses yang sama dapat diubah saat runtime. Keamanan seluruh aplikasi juga belum dibuktikan oleh mutex tersebut: simulateFail berupa bool tanpa sinkronisasi, sehingga demo tidak menunjukkan toggle failure bersamaan dengan request concurrent yang aman.

Flag memilih behavior, authorization memilih izin

README membedakan pertanyaan "bolehkah user membuat booking?" dari "flow booking mana yang aktif untuk user ini?" Implementasi hanya menjawab pertanyaan kedua. Tidak ada authorize(user, "booking:create") yang dijalankan. Targeting internal tidak boleh dipresentasikan sebagai pemeriksaan hak akses.

Uji jalur yang bertambah, lalu bersihkan flag

Test mencakup global OFF, nol persen, targeting internal, contoh ON/OFF pada 10%, evaluasi berulang, kenaikan rollout, kill switch, unknown flag, serta response booking ON/OFF dan skenario gagal lalu OFF. Test persentase mencari contoh user yang ON dan OFF; ia tidak membuktikan distribusi tepat 10%. Tidak ada assertion metrik maupun pengujian konkurensi dalam file test tersebut.

# Dari root repository
make lab-12-demo
make lab-12-test

# Atau masuk ke modul lab
cd labs/12-feature-flags
go run ./cmd/simulate
go test -v -count=1 ./...

Lab memiliki go.mod sendiri yang menyatakan Go 1.26.7. Gunakan direktori modul lab seperti target Makefile; contoh go run berpath lab dari root README perlu memperhatikan batas nested module. Go tidak tersedia di lingkungan penyusunan, sehingga test dan demo dibaca, bukan dijalankan.

Setelah rollout 100% dan stabil berdasarkan bukti yang relevan, README mengarahkan cleanup: hapus flag lalu legacy code yang tidak lagi diperlukan. Cleanup ini masih berupa lifecycle yang diajarkan, belum perubahan kode pada lab. Menyisakan flag selamanya berarti menyisakan jalur dan konfigurasi yang harus terus dipahami serta diuji.

Feature flag memberi kendali kapan dan kepada siapa sebuah perilaku dirilis. Nilainya muncul ketika targeting konsisten, keputusan rollout memakai bukti, fallback benar-benar diuji, dan kesimpulan tentang mitigasi tetap sesuai batas implementasi.
