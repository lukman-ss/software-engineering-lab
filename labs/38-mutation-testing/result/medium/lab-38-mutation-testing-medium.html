Ilusi Keamanan Code Coverage

Code coverage tradisional sering disalahartikan sebagai tolok ukur kualitas pengujian. Metrik ini hanya menjawab pertanyaan apakah sebuah pernyataan dalam sumber pernah dieksekusi selama suite tes berjalan. Pernyataan tersebut bisa saja dieksekusi berkali-kali tanpa pernah memiliki asersi yang memverifikasi nilai keluaran, batasan logika, atau branch kondisional. Akibatnya, tim dapat merasa aman melihat CI berwarna hijau dengan cakupan 100%, padahal tidak ada pengujian yang sanggup mendeteksi kesalahan operator maupun pergeseran nilai batas.

Pada Lab 38, discount_weak_test.go mencapai 100% statement coverage pada discount.go, namun mutation score-nya 0.00%: 0 dari 15 mutant terdeteksi. Test suite lemah menutupi seluruh baris tanpa menangkap fault injection.

Code coverage mengukur eksekusi, bukan verifikasi. Zero killed mutants reveals the gap.

Mengapa Review Manual dan Assertion Naif Gagal

Pemeriksaan manual atau penulisan assertion seadanya tidak cukup karena batas kognitif engineer. Manusia memikirkan skenario paling umum; kondisi pinggir jarang terdeteksi tanpa eksplorasi sistematis. Pada modul diskon ini, logika bercabang meliputi tier VIP, premium, dan standard dengan ambang jumlah item serta kupon.

Bias Konfirmasi

Developer cenderung menulis contoh input yang mendukung implementasi. Edge case acak seperti float precision, batas negatif, atau nol sering terlupa.

Kekurangan Assertion

Assert boolean freeShipping jarang diperiksa. Assert exact discount rate hilang; hanya positivitas yang divalidasi.

Skala Logika

Satu fungsi CalculateDiscount mengandung 8 operator relasional dan 4 boolean. Kombinasi threshold 1000, 500, 100, 200 serta ItemCount > 2 menciptakan lintasan kompleks.

Mutation Testing vs Code Coverage: Model Mental

Model mental mutation testing memisahkan konsep eksekusi dari verifikasi. Code coverageibarat laporan roti yang diolesi selai: yang diukur hanya luas permukaan yang tertutup. Mutation testing menambahkan lapisan skeptisisme dengan menanyakan kandungan selai itu. Jika logika bisnis diubah sedikit—misalnya tanda pembanding atau operator aritmetika—dan test suite masih lolos, maka selai tersebut bukan yang seharusnya.

Analogi Roti dan Selai

Coverage melaporkan berapa persen roti terlapisi selai. Mutation memeriksa apakah selai itu benar cokelat atau zat lain. Roti tertutup penuh bisa jadi selainya salah total.

Rumus Skor

Mutation Score = (Killed / Total) × 100%. Killed adalah mutant terdeteksi oleh test suite yang gagal. Survived adalah mutant lolos karena assertion lemah atau input tidak relevan.

Hipotesis Fundamental

Competent Programmer Hypothesis: bug biasanya operator/tanda kecil. Coupling Effect: fault sederhana bertingkat menjadi kegagalan kompleks.

Pipeline Mesin Mutation Testing

Pipeline ini dibangun murni menggunakan pustaka standar Go tanpa dependensi eksternal. Proses dimulai dengan pemindaian AST untuk mengenali node ekspresi biner dan literal konstanta. Setiap node yang terdeteksi dikemas menjadi rencana mutasi yang menyertakan fungsi transformasi serta fungsi undo.

Langkah Pipeline

Read discount.go → parser.ParseFile dengan go/ast. ast.Inspect collect BinaryExpr dan BasicLit nodes. Build MutationPlan dengan Apply closure dan undo revert.

Eksekusi Paralel

Runner.Run meluncurkan goroutine per rencana mutasi. Tiap goroutine membuat fresh token.FileSet untuk isolasi total. Hasil ditulis ke slice berbasis indeks tanpa mutex.

Output Laporan

Report aggregating Killed, Survived, Equivalent counts. Skor dihitung akhir dengan formula persentase. Breakdown per mutant menampilkan line, operator, dan status.

// internal/engine/mutator.go: build MutationPlan per BinaryExpr node
plans := []MutationPlan{}
switch expr.Op {
case token.GEQ:
    plans = append(plans, MutationPlan{
        Apply: func(f *ast.File) func() {
            expr.Op = token.GTR
            return func() { expr.Op = token.GEQ }
        },
    })
}

AST Mutation pada Relational & Boolean Node

Generator mutasi menelusuri AST menggunakan ast.Inspect. Saat menemui ekspresi biner, ia memeriksa token operator dan menghasilkan rencana yang membalikkan relasional, boolean, atau aritmetika. Closure Apply melakukan modifikasi langsung pada node AST, sementara fungsi undo yang dikembalikan memulihkan state semula.

Relational Example

        Apply: func(f *ast.File) func() {
            expr.Op = token.GTR
            return func() { expr.Op = token.GEQ }
        },
    })

Boolean Flip

case token.OR: // ||

Failure Path: Operator >= Berubah Menjadi >

Kesalahan pergeseran threshold dari >= menjadi > tampak sepele, tetapi mengubah hasil diskon pelanggan dengan total belanja tepat 100.0. Test suite lemah hanya memeriksa apakah diskon tidak negatif; kondisi ini tetap terpenuhi karena rate berubah menjadi nol, bukan nilai negatif. Akibatnya, mutan bertahan dan pelanggan kehilangan potongan yang seharusnya mereka dapatkan.

Kode Asli

else if order.TotalAmount >= 100.0 {
    rate = 0.05
}

Mutan

else if order.TotalAmount > 100.0 {
    rate = 0.05
}

Input Kritis

TotalAmount = 100.0, Tier = STANDARD. Asli: rate = 0.05; Mutan: rate = 0.0. Weak test hanya cek res3.DiscountRate < 0 → tetap PASS.

Mekanisme Mutasi vs Gejala yang Dihasilkan

Setiap kategori mutasi menghasilkan gejala kegagalan yang spesifik. Operator relasional mengubah ambang batas kualifikasi tier dan diskon; boolean flip mengacaukan kondisi VIP dan kupon; aritmetika membalikkan kalkulasi potongan; pergeseran batas menggeser syarat minimum item. Test suite lemah consistently gagal karena semua gejala tersebut tetap menghasilkan nilai uang positif, sehingga asersi berbasis tanda tidak pernah memicu kegagalan.

Tiga Keputusan Kritis Saat Membangun Mutation Engine

Konstruksi mesin mutation testing membutuhkan tiga keputusan arsitektural mendasar. Isolasi AST mencegah goroutine saling menimpa node operator. Seleksi node terbatas pada ekspresi biner dan literal integer memastikan fokus pada fault yang relevan secara bisnis.

Keputusan 1: Isolasi

Pilih fresh token.NewFileSet() per goroutine. Hindari mutex dengan penulisan berbasis indeks slice. Gunakan closure undo untuk memulihkan AST setelah evaluasi.

Keputusan 2: Seleksi Node

Targetkan *ast.BinaryExpr untuk operator. Targetkan *ast.BasicLit bertipe token.INT untuk batas. Abaikan node string/float agar boundary shift fokus pada integer.

Keputusan 3: Kill Condition

TestFunc menerima sourc bytes mutan, bukan eksekusi binary. Strong test membandingkan string AST secara eksak != original. Weak test mensimulasikan heuristik assertion positif saja.

Yang Tidak Dibuktikan

Meskipun demonstrasi ini menunjukkan kontras yang tajam, ada batasan penting yang tidak diselesaikan. Skor mutasi 100% bukanlah standar industri baku; tiap organisasi menetapkan ambang berdasarkan risiko domain. Evaluasi strong test di sini mengandalkan pencocokan teks AST, bukan kompilasi subprocess nyata, sebagai kompromi performa.

  • Skor 100% bukan standar industri universal; target harus disesuaikan dengan profil risiko proyek.
  • Evaluasi AST textual menggunakan perbandingan string AST, bukan subprocess kompilasi—ini trade-off untuk demonstrasi; production tool compile subprocess.
  • Mutan semantik identik tidak dapat dibunuh secara teoretis; penanganan equivalent memerlukan heuristic atau scoped analysis.
  • StatementDelete TIDAK DIPAKAI: Enum dideklarasikan untuk klasifikasi lengkap, tapi tidak diemisi karena target AST tidak memiliki void side-effect-free statement.

Trade-off Arsitektur: Kecepatan vs Ketepatan Deteksi

Trade-off utama terletak pada cara menentukan kill condition. Evaluasi berbasis teks AST menawarkan kecepatan tinggi dengan overhead minimal, cocok untuk pipeline CI harian. Namun, pendekatan ini rentan terhadap false positive akibat perbedaan formatting.

AST Textual (Lab Ini)

Kecepatan: evaluasi sub-milidetik per mutan. Ketepatan: menangkap semua perubahan sintaks, tapi bukan semantic. Risiko: false positive jika formatter mengubah whitespace.

Subprocess Compile (Produksi)

Kecepatan: compilation overhead per mutant. Ketepatan: semantic + syntax; false positive rendah. Risiko: dependency coupling, environment lock.

Rekomendasi Hybrid

Lintasan cepat: textual AST filter untuk PR sehari-hari. Lintasan berat: subprocess compile untuk modul kritikal.

Goroutine -> Validate -> Write Result

Desain konkurensi mesin ini mengutamakan isolasi state AST. Setiap mutan dieksekusi dalam goroutine terpisah yang membuka file set baru dan mem-parsing ulang sumber asli. Hasil evaluasi ditulis langsung ke slice yang dialokasikan sebelumnya menggunakan indeks plan, menghilangkan kebutuhan mutex.

Flow Concurrency

Runner.launch loop for i, plan := range plans. Tiap goroutine: fset := token.NewFileSet() + parser.ParseFile. Apply mutasi, render source, jalankan testFn. Tulis results[idx] langsung tanpa mutex.

Isolasi State

Setiap goroutine memiliki salinan AST sendiri. Closure undo mengembalikan node sebelum keluar goroutine. Sinkronisasi hanya pada sync.WaitGroup.

// internal/engine/runner.go: concurrent mutant execution
var wg sync.WaitGroup
results := make([]Result, len(plans))
for i, plan := range plans {
    wg.Add(1)
    go func(idx int, p MutationPlan) {
        defer wg.Done()
        fset := token.NewFileSet()
        parsed, _ := parser.ParseFile(fset, "src.go", srcBytes, 0)
        undo := p.Apply(parsed)
        mutatedSrc := renderSource(parsed)
        results[idx] = Result{Mutant: p, Killed: testFn(mutatedSrc)}
        undo()
    }(i, plan)
}
wg.Wait()

Verifikasi Race

go test -race ./... passed. Tidak ada shared mutable node antar goroutine.

Analisis Mendalam: Mengapa Mutan Tertentu Lolos

Analisis mendalam menunjukkan pola survival yang konsisten. Mutan Boolean flip lolos karena test tidak pernah mengevaluasi kondisi branch yang berubah. Mutan relasional lolos karena input berada jauh di atas atau bawah threshold, sehingga pergeseran batas tidak mengubah outcome positif.

Mutan 1: || -> &&

Kode: order.Tier == TierVIP || order.TotalAmount >= 1000.0. Mutasi: hanya VIP dengan amount >= 1000 yang masuk. Input weak test: VIP + 1200 → masih masuk, finalAmount positif. Weak assert tidak memeriksa freeShipping boolean.

Mutan 9: > -> >=

Kode: order.ItemCount > 2. Mutasi: ItemCount == 3 tetap memenuhi, bahkan ItemCount == 2 juga. Input weak test: ItemCount = 3 → coupon boost tetap berlaku. Tidak ada assert untuk rate boost eksak.

Mutan 11: * -> /

Kode: discountAmount := order.TotalAmount * rate. Mutasi: perhitungan menjadi pembagian. Input weak test: TotalAmount besar → hasil bagi tetap positif. Assert hanya memeriksa positive, bukan exact formula.

Pertimbangan Performa dan Skalabilitas

Mutation testing memperkenalkan biaya komputasi tambahan karena setiap mutan memerlukan parsing ulang dan evaluasi. Namun, isolasi goroutine dan penulisan hasil berbasis indeks menjaga overhead tetap rendah.

Biaya Komputasi

15 mutant × parse+render+test per mutant. Isolasi AST menambah overhead parse berulang. Runtime tetap sub-detik untuk modul berukuran kecil.

Strategi Skala

Differential mutation: hanya mutasi file yang berubah di PR. Incremental scoring: target skor minimum per modul. Parallel goroutine mengurangi wall-clock time secara linear.

Batasan Produksi

Full mutation testing mahal untuk codebase raksasa. Pertimbangkan focus pada domain core dan jalur kritikal.

Validasi Race-Clean dan Integritas AST

Keamanan konkurensi divisualisasikan melalui race detector Go. Karena setiap goroutine bekerja dengan salinan AST baru dan menulis hasil ke indeks slice yang unik, tidak ada kompetisi akses memori. Fungsi undo menjamin tidak ada state AST yang bocor antar goroutine.

Test Race

Perintah: go test -race ./.... Status: ALL PASSED. Tidak ada report data race pada stdout/stderr.

Mekanisme Keamanan

Setiap goroutine membuat token.NewFileSet() baru. Mutable node hanya diakses dalam goroutine yang sama. Closure undo mengembalikan state sebelum goroutine selesai.

Indikator Keselamatan

Penulisan results[idx] aman karena indeks unik per goroutine. Tidak ada shared pointer atau global mutable state.

Checklist Implementasi Mutation Testing

Adopsi mutation testing memerlukan checklist terstruktur agar tidak overwhelming. Dimulai dari identifikasi modul kritikal, persiapan evaluator AST, hingga eksekusi baseline weak dan strong.

Anti-Pattern yang Menciptakan Survived Mutants

Tiga anti-pattern dominan ditemukan pada suite lemah. Assertion berbasis positivitas saja mengabaikan nilai eksak. Input happy path saja melewatkan boundary shift. Ketidakhadiran exact value assertion membuat arithmetic mutation invisibel.

PolaContohDampak
Assertion Positivitas Sajaassert result > 0 atau assert !errorSemua mutasi arithmetic dan relasional tetap lolos
Input Hanya Happy PathMenggunakan input jauh dari boundaryBoundary shift mutant tidak terdeteksi
Tidak Menggunakan Exact ValueMenghindari assert.Equal(expected, got)Arithmetic mutation tidak mengubah outcome assert

Reproduksi

Ubah >= jadi > pada threshold; test tetap hijau. Shift integer 2 ke 3 dengan ItemCount = 5. Ganti * dengan / pada amount besar; hasil tetap 'positive'.

Takeaway Praktis dan Command Block

Langkah praktis dimulai dengan mengganti asersi longgar menjadi pengecekan exact value dan boolean flag. Tambah test case boundary di setiap ambang tipe tier dan jumlah item. Integrasikan mutation scan diferensial ke dalam pipeline PR sebagai gate tambahan.

Command Base

go test -v ./...           # Run all tests verbosely
go test -race -v ./...     # Verify no data races
go run ./cmd/demo          # Execute mutation testing demo CLI

Actionable Steps

  1. Ganti assertion signe-based dengan exact value/boolean check
  2. Tambahkan test case di setiap threshold boundary
  3. Jalankan mutation scan diferensial sebelum merge PR

Mindset Shift

Coverage hijau bukan jaminan bebas bug. Mutation score adalah proksi kedalaman asersi. Setiap survived mutant adalah bug potensial yang menunggu.

Prinsip Arsitektural Jangka Panjang

Prinsip arsitektural jangka panjang menempatkan mutation testing sebagai disiplin verifikasi berlapis. Coverage tetap berguna sebagai indikator eksekusi, tetapi mutation score mengukur kedalaman asersi. Pendekatan incremental mencegah kelelahan tim sekaligus mempertahankan tekanan kualitas pada modul kritikal.

Disiplin Verifikasi

  • Coverage menjawab 'berapa banyak kode dieksekusi'
  • Mutation scoring menjawab 'seberapa dalam kode diverifikasi'
  • Keduanya komplementer, bukan substitusi

Incremental Quality Gate

  • Tetapkan target skor minimum per modul seiring waktu
  • Fokus pada modul yang mengalami perubahan di setiap PR
  • Hindari perfektisisme global; ukur kemajuan sektoral

Culture Improvement

  • Review survived mutant sebagai sesi pembelajaran tim
  • Document pola asersi kuat sebagai reference
  • Update checklist anti-pattern secara berkala
