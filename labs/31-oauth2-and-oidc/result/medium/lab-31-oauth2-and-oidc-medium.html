Masalah Nyata: Rapuhnya Identitas & Sesi Web

Dalam arsitektur terdistribusi nyata, kebocoran sesi sering kali bukan diakibatkan oleh kelemahan algoritma enkripsi, melainkan kekeliruan desain alur otorisasi. Banyak tim rekayasa perangkat lunak menganggap access token OAuth 2.0 dapat digunakan langsung untuk mengenali identitas user, padahal token tersebut dirancang khusus untuk resource server, bukan client. Selain itu, authorization code yang melintasi browser redirect pada aplikasi mobile atau SPA sangat rentan disadap jika tidak diproteksi oleh bukti kepemilikan kriptografis seperti PKCE.

Mengapa Pendekatan Naif & Implicit Flow Gagal?

Pendekatan naif kerap melakukan decode base64 pada payload JWT tanpa memverifikasi tanda tangan kriptografis dan claims wajibnya. Kode semacam ini memungkinkan penyerang membuat token palsu berisi identitas sembarang dan langsung diterima oleh sistem. Selain itu, penggunaan Implicit Flow yang dahulu populer kini telah resmi didepresiasi oleh RFC 9700 karena mengekspos token secara telanjang pada URL fragment dan history browser, menjadikannya sasaran empuk serangan Cross-Site Scripting (XSS).

func HandleAuthNaive(rawJWT string) (*User, error) {
    // BAHAYA FATAL: Decode payload tanpa verifikasi signature HMAC/RSA!
    parts := strings.Split(rawJWT, ".")
    claimsBytes, _ := base64.RawURLEncoding.DecodeString(parts[1])
    var claims NaiveClaims
    json.Unmarshal(claimsBytes, &claims)
    // Tidak memeriksa iss, aud, exp, maupun nonce anti-replay!
    return &User{ID: claims.Subject}, nil
}

Mental Model: Dual-Token Architecture & Family Lineage

Mental model sistem ini bertumpu pada pemisahan tanggung jawab secara tegas antara otorisasi dan autentikasi. ID Token claims mendefinisikan identitas terverifikasi pengguna dengan enam perimeter verifikasi wajib: penerbit (iss), subjek (sub), penerima sah (aud), masa berlaku (exp), jendela waktu terbit (iat), dan tiket anti-replay (nonce). Di sisi backend sesi, struktur RefreshTokenMeta melacak lineage silsilah token melalui FamilyID dan penanda status Revoked untuk menjamin aturan konsumsi sekali pakai (single-use semantics).

type IDTokenClaims struct {
    Issuer     string `json:"iss"`  // OIDC Provider sah
    Subject    string `json:"sub"`  // Identitas unik user
    Audience   string `json:"aud"`  // Client ID target
    Expiration int64  `json:"exp"`  // Waktu kedaluwarsa
    IssuedAt   int64  `json:"iat"`  // Waktu terbit (±5m)
    Nonce      string `json:"nonce"`// Anti-replay challenge
}
type RefreshTokenMeta struct {
    FamilyID  string    // Silsilah sesi tunggal
    Revoked   bool      // Status single-use consumption
    ExpiresAt time.Time // Kedaluwarsa absolut (30 hari)
}

Pipeline End-to-End: PKCE, Token Minting, & Rotation

Pipeline otorisasi dan identitas ini memperlihatkan interaksi end-to-end antara Client, Authorization Server, dan Resource Server. Pada tahap 1 hingga 3, client menyiapkan proteksi PKCE S256 dan nonce sebelum meminta authorization code yang berumur pendek (5 menit). Pada tahap 4 hingga 6, client menukar authorization code dengan menyertakan bukti kepemilikan code_verifier asli, memungkinkan server menerbitkan access token, ID token terenkripsi, dan refresh token berkategori family. Tahap akhir memverifikasi integritas ID token serta merotasi refresh token secara aman.

Implementasi Inti: Refresh Token Rotation & Family Revocation

Potongan kode ini merupakan benteng pertahanan utama terhadap serangan replay refresh token pada pkg/server/server.go. Setiap kali klien meminta pembaruan token, server memeriksa apakah token tersebut sudah pernah digunakan sebelumnya melalui flag meta.Revoked. Jika token yang sudah berstatus revoked dipresentasikan kembali, sistem menyimpulkan bahwa token tersebut telah dicuri dan sedang direplay oleh pihak jahat. Server seketika memasukkan meta.FamilyID ke dalam daftar hitam revokedFams, membatalkan seluruh sesi login terkait.

if s.revokedFams[meta.FamilyID] {
    return nil, ErrTokenReplayDetected // Keluarga sudah terkompromi
}
if meta.Revoked {
    // REPLAY TERDETEKSI: Penyerang menggunakan token yang sudah dirotasi!
    s.revokedFams[meta.FamilyID] = true // Cabut seluruh sesi aktif
    return nil, ErrTokenReplayDetected
}
meta.Revoked = true // Tandai token saat ini sebagai terpakai
// Terbitkan refresh token baru dengan FamilyID yang sama...

Failure Path: Penolakan Intersepsi & Replay Serangan

Failure path konkret ini diambil langsung dari hasil eksekusi program demo lab cmd/demo/main.go. Pada Langkah 6, penyerang yang berhasil menyadap authorization code mencoba menukarnya menggunakan verifier palsu, namun server menolak transaksi secara mutlak dengan error ketidakcocokan PKCE. Pada Langkah 8, penyerang mencoba menggunakan refresh token usang yang telah dirotasi pada Langkah 7. Server mendeteksi upaya replay ini, menandai keluarga token sebagai terkompromi, dan membatalkan seluruh sesi termasuk token sah milik korban.

Mekanisme vs Gejala: Evaluasi Solusi Autentikasi & Otorisasi

Tabel ini mengevaluasi berbagai mekanisme otorisasi dan autentikasi dalam menghadapi berbagai vektor ancaman dunia nyata. Menggunakan OAuth 2.0 murni tanpa OIDC untuk login pengguna menimbulkan kerentanan fatal karena access token tidak dirancang untuk memverifikasi audiens pemanggil. Implicit flow kini resmi dilarang oleh standar IETF RFC 9700 karena tingginya risiko kebocoran kredensial di URL browser. Hanya kombinasi terpadu antara OIDC, PKCE S256, dan Refresh Token Rotation dengan Family Revocation yang memberikan perlindungan komprehensif.

3 Keputusan Desain Kritis Arsitektur Identitas

Tiga keputusan arsitektural ini memastikan implementasi OAuth 2.0 dan OIDC memenuhi standar ketat IETF RFC 9700. Pertama, PKCE metode S256 diwajibkan tanpa kompromi untuk seluruh jenis client guna memastikan authorization code tidak dapat dieksploitasi meski berhasil disadap di jaringan publik. Kedua, verifikasi ID Token tidak boleh hanya membaca JSON, melainkan wajib mengevaluasi tanda tangan digital dan parameter nonce anti-replay. Ketiga, rotasi refresh token wajib didukung oleh pelacakan FamilyID untuk mematikan sesi penyerang seketika.

Bukti eksekusi terminal membuktikan bahwa seluruh siklus autentikasi dan otorisasi berjalan mulus tanpa celah keamanan. Langkah 1 hingga 5 menunjukkan pembuatan tantangan PKCE S256, penerbitan authorization code, penukaran token yang sah, verifikasi klaim ID Token, hingga akses ke resource server dengan scope yang sesuai. Langkah 6 hingga 8 memperlihatkan simulasi serangan nyata di mana upaya pertukaran kode oleh penyerang digagalkan oleh PKCE, dan upaya penggunaan ulang refresh token curian langsung memicu pemblokiran seluruh keluarga sesi.

YANG TIDAK DIBUKTIKAN

Klaim teknis dalam laboratorium ini dibatasi secara tegas oleh parameter lingkungan pengujian yang dirancang mandiri (self-contained). Authorization server menyimpan state di dalam memori proses tunggal tanpa integrasi database terdistribusi seperti Redis kluster. Penandatanganan ID Token menggunakan skema simetris HMAC-SHA256 untuk kesederhanaan komputasi lokal, bukan infrastruktur kunci publik asimetris dengan endpoint JWKS dinamis. Pengembang tidak boleh mengabaikan kebutuhan constant-time comparison dan mekanisme sender-constrained token (DPoP) saat beralih ke skala produksi.

Trade-off Arsitektur: Keamanan Sesi vs Kompleksitas Server

Penerapan arsitektur OAuth 2.0 dan OIDC modern menuntut kompromi yang cermat antara tingkat keamanan dan kompleksitas operasional. Menghapus token statis dan memberlakukan Refresh Token Rotation memberikan perlindungan maksimal dari pembajakan sesi jangka panjang, namun mewajibkan server mengelola state silsilah FamilyID secara konsisten di penyimpanan terdistribusi. Selain itu, ada risiko kegagalan jaringan sementara (race condition jaringan) di mana klien yang mencoba refresh ulang dapat disalahartikan sebagai penyerang yang melakukan replay.

Validasi Konkurensi: 10 Goroutine Berebut Refresh Token

Uji konkurensi pada TestOAuth2_ConcurrentRefreshReplay membuktikan ketangguhan sistem saat satu refresh token yang sama ditembak secara simultan oleh 10 goroutine. Karena method Refresh di Authorization Server dilindungi oleh sync.Mutex eksklusif, evaluasi status token berlangsung secara linearizable. Tepat satu permintaan berhasil merotasi token, sementara sembilan permintaan lainnya seketika memicu error ErrTokenReplayDetected dan mencabut seluruh family. Pengujian go test -race membuktikan ketiadaan data race pada 20 worker konkruen.

func TestOAuth2_ConcurrentRefreshReplay(t *testing.T) {
    stolenRT := resp.RefreshToken
    var wg sync.WaitGroup; errCount := 0; var mu sync.Mutex
    for i := 0; i < 10; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            _, err := as.Refresh(stolenRT, "client_conc_ref")
            if err != nil { mu.Lock(); errCount++; mu.Unlock() }
        }()
    }
    wg.Wait()
    // Assert: errCount >= 9 akibat rotasi dan family revocation
}

Before vs After: Evolusi Keamanan Sesi Web

Perbandingan before-after ini mengilustrasikan lompatan besar standar keamanan web selama satu dekade terakhir. Pada arsitektur lama, pengembang mengandalkan Implicit Flow dan menyimpan refresh token statis di browser localStorage, menciptakan kerentanan masif terhadap pencurian sesi melalui skrip jahat. Pada arsitektur modern berbasis RFC 9700, authorization code diikat secara kriptografis oleh PKCE, ID Token diverifikasi secara matematis, dan refresh token dirotasi pada setiap pemanggilan sehingga penyusupan dapat dideteksi dan dilumpuhkan secara otomatis.

Test 1: Validasi Kriptografis Tantangan PKCE S256

Unit test pertama memverifikasi pemenuhan standar RFC 7636 pada modul pkg/pkce/pkce.go. Fungsi GeneratePKCEPair terbukti menghasilkan code_verifier berkekuatan 256-bit entropy dengan panjang tepat 43 karakter base64url. Pengujian memvalidasi bahwa perhitungan BASE64URL(SHA256(verifier)) cocok secara sempurna dengan challenge yang dikirimkan. Test verifier bounds memastikan bahwa string yang lebih pendek dari 43 karakter atau lebih panjang dari 128 karakter langsung ditolak demi mencegah serangan degradasi entropi.

func TestPKCE_S256_Valid(t *testing.T) {
    pair, err := pkce.GeneratePKCEPair("S256")
    // Assert: len(pair.CodeVerifier) >= 43 && len(pair.CodeVerifier) <= 128
    err = pkce.Verify(pair.CodeVerifier, pair.CodeChallenge, "S256")
    // Assert: err == nil (SHA-256 base64url matching)
}

Pengujian modul OIDC membuktikan bahwa ID Token tidak dapat dimanipulasi oleh pihak ketiga. Pada TestOIDC_IDToken_TamperedSignature, setiap pengubahan satu karakter pun pada tanda tangan JWT langsung digagalkan oleh pemeriksaan hmac.Equal. Test 3: Pencegahan Serangan Intersepsi Authorization Code

Test ketiga mendemonstrasikan bagaimana proteksi PKCE menggagalkan skenario penyerangan nyata pada client publik. Saat penyerang berhasil menyadap authorization code yang melintasi sistem operasi dan mencoba menukarnya ke server menggunakan verifier palsu, server mendeteksi ketidakcocokan SHA-256 dan membatalkan pertukaran. Klien sah kemudian berhasil menukar kode tersebut dengan verifier aslinya. Ketika kode yang sama dicoba untuk digunakan kembali untuk kedua kalinya, server menolaknya karena kode otorisasi bersifat strictly single-use.

// 1. Client sah menginisiasi flow dan meminta authorization code
ch, _ := cli.BuildAuthorizationRequest("openid profile")
ac, _ := as.Authorize("client_1", "https://app.com/cb", "openid profile", "user_sub_1", ch, "S256", cli.Nonce)
// 2. Attacker menyadap ac.Code, mencoba exchange dengan verifier tebakan
_, err = as.ExchangeCode(ac.Code, "client_1", "https://app.com/cb", "attacker_wrong_verifier_12345678901234567890123")
// Assert: err != nil (PKCE verification failed: challenge mismatch)
// 3. Client sah menukar code dengan verifier asli -> SUKSES
resp, err := cli.Exchange(ac.Code) // Menerima Access, Refresh, & ID Token
// 4. Percobaan penggunaan ulang ac.Code yang sama -> DITOLAK (Used = true)

Studi Kasus Industri: Konsensus Keamanan RFC 9700

Riset standar IETF menunjukkan pergeseran paradigma fundamental dalam keamanan web terdistribusi. Implicit Flow yang dahulu menjadi standar bagi Single Page Application resmi dihapus dalam OAuth 2.1 dan RFC 9700 karena token akses rentan bocor melalui riwayat peramban dan skrip analitik pihak ketiga. Standar industri terkini mewajibkan Authorization Code Flow yang dilindungi PKCE S256 untuk seluruh aplikasi. Di masa depan, proteksi ini semakin diperkuat dengan sender-constrained tokens seperti DPoP untuk menghentikan pencurian token di lapisan jaringan.

Analisis Teknis: Anatomi Token Family Revocation

Mekanisme Token Family Revocation per RFC 9700 Section 4.14 mengubah sifat pasif refresh token menjadi jebakan aktif bagi penyusup. Ketika token yang dicuri oleh penyerang digunakan setelah klien sah melakukan rotasi, server mengenali bahwa token tersebut sudah berstatus terpakai (Revoked=true). Alih-alih hanya menolak satu permintaan tersebut, server secara cerdas mengidentifikasi bahwa seluruh keluarga sesi telah terkompromi. Server langsung mencabut FamilyID secara menyeluruh, memastikan penyerang tidak dapat mempertahankan aksesnya.

Checklist Implementasi Produksi OAuth 2.0 & OIDC

Daftar periksa ini merangkum sembilan prinsip krusial yang wajib dipenuhi sebelum menggelar infrastruktur OAuth 2.0 dan OIDC ke sistem produksi perbankan atau enterprise. Seluruh alur harus mewajibkan PKCE S256 tanpa toleransi metode plain, dan masa berlaku authorization code dibatasi maksimal lima menit. Verifikasi ID Token di sisi client wajib mencakup seluruh aspek kriptografi dan claims. Di lapisan penyimpanan browser, penyimpanan token di localStorage harus dihindari sepenuhnya demi memitigasi risiko XSS.

Anti-Pattern: Kesalahan Desain yang Kerap Terjadi

Mengabaikan prinsip dasar keamanan identitas web dapat berakibat fatal bagi perlindungan data pengguna. Anti-pattern yang paling sering dijumpai adalah menggunakan access token untuk autentikasi dan menyimpan token berumur panjang di localStorage. Hal ini memberikan jalan bebas bagi serangan XSS untuk membajak akun secara permanen. Pengembang dapat mereproduksi kerentanan ini secara langsung di lab dengan melonggarkan validasi single-use pada server.go dan menyaksikan test suite mendeteksi kegagalan tersebut.

Prinsip Arsitektur: Desain Identitas Terdistribusi

Tiga prinsip arsitektural ini melampaui bahasa pemrograman dan framework apapun dalam rekayasa perangkat lunak modern. Pertama, tegakkan batas tegas antara otorisasi dan autentikasi agar sistem tidak terjebak dalam confused deputy attacks. Kedua, jangan pernah mempercayai data yang melintasi browser tanpa pembuktian kepemilikan kriptografis seperti PKCE dan nonce. Ketiga, terapkan paradigma Zero Trust pada sesi pengguna: anggap kredensial dapat bocor sewaktu-waktu, dan gunakan rotasi token keluarga untuk melumpuhkan penyusup seketika.
