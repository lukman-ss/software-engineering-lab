Masalah Nyata: Rapuhnya Identitas dan Sesi Web

Dalam arsitektur terdistribusi nyata, kebocoran sesi sering kali bukan diakibatkan oleh kelemahan algoritma enkripsi, melainkan kekeliruan desain alur otorisasi. Banyak tim menganggap access token OAuth 2.0 dapat digunakan langsung untuk mengenali identitas user, padahal token tersebut dirancang khusus untuk resource server. Selain itu, authorization code yang melintasi browser redirect pada aplikasi mobile atau SPA sangat rentan disadap jika tidak diproteksi oleh bukti kepemilikan kriptografis seperti PKCE.

Mengapa Pendekatan Naif & Implicit Flow Gagal?

Pendekatan naif kerap melakukan decode base64 pada payload JWT tanpa memverifikasi tanda tangan kriptografis dan claims wajibnya. Kode semacam ini memungkinkan penyerang membuat token palsu berisi identitas sembarang dan langsung diterima oleh sistem. Penggunaan Implicit Flow yang dahulu populer kini telah resmi didepresiasi oleh RFC 9700 karena mengekspos token secara telanjang pada URL fragment.

func HandleAuthNaive(rawJWT string) (*User, error) {
    // BAHAYA FATAL: Decode payload tanpa verifikasi signature!
    parts := strings.Split(rawJWT, ".")
    claimsBytes, _ := base64.RawURLEncoding.DecodeString(parts[1])
    var claims NaiveClaims
    json.Unmarshal(claimsBytes, &claims)
    // Tidak memeriksa iss, aud, exp, maupun nonce anti-replay!
    return &User{ID: claims.Subject}, nil
}

Mental Model: Arsitektur Dual-Token & Family Lineage

Mental model sistem ini bertumpu pada pemisahan tanggung jawab secara tegas antara otorisasi dan autentikasi. ID Token claims mendefinisikan identitas terverifikasi pengguna dengan enam perimeter verifikasi wajib: penerbit (iss), subjek (sub), penerima sah (aud), masa berlaku (exp), jendela waktu terbit (iat), dan tiket anti-replay (nonce). Di sisi backend sesi, struktur RefreshTokenMeta melacak lineage silsilah token melalui FamilyID.

type IDTokenClaims struct {
    Issuer     string `json:"iss"`  // OIDC Provider sah
    Subject    string `json:"sub"`  // Identitas unik user
    Audience   string `json:"aud"`  // Client ID target
    Expiration int64  `json:"exp"`  // Waktu kedaluwarsa
    IssuedAt   int64  `json:"iat"`  // Waktu terbit (±5m)
    Nonce      string `json:"nonce"`// Anti-replay challenge
}
type RefreshTokenMeta struct {
    FamilyID  string    // Silsilah sesi tunggal
    Revoked   bool      // Status single-use consumption
    ExpiresAt time.Time // Kedaluwarsa absolut (30 hari)
}

Pipeline End-to-End: PKCE, Token Minting, & Rotation

Pipeline otorisasi dan identitas ini memperlihatkan interaksi end-to-end antara Client, Authorization Server, dan Resource Server. Pada tahap 1 hingga 3, client menyiapkan proteksi PKCE S256 dan nonce sebelum meminta authorization code yang berumur pendek. Pada tahap 4 hingga 6, client menukar authorization code dengan menyertakan bukti kepemilikan code_verifier asli.

1. Client.BuildAuthorizationRequest() -> Hitung S256(verifier) = challenge & generate nonce.
2. Client -> AS: GET /authorize?response_type=code&code_challenge=...&nonce=...&scope=openid profile
3. AS.Authorize() -> Verifikasi client & redirect URI, simpan challenge, terbitkan AuthCode (TTL 5m).
4. Client -> AS: POST /token grant_type=authorization_code&code=...&code_verifier=...
5. AS.ExchangeCode() -> Validasi SHA256(code_verifier) == challenge. Tandai code used = true.
6. AS Menerbitkan: AccessToken (opaque), IDToken (JWT HS256), & RefreshToken (FamilyID).
7. Client.ParseAndVerifyIDToken() -> Verifikasi HMAC, iss, aud, exp, nonce match.
8. Client.RefreshTokens() -> AS rotasi: tandai RT lama Revoked=true, terbitkan pasangan baru.

Implementasi Inti: Refresh Token Rotation & Family Revocation

Potongan kode ini merupakan benteng pertahanan utama terhadap serangan replay refresh token pada server.go. Setiap kali klien meminta pembaruan token, server memeriksa apakah token tersebut sudah pernah digunakan sebelumnya melalui flag meta.Revoked. Jika token yang sudah berstatus revoked dipresentasikan kembali, sistem menyimpulkan bahwa token tersebut telah dicuri.

if s.revokedFams[meta.FamilyID] {
    return nil, ErrTokenReplayDetected // Keluarga sudah terkompromi
}
if meta.Revoked {
    // REPLAY TERDETEKSI: Penyerang menggunakan token yang sudah dirotasi!
    s.revokedFams[meta.FamilyID] = true // Cabut seluruh sesi aktif
    return nil, ErrTokenReplayDetected
}
meta.Revoked = true // Tandai token saat ini sebagai terpakai
// Terbitkan refresh token baru dengan FamilyID yang sama...

YANG TIDAK DIBUKTIKAN

Klaim teknis dalam laboratorium ini dibatasi secara tegas oleh parameter lingkungan pengujian yang dirancang mandiri. Authorization server menyimpan state di dalam memori proses tunggal tanpa integrasi database terdistribusi seperti Redis kluster. Penandatanganan ID Token menggunakan skema simetris HMAC-SHA256 untuk kesederhanaan komputasi lokal, bukan infrastruktur kunci publik asimetris dengan endpoint JWKS dinamis. Pengembang tidak boleh mengabaikan kebutuhan constant-time comparison.

Trade-off Arsitektur: Keamanan Sesi vs Kompleksitas Server

Penerapan arsitektur OAuth 2.0 dan OIDC modern menuntut kompromi yang cermat antara tingkat keamanan dan kompleksitas operasional. Menghapus token statis dan memberlakukan Refresh Token Rotation memberikan perlindungan maksimal dari pembajakan sesi jangka panjang, namun mewajibkan server mengelola state silsilah FamilyID secara konsisten di penyimpanan terdistribusi. Selain itu, ada risiko kegagalan jaringan sementara.

Validasi Konkurensi: 10 Goroutine Berebut Refresh Token

Uji konkurensi pada TestOAuth2_ConcurrentRefreshReplay membuktikan ketangguhan sistem saat satu refresh token yang sama ditembak secara simultan oleh 10 goroutine. Karena method Refresh di Authorization Server dilindungi oleh sync.Mutex eksklusif, evaluasi status token berlangsung secara linearizable. Tepat satu permintaan berhasil merotasi token, sementara sembilan lainnya seketika memicu error.

func TestOAuth2_ConcurrentRefreshReplay(t *testing.T) {
    stolenRT := resp.RefreshToken
    var wg sync.WaitGroup; errCount := 0; var mu sync.Mutex
    for i := 0; i < 10; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            _, err := as.Refresh(stolenRT, "client_conc_ref")
            if err != nil { mu.Lock(); errCount++; mu.Unlock() }
        }()
    }
    wg.Wait()
    // Assert: errCount >= 9 akibat rotasi dan family revocation
}

Test 1: Validasi Kriptografis Tantangan PKCE S256

Unit test pertama memverifikasi pemenuhan standar RFC 7636 pada modul pkg/pkce/pkce.go. Fungsi GeneratePKCEPair terbukti menghasilkan code_verifier berkekuatan 256-bit entropy dengan panjang tepat 43 karakter base64url. Pengujian memvalidasi bahwa perhitungan BASE64URL(SHA256(verifier)) cocok secara sempurna dengan challenge yang dikirimkan. Test verifier bounds memastikan string yang lebih pendek atau lebih panjang ditolak.

func TestPKCE_S256_Valid(t *testing.T) {
    pair, err := pkce.GeneratePKCEPair("S256")
    // Assert: len(pair.CodeVerifier) >= 43 && len(pair.CodeVerifier) <= 128
    err = pkce.Verify(pair.CodeVerifier, pair.CodeChallenge, "S256")
    // Assert: err == nil (SHA-256 base64url matching)
}

Studi Kasus Industri: Konsensus Keamanan RFC 9700

Riset standar IETF menunjukkan pergeseran paradigma fundamental dalam keamanan web terdistribusi. Implicit Flow yang dahulu menjadi standar bagi Single Page Application resmi dihapus dalam OAuth 2.1 dan RFC 9700 karena token akses rentan bocor melalui riwayat peramban. Standar industri terkini mewajibkan Authorization Code Flow yang dilindungi PKCE S256 untuk seluruh aplikasi.

Analisis Teknis: Anatomi Token Family Revocation

Mekanisme Token Family Revocation per RFC 9700 Section 4.14 mengubah sifat pasif refresh token menjadi jebakan aktif bagi penyusup. Ketika token yang dicuri oleh penyerang digunakan setelah klien sah melakukan rotasi, server mengenali bahwa token tersebut sudah berstatus terpakai. Alih-alih hanya menolak satu permintaan, server secara cerdas mengidentifikasi bahwa seluruh keluarga sesi telah terkompromi.

Checklist Implementasi Produksi OAuth 2.0 & OIDC

Daftar periksa ini merangkum sembilan prinsip krusial yang wajib dipenuhi sebelum menggelar infrastruktur OAuth 2.0 dan OIDC ke sistem produksi. Verifikasi ID Token di sisi client wajib mencakup seluruh aspek kriptografi dan claims.

Anti-Pattern: Kesalahan Desain yang Kerap Terjadi

Mengabaikan prinsip dasar keamanan identitas web dapat berakibat fatal bagi perlindungan data pengguna. Anti-pattern yang paling sering dijumpai adalah menggunakan access token untuk autentikasi dan menyimpan token berumur panjang di localStorage. Hal ini memberikan jalan bebas bagi serangan XSS untuk membajak akun secara permanen. Pengembang dapat mereproduksi kerentanan ini secara langsung di lab.
