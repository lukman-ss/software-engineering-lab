Saga Pattern: Mengelola Transaksi Terdistribusi Tanpa Two-Phase Commit di Microservices

Koordinasi orkestrasi vs koreografi, kompensasi LIFO, dan semantic lock di Go

Lukman / lukman-ss · Software Engineering Lab 29

Saga pattern replaces 2PC with independent local transactions and compensating rollbacks.

Ketika Database Terpisah Tidak Bisa Berkomitmen Bersama

Arsitektur microservices modern memberi setiap layanan basis data mandiri. Ketika alur bisnis memerlukan pembuatan order, pemrosesan pembayaran, dan reservasi inventaris secara berurutan, jaminan transaksi ACID klasik yang mengandalkan satu database tunggal langsung runtuh. Protokol Two-Phase Commit (2PC) sering diajukan sebagai solusi, tetapi protokol ini mengunci seluruh resource secara sinkron hingga semua peserta menyetujui commit — mengurangi throughput dan membuat sistem rapuh terhadap partisi jaringan.

Mengapa Pendekatan Naif Gagal Menangani Transaksi Multi-Layanan

Panggilan RPC berurutan tanpa mekanisme rollback otomatis meninggalkan state tidak konsisten. Memanggil service secara berurutan bukan berarti sistem dapat pulih secara otomatis ketika downstream gagal. Jika reservasi inventaris gagal setelah pembayaran berhasil, order tetap tersisa dalam status PENDING sementara saldo pelanggan sudah terpotong. Rekonsiliasi manual yang rumit akhirnya tak terhindarkan untuk menambal state yang terfragmentasi.

func (o *OrderService) CreateFullOrder(orderID string) error {
    o.CreateOrder(orderID)     // DB-commit #1
    p.ProcessPayment(orderID)  // DB-commit #2 — jika gagal?
    i.ReserveInventory(...)    // DB-commit #3 — jika gagal?
    o.ApproveOrder(orderID)    // DB-commit #4
}

Mental Model: Estafet Transaksi dengan Kompensasi Mundur

Pola Saga memodelkan transaksi terdistribusi seperti perlombaan lari estafet. Setiap pelari menyelesaikan etape lokalnya lalu melakukan commit langsung ke database-nya sendiri. Apabila pelari ketiga terjatuh, pelari pertama dan kedua bergerak mundur untuk memulihkan posisi awal mereka. Setiap langkah berdiri sebagai transaksi lokal independen tanpa distributed lock lintas layanan. Kompensasi dijalankan secara terbalik agar refund pembayaran terjadi sebelum order dibatalkan.

Pipeline Orkestrasi: Dari Langkah Eksekusi Hingga Kompensasi

Pipeline eksekusi berpusat pada sebuah koordinator terpusat. Mencatat log transisi tidak otomatis menghapus risiko anomali state jika kompensasi terhenti, namun saat request diterima, orchestrator mengeksekusi setiap langkah ke database lokal masing-masing service. Jika salah satu langkah mengembalikan error, iterasi maju dihentikan dan orchestrator memanggil fungsi kompensasi untuk memutar balik langkah-langkah yang telah berhasil dalam urutan terbalik.

Implementasi Inti: Orchestrator Step & LIFO Compensate

Struktur data Step mengikat pasangan fungsi Execute dan Compensate. Keberadaan fungsi rollback tidak otomatis menyelesaikan seluruh anomali data jika terjadi kegagalan sekunder. Orchestrator menyimpan daftar langkah dan mengeksekusinya secara berurutan. Method compensate() melakukan iterasi mundur dari indeks langkah terakhir yang berhasil dieksekusi hingga nol sambil mengumpulkan error rollback yang terjadi.

type Step struct {
    Name       string
    Execute    func(ctx context.Context) error
    Compensate func(ctx context.Context) error
}

func (o *Orchestrator) compensate(ctx context.Context, executed []Step) error {
    var compErrors []error
    for i := len(executed) - 1; i >= 0; i-- {
        step := executed[i]
        if step.Compensate != nil {
            err := step.Compensate(ctx)
            o.mu.Lock()
            if err != nil {
                o.logs = append(o.logs, StepLog{Name: step.Name, Status: StatusCompensateFailed})
                compErrors = append(compErrors, fmt.Errorf("compensation %s: %w", step.Name, err))
            } else {
                o.logs = append(o.logs, StepLog{Name: step.Name, Status: StatusCompensated})
            }
            o.mu.Unlock()
        }
    }
    if len(compErrors) > 0 {
        return fmt.Errorf("%v", compErrors)
    }
    return nil
}

Failure Path: ReserveInventory Gagal — Urutan Kompensasi LIFO

Ketika stok produk tidak mencukupi, orchestration berhenti setelah order dibuat dan pembayaran diproses. Urutan kompensasi terbalik beroperasi rapi hanya pada jalur ini: RefundPayment dipanggil lebih dulu untuk mengembalikan dana pelanggan, baru kemudian CancelOrder dijalankan untuk mengubah status pesanan menjadi CANCELLED, memulihkan sistem kembali ke state awal.

Tabel Perbandingan: Mekanisme Kompensasi vs Gejala Sistem

Arsitektur Saga mengelompokkan jenis transaksi ke dalam tiga taksonomi: compensable, pivot, dan retryable. Menandai langkah sebagai kompensabel bukan berarti mutasi basis data dapat dibatalkan tanpa efek samping; desain kompensasi harus dirancang secara cermat. Transaksi pivot merupakan batas pemisah yang tidak dapat dibatalkan; setelah pivot tercapai, langkah berikutnya harus bersifat retryable hingga sukses.

Keputusan Arsitektur: Orkestrasi vs Koreografi

Memilih koreografi bukan berarti bebas dari koordinasi; pola ini hanya memindahkan logika koordinasi ke handler masing-masing service. Orkestrasi cocok untuk alur bisnis linear yang membutuhkan audit log terpusat, sedangkan koreografi cocok untuk sistem event-driven yang mengutamakan otonomi service. Trade-off utamanya terletak pada kompleksitas penelusuran end-to-end.

Batasan Bukti Lab: Yang Dibuktikan vs Belum

Trade-off Arsitektur: Availability vs Isolation

Pola Saga menukar isolasi ACID demi ketersediaan sistem yang tinggi. Menerima eventual consistency perlu bukti tambahan melalui pengujian integrasi beban tinggi: setiap langkah commit lokal langsung tanpa holding lock lintas layanan, sehingga throughput tetap tinggi. Konsekuensinya, status antara terlihat inkonsisten sementara hingga proses kompensasi tuntas.

Pipeline Konkurensi: Goroutine → Validate → Mutex → Append Error

Keamanan konkurensi di dalam orchestrator dikelola menggunakan strategi snapshot-and-release dengan sync.Mutex. Menggunakan mutex snapshot melindungi field internal struktur, tetapi tidak otomatis menangkal konflik konkurensi eksternal pada basis data downstream. Orchestrator menyalin slice langkah sebelum melepaskan kunci mutex, menghindari pemblokiran selama panggilan RPC berlangsung.

func (o *Orchestrator) Execute(ctx context.Context) error {
    o.mu.Lock()
    steps := make([]Step, len(o.steps))
    copy(steps, o.steps)  // snapshot tanpa menahan lock selama pemanggilan step
    o.mu.Unlock()

    executed := make([]Step, 0)
    for _, step := range steps {
        err := step.Execute(ctx)
        o.mu.Lock()
        if err != nil {
            o.logs = append(o.logs, StepLog{Name: step.Name, Status: StatusFailed})
            o.mu.Unlock()
            return err
        }
        o.logs = append(o.logs, StepLog{Name: step.Name, Status: StatusExecuted})
        o.mu.Unlock()
        executed = append(executed, step)
    }
    return nil
}

Before vs After: Dari Manual Calls ke Saga Orkestrasi

Transformasi dari panggilan manual tanpa kompensasi ke orkestrasi saga mengubah penanganan kegagalan secara fundamental. Sebelum menerapkan saga, kegagalan parsial meninggalkan order berstatus PENDING dan saldo terpotong tanpa jalan pemulihan otomatis. Setelah saga diterapkan, koordinator melacak status langkah dan memicu kompensasi LIFO secara terstruktur dengan jejak audit yang transparan.

Service Layer: Semantic Lock, Idempotency, dan Atomic Stock Mutation

Keandalan transaksi bertumpu pada pertahanan mandiri pada masing-masing service. Service guards ini membatasi risiko state korup hanya pada jalur ini: OrderService menerapkan semantic lock untuk menolak pembuatan order duplikat, PaymentService memeriksa idempotency key agar tidak mendebit dana ganda saat retry, dan InventoryService memutasi stok barang secara atomik di bawah proteksi mutex.

Choreography Pattern: Event Bus Decoupled via Pub/Sub

Pola koreografi meniadakan koordinator terpusat dengan memanfaatkan komunikasi event pub/sub. Menerapkan event decoupling bukan berarti boundary transaksi hilang sepenuhnya; ia memindahkan koordinasi ke subscriber masing-masing layanan. Struktur EventBus menggunakan sync.RWMutex untuk thread safety saat pendaftaran handler dan penerbitan event.

type EventBus struct {
    mu       sync.RWMutex
    handlers map[EventType][]EventHandler
}

func (b *EventBus) Publish(ctx context.Context, e Event) {
    b.mu.RLock()
    handlers := append([]EventHandler(nil), b.handlers[e.Type]...)
    b.mu.RUnlock()
    for _, h := range handlers { h(ctx, e) }
}

Bukti LIFO Log: Verifikasi Urutan Status Step pada Kompensasi

Ketepatan kronologi eksekusi dibuktikan lewat rekaman audit log pada test TestOrchestrator_FailureCompensatesLIFO. Ketika reservasi stok gagal, orchestrator mencatat tepat lima entri status berurutan: EXECUTED untuk CreateOrder, EXECUTED untuk ProcessPayment, FAILED untuk ReserveInventory, disusul COMPENSATED untuk refund dan cancel. Bukti ini menegaskan urutan rollback LIFO berjalan sesuai ekspektasi.

func TestOrchestrator_FailureCompensatesLIFO(t *testing.T) {
    logs := orch.Logs()
    expectedOrder := []saga.StepStatus{
        saga.StatusExecuted,    // CreateOrder
        saga.StatusExecuted,    // ProcessPayment
        saga.StatusFailed,      // ReserveInventory
        saga.StatusCompensated, // ProcessPayment (Refund)
        saga.StatusCompensated, // CreateOrder (Cancel)
    }
    for i, l := range logs {
        if l.Status != expectedOrder[i] {
            t.Errorf("log[%d] status mismatch: got %v, want %v", i, l.Status, expectedOrder[i])
        }
    }
}

Bukti Context Cancellation: Kompensasi Saat Saga Dibatalkan

Saat request dibatalkan oleh klien, eksekusi saga tidak boleh meninggalkan state yang menggantung. Detached context memungkinkan kompensasi lokal selesai, tetapi production masih perlu propagasi tracing terdistribusi: test TestOrchestrator_ContextCancellation membuktikan bahwa pembatalan context menghentikan langkah berikutnya dan memicu compensate() menggunakan context.Background() independen.

func TestOrchestrator_ContextCancellation(t *testing.T) {
    ctx, cancel := context.WithCancel(context.Background())
    orch := saga.NewOrchestrator()
    step1Compensated := false
    orch.AddStep(saga.Step{
        Name: "Step1",
        Execute: func(ctx context.Context) error {
            cancel() // Batalkan context sebelum langkah 2
            return nil
        },
        Compensate: func(ctx context.Context) error {
            step1Compensated = true
            return nil
        },
    })
    _ = orch.Execute(ctx)
    if !step1Compensated {
        t.Fatal("expected step 1 to be compensated upon cancellation")
    }
}

Checklist Implementasi Saga Pattern yang Benar

Menerapkan pola Saga di production menuntut kepatuhan terhadap checklist berikut:

  • Setiap langkah transaksi compensable memiliki fungsi rollback teruji.
  • Aksi eksekusi forward dan kompensasi rollback bersifat idempoten terhadap retry.
  • Semantic lock atau version checking diterapkan pada entitas yang diakses secara bersamaan.
  • Koordinator mengambil snapshot slice langkah sebelum eksekusi untuk menjaga keamanan thread.
  • Kompensasi rollback dieksekusi dengan detached context agar tidak terinterupsi saat request dibatalkan.
  • Audit log merekam status transisi secara terstruktur: PENDING, EXECUTED, FAILED, COMPENSATED, dan COMPENSATE_FAILED.
  • Pengujian go test -race melaporkan hasil bersih tanpa peringatan data race.
  • Dead-letter queue dipersiapkan untuk menampung transaksi yang gagal dikompensasi secara otomatis.

Anti-Pattern Saga: Yang Harus Dihindari di Production

Menghindari circular dependency tidak otomatis menuntaskan thread worker yang hang jika pemanggilan downstream tidak dibatasi timeout. Selain itu, fungsi kompensasi non-idempoten dapat memicu refund ganda saat retry jaringan terjadi. Mengabaikan kompensasi pada langkah non-pivot meninggalkan entitas menggantung, sementara panggilan HTTP sinkron yang lambat di dalam kompensasi dapat memblokir worker pool.

Takeaway Praktis: Command & Runbook untuk Saga Pattern

Perintah di bawah ini merupakan titik awal reproduksi mandiri. Perintah pengujian lokal memberikan baseline verifikasi, tetapi perlu bukti tambahan dari chaos testing sebelum rilis ke production. Runbook operasional wajib memantau status kompensasi yang gagal agar engineer on-call dapat melakukan rekonsiliasi manual.

Prinsip Arsitektural Jangka Panjang: Eventual Consistency sebagai Kontrak

Pola Saga menegaskan bahwa konsistensi eventual adalah kontrak desain yang sah untuk ketersediaan tinggi di sistem terdistribusi. Dengan mengizinkan setiap service memegang kendali penuh atas databasenya sendiri dan menyediakan alur kompensasi yang auditable, sistem terdistribusi mampu bertahan menghadapi kegagalan parsial tanpa harus mengorbankan ketersediaan layanan secara menyeluruh.
