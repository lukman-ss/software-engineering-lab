Ketika Database Terpisah Tidak Bisa Berkomitmen Bersama

Di arsitektur microservices modern, setiap service mengelola database sendiri. Saat flow bisnis melibatkan order-creation, payment-processing, dan inventory-reservation secara berurutan, transaksi ACID klasik yang mengandalkan single database transaction langsung runtuh. Dua-phase commit (2PC) muncul sebagai solusi teoretis, namun protokol ini mengunci semua resource secara sinkron hingga seluruh peserta memberikan suara commit — menyebabkan latency tinggi dan vulnerabilitas terhadap network partition.

Mengapa Pendekatan Naif Gagal Menangani Transaksi Multi-Layanan

Implementasi naif mencoba memanggil setiap service berurutan tanpa mekanisme rollback lintas domain. Jika payment service gagal setelah order berhasil dibuat, database order mencatat status PENDING namun payment mencatat gagal. State sistem menjadi inkonsisten dan tidak ada jalan mundur otomatis. Pendekatan manual ini juga menyulitkan observabilitas karena tidak ada log eksekusi terpusat yang merekam status setiap langkah.

func (o *OrderService) CreateFullOrder(orderID string) error {
    o.CreateOrder(orderID)     // DB-commit #1
    p.ProcessPayment(orderID)  // DB-commit #2 — jika gagal?
    i.ReserveInventory(...)    // DB-commit #3 — jika gagal?
    o.ApproveOrder(orderID)    // DB-commit #4
}

Mental Model: Estafet Transaksi dengan Kompensasi Mundur

Bayangkan proses estafet di mana setiap pelari menyelesaikan bagiannya dan langsung mencatat hasil ke database lokal. Jika pelari ketiga terjatuh, pelari satu dan dua berlari mundur untuk mengembalikan posisi awal mereka. Setiap langkah berdiri sendiri sebagai transaksi lokal yang commit-segera; tidak ada locking lintas layanan. Ketika kegagalan terjadi, orchestrator memicu chain of compensations secara Last-In-First-Out untuk memulihkan konsistensi.

Pipeline Orkestrasi: Dari Langkah Eksekusi Hingga Kompensasi

Pipeline orkestrasi dimulai ketika client mengirimkan request ke orchestrator. Orchestrator mengiterasi daftar langkah secara sekuensial, mengeksekusi setiap langkah ke database lokal masing-masing service. Pada setiap keberhasilan, langkah dicatat ke dalam stack executed. Jika langkah manapun gagal, loop berhenti dan orchestrator memanggil fungsi compensate() yang berjalan mundur dari stack — memastikan refund terjadi sebelum cancel order. Log Status setiap langkah direkam secara atomik di mutex untuk konsistensi konkuren.

Implementasi Inti: Orchestrator Step & LIFO Compensate

Struktur data Step mendefinisikan sepasang fungsi Execute dan Compensate untuk setiap transaksi lokal. Orchestrator menyimpan slice Step ini dan mengeksekusinya secara berurutan. Fungsi compensate() melakukan iterasi mundur dari index terakhir ke nol — inilah inti LIFO rollback. Jika compensate() sendiri gagal pada suatu langkah, error di agregasi ke dalam slice compErrors dan dilaporkan bersama error langkah utama.

type Step struct {
    Name       string
    Execute    func(ctx context.Context) error
    Compensate func(ctx context.Context) error
}

func (o *Orchestrator) compensate(ctx context.Context, executed []Step) error {
    for i := len(executed) - 1; i >= 0; i-- {
        step := executed[i]
        if step.Compensate != nil {
            err := step.Compensate(ctx)  // LIFO unwind
            ...
        }
    }
}

Failure Path: ReserveInventory Gagal — Urutan Kompensasi LIFO

Skenario ini menunjukkan failure path realistis di mana reservasi inventaris gagal karena stok tidak mencukupi. Order sudah dibuat dan payment sudah diproses sebelum kegagalan terdeteksi. Orchestrator kemudian memicu kompensasi LIFO: pertama-tama memproses refund payment, kemudian membatalkan order. Dengan urutan ini, sistem kembali ke keadaan sebelum saga dimulai — payment refund terjadi sebelum order cancel, menjaga konsistensi urutan finansial.

Tabel Perbandingan: Mekanisme Kompensasi vs Gejala Sistem

Tabel ini memetakan taksonomi tiga tipe transaksi saga menurut Azure Architecture Center ke implementasi spesifik lab. Compensation step adalah yang paling umum — setiap langkah kecuali ApproveOrder memiliki fungsi Compensate. Pivot transaction merepresentasikan titik balik yang tidak dapat digagalkan, sedangkan retryable transaction menjamin kesuksesan setelah pivot. Dalam lab ini, ApproveOrder berperan sebagai final step tanpa kompensasi karena ia sudah merupakan state terminal.

Keputusan Arsitektur: Orkestrasi vs Koreografi

Pemilihan antara orkestrasi dan koreografi bukanlah keputusan hitam-putih. Orkestrasi unggul ketika urutan langkah memiliki dependensi ketat dan perlu logging terpusat, seperti pada flow checkout e-commerce. Koreografi lebih cocok untuk sistem event-driven di mana layanan perlu bereaksi mandiri terhadap event tanpa mengetahui orchestrator. Lab ini mengimplementasikan kedua pola untuk menunjukkan trade-off masing-masing.

Batasan Bukti Lab: Yang Dibuktikan vs Belum

Lab ini membuktikan kebenaran logika komputasional dan concurrency safety dalam lingkungan in-memory. Namun, batasan tegas harus diakui: tidak ada simulasi network partition, database crash, atau persistence layer riil. Dalam produksi, kegagalan kompensasi bisa terjadi karena service unavailable — scenario yang tidak tercakup oleh test suite saat ini. Dead-letter queue dan manual reconciliation adalah countermeasures yang diperlukan di luar cakupan lab.

Trade-off Arsitektur: Availability vs Isolation

Saga menukar isolation level tinggi menjadi availability tinggi. Setiap langkah committed segera tanpa lock lintas service, sehingga tidak ada blocking antar layanan. Namun, window inconsistency muncul antara step execute dan kompensasi — order bisa tercatat APPROVED sementara payment belum diproses. Developer harus menulis compensation logic secara eksplisit, menambah complexity aplikasi dibanding solusi monolitik.

Pipeline Konkurensi: Goroutine → Validate → Mutex → Append Error

Keamanan konkuren dicapai melalui strategi snapshot-and-release. Saat Execute dipanggil, orchestrator menyalin slice steps ke variabel lokal sementara mutex dilepaskan, menghindari blocking selama step execution berlangsung. Log append dan read dilindungi mutex individual untuk memastikan konsistensi pembacaan. Test concurrency menjalankan 10 goroutine simultan dengan mutex dan race detector Go melaporkan status bersih tanpa data race.

func (o *Orchestrator) AddStep(step Step) {
    o.mu.Lock()
    defer o.mu.Unlock()
    o.steps = append(o.steps, step)
}

func (o *Orchestrator) Execute(ctx context.Context) error {
    o.mu.Lock()
    steps := make([]Step, len(o.steps))
    copy(steps, o.steps)  // snapshot tanpa lock holder
    o.mu.Unlock()
    // ...execute steps without holding mu during step calls
    o.mu.Lock()
    o.logs = append(o.logs, StepLog{Name: step.Name, Status: ...})
    o.mu.Unlock()
}

Before vs After: Dari Manual Calls ke Saga Orkestrasi

Perbandingan sebelum dan sesudah menunjukkan transformasi fundamental dari state management manual ke orchestration terstruktur. Sebelum saga, kegagalan di satu service meninggalkan state inconsistency yang memerlukan intervensi manual. Setelah saga, orchestrator secara otomatis mencatut log status dan memicu kompensasi berurutan. Setiap langkah memiliki jejak audit trail yang memungkinkan debugging cepat tanpa perlu menggabungkan log dari multiple service.

Service Layer: Semantic Lock, Idempotency, dan Atomic Stock Mutation

Service layer bukan sekadar storage abstraction — setiap service mengandung mekanisme proteksi mandiri. OrderService menggunakan semantic lock untuk mencegah double-creation order dalam satu saga instance. PaymentService mengandalkan idempotency key untuk menangani retry berulang pada payment step. InventoryService menjamin atomicity stock mutation melalui mutex tunggal. Tanpa proteksi ini, saga kompensasi sendiri bisa menimbulkan race condition.

Choreography Pattern: Event Bus Decoupled via Pub/Sub

Choreography pattern menghilangkan koordinator terpusat sepenuhnya. Setiap layanan mendengarkan event dari layanan lain dan bereaksi sesuai handler yang terdaftar. Event bus menggunakan RWMutex untuk keamanan konkuren: Subscribe memegang write lock, Publish memegang read lock sementara menyalin handler slice. Pola ini menghasilkan loose coupling tetapi mengurangi observabilitas karena tidak ada central log eksekusi.

type EventBus struct {
    mu       sync.RWMutex
    handlers map[EventType][]EventHandler
}

func (b *EventBus) Subscribe(t EventType, h EventHandler) {
    b.mu.Lock()
    b.handlers[t] = append(b.handlers[t], h)
    b.mu.Unlock()
}

func (b *EventBus) Publish(ctx context.Context, e Event) {
    b.mu.RLock()
    handlers := append([]EventHandler(nil), b.handlers[e.Type]...)
    b.mu.RUnlock()
    for _, h := range handlers { h(ctx, e) }
}

Bukti Invarian: Idempotency Payment dan Semantic Lock Order

Test idempotency membuktikan bahwa payment service menerima panggilan berulang dengan ID yang sama tanpa melakukan double charge. Test semantic lock membuktikan bahwa order service menolak kreasi order duplikat selama saga instance masih berjalan — mencegah race condition antara concurrent saga instances yang menggunakan orderID sama.

func TestPayment_Idempotency(t *testing.T) {
    paymentSvc := services.NewPaymentService()
    id := "tx-1"
    // First call: records payment
    paymentSvc.ProcessPayment(id, 100, false)
    // Second call with same ID: idempotent no-op
    err := paymentSvc.ProcessPayment(id, 100, false)
    // Must succeed (nil error) — double charge prevented
    if err != nil { t.Fatalf(...) }
}

func TestSemanticLock(t *testing.T) {
    orderSvc := services.NewOrderService()
    id := "ord-lock"
    orderSvc.CreateOrder(id)  // sets locks[id] = true
    err := orderSvc.CreateOrder(id)  // should FAIL
    if err == nil { t.Fatal("second create should fail due to semantic lock") }
}

Enam entri log — dua EXECUTED, satu FAILED, dua COMPENSATED — membentuk sequence yang membuktikan LIFO rollback bekerja sesuai desain. Urutan ini penting untuk debugging: engineer bisa merekonstruksi kronologi exact failure.

Bukti Context Cancellation: Kompensasi Saat Saga Dibatalkan

Test ini memvalidasi perilaku saga ketika context dibatalkan di tengah eksekusi. Context cancellation dideteksi pada select case di loop Execute, menghentikan iterasi sebelum step berikutnya dijalankan. Meskipun context dibatalkan, compensate() tetap dipanggil dengan context.Background() — memastikan kompensasi tidak terhenti oleh cancellation propagation. Step yang sudah dieksekusi pasti dikompensasi, mempertahankan invarian atomicity.

func TestOrchestrator_ContextCancellation(t *testing.T) {
    ctx, cancel := context.WithCancel(context.Background())
    orch := saga.NewOrchestrator()
    step1Compensated := false
    orch.AddStep(saga.Step{
        Name: "Step1",
        Execute: func(ctx context.Context) error {
            cancel() // cancel context before step 2
            return nil
        },
        Compensate: func(ctx context.Context) error {
            step1Compensated = true
            return nil
        },
    })
    orch.AddStep(saga.Step{
        Name: "Step2",
        Execute: func(ctx context.Context) error {
            t.Fatal("step 2 should not execute when context cancelled")
            return nil
        },
    })
    err := orch.Execute(ctx)
    if !step1Compensated { t.Fatal("expected step 1 compensated") }
}

Checklist Implementasi Saga Pattern yang Benar

Checklist ini merangkum delapan persyaratan kritis untuk implementasi saga pattern yang production-ready. Poin paling sering terlewat adalah idempotensi kompensasi — jika compensate() dipanggil dua kali, sistem harus tetap stabil. Poin keenam tentang dead-letter queue juga krusial: compensation failure permanen memerlukan mekanisme manual intervention yang harus direncanakan sebelum deployment.

Anti-Pattern Saga: Yang Harus Dihindari di Production

Empat anti-pattern ini paling umum ditemukan di implementasi saga production. Non-idempotent compensate adalah penyebab utama double-refund yang merugikan financial reconciliation. Circular dependency antara kompensasi step menciptakan infinite loop yang melumpuhkan orchestrator. Missing compensate pada final step berarti approval state permanen meskipun step lain dikompensasi. Blocking long-running compensate mengunci goroutine orchestrator dan mencegah step selanjutnya dieksekusi.

Takeaway Praktis: Command & Runbook untuk Saga Pattern

Takeaway praktis untuk engineer yang mengadopsi saga pattern di production: command di atas adalah titik awal reproduksi mandiri. Prinsip operasional ketiga poin terakhir merupakan panduan monitoring yang harus diimplementasikan sebelum go-live. Compensation failure yang masuk ke DLQ harus diproses secara manual oleh on-call engineer dengan konsol admin — tidak ada fully-automatic resolution untuk semua kasus.

# Jalankan seluruh test suite
go test -v ./...

# Verifikasi race condition
go test -race -v ./...

# Demo interaktif (happy path + rollback)
go run ./cmd/demo

# Production runbook:
# 1. Monitor orch.Logs() untuk STATUS_FAILED / STATUS_COMPENSATE_FAILED
# 2. Alert on COMPENSATE_FAILED → trigger DLQ processing
# 3. Manual reconciliation via admin console for stuck compensations
# 4. Regular healthcheck: verify all in-flight sagas reached terminal state
