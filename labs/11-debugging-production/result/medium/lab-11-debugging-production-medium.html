Debugging Production: Uji Hipotesis, Bukan Tebak Penyebab

Membaca batas pengukuran, mengisolasi bottleneck, dan memverifikasi perubahan lewat simulasi Go.

Lukman / lukman-ss · Software Engineering Lab 11

Endpoint purchase orders untuk rentang satu tahun terasa lambat. Di skenario README, pengguna akhirnya melihat 504 Gateway Timeout. Respons spontan mungkin menyalahkan database atau menambah timeout. Lab 11 mengajak kita berhenti sejenak: gejala belum menjelaskan bagian mana yang menghabiskan waktu, apalagi alasan bagian itu lambat.

Mental model-nya sederhana: Debugging is testing hypotheses, not guessing causes. Buat dugaan yang bisa diperiksa, kumpulkan bukti dengan makna yang jelas, lalu ubah satu variabel. Bahkan nama field pengukuran perlu diperiksa sebelum dipakai untuk menyimpulkan penyebab.

Pahami apa yang benar-benar dijalankan

Repository menyediakan tiga file utama: README.md, main.go, dan main_test.go. Implementasinya adalah simulasi berlapis Handler, Service, dan Repository. Test memanggil HandleGetOrders secara langsung. Tidak ada HTTP server, router, load balancer, query database, atau JSON marshaling dalam folder lab ini. Karena itu, 504 adalah konteks masalah di README, bukan respons HTTP yang direproduksi test.

SlowRepository menunggu empat detik ketika rangeType persis "1y". Untuk nilai lain, ia menunggu sepuluh milidetik. FastRepository selalu menunggu sepuluh milidetik. Keduanya mengembalikan satu purchase order yang sama: ID po-1 dan Amount 100. Range tahunan mengubah delay, bukan jumlah baris hasil. Tidak ada filtering tanggal atau validasi range.

// main.go: isi SlowRepository.FetchOrders
if rangeType == "1y" {
    time.Sleep(4 * time.Second)
} else {
    time.Sleep(10 * time.Millisecond)
}
return []PurchaseOrder{{ID: "po-1", Amount: 100}}, nil

Missing index atau query tidak efisien disebut sebagai analogi di README. Kode ini tidak memiliki database untuk membuktikan keduanya. Penyebab delay yang dapat ditunjuk langsung pada simulasi adalah time.Sleep empat detik. Perbedaan antara analogi dan bukti implementasi ini penting agar latihan tidak berubah menjadi cerita insiden yang tidak pernah diukur.

Mulai dari reproduksi yang spesifik

TestReproduceBug merangkai handler dengan SlowRepository lalu memanggil range "1y". Test gagal jika TotalDuration kurang dari empat detik. Secara tepat, assertion menerima durasi minimal empat detik, meskipun pesan error memakai tulisan "> 4s". Reproduksi ini mempersempit kondisi yang sedang diperiksa: repository lambat, input tahunan, dan jalur sukses.

cd labs/11-debugging-production
go test -v -run TestReproduceBug
go test -v -run TestCollectEvidence
go test -v -run TestVerifyFix

Perintah di atas mengikuti README, dijalankan dari salinan repository dengan Go yang sesuai go.mod root (Go 1.25.0). Go tidak tersedia di lingkungan penyusunan artikel ini, sehingga test dibaca, bukan dijalankan. Tidak ada klaim passing atau angka benchmark aktual dalam pembahasan berikut.

Tulis hipotesis, lalu tentukan buktinya

Hipotesis READMEPertanyaan yang harus dijawab
H1: handler / JSONApakah pekerjaan handler memang yang menghabiskan waktu? JSON tidak diimplementasikan di sini.
H2: serviceApakah durasi berasal dari pekerjaan service sendiri, atau waktu menunggu repository?
H3: repositoryApakah mengganti repository, dengan input dan layer lain tetap, mengubah jalur lambat?

Ketiga dugaan itu membantu mengatur investigasi. Namun, angka service yang besar tidak langsung mendukung H2: service bisa sekadar menunggu dependency. Demikian juga, waktu persiapan handler yang kecil tidak membuktikan bahwa JSON cepat pada server sungguhan, karena serialisasi sama sekali tidak dilakukan oleh simulasi ini.

Baca batas timer sebelum membaca nilainya

ServiceDuration mencakup repository

// main.go: isi Service.GetOrders
start := time.Now()
time.Sleep(10 * time.Millisecond)
orders, err := s.repo.FetchOrders(ctx, rangeType)
dur := time.Since(start)
return orders, dur, err

Timer dimulai sebelum pekerjaan service dan berhenti sesudah FetchOrders selesai. ServiceDuration bersifat inklusif: ada waktu service sekaligus waktu repository di dalamnya. Jika repository menunggu empat detik, durasi service ikut tinggi. Ini bukan bukti bahwa business logic service sendiri membutuhkan empat detik.

RepositoryDuration adalah nilai turunan

// main.go: cuplikan HandleGetOrders
totalDur := time.Since(totalStart)
repoDur := svcDur - 10*time.Millisecond

RepositoryDuration tidak berasal dari timer terpisah yang membungkus FetchOrders. Kode mengurangi konstanta sepuluh milidetik dari durasi service. Jika sleep service berlangsung lebih lama atau ada overhead lain, selisih itu ikut masuk ke estimasi repository. Nilai turunan ini berguna untuk memahami demo, tetapi jangan menyebutnya pengukuran independen.

FieldCakupan aktual
HandlerDurationHanya persiapan handler, termasuk sleep 5 ms.
ServiceDurationPekerjaan service dan pemanggilan repository.
RepositoryDurationServiceDuration dikurangi konstanta 10 ms.
TotalDurationRentang keseluruhan jalur sukses handler.

Jangan menjumlahkan ketiga durasi layer untuk mendapatkan total. Menambahkan ServiceDuration dan RepositoryDuration akan menghitung waktu repository dua kali. Nama field yang terdengar sejajar tidak berarti jendela waktunya saling terpisah. Pertanyaan pertama untuk setiap metrik adalah: timer mulai dan berhenti di mana?

Jangan menyalin contoh log sebagai hasil eksperimen

README menampilkan contoh service_duration=12ms dan repository_duration=4200ms. Pasangan ini tidak konsisten dengan implementasi sekarang: repository_duration selalu dihitung dari service_duration dikurangi 10 ms. Contoh tersebut tidak dapat dipakai sebagai output aktual fungsi ini.

JalurJumlah sleep yang dikonfigurasi
SlowRepository, 1y5 + 10 + 4000 = 4015 ms
SlowRepository, selain 1y5 + 10 + 10 = 25 ms
FastRepository, 1y5 + 10 + 10 = 25 ms

Tabel ini adalah aritmetika konfigurasi, bukan hasil pengukuran. Waktu aktual dipengaruhi penjadwalan dan overhead. Klaim README bahwa jalur 1m kurang dari 20 ms juga tidak selaras dengan jumlah sleep 25 ms pada kode. Membandingkan narasi dengan implementasi adalah bagian dari membaca bukti, bukan detail kosmetik.

TestCollectEvidence mencetak field durasi, tetapi tidak meng-assert bahwa repository adalah bottleneck. Baris request_id=abc123 juga hardcoded. Ia tidak menunjukkan sistem pembentukan ID unik atau tracing lintas request. Log membantu mengamati; log saja bukan assertion otomatis maupun bukti korelasi production.

Ubah satu variabel, verifikasi klaim yang terbatas

TestVerifyFix mengganti SlowRepository dengan FastRepository. Range tetap "1y", handler dan service tetap sama. Dengan menahan bagian lain tetap, latihan mengisolasi delay pada implementasi repository. Ini lebih informatif daripada mengubah handler, service, dan repository sekaligus lalu hanya melihat total membaik.

// main_test.go: assertion TestVerifyFix
if res.TotalDuration > 100*time.Millisecond {
    t.Fatalf("expected request to be fast (< 100ms), but took %v", res.TotalDuration)
}

Assertion menerima durasi sampai 100 ms, termasuk tepat 100 ms. Batas ini merupakan kriteria test lab, bukan SLO production atau jaminan latency. Karena memakai waktu nyata, hasil test juga dapat dipengaruhi lingkungan eksekusi. Mengganti sleep lambat dengan sleep cepat bukan bukti bahwa sebuah index database sudah diperbaiki atau perubahan sudah dirilis.

Catat apa yang belum dibuktikan

Ketiga test hanya memakai range "1y" dan context.Background. Tidak ada assertion isi purchase order, pengujian 1m, pembatalan context, atau respons HTTP 504. Walaupun context diteruskan, kedua repository tidak memeriksanya dan time.Sleep tidak dibuat responsif terhadap cancellation. Jangan menyimpulkan dukungan timeout hanya karena signature menerima context.

Interface juga mengembalikan error, tetapi kedua implementasi selalu mengembalikan nil. Jika error terjadi, handler mengembalikan RequestResult kosong sehingga timing tidak ikut dikembalikan. Jalur itu belum diuji dengan repository yang gagal. Pemeriksaan tambahan tersebut adalah calon pengembangan, bukan fitur yang sudah tersedia.

Pelajaran yang bisa dibawa keluar dari lab

Mulai dengan kondisi reproduksi yang jelas. Pisahkan fakta implementasi, contoh dokumentasi, dan asumsi. Tulis hipotesis beserta bukti yang dapat membantahnya. Pastikan batas timer sesuai pertanyaan, lalu lakukan perubahan terkontrol dan verifikasi hasil dengan kriteria eksplisit.

Kesimpulan lab ini cukup spesifik: delay buatan pada repository menjelaskan jalur lambat yang dimodelkan. Kita belum mendiagnosis database production. Disiplin menyatakan batas kesimpulan itulah inti hypothesis-driven debugging: bukti menentukan seberapa jauh sebuah klaim boleh dibuat.
