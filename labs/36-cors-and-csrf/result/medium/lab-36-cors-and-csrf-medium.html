Miskonsepsi Fatal: CORS Bukan Firewall

Banyak tim backend mengira CORS adalah pelindung mutasi endpoint. Padahal, CORS hanya mengatur izin JavaScript untuk membaca respons. Mutasi status database langsung dieksekusi sebelum browser menilai header CORS.

Serangan CSRF mengeksploitasi kepercayaan ambient cookie. Ketika form tersembunyi disubmit lintas origin, browser melampirkan kredensial sessi korban secara otomatis. Server backend mengeksekusi transfer dana hingga tuntas. Meskipun browser kemudian menolak memberikan isi response kepada penyerang, mutasi saldo sudah selesai dicatat.

Core Mental Model: SOP vs CORS vs CSRF

Three pillars of web security: SOP blocks cross-origin reads, CORS relaxes read restrictions, CSRF exploits unrestricted cross-origin writes via ambient credentials.

Same-Origin Policy (SOP) melarang script membaca respons dari origin berbeda. Namun, SOP secara historis memperbolehkan outbound write request seperti form submit. CORS hadir sebagai mekanisme negosiasi, mengizinkan server menyatakan origin mana yang boleh membaca data API. CSRF manfaatkan ketidakseimbangan ini: penyerang tidak butuh membaca reply untuk mencurigai aset atau mengubah rekaman.

  • POST /api/transfer/vulnerable: Transfer rentan hanya dengan middleware CORS
  • POST /api/transfer/protected: Transfer aman dengan proteksi token
  • POST /api/transfer/fetch-metadata: Transfer aman via Sec-Fetch-Site
  • POST /api/transfer/custom-header: Transfer aman dengan X-Requested-With

Simple Request vs Preflight OPTIONS

Browser membedakan request menjadi simple request dan preflighted request. Simple request langsung dikirim, sementara preflight requests memerlukan permission dulu.

Simple request menggunakan GET, HEAD, atau POST dengan encoding standar (`application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`). Request ini dikirim langsung tanpa konfirmasi awal. Non-simple request (method PUT/DELETE/PATCH, content-type application/json, atau custom header) memicu preflight OPTIONS terlebih dahulu untuk mendapatkan izin CORS.

Anatomi Serangan CSRF

CSRF mengeksploitasi kepercayaan server terhadap sessi browser korban. Ketika form submit tersembunyi dipicu dari situs penyerang, browser melampirkan cookie sessi secara otomatis. Server bank mengeksekusi transfer tersebut hingga tuntas.

Lima langkah eksploitasi:

  1. Korban login ke bank, memegang cookie sessi aktif
  2. Korban membuka tab situs penyerang (evil-attacker.com)
  3. Halaman jahat menjalankan form submit tersembunyi
  4. Browser melampirkan cookie sessi korban ke request POST bank
  5. Server memvalidasi cookie dan mengeksekusi transfer dana
Mereka tidak butuh membaca response; saldo korban sudah terlanjur lenyap.

Bukti Empiris: CORS Tidak Mencegah Eksekusi

POST request lintas origin mengubah status backend terlepas dari konfigurasi CORS. Endpoint vulnerable mengembalikan 200 OK dan menarik $300 dari korban walaupun tanpa header Access-Control-Allow-Origin.

req := httptest.NewRequest(POST, "/api/transfer/vulnerable", body)
req.Header.Set("Origin", "https://evil-attacker.com")
req.AddCookie(&http.Cookie{Name: "session_id", Value: "session-victim-secret"})

app.ServeHTTP(rec, req)
// Response: 200 OK!
// Header Access-Control-Allow-Origin: Omitted
// Victim Balance: $1000 → $700!

Implementasi Middleware CORS Standar W3C

CORS middleware mengikuti spesifikasi W3C Fetch. Origin yang tidak terdaftar ditolak pada preflight OPTIONS, namun simple request diteruskan ke handler berikutnya.

if !m.isOriginAllowed(origin) {
    if r.Method == http.MethodOptions {
        w.WriteHeader(http.StatusForbidden); return
    }
    next.ServeHTTP(w, r) // Non-preflight diteruskan!
}

ATuran spesifikasi: Jika AllowCredentials: true, wildcard '*' dilarang keras oleh browser.

Aturan Kredensial & Wildcard Origin

Spesifikasi web larang Access-Control-Allow-Origin: * dengan Access-Control-Allow-Credentials: true. Jika kredensial disertakan, server harus merefleksikan origin secara eksplisit.

Jika backend menggabungkan `Access-Control-Allow-Origin: *` dengan `Access-Control-Allow-Credentials: true`, browser otomatis menolak respons dan menyembunyikan data dari JavaScript clients untuk mencegah kebocoran kredensial tidak sengaja ke seluruh web.

Multi-Layer Anti-CSRF Defense Architecture

Pertahanan CSRF tangguh tidak boleh bergantung pada satu mekanisme tunggal. Kombinasikan Signed Token, Fetch Metadata, Custom Header, dan SameSite Cookie.

Signed Double-Submit CSRF Token (HMAC)

Pattern Signed Double-Submit menghasilkan proteksi CSRF tanpa beban memori. Token menggabungkan Session ID, timestamp, dan nonce yang ditandatangani HMAC-SHA256.

Payload:   sessionID : timestamp : nonce
Signature: HMAC-SHA256(secret_key, payload)
Token:     base64(payload : base64(signature))

Keuntungan:

  • Stateless: Server tidak perlu menyimpan token di Redis
  • Kriptografi Terikat: Terikat pada ID sesi pengguna
  • Anti-Replay: Dilengkapi TTL yang datang

Token Generation & Validation in Go

Validator memeriksa kecocokan Session ID, masa berlaku timestamp, dan HMAC signature menggunakan constant-time compare untuk mencegah timing attack.

Anti-CSRF Middleware in HTTP Handler

Middleware CSRF menolak request mutasi tanpa token valid. GET, HEAD, OPTIONS dilewati gratis. POST, PUT, DELETE memerlukan token dari header atau form body.

if r.Method == GET || r.Method == HEAD || r.Method == OPTIONS {
    next.ServeHTTP(w, r); return
}
token := r.Header.Get("X-CSRF-Token")
if token == "" { token = r.PostFormValue("csrf_token") }
if err := m.tokenManager.ValidateToken(token, cookie.Value); err != nil {
    http.Error(w, "Forbidden: CSRF validation failed", 403); return
}

Fetch Metadata: Leveraging Sec-Fetch-Site

Header Sec-Fetch-Site ditentukan browser dan tidak dapat diubah JavaScript. Nilai cross-site pada method mutasi otomatis ditolak.

fetchSite := r.Header.Get("Sec-Fetch-Site")
if fetchSite == "cross-site" && r.Method != GET && r.Method != HEAD {
    http.Error(w, "Forbidden: Cross-site rejected", 403)
    return
}

Nilai:

  • same-origin: Request dari origin yang sama (Aman)
  • same-site: Request dari subdomain dalam domain yang sama
  • cross-site: Request dari situs luar (Waspada!)
  • none: Navigasi langsung user (misal ketik URL di address bar)

API Custom Header Enforcement

Mengharuskan header kustom seperti X-Requested-With mematikan eksploitasi CSRF klasik. Form HTML standar tidak bisa mengirim header custom.

val := r.Header.Get("X-Requested-With")
if val == "" || !strings.EqualFold(val, "XMLHttpRequest") {
    http.Error(w, "Forbidden: Missing custom header", 403)
    return
}

Mengapa efektif: Form HTML tidak bisa menyetel custom HTTP headers. Hanya JavaScript (fetch/axios) yang dapat menambahkannya, yang secara otomatis memicu preflight OPTIONS.

Cookie SameSite Attributes: Lax vs Strict

SameSite=Lax menahan cookie pada request POST lintas situs. Namun, cookie tetap dikirim pada navigasi GET top-level, sehingga endpoint GET harus read-only.

SameSite=Strict: Cookie tidak pernah dikirim pada request lintas situs. Sangat aman, namun mengorbankan kenyamanan login eksternal.

SameSite=Lax (default modern browser): Cookie ditahan pada cross-site POST, tetapi tetap dikirim pada top-level GET navigation. Endpoint GET wajib idempotent dan tidak boleh memutasi state!

XSS Defeats Anti-CSRF

Jika aplikasi punya celah XSS, seluruh pertahanan CSRF runtuh. Script yang disuntik berjalan di origin yang sah dan bisa membaca token CSRF.

Jika penyerang menemukan celah Stored/Reflected XSS pada domain target, script tersebut dieksekusi di dalam context origin yang sah. Karena berada di origin yang sama, SOP mengizinkan script membaca token CSRF secara sah dan mengeksekusi transaksi atas nama korban.

XSS adalah kerentanan tingkat origin yang mengalahkan seluruh pertahanan CSRF.

Lab 36 Model Boundaries & Constraints

Lab menyederhanakan infrastruktur produksi untuk kelancaran. Kunci HMAC di-hardcode, token diurai menggunakan string delimiter sederhana.

  • Batas 1: SECRET KEY IN-MEMORY - Produksi wajib AWS Secrets Manager, Vault, dan key rotation
  • Batas 2: DELIMITER STRING - Jika sessionID mengandung ':', parsing token akan terganggu. Produksi butuh JSON, Protobuf, atau hex encoding
  • Batas 3: LINGKUP BROWSER - HTTP client non-browser tidak terikat aturan SOP, CORS, CSRF

Security Audit Checklist: CORS & CSRF

Gunakan checklist ini saat review keamanan backend. Pastikan GET read-only, CORS whitelist eksplisit, token HMAC terikat sesi, dan cookie SameSite.

  • [x] GET, HEAD, OPTIONS bebas dari mutasi database
  • [x] CORS whitelist hanya domain tepercaya (tanpa refleksi liar)
  • [x] AllowCredentials: true TIDAK PERNYA dengan origin '*'
  • [x] Semua endpoint mutasi dilindungi Anti-CSRF Token
  • [x] Token CSRF ditandatangani HMAC-SHA256, terikat Session ID, punya TTL
  • [x] Validasi signature menggunakan subtle.ConstantTimeCompare
  • [x] Cookie otentikasi: HttpOnly, Secure, SameSite=Lax
  • [x] API gateway verifikasi Sec-Fetch-Site & Custom Header
  • [x] Aplikasi dilindungi dari XSS via Content Security Policy (CSP)

Three Core Cross-Origin Security Principles

Jangan pernah mempercayai CORS untuk jaga integritas database. Selalu ikat token CSRF ke ID sesi secara kriptografis, dan terapkan defense-in-depth.

  1. Never Trust Client Boundaries for Server Integrity: CORS adalah aturan kepatuhan browser, bukan pelindung integritas database.
  2. Bind Tokens Cryptographically to Sessions: Token harus terikat secara kriptografis ke identitas sesi aktif.
  3. Defense in Depth Wins: Kombinasikan Signed Token, SameSite Cookie, Fetch Metadata, dan Custom Header.
