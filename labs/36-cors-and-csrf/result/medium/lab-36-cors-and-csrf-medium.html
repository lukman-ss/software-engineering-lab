Miskonsepsi Fatal: CORS Bukan Firewall

Miskonsepsi bahwa CORS bertindak sebagai firewall backend masih sangat umum ditemukan. Padahal, CORS dirancang oleh browser murni untuk mengontrol izin pembacaan respons oleh JavaScript, bukan membatasi server dalam memproses request. Tanpa pertahanan CSRF di backend, penyerang dapat memicu mutasi state di database hanya melalui tag form HTML biasa.

Mental Model: SOP vs CORS vs CSRF

Arsitektur keamanan web berdiri di atas tiga pilar ini. SOP melarang pembacaan respons lintas origin. CORS hadir sebagai mekanisme izin agar JavaScript dapat membaca data respons tersebut. Sementara itu, CSRF mengeksploitasi izin pengiriman data form yang secara historis diizinkan oleh SOP dengan memanfaatkan cookie sesi yang terlampir otomatis.

Topologi Arsitektur Simulasi Bank

Lab 36 mengimplementasikan bank service lengkap di internal/bank/app.go. Terdapat endpoint transfer yang sengaja dibiarkan rentan hanya dengan middleware CORS, serta varian endpoint terlindungi yang dibungkus oleh Anti-CSRF Token, Fetch Metadata, dan Custom Header middleware untuk membandingkan perilaku eksekusinya secara langsung.

Simple Request vs Preflight OPTIONS

Standar WHATWG Fetch membedakan request menjadi simple request dan non-simple request. Simple request menggunakan method standar dan encoding form tanpa custom header, sehingga dikirimkan langsung oleh browser tanpa konfirmasi awal. Sebaliknya, non-simple request memicu preflight OPTIONS. Penyerang CSRF memanfaatkan sifat simple request untuk mengeksekusi mutasi server seketika.

Anatomi Serangan Cross-Site Request Forgery

Serangan CSRF mengeksploitasi kepercayaan server terhadap browser korban. Ketika form submit otomatis dipicu dari situs penyerang, browser melampirkan cookie sesi milik korban. Server bank memproses transfer tersebut hingga tuntas. Walaupun browser kemudian menolak memberikan isi response kepada penyerang karena aturan CORS, mutasi saldo sudah selesai dicatat di database.

Bukti Empiris: CORS Tidak Mencegah Eksekusi

Pengujian TestIntegration_CORS_Does_Not_Prevent_CSRF_Execution membuktikan realitas ini secara definitif. Request POST dari origin evil-attacker.com berhasil memicu pemotongan saldo korban sebesar $300 dan menambah saldo penyerang. Meskipun middleware CORS tidak menyertakan header Access-Control-Allow-Origin, mutasi transaksi telah tuntas.

req := httptest.NewRequest(POST, "/api/transfer/vulnerable", body)
req.Header.Set("Origin", "https://evil-attacker.com")
req.AddCookie(&http.Cookie{Name: "session_id", Value: "session-victim-secret"})

app.ServeHTTP(rec, req)
// Response: 200 OK!
// ACAO Header: Kosong (ditolak untuk evil-attacker.com)
// Saldo Korban: Turun dari $1000 menjadi $700!

Implementasi Middleware CORS Standar W3C

Di dalam internal/cors/middleware.go, kepatuhan terhadap spesifikasi W3C Fetch terlihat jelas. Ketika origin tidak terdaftar, request preflight OPTIONS langsung ditolak dengan HTTP 403. Namun, untuk request non-preflight (seperti simple POST), middleware harus meneruskan request ke handler berikutnya tanpa menyertakan header ACAO.

if !m.isOriginAllowed(origin) {
    if r.Method == http.MethodOptions {
        w.WriteHeader(http.StatusForbidden); return
    }
    next.ServeHTTP(w, r) // Non-preflight tetap diteruskan!
    return
}
if m.config.AllowCredentials {
    w.Header().Set("Access-Control-Allow-Origin", origin)
    w.Header().Set("Access-Control-Allow-Credentials", "true")
}

Aturan Kredensial & Wildcard Origin

Spesifikasi web secara eksplisit melarang penggunaan Access-Control-Allow-Origin: * jika Access-Control-Allow-Credentials bernilai true. Jika server melanggar aturan ini, browser otomatis menolak respons. Backend wajib merefleksikan origin secara selektif hanya jika origin tersebut telah terverifikasi dalam whitelist aman.

Arsitektur Pertahanan CSRF Multi-Layer

Pertahanan CSRF yang tangguh tidak boleh bergantung pada satu mekanisme tunggal. Pendekatan defense-in-depth menggabungkan Signed Double-Submit Token berbasis HMAC, verifikasi Fetch Metadata dari browser, penegakan header custom untuk API AJAX, serta konfigurasi cookie SameSite yang ketat pada sisi klien.

Signed Double-Submit Token (HMAC-SHA256)

Pola Signed Double-Submit Token menggabungkan efisiensi stateless dengan integritas kriptografis. Payload token berisi Session ID, timestamp pembuatan, dan random nonce 16-byte yang ditandatangani dengan HMAC-SHA256. Penyerang yang menguasai subdomain tidak dapat memalsukan token karena tidak memiliki secret key server.

Implementasi Generate & Validate Token

Method ValidateToken() di internal/csrf/token.go menjalankan validasi berlapis. Token diurai menjadi empat komponen. Validator memeriksa kecocokan Session ID, memastikan timestamp belum kedaluwarsa, dan menghitung ulang HMAC signature. subtle.ConstantTimeCompare digunakan untuk mencegah penyerang membongkar signature via timing attack.

parts := strings.Split(string(decoded), ":")
sessionID, tsStr, nonceStr, sigB64 := parts[0], parts[1], parts[2], parts[3]
if sessionID != expectedSessionID { return ErrInvalidToken }

ts, err := strconv.ParseInt(tsStr, 10, 64)
if err != nil || time.Since(time.Unix(ts, 0)) > tm.ttl {
    return ErrExpiredToken
}
expectedSig := hmac.New(sha256.New, tm.secret).Sum(payload)
if subtle.ConstantTimeCompare(actualSig, expectedSig) != 1 {
    return ErrInvalidToken

Middleware Proteksi CSRF di HTTP Handler

Middleware CSRF bertindak sebagai gerbang pengaman mutasi data. Request dengan method aman (GET, HEAD, OPTIONS) langsung dilewatkan. Untuk method mutasi (POST, PUT, DELETE), middleware mengekstrak cookie sesi dan mengambil token CSRF dari header atau form field. Jika token tidak cocok atau kedaluwarsa, server menolak dengan HTTP 403 Forbidden.

if r.Method == GET || r.Method == HEAD || r.Method == OPTIONS {
    next.ServeHTTP(w, r); return
}
cookie, err := r.Cookie(m.cookieName)
if err != nil || cookie.Value == "" {
    http.Error(w, "Unauthorized: missing cookie", 401); return
}
token := r.Header.Get("X-CSRF-Token")
if token == "" { token = r.PostFormValue("csrf_token") }

if err := m.tokenManager.ValidateToken(token, cookie.Value); err != nil {
    http.Error(w, "Forbidden: CSRF validation failed", 403); return
}

Fetch Metadata: Memanfaatkan Sec-Fetch-Site

Fetch Metadata merupakan standar W3C modern di mana browser melampirkan header Sec-Fetch-Site pada setiap request keluar. Header ini bernilai cross-site jika dipicu dari domain luar. Karena header ini dikelola langsung oleh mesin browser dan dilindungi dari manipulasi JavaScript, backend dapat menolak request mutasi cross-site tanpa perlu token sama sekali.

fetchSite := r.Header.Get("Sec-Fetch-Site")
if fetchSite == "cross-site" {
    if r.Method != GET && r.Method != HEAD && r.Method != OPTIONS {
        http.Error(w, "Forbidden: Cross-site rejected", 403)
        return
    }
}

Custom Header Enforcement untuk API

Salah satu pertahanan paling sederhana namun ampuh untuk API backend adalah mewajibkan header kustom seperti X-Requested-With: XMLHttpRequest. Karena tag form HTML standar di browser tidak memiliki kemampuan menambahkan custom header HTTP, seluruh upaya eksploitasi form CSRF klasik langsung gagal sebelum mencapai handler bisnis.

func RequireCustomHeaderMiddleware(headerKey, expectedValue string) {
    val := r.Header.Get(headerKey)
    if val == "" || !strings.EqualFold(val, expectedValue) {
        http.Error(w, "Forbidden: Missing custom header", 403); return
    }
}

Peran Atribut Cookie SameSite: Lax vs Strict

Atribut SameSite pada cookie menentukan kapan browser diizinkan melampirkan cookie sesi. SameSite=Lax yang menjadi default browser modern menahan cookie pada request POST lintas situs. Namun, karena cookie tetap dikirim pada navigasi top-level GET, sistem tidak boleh melakukan mutasi saldo atau perubahan data melalui method GET.

Ancaman Tersembunyi: XSS Melumpuhkan CSRF

Penting untuk diingat bahwa seluruh pertahanan anti-CSRF (baik token, SameSite, maupun Fetch Metadata) runtuh jika aplikasi memiliki kerentanan Cross-Site Scripting (XSS). Jika penyerang dapat menyuntikkan script ke origin target, script tersebut memiliki hak istimewa SOP untuk membaca token CSRF secara sah dan mengeksekusi transaksi atas nama korban.

Batasan Model & Implementasi Lab 36

Lab ini menyederhanakan beberapa aspek infrastruktur untuk menjaga fokus edukasi. Kunci rahasia HMAC di-hardcode dalam memori, dan token diurai menggunakan string delimiter sederhana. Dalam sistem produksi riil, kunci HMAC wajib dikelola melalui key management service dan token sebaiknya menggunakan format terstruktur seperti JSON Web Signature (JWS) atau Protobuf.

Checklist Audit Keamanan CORS & CSRF

Gunakan checklist ini saat melakukan security audit pada sistem web Anda. Pastikan endpoint GET bebas dari efek samping mutasi data, jangan pernah menggabungkan wildcard CORS dengan kredensial, wajibkan validasi token HMAC yang terikat ke sesi pada setiap mutasi POST, dan perkuat perimeter dengan header Sec-Fetch-Site serta cookie SameSite.

Tiga Prinsip Inti Keamanan Cross-Origin

Menjaga keamanan backend menuntut pemahaman arsitektural yang jelas. Jangan pernah mempercayai CORS untuk menjaga integritas database. Selalu ikat token CSRF ke ID sesi pengguna secara kriptografis, dan terapkan arsitektur pertahanan berlapis untuk menangkal berbagai vektor serangan lintas origin secara efektif.
