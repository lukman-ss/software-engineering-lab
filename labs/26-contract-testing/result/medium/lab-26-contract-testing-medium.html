Contract Testing: Consumer-Driven Contracts & CI/CD Deployment Gates di Go

Memindahkan verifikasi kompatibilitas API dari staging runtime ke pipeline build yang deterministik dengan deteksi breaking change otomatis.

Lukman / lukman-ss · Software Engineering Lab 26

1. Pendahuluan / Latar Belakang

Dalam arsitektur layanan mikro terdistribusi, komunikasi antar-layanan melalui protokol HTTP REST merupakan fondasi utama interaksi sistem. Namun, kecepatan rilis yang tinggi pada masing-masing repositori sering kali memicu kekhawatiran integrasi: apakah perubahan struktur payload JSON yang dirilis oleh tim penyedia layanan (provider) akan merusak logika parsing yang telah dibangun oleh tim aplikasi konsumen (consumer)?

Pendekatan tradisional untuk memverifikasi kompatibilitas antarmuka ini biasanya bertumpu pada dua kutub ekstrem: pengujian unit dengan mock di sisi lokal, atau pengujian menyeluruh (End-to-End/E2E testing) di lingkungan staging terintegrasi. Kedua pendekatan ini memiliki kelemahan mendasar. Pengujian unit berbasis mock lokal sangat cepat, namun mock yang dirawat secara manual cenderung mengalami pergeseran (drift) dan cepat usang dibanding implementasi backend yang sebenarnya. Sebaliknya, suite pengujian E2E di lingkungan staging membutuhkan seluruh kluster layanan mikro, antrean pesan, dan basis data aktif secara bersamaan. Akibatnya, pengujian E2E sangat lambat, membutuhkan biaya infrastruktur yang mahal, dan rentan terhadap kegagalan jaringan acak (flaky tests).

Consumer-Driven Contract (CDC) testing hadir sebagai solusi yang mengisi celah di antara kedua metode tersebut. Pola ini membalikkan arah kendali perancangan kontrak: konsumen menyatakan secara eksplisit subset skema payload dan interaksi HTTP yang benar-benar dibutuhkannya, lalu membungkus ekspektasi tersebut ke dalam sebuah artefak kontrak. Artefak kontrak ini kemudian diuji secara langsung terhadap penyedia layanan di dalam pipeline Continuous Integration (CI) milik provider sebelum artefak biner dipublikasikan atau dideploy ke kluster produksi.

Lab 26 mengimplementasikan arsitektur CDC dan gerbang deployment (deployment gate) ini secara murni menggunakan pustaka standar bahasa Go (standard library). Tanpa memerlukan dependensi daemon eksternal seperti Ruby atau binary Pact yang berat, implementasi ini mendemonstrasikan secara transparan bagaimana kontrak konsumen dibuat, bagaimana mesin verifikasi memeriksa kepatuhan provider, dan bagaimana gerbang CI mampu memblokir rilis berbahaya secara otomatis dalam hitungan milidetik.

2. Masalah yang Diselesaikan: Tiga Skenario Mutasi Payload Berbahaya

Untuk memahami urgensi dari contract testing, kita meneliti skenario nyata interaksi antara dua layanan di dalam Lab 26: MobileApp sebagai konsumen dan OrderService sebagai penyedia data pesanan. Konsumen seluler memiliki DTO lokal bernama MobileOrderSummary yang memetakan subset informasi dari endpoint GET /v1/orders/{id}:

// internal/consumer/client.go: DTO Konsumen
type MobileOrderSummary struct {
    ID           string
    Status       string
    CustomerName string
    Total        int64
}

Perhatikan bahwa konsumen hanya membutuhkan empat atribut ini untuk menampilkan kartu ringkasan pesanan di layar perangkat bergerak. Penyedia layanan sebenarnya mengembalikan field tambahan seperti customer.id dan notes, namun konsumen secara sadar mengabaikan field-field tersebut.

Masalah kritis terjadi ketika tim backend penyedia layanan melakukan optimasi atau refaktorisasi internal tanpa menyadari ketergantungan konsumen. Lab 26 memodelkan tiga jenis perubahan yang merusak (breaking changes) yang sering terjadi di industri:

  1. Perubahan Casing Nilai Enum (Enum Value Casing Mutation): Backend memutuskan untuk menstandardisasi nilai status order dari huruf kapital penuh (IN_PROGRESS) menjadi huruf kecil (in_progress). Bagi tim backend, arti semantiknya tidak berubah. Namun, klien seluler menerapkan validasi status yang ketat: jika status bukan IN_PROGRESS atau COMPLETED, klien memicu pengecualian fatal.
  2. Penggantian Nama Kunci JSON (Field Key Renaming): Backend merestrukturisasi atribut pelanggan dari {"customer": {"name": "Budi Santoso"}} menjadi {"customer": {"full_name": "Budi Santoso"}}. Klien seluler yang memetakan customer.name mendapati field tersebut bernilai kosong, memicu kegagalan kontrak: contract violation: customer.name is missing.
  3. Mutasi Tipe Data Primitif (Primitive Type Mutation): Backend mengubah tipe representasi jumlah transaksi dari bilangan bulat 64-bit (150000) menjadi string yang diformat ("150000"). Deserializer JSON bawaan Go (json.Unmarshal) menolak mengurai token string ke dalam variabel bertipe int64, memicu kegagalan fatal pada fungsi parsing HTTP klien.

Jika verifikasi hanya mengandalkan mock di pipeline konsumen, tes konsumen akan selalu lulus karena mock tidak mengetahui perubahan kode di repositori backend. Jika verifikasi mengandalkan E2E di staging, kesalahan baru ditemukan berjam-jam kemudian, mengaburkan akar masalah sebenarnya. Di sinilah deployment gate berbasis CDC berperan sebagai pencegah otomatis.

3. Arsitektur / Desain Solusi: Pola Consumer-Driven Contract

Solusi yang dirancang pada Lab 26 memisahkan tanggung jawab penentuan kontrak dan pembuktian kepatuhan ke dalam dua tahap yang saling melengkapi di dalam siklus hidup rekayasa perangkat lunak:

+----------------------------+
| Consumer (MobileApp Client)|
+----------------------------+
              |
              | 1. Generate Contract (Minimal Subset)
              v
+----------------------------+
|  Contract Definition JSON  |
|  - Request (Method, Path)  |
|  - Expected Status (200)   |
|  - Expected Subset Schema  |
+----------------------------+
              |
              | 2. Verify against Ephemeral Provider
              v
+----------------------------+
|   CDC Verifier Engine      |
+----------------------------+
        |             |
        | PASS        | FAIL (Diffs Detected)
        v             v
+---------------+  +-----------------------------+
| CI Gate: OK   |  | CI Gate: BLOCKED            |
| Deploy Allowed|  | Outage Prevented in CI      |
+---------------+  +-----------------------------+

Arsitektur ini didasarkan pada empat prinsip struktural:

  • Minimal Subset Expectation: Kontrak hanya memuat atribut yang dikonsumsi secara aktif oleh MobileApp. Atribut tambahan yang disediakan oleh server (seperti metadata internal) tidak dimasukkan ke dalam kontrak, sehingga provider tetap leluasa menambah field baru tanpa khawatir melanggar kontrak lama.
  • Deterministic In-Memory Verification: Verifikasi provider dijalankan menggunakan server HTTP in-memory (httptest.Server) yang berjalan secepat unit test biasa. Tidak ada latensi jaringan eksternal dan tidak ada ketergantungan pada status database staging yang fluktuatif.
  • Recursive Schema Diffing: Engine verifikasi membaca payload aktual dan melakukan penelusuran pohon JSON secara rekursif terhadap spesifikasi kontrak. Engine membedakan tipe data primitif secara ketat, termasuk membedakan angka (json.Number) dengan string representasi angka.
  • Deployment Gate Barrier: Hasil verifikasi berupa nilai boolean Passed dan daftar pesan kesalahan terperinci. Dalam pipeline CI/CD, jika Passed == false, proses build mengembalikan exit code 1 yang membatalkan penggabungan kode (merge) atau penerbitan container image.

4. Implementasi Step-by-Step Berbasis Kode Go Aktual

Implementasi Lab 26 tersusun rapi di dalam empat direktori internal: internal/model, internal/consumer, internal/contract, dan internal/provider.

Langkah 1: Pembuatan Kontrak oleh Konsumen

Pada file internal/consumer/client.go, konsumen seluler mendefinisikan generator kontrak yang merefleksikan kebutuhan interaksinya:

// internal/consumer/client.go: Pembuatan Kontrak Konsumen
func GenerateMobileContract() *contract.Contract {
    return &contract.Contract{
        Consumer: "MobileApp",
        Provider: "OrderService",
        Interactions: []contract.Interaction{
            {
                Description:   "A request for order details by ID",
                ProviderState: "Order ORD-123 exists and is IN_PROGRESS",
                Request: contract.RequestDefinition{
                    Method: http.MethodGet,
                    Path:   "/v1/orders/ORD-123",
                },
                Response: contract.ResponseDefinition{
                    Status: http.StatusOK,
                    Headers: map[string]string{
                        "Content-Type": "application/json",
                    },
                    Body: map[string]interface{}{
                        "id":     "ORD-123",
                        "status": "IN_PROGRESS",
                        "customer": map[string]interface{}{
                            "name": "Budi Santoso",
                        },
                        "total": json.Number("150000"),
                    },
                },
            },
        },
    }
}

Perhatikan penggunaan json.Number("150000"). Hal ini krusial agar verifier engine dapat menegakkan pemeriksaan tipe data numerik saat memvalidasi respons JSON yang diterima dari provider.

Langkah 2: Mesin Verifikasi (CDC Verifier Engine)

Mesin verifikasi pada internal/contract/verifier.go mengeksekusi request HTTP terhadap server target dan memvalidasi kode status, header, serta payload respons:

// internal/contract/verifier.go: Eksekusi dan Validasi HTTP
func (v *Verifier) Verify(baseURL string, c *Contract) VerificationResult {
    result := VerificationResult{Passed: true}

    for _, interaction := range c.Interactions {
        targetURL := strings.TrimRight(baseURL, "/") + interaction.Request.Path
        req, err := http.NewRequest(interaction.Request.Method, targetURL, nil)
        if err != nil {
            result.Passed = false
            result.Errors = append(result.Errors, fmt.Sprintf("[%s] failed to build request: %v", interaction.Description, err))
            continue
        }

        resp, err := v.Client.Do(req)
        if err != nil {
            result.Passed = false
            result.Errors = append(result.Errors, fmt.Sprintf("[%s] request failed: %v", interaction.Description, err))
            continue
        }

        if resp.StatusCode != interaction.Response.Status {
            result.Passed = false
            result.Errors = append(result.Errors, fmt.Sprintf("[%s] status code mismatch: expected %d, got %d",
                interaction.Description, interaction.Response.Status, resp.StatusCode))
        }

        // Pengecekan Header Content-Type
        for expectedHeaderKey, expectedHeaderVal := range interaction.Response.Headers {
            actualHeaderVal := resp.Header.Get(expectedHeaderKey)
            if !strings.EqualFold(actualHeaderVal, expectedHeaderVal) {
                result.Passed = false
                result.Errors = append(result.Errors, fmt.Sprintf("[%s] header mismatch for '%s': expected %q, got %q",
                    interaction.Description, expectedHeaderKey, expectedHeaderVal, actualHeaderVal))
            }
        }

        var actualBody map[string]interface{}
        decoder := json.NewDecoder(resp.Body)
        decoder.UseNumber()
        _ = decoder.Decode(&actualBody)

        diffs := diffValues("", interaction.Response.Body, actualBody)
        if len(diffs) > 0 {
            result.Passed = false
            for _, d := range diffs {
                result.Errors = append(result.Errors, fmt.Sprintf("[%s] %s", interaction.Description, d))
            }
        }
    }
    return result
}

Langkah 3: Algoritma Rekursif Subset Diffing

Inti dari verifikasi skema adalah fungsi diffValues yang mampu mentoleransi penambahan field baru oleh provider, namun sangat ketat terhadap field yang tercantum dalam kontrak:

// internal/contract/verifier.go: Recursive Schema Diffing
func diffValues(path string, expected, actual interface{}) []string {
    var diffs []string
    if expected == nil {
        return diffs
    }

    expMap, isExpMap := expected.(map[string]interface{})
    actMap, isActMap := actual.(map[string]interface{})

    if isExpMap {
        if !isActMap {
            return []string{fmt.Sprintf("path '%s': expected object, got %T", path, actual)}
        }
        for key, expVal := range expMap {
            childPath := key
            if path != "" {
                childPath = path + "." + key
            }
            actVal, exists := actMap[key]
            if !exists {
                diffs = append(diffs, fmt.Sprintf("missing expected field '%s'", childPath))
                continue
            }
            diffs = append(diffs, diffValues(childPath, expVal, actVal)...)
        }
        return diffs
    }

    // Perbandingan presisi tipe angka vs string
    expNum, isExpNum := expected.(json.Number)
    actNum, isActNum := actual.(json.Number)
    if isExpNum || isActNum {
        if !(isExpNum && isActNum) {
            diffs = append(diffs, fmt.Sprintf("path '%s': type mismatch (expected %v [%T], got %v [%T])",
                path, expected, expected, actual, actual))
            return diffs
        }
        if expNum.String() != actNum.String() {
            diffs = append(diffs, fmt.Sprintf("path '%s': value mismatch (expected %s, got %s)",
                path, expNum.String(), actNum.String()))
        }
        return diffs
    }

    if reflect.TypeOf(expected) != reflect.TypeOf(actual) {
        diffs = append(diffs, fmt.Sprintf("path '%s': type mismatch (expected %v [%T], got %v [%T])",
            path, expected, expected, actual, actual))
        return diffs
    }

    if expected != actual {
        diffs = append(diffs, fmt.Sprintf("path '%s': value mismatch (expected %q, got %q)", path, expected, actual))
    }
    return diffs
}

Langkah 4: Evolusi API Tanpa Merusak Kontrak (ProviderDual)

Ketika provider harus merilis format data baru (V2), cara yang benar bukanlah mengubah endpoint V1 yang sudah terikat kontrak, melainkan menerapkan parallel routing (pola Expand-Contract). File internal/provider/server.go memperlihatkan bagaimana ProviderDual tetap melayani kontrak lama di jalur /v1 sekaligus mengekspos fitur baru di jalur /v2:

// internal/provider/server.go: ProviderDual melayani V1 dan V2 bersamaan
func (p *ProviderDual) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    if strings.HasPrefix(r.URL.Path, "/v1/orders/") {
        id := strings.TrimPrefix(r.URL.Path, "/v1/orders/")
        respV1 := model.OrderResponseV1{
            ID:     id,
            Status: "IN_PROGRESS",
            Customer: model.CustomerResponseV1{ID: "cust-100", Name: "Budi Santoso"},
            Total: 150000,
        }
        w.Header().Set("Content-Type", "application/json")
        _ = json.NewEncoder(w).Encode(respV1)
        return
    }

    if strings.HasPrefix(r.URL.Path, "/v2/orders/") {
        id := strings.TrimPrefix(r.URL.Path, "/v2/orders/")
        respV2 := model.OrderResponseV2{
            ID:       id,
            Status:   "in_progress",
            Customer: model.CustomerResponseV2{ID: "cust-100", FullName: "Budi Santoso"},
            Total:    "150000",
            Currency: "IDR",
        }
        w.Header().Set("Content-Type", "application/json")
        _ = json.NewEncoder(w).Encode(respV2)
        return
    }
    http.NotFound(w, r)
}

Menerapkan pengujian berbasis kontrak secara fundamental merombak cara tim rekayasa perangkat lunak mengelola siklus hidup rilis layanan mikro:

7. Trade-off & Batasan Implementasi Lab 26

Meskipun CDC menawarkan efisiensi tinggi, pendekatan ini membawa sejumlah trade-off yang wajib dipertimbangkan oleh tim rekayasa perangkat lunak:

  • Beban Koordinasi Organisasi: CDC menuntut kedisiplinan tim konsumen untuk senantiasa mempublikasikan kontrak versi terbaru setiap kali ada perubahan kebutuhan DTO. Tanpa otomatisasi pipeline penerbitan kontrak, kontrak di repositori pusat dapat menjadi tidak sinkron.
  • Bukan Pengganti Pengujian Fungsional Mendalam: Kontrak CDC hanya memverifikasi bentuk skema antarmuka, tipe data, dan semantik kode status HTTP. CDC tidak memverifikasi apakah algoritma kalkulasi diskon atau alur transaksi database di backend telah berjalan secara benar. Pengujian logika bisnis tetap menjadi tanggung jawab unit test dan integration test domain.
  • Kompleksitas Manajemen Provider State: Pada skenario dunia nyata, interaksi kontrak sering kali bergantung pada status data tertentu (misalnya: "Order ORD-123 exists and is paid"). Provider harus menyediakan mekanisme setup fixture data (state callbacks) sebelum pengujian kontrak dieksekusi.

Adapun batasan implementasi spesifik pada Lab 26 adalah sebagai berikut:

  1. In-Memory Mock Exchange: Lab ini menggunakan pertukaran kontrak langsung di dalam memori/proses Go, tanpa menghubungkan ke server Pact Broker eksternal seperti Pactflow.
  2. Deterministic Path Routing: State provider disimulasikan menggunakan routing statis (/v1/orders/ORD-123), bukan melalui callback endpoint dinamis untuk persiapan basis data relasional.
  3. Protokol Terfokus pada REST HTTP: Implementasi berfokus secara eksklusif pada request-response HTTP REST JSON, dan belum mencakup contract testing asinkron untuk message broker seperti Kafka, RabbitMQ, atau gRPC Protobuf.

8. Kapan Menggunakan Pattern Ini?

Pola Consumer-Driven Contract testing sangat tepat diadopsi dalam kondisi-kondisi berikut:

  • Arsitektur Multi-Layanan dengan Tim Independen: Ketika sistem Anda terdiri dari puluhan layanan mikro yang dikembangkan oleh tim terpisah yang ingin melakukan rilis secara independen tanpa pertemuan koordinasi manual yang panjang.
  • Aplikasi Klien Seluler atau Frontend SPA: Klien seluler memiliki siklus rilis yang lambat karena harus melalui proses peninjauan toko aplikasi (App Store/Play Store). Sekali breaking change lolos ke produksi, pengguna lama akan mengalami crash tanpa bisa segera diperbaiki secara instan. CDC menjamin backend tidak merusak versi aplikasi lama yang masih aktif di pasar.
  • Lingkungan Staging yang Menjadi Bottleneck: Jika tim Anda sering mengeluhkan staging environment yang lambat, sering rusak (broken environment), atau biaya cloud staging membengkak, CDC memungkinkan Anda memangkas lebih dari 70% pengujian integrasi langsung ke level unit CI.

Sebaliknya, CDC kurang efektif diterapkan pada aplikasi monolitik murni di mana seluruh dependensi antarmuka diselesaikan pada level kompilasi bahasa (seperti Go interfaces atau TypeScript types), atau pada API publik terbuka yang memiliki jutaan konsumen tak dikenal di mana pola Provider-Driven (OpenAPI specification) lebih lazim diterapkan.
