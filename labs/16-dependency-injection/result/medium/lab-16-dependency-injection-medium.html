Dependency Injection: Memisahkan Konfigurasi dari Penggunaan di Go

Constructor Injection versus Service Locator — enam unit test, mock gateway, dan batasan bukti yang jujur.

Lukman / lukman-ss · Software Engineering Lab 16

Hard-coded dependency menghancurkan testability

Jika Processor menginisialisasi RealGateway secara internal, setiap unit test terpaksa memanggil infrastruktur nyata atau mengubah sumber. Tidak ada jalur mocking tanpa merusak isolasi. Setiap pergantian provider pembayaran memaksa modifikasi di semua consumer.

Mengapa refactor manual sering bocor

Developer bisa mengubah signature constructor tetapi melupakan wiring di composition root. Instansi lama tetap dibuat di tempat lama. Go tidak memiliki compile-time guard untuk binding yang hilang — hasilnya adalah nil pointer panic saat runtime, bukan error saat build.

Model mental: graf dependensi sebagai DAG

DI membentuk Directed Acyclic Graph: node adalah interface atau tipe konkret, edge adalah provider atau injeksi. Composition root berada di titik masuk graf, merakit semua objek sebelum logika bisnis berjalan. Setiap siklus dalam graf menandakan kesalahan desain.

Pipeline: dari wiring hingga eksekusi

  1. Composition root (cmd/demo/main.go) menginisialisasi tipe konkret.
  2. Konstruktor consumer menerima interface, bukan tipe konkret.
  3. Metode consumer memvalidasi input, lalu mendelegasikan ke dependensi.
  4. Test mengganti MockGateway untuk RealGateway tanpa mengubah Processor.

Kode: kontrak interface dan provider

type PaymentGateway interface {
    Charge(m Money) error
}

type Processor struct {
    gateway PaymentGateway
}

func NewProcessor(g PaymentGateway) *Processor {
    return &Processor{gateway: g}
}

NewProcessor menjamin Processor lahir dalam keadaan valid. Field gateway tidak diekspor, sehingga dependensi tidak bisa diubah setelah konstruksi — immutability at birth.

Gagal jalan: input tidak valid

func (p *Processor) ProcessPayment(amount int) error {
    if amount <= 0 {
        return errors.New("invalid amount")
    }
    m := Money{Amount: amount, Currency: "USD"}
    return p.gateway.Charge(m)
}

TestProcessor_InvalidAmount mengirim -10. Test mengharapkan error non-nil dan mock.ChargedMoney.Amount == 0, membuktikan gateway tidak pernah dipanggil. Validasi adalah tanggung jawab domain, bukan infrastruktur DI.

Tiga keputusan kunci saat mengadopsi DI

  • Bind per request atau singleton? Lab membuat objek baru setiap panggilan. Lifecycle management (singleton, scoped, transient) dibahas di README tetapi tidak diimplementasikan.
  • Pilih interface, bukan tipe konkret.
  • Injeksikan hanya service yang berinteraksi dengan infrastruktur eksternal. Money adalah value object — buat langsung.

Batasan: apa yang tidak dibuktikan

  • Lifecycle management. Singleton, scoped, dan transient tidak diimplementasikan atau diuji.
  • Overhead performa. Tidak ada benchmark membandingkan manual wiring dengan DI framework.
  • Konkurensi selain race detector. go test -race lulus karena Processor tidak memiliki mutable shared state — keamanan konkurensi mengikuti dari immutability, bukan locking.

Trade-off: kode bersih vs indireksi tambahan

Manfaat: testable tanpa setup infrastruktur, implementasi bisa diganti tanpa menyentuh domain, tipe-safe secara compile-time.

Biaya: boilerplate composition root tumbuh seiring jumlah service, behavior terpisah dari construction sehingga tracing lebih sulit, adopsi framework menambah dependensi baru.

Propagasi error: identik di kedua pola

TestProcessor_GatewayError dan TestBadProcessor_GatewayError sama-sama mengaktifkan ShouldFail: true pada MockGateway. Keduanya mengharapkan err != nil, membuktikan DI tidak menelan error gateway — caller tetap mendapat sinyal kegagalan.

Performa: tidak ada bukti benchmark

Metrik perbandingan di README bersifat ilustratif, tidak terukur. Lab ini tidak menyertakan benchmark yang membandingkan latensi constructor injection terhadap new langsung atau container lookup. Jangan mengutip angka "15 ms vs 40 ms" sebagai data empiris.

Keamanan reflection: tidak digunakan

Lab menghindari reflection-based DI sepenuhnya. Manual wiring memberikan type checking compile-time — NewProcessor(realGateway) menolak ketidakcocokan tipe saat build. Tidak ada penggunaan reflect dalam implementasi.

Checklist implementasi DI yang benar

  • [ ] Dependensi dideklarasikan sebagai interface, bukan tipe konkret.
  • [ ] Constructor injection sebagai default; semua dependensi eksplisit di signature.
  • [ ] Composition root adalah satu-satunya tempat yang menginisialisasi implementasi konkret.
  • [ ] Tidak ada container.Get(...) di dalam logika domain.
  • [ ] Value object diinisialisasi langsung, bukan melalui container.
  • [ ] Setiap service bisa diuji dengan mock tanpa setup infrastruktur.
  • [ ] Validasi input berjalan sebelum delegasi ke dependensi eksternal.
  • [ ] go test -race ./... lulus tanpa warning.

Anti-pattern: Service Locator abuse

func (p *BadProcessor) ProcessPayment(amount int) error {
    if amount <= 0 {
        return errors.New("invalid amount")
    }
    m := Money{Amount: amount, Currency: "USD"}
    return p.container.GetPaymentGateway().Charge(m)
}

BadProcessor menerima Container dan memanggil GetPaymentGateway() di dalam method. Dependensi sebenarnya (PaymentGateway) tersembunyi di balik container. Consumer bergantung pada API container, bukan kontrak service.

PSR-11 menyatakan pengguna SHOULD NOT meneruskan container ke dalam objek — rekomendasi kuat, bukan larangan mutlak. Masalah Service Locator: dependensi tidak terlihat dari signature constructor, setiap test harus mem-mock container, dan refactoring nama service hanya error di runtime jika tipe bergeser.

Komando praktis

go run ./cmd/demo          # jalankan kedua pola
go test -v ./...           # jalankan enam unit test
go test -race ./...        # verifikasi tanpa race condition

Prinsip jangka panjang

Depend on abstractions, not concretions.

Constructor injection mencapai ini dengan menjadikan setiap dependensi eksplisit saat konstruksi. Service menjadi consumer stabil dari sebuah interface; implementasinya bisa berubah, diganti, atau disubstitusi dengan test double tanpa menyentuh consumer.

DI adalah disiplin struktural, bukan optimasi performa. Ia membuat sistem lebih murah untuk dites dan lebih murah untuk berevolusi — tetapi tidak memperbaiki validasi yang buruk, error handling yang kurang, atau masalah arsitektur yang mendahului wiring.
