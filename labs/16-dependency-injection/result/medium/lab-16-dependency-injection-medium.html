Dependency Injection: Memisahkan Konfigurasi dari Penggunaan

Memisahkan Konfigurasi dari Penggunaan untuk Testability & Evolvability

Lukman / lukman-ss · Software Engineering Lab 16

Prinsip paling fundamental dari Dependency Injection bukanlah framework atau container, melainkan pemisahan waktu perakitan objek dari waktu pemakaian objek.

Ketika sebuah modul bisnis bertanggung jawab menginstansiasi dependensi infrastrukturnya sendiri, isolasi logika dan kemampuan pengujian otomatis langsung runtuh. Lab 16 mendemonstrasikan bagaimana membalikkan kendali pembentukan objek menggunakan Go standard library, membandingkan Constructor Injection dengan anti-pattern Service Locator secara deterministik.

Infrastruktur Terkunci di Logika Bisnis

Penginstansiasian dependensi konkret secara langsung di dalam method bisnis menciptakan kopling ketat (tight coupling). Logika pembayaran terkunci pada satu implementasi vendor tertentu, membuat pengujian unit murni mustahil dilakukan tanpa koneksi internet atau mock HTTP server yang lamban.

// Anti-pattern: Logika bisnis mengunci diri ke RealGateway
func (p *BadProcessor) ChargeDirect(amount int) error {
    gw := &RealGateway{} // Hard-coded dependency
    return gw.Charge(Money{Amount: amount, Currency: "USD"})
}

Perubahan pada detail vendor memaksa kompilasi dan modifikasi ulang di lapisan consumer. Dampak perubahan merambat liar ke seluruh sistem hanya karena satu detail infrastruktur diganti.

Review Manual Melewatkan Hidden Dependencies

Pendekatan naif sering mencoba menyelesaikan masalah kopling dengan menyuntikkan container umum atau Service Locator. Di atas kertas, kode tampak bersih karena hanya menerima satu parameter konfigurasi.

// locator.go: Interface Container menyamarkan kebutuhan dependensi
type Container interface {
    GetPaymentGateway() PaymentGateway
}

type BadProcessor struct {
    container Container
}

Namun, reviewer kode tidak dapat mengetahui dependensi apa yang sebenarnya dibutuhkan oleh BadProcessor tanpa membaca baris demi baris implementasinya. Jika container lupa meregistrasikan gateway, compiler tetap mengizinkan kompilasi, namun aplikasi meledak dengan runtime panic saat dieksekusi di produksi.

Separation of Configuration from Use

Berdasarkan formulasi Martin Fowler, sistem harus memisahkan dua fase hidup objek secara tegas: fase perakitan dan fase eksekusi. Komponen luar (assembler) merakit graf dependensi saat startup, sedangkan komponen bisnis hanya menjalankan fungsionalitasnya.

// 1. Fase Konfigurasi (Composition Root di main.go):
realGateway := &di.RealGateway{}
processor := di.NewProcessor(realGateway)

// 2. Fase Penggunaan (Eksekusi Bisnis):
err := processor.ProcessPayment(100)

Service Processor hanya bergantung pada abstraksi PaymentGateway. Ia tidak peduli apakah implementasi di baliknya adalah klien REST API, gRPC stub, atau mock in-memory untuk pengujian.

Pipeline Alur Eksekusi Dependency Injection

Alur eksekusi bergerak secara linear dari titik masuk aplikasi (entry point) hingga batas infrastruktur eksternal tanpa melanggar batasan tanggung jawab layer.

cmd/demo/main.go               | Composition Root inisialisasi RealGateway
di.NewProcessor(gateway)       | Konstruktor menerima kontrak PaymentGateway
processor.ProcessPayment(100)  | Validasi input amount <= 0 & buat Money
gateway.Charge(Money)          | Delegasi eksekusi ke implementasi konkret

Pemisahan tanggung jawab ini menjamin bahwa validasi input diselesaikan sebelum data menyentuh infrastruktur jaringan.

Constructor Injection: Valid State at Birth

Menerapkan Constructor Injection dengan field struct unexported memastikan objek tidak pernah berada dalam kondisi setengah jadi atau tidak valid saat diciptakan.

type Processor struct {
    gateway PaymentGateway
}

func NewProcessor(g PaymentGateway) *Processor {
    return &Processor{gateway: g}
}

Pola ini mencegah runtime dereference nil pointer karena compiler Go memvalidasi bahwa parameter yang memenuhi interface wajib disediakan saat memanggil NewProcessor.

Early Validation: Pencegahan Eksekusi I/O Sia-sia

Dependency injection tidak meniadakan validasi defensif pada boundary domain. Pemeriksaan nilai masukan pada level service memotong eksekusi sebelum memanggil resource downstream.

func (p *Processor) ProcessPayment(amount int) error {
    if amount <= 0 {
        return errors.New("invalid amount")
    }
    m := Money{Amount: amount, Currency: "USD"}
    return p.gateway.Charge(m)
}

Ketika transaksi dengan nominal tidak valid dikirimkan, alur langsung berhenti seketika. Pemanggilan downstream I/O dicegah sejak awal, menghemat kuota jaringan dan biaya transaksi API pihak ketiga.

Tiga Keputusan Desain Dependensi

Dalam merancang batas arsitektural yang bersih, tim perlu menerapkan tiga urutan keputusan konkret:

  1. Program to Interface: Abstraksikan batasan I/O eksternal melalui interface minimal seperti PaymentGateway yang hanya mengekspos method Charge(Money) error.
  2. Wajibkan Constructor Injection: Tolak service locator global. Operkan seluruh dependensi esensial langsung ke signature konstruktor.
  3. Instansiasi Value Object Langsung: Bebaskan struktur data murni tanpa efek samping (seperti Money) dari mekanisme injeksi atau container.

Keputusan ini memastikan bahwa abstraksi hanya diletakkan pada batas sistem yang rentan terhadap perubahan infrastruktur.

Meskipun kedua pola menghasilkan output akhir yang sama pada konsol, Constructor Injection mencapai hasil tersebut tanpa mengikat kode bisnis ke API container.

Batasan Bukti: Cakupan Verifikasi Lab

Penting untuk menegaskan batas integritas pengujian laboratorium agar tidak terjadi overclaim dalam evaluasi arsitektur produksi.

  • Yang Terbukti di Lab: MockGateway mengisolasi Processor secara total tanpa lalu lintas jaringan; validasi pre-check mencegah pemanggilan gateway; propagasi error downstream diteruskan utuh; race detector bersih tanpa data race.
  • Yang Tidak Dibuktikan: Lab ini tidak mengukur overhead performa container berbasis refleksi vs inisialisasi manual; tidak membuktikan penurunan rasio bug pada skala tim besar; tidak menguji manajemen lifecycle kompleks (Singleton, Scoped, Transient); dan tidak mengevaluasi framework DI otomatis skala masif.

Hasil pengujian memvalidasi keandalan struktur isolasi kode, bukan klaim performa ekosistem berskala masif.

Trade-off Arsitektur: Kontrol Bersih vs Boilerplate

Setiap keputusan decoupling menukar kemudahan penulisan kode lokal dengan disiplin perakitan.

  • Keuntungan Diperoleh: Pengujian unit terisolasi yang berjalan dalam orde mikrodetik; kebebasan menukar vendor tanpa mengubah logika bisnis; immutabilitas dependensi setelah konstruksi.
  • Konsekuensi Dihadapi: Bertambahnya baris perakitan (wiring) manual di Composition Root; keharusan menavigasi file interface saat menelusuri alur kode; risiko terjadinya pembengkakan parameter constructor.

Biaya boilerplate pada Composition Root adalah harga yang wajar demi mendapatkan isolasi pengujian yang deterministik.

Pipeline Validasi & Thread-Safety

Karena Processor berstatus stateless dan hanya menyimpan referensi interface yang immutable, pemrosesan pembayaran aman dieksekusi secara konkuren.

Goroutine Request   | Panggilan paralel ke ProcessPayment(amount)
Pure Pre-Check      | amount <= 0 divalidasi tanpa mutasi shared state
Value Object Build  | Money{Amount, Currency} dialokasikan di stack per request
Thread-Safe Charge  | Gateway downstream dieksekusi tanpa race condition

Uji konkurensi dengan flag -race membuktikan bahwa ketiadaan mutable state internal pada service membuat sistem kebal terhadap bahaya data race.

Sebelum vs Sesudah Penerapan DI

Transformasi dari struktur tightly-coupled ke Constructor Injection memberikan peningkatan dramatis pada aspek pemeliharaan perangkat lunak.

  • Sebelum (Tightly Coupled): Processor membuat RealGateway sendiri di dalam method; test terpaksa menyentuh jaringan nyata; pergantian vendor menuntut penulisan ulang logika bisnis; simulasi kegagalan vendor sulit dilakukan.
  • Sesudah (Constructor Injection): Processor menerima PaymentGateway lewat NewProcessor; unit test cukup menyuntikkan MockGateway lokal; pergantian vendor hanya mengubah satu baris di main.go; skenario kegagalan dapat diuji deterministik 100%.

Pemisahan ini mengubah pengujian integrasi yang rapuh menjadi pengujian unit yang cepat dan stabil.

Test Suite 01: Verifikasi Happy Path Terisolasi

Pengujian pertama memverifikasi keberhasilan transaksi 50 USD tanpa memerlukan server pembayaran eksternal.

func TestProcessor_Success(t *testing.T) {
    mock := &MockGateway{}
    proc := di.NewProcessor(mock)

    err := proc.ProcessPayment(50)
    if err != nil {
        t.Fatalf("expected nil error, got %v", err)
    }
    if mock.ChargedMoney.Amount != 50 || mock.ChargedMoney.Currency != "USD" {
        t.Errorf("expected 50 USD, got %+v", mock.ChargedMoney)
    }
}

Pemeriksaan nilai pada mock.ChargedMoney membuktikan bahwa data didelegasikan secara akurat ke gateway dalam waktu 0.00 detik.

Test Suite 02: Propagasi Kegagalan Gateway

Pengujian kegagalan memverifikasi bahwa error dari layer infrastruktur diteruskan secara utuh kepada pemanggil tanpa ditelan.

func TestProcessor_GatewayError(t *testing.T) {
    mock := &MockGateway{ShouldFail: true}
    proc := di.NewProcessor(mock)

    err := proc.ProcessPayment(50)
    if err == nil {
        t.Fatalf("expected error from gateway, got nil")
    }
}

Dengan menyetel flag ShouldFail: true pada mock, kondisi down time vendor dapat disimulasikan secara instan dan deterministik.

Test Suite 03: Short-Circuit Invalid Amount

Pengujian defensif memastikan bahwa logika bisnis membatalkan transaksi bernilai negatif sebelum menyentuh gateway.

func TestProcessor_InvalidAmount(t *testing.T) {
    mock := &MockGateway{}
    proc := di.NewProcessor(mock)

    err := proc.ProcessPayment(-10)
    if err == nil {
        t.Fatalf("expected error for negative amount, got nil")
    }
    if mock.ChargedMoney.Amount != 0 {
        t.Errorf("gateway should not have been called, but got amount %d", mock.ChargedMoney.Amount)
    }
}

Assertion mock.ChargedMoney.Amount == 0 mengonfirmasi bahwa method Charge() tidak pernah dipanggil saat input tidak valid.

Desain Rasional: Value Object Bebas DI

Kesalahan umum dalam adopsi DI adalah kecenderungan untuk mengabstraksikan dan menginjeksikan seluruh struktur data.

// gateway.go: Value Object murni tanpa efek samping
type Money struct {
    Amount   int
    Currency string
}

Struktur data murni seperti Money, alamat, atau tanggal tidak memiliki dependensi I/O. Menginjeksikan value object melalui container hanya menambah kompleksitas indirection tanpa memberikan manfaat pengujian apa pun.

Bahaya Service Locator: PSR-11 Warning

Menjadikan Service Locator sebagai perantara dependensi menciptakan ilusi modularitas yang berbahaya.

// BadProcessor terikat pada interface Container, bukan service yang dibutuhkan
type BadProcessor struct {
    container Container
}

func (p *BadProcessor) ProcessPayment(amount int) error {
    return p.container.GetPaymentGateway().Charge(Money{Amount: amount, Currency: "USD"})
}

Standar PHP-FIG PSR-11 secara eksplisit menyatakan bahwa pengguna tidak boleh mengoper container ke dalam objek. Pengujian BadProcessor terpaksa mengimplementasikan MockContainer hanya untuk mengembalikan MockGateway, melipatgandakan beban pemeliharaan test suite.

Checklist Adopsi Dependency Injection

Gunakan checklist berikut saat melakukan peninjauan kode (code review) arsitektur sistem:

  • Deklarasikan seluruh dependensi eksternal sebagai interface, bukan tipe struct konkret.
  • Gunakan Constructor Injection sebagai standar default; tolak setter injection opsional.
  • Pusatkan perakitan objek konkret hanya pada Composition Root (seperti main.go).
  • Larang keras mengoper instance Container atau Service Locator ke dalam domain logic.
  • Instansiasi struct data murni (Value Objects) langsung tanpa melalui DI.
  • Lengkapi setiap service bisnis dengan unit test terisolasi menggunakan mock interface.

Disiplin terhadap checklist ini mencegah bocornya detail infrastruktur ke dalam domain sistem.

Anti-Pattern & Cara Menghindarinya

Tiga kesalahan desain yang sering ditemui saat mengimplementasikan DI:

  1. Constructor Bloat: Konstruktor yang menerima terlalu banyak parameter menandakan pelanggaran Single Responsibility Principle (SRP). Solusinya adalah memecah kelas tersebut, bukan menyembunyikannya ke dalam container.
  2. Service Locator Disguise: Membungkus dependensi ke dalam Map atau Context serbaguna demi memperpendek parameter konstruktor.
  3. Over-Abstracting Everything: Membuat interface untuk setiap struct utilitas internal yang tidak pernah memiliki varian implementasi lain atau kebutuhan mocking.

Constructor bloat adalah sinyal desain yang bermanfaat untuk mengevaluasi kembali batasan tanggung jawab sebuah kelas.

Prinsip Arsitektur Jangka Panjang

Dependency Injection adalah wujud nyata dari Hollywood Principle: "Don't call us, we'll call you."

Modul tingkat tinggi (domain logic) tidak boleh bergantung pada modul tingkat rendah (infrastruktur vendor). Keduanya harus bergantung pada abstraksi. Dengan membalikkan kontrol pembuatan objek keluar dari domain logic, sistem memiliki evolvability tinggi—mampu beradaptasi terhadap perubahan teknologi tanpa membongkar aturan bisnis inti.
