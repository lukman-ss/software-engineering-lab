Dependency Injection di Go: Constructor Injection vs Service Locator

Constructor Injection vs Service Locator: Trade-off Konkret untuk Testability

Lukman / lukman-ss · Software Engineering Lab 16

Coupling Mengunci Gateway di Domain

Ketika sebuah modul bisnis seperti Processor menginstansiasi dependensi konkretnya sendiri secara langsung, modul tersebut terkunci pada detail infrastruktur eksternal. Perubahan vendor atau penggantian payment provider memaksa modifikasi langsung pada kode domain inti. Akibatnya, pengujian unit menjadi lambat dan rapuh karena tidak dapat berjalan tanpa menghubungi jaringan produksi nyata.

Konstruktor Tanpa Interface Menyulitkan Swap

Konstruktor tanpa parameter menyembunyikan dependensi eksternal dari caller. Menjadikan PaymentGateway sebagai parameter interface pada fungsi konstruktor memindahkan keputusan instansiasi ke luar modul tanpa mengubah sedikit pun alur logika bisnis di dalam ProcessPayment. Hal ini membuka fleksibilitas pengujian terisolasi melalui mock tanpa harus merombak seluruh call site.

IoC Bukan Fitur, Tapi Arah Kendali

Inversion of Control (IoC) adalah prinsip desain arsitektural yang mengatur arah kendali eksekusi. Dependency Injection merupakan penerapan spesifik IoC untuk perakitan objek: alih-alih modul bisnis yang secara aktif mencari dependensinya, kode eksternal seperti composition root di main.go yang memegang kendali penuh untuk menginstansiasi dan menyuntikkan dependensi konkret ke dalam consumer.

Alur Request dari Composition Root ke Gateway

Alur eksekusi request dimulai dari fase konfigurasi di mana main.go membuat RealGateway dan menyuntikkannya ke NewProcessor. Ketika caller memanggil ProcessPayment(100), Processor terlebih dahulu memvalidasi bahwa nilai pembayaran valid, menginstansiasi value object Money secara langsung, dan mendelegasikan panggilan ke gateway.Charge(m) sebelum mengembalikan error ke caller.

Constructor Membuat Dependency Terlihat

Konstruktor publik bertindak sebagai kontrak eksplisit yang memperlihatkan dependensi wajib sebuah komponen. Dengan menerima interface PaymentGateway pada NewProcessor, caller mengetahui secara pasti apa yang dibutuhkan oleh komponen tersebut, sementara field unexported memastikan integritas referensi tidak dapat dimodifikasi sembarangan dari luar.

func NewProcessor(g PaymentGateway) *Processor {
    return &Processor{gateway: g}
}

func (p *Processor) ProcessPayment(amount int) error {
    if amount <= 0 { return errors.New("invalid amount") }
    m := Money{Amount: amount, Currency: "USD"}
    return p.gateway.Charge(m)
}

Service Locator Menyembunyikan Dependency

Sebagai kontras, BadProcessor menerima interface Container secara generik. Di dalam method ProcessPayment, dependensi diambil secara dinamis melalui container.GetPaymentGateway(). Pola ini merupakan anti-pattern Service Locator karena menyembunyikan dependensi aktual dari signature konstruktor dan memaksa unit test untuk mem-mock container alih-alih dependensi langsung.

Biaya Tersembunyi: Indirection vs Eksplisitas

Meskipun Service Locator sekilas tampak praktis karena mempersingkat daftar parameter konstruktor, ia menimbulkan biaya pemeliharaan jangka panjang. Keterbacaan kode menurun karena dependensi tersembunyi di balik API container, dan setiap unit test terpaksa membuat mock ganda untuk container dan gateway.

Trade-off: Boilerplate Konstruksi vs Kemampuan Uji

Menerapkan Constructor Injection secara manual menuntut sedikit penulisan kode perakitan di composition root. Namun trade-off ini sebanding karena memberikan isolasi pengujian mutlak, kejelasan arsitektur, dan validasi compile-time tanpa memerlukan framework DI berbasis refleksi yang rumit.

Nil Guard Menutupi Runtime Risk

Walaupun konstruktor mewajibkan parameter interface diisi, kompiler Go tetap mengizinkan nilai nil dilewatkan. Tanpa penjaga eksplisit, nil pointer dereference akan memicu kepanikan runtime saat method gateway dipanggil. Penambahan nil check pada konstruktor merupakan langkah defensif penting untuk production safety.

func NewProcessor(g PaymentGateway) *Processor {
    if g == nil {
        return nil // atau panic, tergantung kebijakan tim
    }
    return &Processor{gateway: g}
}

Sebelum vs Sesudah: Konstruktor Injection

Perbandingan struktural memperlihatkan bahwa logika komputasi transaksi tidak berubah sama sekali. Perubahan hanya terjadi pada batas modul: parameter interface menggantikan tipe konkret sehingga ketergantungan domain menjadi fleksibel dan mudah digantikan oleh test double.

Apa yang Tidak Dicakup oleh Lab Ini

Eksperimen lab ini sengaja membatasi ruang lingkup pada pola pemisahan struktural dasar. Lab ini tidak mencakup pengelolaan lifecycle objek yang rumit (seperti singleton, scoped, atau transient), evaluasi overhead framework DI otomatis, maupun sinkronisasi konkurensi pada shared mutable state antar-goroutine.

Edge Case: Nil Dependency Menghasilkan Panic

Jika caller memberikan nil sebagai parameter PaymentGateway pada NewProcessor, proses kompilasi tetap berhasil. Kegagalan fatal baru meletus di runtime saat ProcessPayment memanggil Charge pada interface kosong tersebut. Ini menegaskan perlunya validasi guard clause pada batas inisialisasi.

Test Suite Membuktikan Tiga Jalur Saja

Suite pengujian otomatis membuktikan tiga perilaku konkret: pemanggilan sukses mencatat nilai Money yang akurat, kegagalan gateway diteruskan tanpa distorsi, dan nominal tidak valid ditolak sebelum memanggil gateway eksternal. Pengujian ini tidak membuktikan kesiapan sistem pada beban produksi penuh.

Yang Belum Dibuktikan oleh Test Suite

Keberhasilan suite pengujian tidak membuktikan keamanan konkurensi multi-goroutine, ketahanan terhadap kegagalan jaringan acak, atau efisiensi alokasi memori pada skala besar. Aspek operasional tersebut tetap memerlukan pengujian integrasi dan load testing terpisah.

Risiko Menerapkan Pola Tanpa Pertimbangan Lifecycle

Menerapkan DI secara ceroboh tanpa memahami lifecycle objek dapat memicu kebocoran memori jika instansiasi baru terus dibuat pada setiap request HTTP. Selain itu, dependensi bersama yang menyimpan state internal membutuhkan mekanisme penguncian konkurensi agar aman dari race condition.

Checklist Implementasi Dependency Injection yang Aman

Terapkan prinsip-prinsip berikut saat mengadopsi DI: deklarasikan dependensi sebagai interface, utamakan constructor injection agar dependensi terlihat jelas, batasi instansiasi konkret hanya di composition root, instansiasi value object murni secara langsung, dan selalu jalankan tes deteksi race sebelum melakukan deployment.

Anti-Pattern: Service Locator di Domain Logic

Menyuntikkan container ke dalam entitas logika domain merupakan anti-pattern yang merusak enkapsulasi. Pola ini mengikat kode domain pada framework container, menyamarkan kebutuhan dependensi riil, dan mempersulit pengujian unit karena membutuhkan pembuatan tiruan container yang rumit.
