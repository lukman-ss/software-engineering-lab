Instansiasi Langsung di Logika Bisnis Mengunci Dependensi

Ketika kelas menginstansiasi dependensi secara langsung di dalam method, logika bisnis terkunci ke infrastruktur konkret. Kode mungkin bekerja tanpa error di tahap awal, bukan berarti arsitekturnya sehat ketika vendor pihak ketiga harus diganti.

Service Locator Terlihat Bersih Namun Menyembunyikan Keterikatan

Banyak tim mengira Service Locator menyelesaikan kopling karena objek tidak lagi memanggil new secara langsung. Faktanya, menyuntikkan container tidak otomatis menghasilkan kode decoupled jika dependensi sebenarnya tersembunyi di balik API lookup.

Pemisahan Konfigurasi dari Penggunaan: Dua Fase Terisolasi

Prinsip utama Fowler membedakan dua fase: perakitan graf objek di composition root dan eksekusi logika di domain. Hanya pada jalur ini komponen bisnis tetap bersih dari detail infrastruktur, sementara value object tetap diinstansiasi langsung.

Alur Eksekusi: Composition Root ke Processor dan Gateway

Alur eksekusi dimulai dari instansiasi konkret di composition root, dilanjutkan validasi input lokal sebelum memanggil antarmuka gateway. Arsitektur ini mengisolasi logika, namun belum membuktikan keandalan sistem pada jaringan berlatensi tinggi.

Constructor Injection: Dependensi Eksplisit dan Valid Saat Lahir

Processor mendeklarasikan gateway sebagai unexported field dan menerimanya saat konstruksi. Penggunaan interface bukan berarti arsitektur bebas alokasi memori; teknik ini menukar overhead pointer interface demi isolasi total dependensi domain.

type Processor struct {
    gateway PaymentGateway
}
func NewProcessor(g PaymentGateway) *Processor {
    return &Processor{gateway: g}
}
func (p *Processor) ProcessPayment(amount int) error {
    if amount <= 0 { return errors.New("invalid amount") }
    m := Money{Amount: amount, Currency: "USD"}
    return p.gateway.Charge(m)
}

Kegagalan Service Locator: Keterikatan Tersembunyi Container

Service Locator menyembunyikan dependensi nyata di dalam tubuh method dan berisiko memicu panic saat lookup gagal. Hanya pada jalur ini unit test dipaksa membuat MockContainer tambahan yang tidak relevan dengan kebutuhan bisnis.

Matriks Komparasi: Constructor Injection vs Service Locator

Matriks ini memetakan keunggulan mutlak Constructor Injection atas Service Locator. Injeksi via konstruktor menjamin verifikasi tipe pada saat kompilasi, sedangkan Service Locator menunda deteksi dependensi yang hilang ke runtime.

Keputusan Arsitektur: Memilih Pola Perakitan Dependensi

Keputusan arsitektural menetapkan Constructor Injection sebagai standar baku dan menginstansiasi value object secara langsung. Memilih manual wiring di main.go bukan berarti anti-framework, melainkan keputusan pragmatis menjaga kesederhanaan aplikasi Go.

Batasan Bukti Lab: Yang Dibuktikan vs Belum

Lab ini membuktikan isolasi pengujian unit dan validasi input sebelum pemanggilan infrastruktur eksternal. Hasil ini belum membuktikan efektivitas lifecycle management kompleks atau klaim penurunan tingkat cacat di production.

Trade-off Penerapan Dependency Injection

Penerapan DI membawa konsekuensi penelusuran alur yang lebih rumit karena implementasi konkret terpisah dari titik penggunaan. Menambahkan interface dan injector tidak otomatis membuat arsitektur lebih baik jika sistemnya masih monolitik sederhana.

Keamanan Konkurensi pada Komponen Stateless

Processor bersifat stateless setelah dikonstruksi sehingga aman dipanggil konkuren lintas goroutine tanpa mutasi internal. Simulasi ini tidak sama dengan gateway jaringan riil yang mengelola koneksi socket dan state pool secara terdistribusi.

// Processor stateless: gateway bersifat read-only setelah konstruksi
type Processor struct {
    gateway PaymentGateway
}
// Aman dipanggil lintas goroutine selama gateway thread-safe
func (p *Processor) ProcessPayment(amount int) error {
    if amount <= 0 { return errors.New("invalid amount") }
    m := Money{Amount: amount, Currency: "USD"}
    return p.gateway.Charge(m)
}

Transformasi Desain: Hardcoded vs Constructor Injection

Sebelum menerapkan DI, logika pembayaran terkunci pada implementasi RealGateway konkret yang menyulitkan pengujian offline. Memisahkan konstruksi ke NewProcessor bukan berarti menambah kompleksitas, melainkan membebaskan domain dari detail eksternal.

Interface Minimal dan Pengecualian untuk Value Object

Interface PaymentGateway dirancang ramping hanya dengan satu method Charge, sedangkan Money diinstansiasi langsung tanpa perantara container. Keputusan membedakan service dan value object ini cakupannya mengikuti test skenario spesifik lab ini.

// Money adalah value object data murni: instansiasi langsung
type Money struct {
    Amount   int
    Currency string
}
// PaymentGateway mendefinisikan kontrak minimal abstraction
type PaymentGateway interface {
    Charge(m Money) error
}

Pengujian Terisolasi Menggunakan Test Double MockGateway

MockGateway mensimulasikan kegagalan jaringan dan mencatat payload transaksi tanpa koneksi HTTP riil. Menulis unit test dengan mock tidak otomatis menjamin integritas integrasi vendor jika payload skema production mengalami perubahan.

type MockGateway struct {
    ChargedMoney di.Money
    ShouldFail   bool
}
func (m *MockGateway) Charge(money di.Money) error {
    if m.ShouldFail { return errors.New("gateway unavailable") }
    m.ChargedMoney = money
    return nil
}

Validasi Pre-Check Mencegah Panggilan Jaringan Sia-sia

Test memastikan bahwa input negatif langsung ditolak di lapisan domain sebelum menyentuh gateway. Hanya pada jalur ini mock memverifikasi bahwa amount tetap 0, membuktikan panggilan jaringan berhasil dicegah sejak awal.

func TestProcessor_InvalidAmount(t *testing.T) {
    mock := &MockGateway{}
    proc := di.NewProcessor(mock)
    err := proc.ProcessPayment(-10)
    if err == nil { t.Fatalf("expected error for negative amount") }
    if mock.ChargedMoney.Amount != 0 {
        t.Errorf("gateway should not have been called, got %d",
            mock.ChargedMoney.Amount)
    }
}

Propagasi Error Transparan dari Lapisan Infrastruktur

Processor meneruskan error dari gateway secara transparan ke caller. Meneruskan error mentah bukan berarti sistem tidak butuh retry policy; ini membuktikan kontrak interface mampu mengalirkan status kegagalan infrastruktur secara akurat.

func TestProcessor_GatewayError(t *testing.T) {
    mock := &MockGateway{ShouldFail: true}
    proc := di.NewProcessor(mock)
    err := proc.ProcessPayment(50)
    if err == nil {
        t.Fatalf("expected error from gateway, got nil")
    }
    // Verifikasi error gateway sampai ke pemanggil
}

Composition Root di cmd/demo: Satu Titik Perakitan Objek

Fungsi main bertindak sebagai composition root tunggal tempat semua struct konkret dibuat dan dirakit. Struktur sederhana ini sengaja dipilih tanpa framework DI pihak ketiga, dan cakupannya mengikuti test verifikasi perilaku lab.

func main() {
    // Instansiasi dependensi konkret
    realGateway := &di.RealGateway{}
    // Constructor Injection eksplisit
    processor := di.NewProcessor(realGateway)
    _ = processor.ProcessPayment(100)
    // Service Locator anti-pattern untuk demonstrasi
    container := &SimpleContainer{gateway: realGateway}
    badProcessor := di.NewBadProcessor(container)
    _ = badProcessor.ProcessPayment(200)
}

Checklist Penerapan Dependency Injection di Go

Checklist ini merangkum disiplin perancangan DI: kontrak berbasis interface, injeksi eksplisit via constructor, isolasi composition root, larangan container di domain, instansiasi langsung value object, dan pengujian unit terisolasi.

Anti-Pattern Umum dalam Penerapan Dependency Injection

Menyuntikkan container ke domain menyembunyikan dependensi, sedangkan konstruktor dengan belasan parameter menandakan pelanggaran SRP. Memasukkan value object ke dalam container bukan berarti arsitektur lebih rapi, melainkan menambah boilerplate sia-sia.

Reproduksi Mandiri di Mesin Lokal Menggunakan Go

Seluruh mekanisme validasi ditulis menggunakan Go standard library murni tanpa framework eksternal. Skenario lokal ini memverifikasi isolasi logika, namun production masih perlu mempertimbangkan auto-wiring tool seperti wire pada skala ribuan komponen.

cd labs/16-dependency-injection
go test -v ./...    # validasi unit test terisolasi Processor dan BadProcessor
go test -race ./... # verifikasi konkurensi stateless bebas race condition
go run ./cmd/demo   # eksekusi komparasi Constructor Injection vs Service Locator

Prinsip Inti: Pisahkan Konfigurasi, Eksplisitkan Kontrak

Dependency Injection adalah teknik memisahkan fase konfigurasi dari eksekusi logika. Menyuntikkan dependensi via interface tidak otomatis menyelesaikan kekacauan arsitektur jika tanggung jawab domain sejak awal tidak dirancang dengan batas yang tegas.
