Hard-Coded Dependencies Mengunci Logika Bisnis pada Infrastruktur

Ketika sebuah kelas membangun dependensinya sendiri, logika bisnis menjadi terkunci pada infrastruktur eksternal. Pengujian unit jadi sulit karena harus mengandalkan status jaringan nyata yang tidak deterministik.

// Sebelum: tight coupling
type Processor struct{}

func (p *Processor) ProcessPayment(amount int) error {
    gw := &RealGateway{}           // instansiasi internal
    return gw.Charge(Money{...})
}

Kode ini menggabungkan validasi, aturan bisnis, dan panggilan jaringan ke dalam satu method. Mocking menjadi mustahil tanpa mengubah kode produksi.

Mengapa Review Manual Gagal Menangkap Dependensi Tersembunyi

Reviewer sering fokus pada alur kontrol dan mungkin melewatkan pemanggilan new() yang tersembunyi di dalam helper. Review manual tidak dapat memverifikasi bahwa setiap dependensi eksternal telah diekstrak ke parameter konstruktor.

Pada codebase yang lebih besar, rantai dependensi tersebar di banyak file. Mengandalkan perhatian manusia saja meninggalkan coupling implisit yang sulit dilacak.

Mental Model Inti: Pisahkan Konfigurasi dari Penggunaan

DI memisahkan pembentukan objek menjadi dua fase. Composition root merakit implementasi konkret; modul bisnis mengonsumsi interface tanpa mengetahui asalnya.

  • Fase konfigurasi (main.go): instansiasi RealGateway, teruskan ke NewProcessor.
  • Fase penggunaan (Processor): validasi input, delegasi ke gateway.Charge, kembalikan error.

Pipeline Eksekusi DI Manual

Pipeline dimulai dari composition root, mengalir melalui constructor injection, memvalidasi input, mendelegasikan ke gateway, dan mempropagasikan error ke atas.

// main.go — composition root
realGateway := &di.RealGateway{}
processor := di.NewProcessor(realGateway)
err := processor.ProcessPayment(100)

Setiap langkah eksplisit. Tidak ada pencarian container runtime di dalam ProcessPayment.

Constructor Injection: NewProcessor Menerima Interface

Struktur Processor menyimpan interface PaymentGateway. Konstruktor menerima interface tersebut; struktur tidak pernah mereferensikan RealGateway secara langsung.

// internal/di/processor.go
type Processor struct {
    gateway PaymentGateway
}

func NewProcessor(g PaymentGateway) *Processor {
    return &Processor{gateway: g}
}

func (p *Processor) ProcessPayment(amount int) error {
    if amount <= 0 {
        return errors.New("invalid amount")
    }
    m := Money{Amount: amount, Currency: "USD"}
    return p.gateway.Charge(m)
}

Dependensi yang diinject bersifat immutable setelah konstruksi. Mengganti implementasi hanya memerlukan perubahan di composition root.

Service Locator Menyembunyikan Dependensi Sesungguhnya

BadProcessor menerima Container alih-alih PaymentGateway. Dependensi aktual menjadi pencarian runtime daripada kontrak compile-time.

// internal/di/locator.go
type BadProcessor struct {
    container Container
}

func (p *BadProcessor) ProcessPayment(amount int) error {
    gw := p.container.GetPaymentGateway()  // dependensi tersembunyi
    // ...
}

Test harus mengonfigurasi container, bukan menginject mock secara langsung. Hal ini menambah indirection dan mengurangi keterbacaan.

Tiga Keputusan Arsitektural pada Lab Ini

Lab ini membuat pilihan terfokus untuk menjaga contoh tetap sederhana. Pilihan-pilihan ini menentukan struktur tanpa over-engineering.

  1. Pilih constructor injection sebagai pola default untuk dependensi yang eksplisit dan mudah diuji.
  2. Hindari service locator di domain code; gunakan hanya untuk mendemonstrasikan anti-pattern.
  3. Gunakan value object langsung (Money) karena tidak memiliki dependensi infrastruktur.

Trade-off: Manual Wiring vs Framework DI

Manual wiring menambah boilerplate di main.go tetapi menjamin type safety compile-time tanpa dependensi eksternal. Framework DI mengurangi repetisi tetapi memperkenalkan refleksi, file konfigurasi, dan object graph yang opaque.

Pada skala kecil, manual wiring seringkali lebih jelas. Pada object graph yang sangat besar, boilerplate dapat menjadi beban. Lab ini menerima boilerplate untuk menjaga contoh tetap self-contained.

Race Safety pada Implementasi DI

Race detector Go memeriksa akses memori konkuren. Implementasi DI ini tidak menggunakan goroutine atau shared state di dalam Processor. Test membangun instance secara sekuensial, sehingga tidak ada race yang dapat dideteksi.

func TestProcessor_Success(t *testing.T) {
    mock := &MockGateway{}
    proc := di.NewProcessor(mock)
    err := proc.ProcessPayment(50)
    if err != nil {
        t.Fatalf("expected nil error, got %v", err)
    }
}

Komponen stateless dengan dependensi yang diinject secara alami menghindari race condition.

Transformasi: Dari Hard-Coded ke Constructor Injection

Sebelum DI, processor menginstansiasi RealGateway secara internal. Sesudah DI, processor menerima PaymentGateway melalui konstruktornya. Test mengganti gateway nyata dengan mock tanpa menyentuh kode produksi.

Sebelum (Tight Coupling)Sesudah (Manual DI)
Processor membuat RealGateway secara internalNewProcessor menerima PaymentGateway
Test tidak bisa mock gatewayTest inject MockGateway langsung
Mengganti provider memerlukan edit kodeMengganti provider memerlukan satu baris di main.go

Interface PaymentGateway: Kontrak Tunggal

Interface ini mendefinisikan satu method. Semua implementasi berbagi kontrak yang sama.

// internal/di/gateway.go
type Money struct {
    Amount   int
    Currency string
}

type PaymentGateway interface {
    Charge(m Money) error
}

Konsumen bergantung pada interface. Produsen mengimplementasikannya. Pemisahan ini memungkinkan substitusi tanpa memodifikasi konsumen.

Money: Value Object yang Diinstansiasi Langsung

Money hanya berisi data. Ia tidak memiliki dependensi infrastruktur, sehingga dibuat langsung di dalam ProcessPayment.

m := Money{Amount: amount, Currency: "USD"}
return p.gateway.Charge(m)

Menginject value object melalui DI akan menambah abstraksi tanpa manfaat. Value object milik domain layer, bukan composition root.

MockGateway: Test Double untuk Isolasi Pengujian

MockGateway merekam panggilan dan dapat dikonfigurasi untuk berhasil atau gagal. Test memverifikasi behavior tanpa akses jaringan.

// tests/processor_test.go
type MockGateway struct {
    ChargedMoney di.Money
    ShouldFail   bool
}

func (m *MockGateway) Charge(money di.Money) error {
    if m.ShouldFail {
        return errors.New("gateway unavailable")
    }
    m.ChargedMoney = money
    return nil
}

Mock adalah tipe terstruktur yang memenuhi interface. Mereka mengganti infrastruktur tanpa mengubah kode produksi.

Composition Root: main.go sebagai Titik Penyambungan

main.go adalah satu-satunya file yang mengetahui tentang RealGateway. Ia merakit object graph dan meneruskan dependensi ke dalam.

// cmd/demo/main.go
func main() {
    realGateway := &di.RealGateway{}
    processor := di.NewProcessor(realGateway)
    fmt.Println("--- Running Constructor Injection ---")
    err := processor.ProcessPayment(100)
    if err != nil {
        fmt.Printf("Error: %v\n", err)
    }
}

Modul bisnis tidak pernah mengimpor implementasi konkret. Hal ini menjaga composition root terpusat dan domain tetap murni.

Validasi Input Sebelum Delegasi ke Gateway

ProcessPayment menolak amount yang tidak valid sebelum memanggil gateway. Ini mencegah panggilan eksternal yang tidak perlu dan gagal cepat.

if amount <= 0 {
    return errors.New("invalid amount")
}

Validasi milik domain layer. Gateway harus menjalankan invariant bisnis, bukan memaksanya.

Checklist Implementasi Dependency Injection

  • Dependensi dideklarasikan sebagai interface, bukan tipe konkret
  • Constructor injection digunakan sebagai default untuk semua service
  • Composition root adalah satu-satunya tempat membuat implementasi konkret
  • Tidak ada panggilan container.Get(...) di dalam logika domain
  • Value objects diinstansiasi langsung
  • Setiap service dapat diuji dengan mock, tanpa setup infrastruktur
  • Validasi input dilakukan sebelum delegasi ke dependensi eksternal
  • Test mencakup happy path, propagasi error, dan input tidak valid
  • go test -race ./... lolos tanpa warning

Prinsip Inti: Dependensi Harus Eksplisit

Arsitektur DI bertumpu pada tiga pilar:

  1. Separation of concerns — konfigurasi (composition root) terpisah dari penggunaan (business logic).
  2. Program to interfaces — konsumen bergantung pada kontrak, bukan implementasi.
  3. Explicit over implicit — semua dependensi dinyatakan di constructor; tidak ada magic lookup.

Prinsip-prinsip ini membuat sistem dapat diuji, dipahami, dan dikembangkan.
