Dependency Injection & Inversion of Control: Pisahkan Konfigurasi dari Penggunaan

Memisahkan konfigurasi dari logika bisnis untuk pengujian terisolasi di Go tanpa dependency eksternal.

Lukman / lukman-ss · Software Engineering Lab 16

Instansiasi Langsung Mengunci Dependensi ke Infrastruktur

Ketika sebuah kelas memanggil new ConcreteService di dalam method bisnis, logika domain menjadi terikat pada infrastruktur eksternal. Kode mungkin berjalan tanpa error pada tahap awal pengembangan; hal itu bukan berarti arsitekturnya sehat ketika vendor pihak ketiga harus diganti. Seluruh lapisan domain akan memerlukan refaktorisasi besar hanya untuk menukar satu dependensi.

Service Locator Terlihat Bersih namun Menyembunyikan Keterikatan

Banyak tim mengira Service Locator menyelesaikan masalah kopling karena pemanggilan new langsung hilang dari kode. Faktanya, menyuntikkan container generik tidak otomatis menghasilkan kode yang loosely coupled apabila dependensi sebenarnya masih tersembunyi di balik metode lookup runtime. Signature konstruktor NewBadProcessor(Container) sama sekali tidak memberitahu reviewer service apa saja yang dibutuhkan processor.

Pemisahan Konfigurasi dari Penggunaan

Prinsip dasar Fowler membedakan dua fase: perakitan graf objek dilakukan di composition root, sementara eksekusi logika bisnis terjadi di domain. Hanya pada jalur ini komponen bisnis tetap bersih dari detail infrastruktur. Value object murni seperti Money diinstansiasi langsung dan tidak pernah dilewatkan melalui container maupun injector apapun.

Alur Eksekusi Transaksi Pembayaran

Eksekusi dimulai dari instansiasi konkret di main.go, dilanjutkan pemeriksaan validasi input sebelum delegasi ke antarmuka gateway. Processor.ProcessPayment memeriksa amount <= 0 dan mengembalikan error secara instan tanpa pernah menyentuh gateway. Struct Money dibentuk langsung di stack memory. Arsitektur ini mengisolasi logika dengan baik.

Constructor Injection: Dependensi Eksplisit

type Processor struct {
    gateway PaymentGateway
}

func NewProcessor(g PaymentGateway) *Processor {
    return &Processor{gateway: g}
}

func (p *Processor) ProcessPayment(amount int) error {
    if amount <= 0 { return errors.New("invalid amount") }
    m := Money{Amount: amount, Currency: "USD"}
    return p.gateway.Charge(m)
}

Processor menyimpan interface gateway sebagai field unexported dan menerimanya strictly saat konstruksi. Penggunaan interface bukan berarti arsitektur bebas alokasi memori; teknik ini menukar overhead pointer interface demi isolasi total dependensi domain.

Kegagalan Service Locator: Container Mengabut Dependensi

// locator.go — anti-pattern
func (p *BadProcessor) ProcessPayment(amount int) error {
    if amount <= 0 {
        return errors.New("invalid amount")
    }
    m := Money{Amount: amount, Currency: "USD"}
    return p.container.GetPaymentGateway().Charge(m)
}

Service Locator menyembunyikan dependensi nyata di dalam tubuh method dan berisiko memicu nil-pointer panic saat GetPaymentGateway() mengembalikan nil pada runtime. Hanya pada jalur ini unit test dipaksa membuat MockContainer tambahan yang tidak relevan dengan kebutuhan bisnis.

Matriks Perbandingan Constructor Injection vs Service Locator

DimensiConstructor Injection (Processor)Service Locator (BadProcessor)
Deklarasi DependensiEksplisit di parameter NewProcessorTersembunyi di balik Container
Type SafetyCompile-time check, valid saat lahirRuntime resolution, rawan nil panic
Beban MockingMinimal: injeksi MockGateway langsungGanda: wajib MockContainer + MockGateway
Kopling DomainNol ke framework/containerTerikat langsung ke interface Container
RekomendasiBest practice industri modernDiskouraged (PSR-11: SHOULD NOT)

Matriks ini memetakan keunggulan mutlak Constructor Injection atas Service Locator. Injeksi via konstruktor menjamin verifikasi tipe pada saat kompilasi, sedangkan Service Locator menunda deteksi dependensi yang hilang ke runtime.

Tiga Keputusan Arsitektural Wiring Dependensi

Pertama, gunakan Constructor Injection sebagai standar baku untuk semua service inti demi validitas status dan immutability. Kedua, instansiasi langsung struct data murni seperti Money—jangan kelola DTO di dalam injector. Ketiga, gunakan manual wiring di main.go; memilih manual wiring bukan berarti anti-framework, melainkan keputusan pragmatis menjaga kesederhanaan aplikasi Go sesuai prinsip YAGNI.

Trade-off Penerapan Dependency Injection

Penerapan DI membawa konsekuensi penelusuran alur yang lebih rumit karena implementasi konkret terpisah dari titik penggunaan. Manual wiring menambah baris perakitan di composition root seiring membesarnya object graph. Menambahkan interface dan injector tidak otomatis membuat arsitektur lebih baik jika sistem masih monolitik sederhana dan tidak memerlukan pertukaran implementasi.

Keamanan Konkurensi pada Komponen Stateless

// Processor stateless: gateway read-only setelah konstruksi
type Processor struct {
    gateway PaymentGateway
}

func (p *Processor) ProcessPayment(amount int) error {
    if amount <= 0 { return errors.New("invalid amount") }
    m := Money{Amount: amount, Currency: "USD"}
    return p.gateway.Charge(m)
}

Processor bersifat stateless setelah dikonstruksi sehingga aman dipanggil konkuren lintas goroutine tanpa mutasi internal. Simulasi ini tidak sama dengan gateway jaringan riil yang mengelola koneksi socket dan state pool secara terdistribusi, namun lolos race detector Go dengan bersih.

Transformasi Desain: Hardcoded vs Constructor Injection

Sebelum menerapkan DI, logika pembayaran menginstansiasi RealGateway konkret di dalam method sehingga unit test mustahil berjalan tanpa koneksi internet. Memisahkan konstruksi ke NewProcessor bukan berarti menambah kompleksitas—hanya menambah sekitar tiga baris kode—namun membuka kemampuan testability penuh pada domain layer.

Interface Minimal dan Pengecualian Value Object

type Money struct {
    Amount   int
    Currency string
}

type PaymentGateway interface {
    Charge(m Money) error
}

Interface PaymentGateway dirancang ramping hanya dengan satu method Charge, sedangkan Money diinstansiasi langsung tanpa perantara container. Keputusan membedakan service dan value object ini cakupannya mengikuti test skenario spesifik lab ini.

Pengujian Terisolasi Menggunakan MockGateway

type MockGateway struct {
    ChargedMoney di.Money
    ShouldFail   bool
}

func (m *MockGateway) Charge(money di.Money) error {
    if m.ShouldFail { return errors.New("gateway unavailable") }
    m.ChargedMoney = money
    return nil
}

MockGateway mensimulasikan kegagalan jaringan dan mencatat payload transaksi tanpa koneksi HTTP riil. Menulis unit test dengan mock tidak otomatis menjamin integritas integrasi vendor jika payload skema production mengalami perubahan di masa depan.

Validasi Pre-Check Mencegah Panggilan Jaringan Sia-sia

func TestProcessor_InvalidAmount(t *testing.T) {
    mock := &MockGateway{}
    proc := di.NewProcessor(mock)
    err := proc.ProcessPayment(-10)
    if err == nil { t.Fatalf("expected error for negative amount") }
    if mock.ChargedMoney.Amount != 0 {
        t.Errorf("gateway should not have been called, got %d", mock.ChargedMoney.Amount)
    }
}

Test memastikan bahwa input negatif langsung ditolak di lapisan domain sebelum menyentuh gateway. Hanya pada jalur ini mock memverifikasi bahwa amount tetap 0, membuktikan bahwa panggilan jaringan berhasil dicegah sejak awal.

Propagasi Error Transparan dari Lapisan Infrastruktur

func TestProcessor_GatewayError(t *testing.T) {
    mock := &MockGateway{ShouldFail: true}
    proc := di.NewProcessor(mock)
    err := proc.ProcessPayment(50)
    if err == nil { t.Fatalf("expected error from gateway, got nil") }
}

Processor meneruskan error dari gateway secara transparan ke caller. Meneruskan error mentah bukan berarti sistem tidak butuh retry policy; ini membuktikan bahwa kontrak interface mampu mengalirkan status kegagalan infrastruktur secara akurat.

Composition Root di cmd/demo/main.go

func main() {
    realGateway := &di.RealGateway{}
    processor := di.NewProcessor(realGateway)
    _ = processor.ProcessPayment(100)

    container := &SimpleContainer{gateway: realGateway}
    badProcessor := di.NewBadProcessor(container)
    _ = badProcessor.ProcessPayment(200)
}

Fungsi main bertindak sebagai composition root tunggal tempat semua struct konkret dibuat dan dirakit. Struktur sederhana ini sengaja dipilih tanpa framework DI pihak ketiga, dan cakupannya mengikuti test verifikasi perilaku lab.

Checklist Penerapan Dependency Injection

  • Dependensi infrastruktur dideklarasikan sebagai interface, bukan struct konkret, di kode domain.
  • Constructor injection digunakan sebagai default; semua dependensi eksplisit di parameter konstruktor.
  • Composition root (main.go) adalah satu-satunya titik perakitan implementasi konkret.
  • Tidak ada pemanggilan container.Get() di dalam lapisan logika domain bisnis.
  • Value object murni (Money, DateTime) diinstansiasi langsung tanpa container.
  • Seluruh service memiliki unit test terisolasi menggunakan mock tanpa akses jaringan.

Anti-Pattern Umum dalam Penerapan DI

Service Locator leak: mengoper Container ke domain menyembunyikan dependensi nyata di balik lookup method runtime. Constructor bloat: konstruktor menerima belasan parameter merupakan sinyal keras pelanggaran Single Responsibility Principle. Value object injection: memasukkan struct data murni ke container DI bukan berarti arsitektur lebih rapi, melainkan menambah boilerplate sia-sia.

Prinsip Inti Arsitektur Jangka Panjang

Dependency Injection adalah teknik memisahkan fase konfigurasi dari eksekusi logika bisnis. Menyuntikkan dependensi via interface tidak otomatis menyelesaikan semua masalah arsitektur jika batasan bounded context tidak dirancang dengan tegas sejak awal. Tiga pilar kelangsungan arsitektur: pisahkan konfigurasi di composition root, nyatakan kontrak dependensi secara eksplisit via constructor, dan tegakkan disiplin batas domain sebelum menerapkan DI.
