Dependency Injection: Memisahkan Konstruksi dari Logika Bisnis di Go

Kontras Constructor Injection dan Service Locator di Go: validasi input, mocking tanpa jaringan, dan batas container.

Lukman / lukman-ss · Software Engineering Lab 16

Separation of Configuration from Use

Ketika sebuah fungsi bisnis menginisialisasi dependensi teknis secara langsung—misalnya Processor memanggil new RealGateway() di dalam method-nya—logika domain terkunci pada vendor infrastruktur spesifik. Perubahan protokol jaringan, kredensial API, atau implementasi mock untuk pengujian memaksa modifikasi di dalam inti logika bisnis. Martin Fowler menegaskan bahwa prinsip Separation of Configuration from Use jauh lebih fundamental daripada perdebatan sintaksis antara Dependency Injection dan Service Locator. Objek bisnis tidak boleh mencari atau merakit dependensinya sendiri; perakitan didelegasikan ke assembler luar.

Value object Money tidak menyentuh I/O

Struktur data murni seperti uang atau koordinat tidak memiliki siklus hidup independen, tidak memegang koneksi socket, dan tidak menyentuh I/O eksternal. Pada file internal/di/gateway.go, Money didefinisikan sebagai struct sederhana dengan dua field integer dan string. Lab ini secara tegas memisahkan perlakuan terhadap value object: Money diinstansiasi langsung pada baris pemanggilan logika bisnis, bukan didaftarkan ke dalam container DI atau diinjeksi via interface. Menyuntikkan struct data tanpa perilaku infrastruktur ke dalam container hanya menghasilkan abstraksi berlebihan (over-engineering) tanpa manfaat pengujian.

type Money struct {
    Amount   int
    Currency string
}

Interface PaymentGateway didefinisikan di sisi konsumen

Bahasa Go menganut konvensi idiomatik di mana konsumen abstraksi menentukan interface yang dibutuhkannya, bukan provider yang menyediakannya. PaymentGateway hanya mendeklarasikan satu method Charge(m Money) error. Interface minimalis ini melindungi Processor dari detail teknis implementasi konkret seperti pooling HTTP client, marshalling JSON, atau konfigurasi TLS. Jika di kemudian hari sistem berpindah dari RealGateway ke vendor perbankan lain, kontrak bisnis tetap utuh tanpa modifikasi struktural.

type PaymentGateway interface {
    Charge(m Money) error
}

Constructor injection menjamin kelengkapan inisialisasi

Pola Constructor Injection diimplementasikan pada internal/di/processor.go melalui fungsi NewProcessor(g PaymentGateway) *Processor. Dengan menerima kontrak interface secara eksplisit saat pembentukan objek, struct Processor tidak pernah berada dalam status separuh jadi (half-baked). Semua dependensi wajib harus disediakan sebelum objek dapat memproses transaksi bisnis. Tidak ada setter mutable yang dapat dimodifikasi secara sengaja atau tidak sengaja setelah fase perakitan selesai.

type Processor struct {
    gateway PaymentGateway
}

func NewProcessor(g PaymentGateway) *Processor {
    return &Processor{gateway: g}
}

Compiler Go menggagalkan dependensi yang tertinggal

Keunggulan utama Constructor Injection dibandingkan pendekatan dinamis adalah validasi pada waktu kompilasi (compile-time safety). Jika pengembang menambahkan dependensi baru ke dalam NewProcessor—misalnya interface AuditLogger—compiler Go akan langsung menolak seluruh kode pemanggilan yang belum menyediakan parameter tersebut. Kesalahan konfigurasi terdeteksi sebelum binary selesai dibangun, mengeliminasi risiko crash saat aplikasi menerima request pertama di lingkungan produksi.

Jebakan nil pointer pada constructor tanpa guard

Meskipun signature fungsi mewajibkan parameter bertipe interface PaymentGateway, runtime Go tetap mengizinkan pemanggilan NewProcessor(nil). Jika constructor tidak memiliki defensive guard if g == nil, objek Processor akan berhasil dibuat namun akan memicu panic: runtime error: invalid memory address or nil pointer dereference saat method p.gateway.Charge(m) dieksekusi. Lab ini mencatat bahwa pada aplikasi produksi berstandar tinggi, constructor injection wajib memvalidasi non-nil parameter atau mengembalikan tuple (*Processor, error).

Service Locator menyembunyikan dependency graph

Sebagai kontras terhadap pendekatan bersih, lab mengimplementasikan Service Locator anti-pattern pada internal/di/locator.go. Struct BadProcessor tidak menerima PaymentGateway secara langsung, melainkan menerima Container generik:

type Container interface {
    GetPaymentGateway() PaymentGateway
}

type BadProcessor struct {
    container Container
}

func NewBadProcessor(c Container) *BadProcessor {
    return &BadProcessor{container: c}
}

Pola ini menyembunyikan dependency graph sistem. Membaca konstruktor NewBadProcessor tidak memberikan petunjuk apa pun mengenai layanan eksternal apa yang sebenarnya dibutuhkan oleh prosesor untuk memproses pembayaran.

Query runtime menggantikan validasi compile-time

Pada saat pemanggilan ProcessPayment, BadProcessor melakukan query runtime ke container: p.container.GetPaymentGateway().Charge(m). Jika implementasi container lupa mendaftarkan gateway atau mengembalikan nil, compiler tidak memberikan peringatan apa pun. Kesalahan arsitektur baru meledak saat kode jalur tersebut benar-benar dilewati oleh alur eksekusi pengguna. Keterikatan terhadap API container juga mempersulit portabilitas modul ke sistem lain.

Composition Root terpusat di cmd/demo/main.go

Titik di mana fase konfigurasi dieksekusi dan graf objek dirakit disebut Composition Root. Pada cmd/demo/main.go, fungsi main bertindak sebagai assembler aplikasi. Di sinilah satu-satunya lokasi kode di mana implementasi konkret &di.RealGateway{} diinstansiasi dan disambungkan ke di.NewProcessor(realGateway). Lapisan logika bisnis di dalam internal/di/ sama sekali tidak mengimpor atau mengetahui keberadaan struct konkret ini.

func main() {
    realGateway := &di.RealGateway{}

    // Jalur Constructor Injection (Eksplisit)
    processor := di.NewProcessor(realGateway)
    _ = processor.ProcessPayment(100)

    // Jalur Service Locator (Anti-Pattern)
    container := &SimpleContainer{gateway: realGateway}
    badProcessor := di.NewBadProcessor(container)
    _ = badProcessor.ProcessPayment(200)
}

Isolasi pengetahuan tipe konkret di entrypoint

Dengan mengisolasi instansiasi tipe konkret pada entrypoint aplikasi, restrukturisasi infrastruktur menjadi sangat terlokalisasi. Jika RealGateway diganti dengan gateway yang mendukung HTTP retry, rate limiting, atau circuit breaker, perubahan hanya dilakukan pada satu baris di main.go. Seluruh kode domain pemrosesan pembayaran tetap steril tanpa ada perubahan satu baris pun pada file processor.go.

Validasi input sebelum menguras sumber daya gateway

Kedua implementasi prosesor menerapkan guard clause sebelum memanggil gateway: if amount <= 0 { return errors.New("invalid amount") }. Logika ini memverifikasi bahwa aturan domain divalidasi lebih awal di lapisan memori lokal. Transaksi invalid tidak pernah membuang koneksi jaringan, kuota API pihak ketiga, atau latensi I/O. Desain DI memastikan bahwa kepatuhan guard clause ini dapat diuji secara mandiri tanpa menyentuh gateway riil.

func (p *Processor) ProcessPayment(amount int) error {
    if amount <= 0 {
        return errors.New("invalid amount")
    }
    m := Money{Amount: amount, Currency: "USD"}
    return p.gateway.Charge(m)
}

Error propagation transparan tanpa masking

Ketika pemanggilan p.gateway.Charge(m) menghasilkan error, Processor mempropagasikan error tersebut langsung ke pemanggil tanpa menelan (swallowing) atau mengaburkan informasi kegagalan. Keterbukaan propagasi error ini krusial untuk observabilitas: layer atas (HTTP handler atau message subscriber) berhak menentukan apakah transaksi harus diulang (retry), dikirim ke Dead Letter Queue (DLQ), atau dikembalikan sebagai respons 502/503.

Test double MockGateway tanpa jaringan

Pengujian unit pada tests/processor_test.go mendefinisikan struct MockGateway yang mencatat argumen pemanggilan dan menyediakan flag pengontrol kegagalan:

type MockGateway struct {
    ChargedMoney di.Money
    ShouldFail   bool
}

func (m *MockGateway) Charge(money di.Money) error {
    if m.ShouldFail {
        return errors.New("gateway unavailable")
    }
    m.ChargedMoney = money
    return nil
}

Test double ini memungkinkan test suite berjalan instan dalam hitungan mikrodetik tanpa port jaringan, tanpa container Docker, dan tanpa ketergantungan pada server sandbox pihak ketiga.

Assertion negatif: amount tidak valid dan error gateway

Pengujian negatif memverifikasi bahwa invariant sistem tetap terjaga dalam kondisi ekstrem. Pada TestProcessor_InvalidAmount, assertion mock.ChargedMoney.Amount != 0 memastikan bahwa ketika input negatif dimasukkan, pemanggilan method Charge sama sekali tidak terjadi. Pengujian ini membuktikan bahwa validasi domain mengeksekusi *short-circuit* sebelum I/O gateway tersentuh.

Bahaya interface pollution dan package cycle di Go

Dua jebakan paling umum dalam arsitektur Go adalah interface pollution dan cyclic dependency. Interface pollution terjadi ketika pengembang menciptakan interface untuk setiap struct tunggal tanpa kebutuhan substitusi nyata, membuat navigasi kode via IDE menjadi berbelit-belit. Selain itu, jika Paket A membutuhkan Paket B dan Paket B membutuhkan Paket A untuk menyelesaikan dependency injection, compiler Go secara tegas menolak kompilasi package cycle. Solusinya adalah memindahkan interface ke sisi konsumen (consumer package) atau mendefinisikan interface pada lapisan domain inti.
