Dependency Injection: Memisahkan Konstruksi dari Logika Bisnis

Kontras Constructor Injection dan Service Locator di Go: validasi input, mocking tanpa jaringan, dan batas container.

Lukman / lukman-ss · Software Engineering Lab 16

Ketika sebuah modul bisnis menginisialisasi dependensinya secara langsung di dalam method, detail infrastruktur mengunci logika domain. Mengganti implementasi payment gateway, mengalihkan vendor notifikasi, atau mengisolasi unit test tanpa koneksi internet menjadi tugas yang rumit. Setiap modifikasi infrastruktur memaksa perubahan pada kode bisnis, dan unit test berubah menjadi integration test yang lambat.

Separation of configuration from use: biarkan pihak luar merakit dependensi, sementara domain hanya fokus mengeksekusi kontrak.

Software Engineering Lab 16 membuktikan prinsip ini dalam Go standar tanpa framework eksternal. Melalui implementasi payment processor, lab ini mengontraskan Constructor Injection dengan Service Locator anti-pattern, menunjukkan pengujian terisolasi memakai test double mock, serta menguraikan batas perlakuan terhadap value object murni.

Kontrak Interface dan Value Object

Fondasi abstraksi terletak pada file internal/di/gateway.go. Sebuah interface mendefinisikan batas kemampuan yang dibutuhkan oleh domain bisnis, terlepas dari siapa penyedianya:

// internal/di/gateway.go:11-14
type PaymentGateway interface {
    Charge(m Money) error
}

Pada file yang sama, Money didefinisikan sebagai struktur data representasional:

// internal/di/gateway.go:6-9
type Money struct {
    Amount   int
    Currency string
}

Struktur data murni seperti Money tidak menyentuh database, jaringan, atau sistem operasi. Objek semacam ini adalah value object yang diinstansiasi langsung pada baris pemanggilan, bukan disuntikkan lewat dependency injection. Memasukkan struct data ke dalam container DI hanya menambah kompleksitas tanpa nilai arsitektural.

Constructor Injection vs Service Locator

Lab mengimplementasikan dua pendekatan pemrosesan transaksi yang kontras:

1. Pendekatan Bersih: Constructor Injection

Struktur Processor di internal/di/processor.go menerima kontrak secara eksplisit melalui fungsi konstruktor:

// internal/di/processor.go:6-13
type Processor struct {
    gateway PaymentGateway
}

func NewProcessor(g PaymentGateway) *Processor {
    return &Processor{gateway: g}
}

Pola ini memberikan jaminan konkret:

  • Dependensi tampak jelas pada signature fungsi NewProcessor.
  • Objek tidak dapat dibuat dalam status setengah jadi tanpa gateway.
  • Processor tidak mengetahui keberadaan framework DI, reflection, atau container registrasi.

2. Anti-Pattern: Service Locator

Struktur BadProcessor di internal/di/locator.go menerima container generik alih-alih kontrak yang dibutuhkan:

// internal/di/locator.go:6-17
type Container interface {
    GetPaymentGateway() PaymentGateway
}

type BadProcessor struct {
    container Container
}

func NewBadProcessor(c Container) *BadProcessor {
    return &BadProcessor{container: c}
}

Pada saat pemanggilan method ProcessPayment, dependensi ditarik dari container secara dinamis:

// internal/di/locator.go:19-25
func (p *BadProcessor) ProcessPayment(amount int) error {
    if amount <= 0 {
        return errors.New("invalid amount")
    }
    m := Money{Amount: amount, Currency: "USD"}
    return p.container.GetPaymentGateway().Charge(m)
}

Pendekatan Service Locator ini menghadirkan tiga kelemahan utama:

  1. Dependensi tersembunyi di dalam implementasi method; inspeksi constructor tidak memberitahukan service apa saja yang sebenarnya dipakai.
  2. Kelas bisnis terikat erat pada API Container.
  3. Pengujian unit mewajibkan pembuatan mock container buatan, bukan sekadar menyediakan mock service.

Alur Eksekusi di Composition Root

Titik perakitan dependensi (Composition Root) ditempatkan secara terpusat pada file cmd/demo/main.go. Kode domain tidak mengurus instansiasi struct konkret:

// cmd/demo/main.go:16-35
func main() {
    realGateway := &di.RealGateway{}

    // Jalur Constructor Injection
    processor := di.NewProcessor(realGateway)
    fmt.Println("--- Running Constructor Injection ---")
    _ = processor.ProcessPayment(100)

    // Jalur Service Locator (Anti-Pattern)
    container := &SimpleContainer{gateway: realGateway}
    badProcessor := di.NewBadProcessor(container)
    fmt.Println("--- Running Service Locator ---")
    _ = badProcessor.ProcessPayment(200)
}

Hasil eksekusi program demo membuktikan kedua jalur mampu menjalankan transaksi:

--- Running Constructor Injection ---
RealGateway charging 100 USD
--- Running Service Locator ---
RealGateway charging 200 USD

Keduanya menghasilkan output yang setara, namun jalur konstruktor mengekspos seluruh kebutuhan objek pada fase kompilasi tanpa resolusi runtime tambahan.

Bukti Pengujian: 6 Assertion Tanpa Jaringan

Pengujian pada tests/processor_test.go memverifikasi kebenaran logika bisnis menggunakan test double MockGateway:

// tests/processor_test.go:10-21
type MockGateway struct {
    ChargedMoney di.Money
    ShouldFail   bool
}

func (m *MockGateway) Charge(money di.Money) error {
    if m.ShouldFail {
        return errors.New("gateway unavailable")
    }
    m.ChargedMoney = money
    return nil
}

Pengujian memverifikasi 3 skenario untuk masing-masing processor (total 6 kasus):

  1. Skenario Sukses: Transaksi valid (amount 50 dan 75) berhasil dieksekusi, status error bernilai nil, dan nilai amount serta currency tercatat presisi di dalam ChargedMoney.
  2. Propagasi Error Gateway: Ketika ShouldFail aktif, pesan error gateway unavailable diteruskan ke pemanggil tanpa diabaikan.
  3. Validasi Input Sebagai Pelindung: Ketika input bernilai negatif (amount -10 atau -5), sistem mengembalikan error invalid amount. Assertion mock.ChargedMoney.Amount == 0 memastikan bahwa panggilan ke gateway infrastruktur tidak pernah dilakukan.

Seluruh pengujian unit berjalan selesai dalam hitungan milidetik secara terisolasi tanpa memerlukan dependensi eksternal, konfigurasi database, atau kredensial API.

Pertimbangan Praktis Arsitektur

Penerapan Dependency Injection menuntut disiplin desain:

  • Manual Wiring vs Framework DI: Pada codebase Go berukuran kecil hingga menengah, perakitan manual di fungsi main memberikan visibilitas tinggi dan keamanan tipe saat kompilasi. Penggunaan reflection container menambah beban penelusuran alur eksekusi saat debugging.
  • Sinyal Constructor Bloat: Konstruktor dengan lebih dari 4 hingga 6 parameter merupakan indikasi pelanggaran Single Responsibility Principle. Solusinya adalah memecah tanggung jawab kelas, bukan membungkus seluruh parameter ke dalam satu service locator.
  • Interface Segregation: Deklarasikan interface sekecil mungkin sesuai kebutuhan pemanggil. Interface PaymentGateway hanya menuntut satu method Charge(m Money) error, menjaga kemudahan penulisan test double.
