Hard-Coded Dependencies Mengunci Logika Bisnis pada Infrastruktur

Ketika sebuah kelas membangun dependensinya sendiri, logika bisnis menjadi terkunci pada infrastruktur eksternal. Pengujian unit jadi sulit karena harus mengandalkan status jaringan nyata yang tidak deterministik.

Code Review Manual Tidak Menangkap Dependensi Tersembunyi

Code review manual mengandalkan perhatian manusia untuk menangkap pola coupling. Pendekatan ini tidak otomatis menjamin bahwa setiap dependensi eksternal telah diinjeksi melalui constructor.

Separation of Configuration from Use

Prinsip inti Dependency Injection adalah memisahkan pembentukan objek dari penggunaannya. Composition root bertugas merakit object graph, sementara modul bisnis hanya menggunakan dependensi yang telah tersedia.

Alur Kerja Dependency Injection Manual

Pipeline DI manual dimulai dari composition root yang menginialisasi implementasi konkret. Konstruktor menyimpan dependensi sebagai field, method bisnis memvalidasi input lalu mendelegasikan ke gateway.

Constructor Injection: NewProcessor Menerima Interface

Constructor injection menjamin Processor hanya mengenal interface PaymentGateway, bukan implementasi konkrét RealGateway. Dependensi dibuat eksplisit di signature constructor.

type Processor struct {
    gateway PaymentGateway
}

func NewProcessor(g PaymentGateway) *Processor {
    return &Processor{gateway: g}
}

func (p *Processor) ProcessPayment(amount int) error {
    if amount <= 0 {
        return errors.New("invalid amount")
    }
    m := Money{Amount: amount, Currency: "USD"}
    return p.gateway.Charge(m)
}

Service Locator Menyembunyikan Dependensi Sesungguhnya

Service Locator menyembunyikan dependensi sebenarnya di balik interface container. Hal ini mengurangi keterbacaan dan mempersulit mocking karena test harus menyiapkan container, bukan dependensi langsung.

Kontras Constructor Injection vs Service Locator

Tabel ini memetakan perbedaan mendasar antara dua pendekatan. Constructor injection menghasilkan dependensi yang eksplisit dan mudah diuji; service locator memperkenalkan lapisan tambahan yang menyulitkan isolasi.

AspekConstructor InjectionService Locator
DependensiEksplisit di constructorTersembunyi di container
MockingLangsung inject mockHarus mock container + get()
KekekalanField immutable setelah konstruksiBisa berubah jika container berubah
KompleksitasMudah dipahamiMenambah indirection layer
Standar IndustriDiproleh sebagai best practiceDisebabkan sebagai anti-pattern

Race Safety pada Implementasi DI

Race detector Go memeriksa akses konkuren ke memori. Implementasi DI ini tidak menggunakan goroutine atau shared state, sehingga test berlari bersih tanpa warning race condition.

func TestProcessor_Success(t *testing.T) {
    mock := &MockGateway{}
    proc := di.NewProcessor(mock)
    err := proc.ProcessPayment(50)
    if err != nil {
        t.Fatalf("expected nil error, got %v", err)
    }
    // Race detector passes; no shared mutable state
}

Transformasi: Dari Hard-Coded ke Constructor Injection

Sebelum DI, kelas bisnis langsung menginstal dependensi kongkrit, mengunci pada satu implementasi. Setelah DI, dependensi datang dari luar, memungkinkan penggantian dan pengujian terisolasi.

Interface PaymentGateway: Kontrak Tunggal

Interface PaymentGateway mendefinisikan kontrak tunggal untuk semua implementasi gateway. Money adalah value object yang mewakili uang dengan amount dan currency.

type Money struct {
    Amount   int
    Currency string
}

type PaymentGateway interface {
    Charge(m Money) error
}

Money: Value Object yang Diinstansiasi Langsung

Money dibuat langsung di dalam method karena merupakan struktur data murni tanpa dependensi infrastruktur. Menggunakan DI untuk value object akan menambah abstraksi tanpa manfaat.

func (p *Processor) ProcessPayment(amount int) error {
    if amount <= 0 {
        return errors.New("invalid amount")
    }
    m := Money{Amount: amount, Currency: "USD"}
    return p.gateway.Charge(m)
}

MockGateway: Test Double untuk Isolasi Pengujian

MockGateway merekam panggilan Charge dan dapat dikonfigurasi untuk gagal. Hal ini memungkinkan pengujian error propagation tanpa koneksi jaringan riil.

type MockGateway struct {
    ChargedMoney di.Money
    ShouldFail   bool
}

func (m *MockGateway) Charge(money di.Money) error {
    if m.ShouldFail {
        return errors.New("gateway unavailable")
    }
    m.ChargedMoney = money
    return nil
}

Composition Root: main.go sebagai Titik Penyambungan

Composition root adalah fungsi main yang bertanggung jawab merakit object graph. Ia satu-satunya place yang mengimpor implementasi konkret RealGateway.

func main() {
    realGateway := &di.RealGateway{}
    processor := di.NewProcessor(realGateway)
    fmt.Println("--- Running Constructor Injection ---")
    err := processor.ProcessPayment(100)
    if err != nil {
        fmt.Printf("Error: %v\n", err)
    }
}

Validasi Input Sebelum Delegasi ke Gateway

Validasi input dilakukan sebelum delegasi ke dependensi eksternal. Ini mencegah panggilan jaringan sia-sia dan memastikan hanya amount yang valid yang diproses.

func (p *Processor) ProcessPayment(amount int) error {
    if amount <= 0 {
        return errors.New("invalid amount")
    }
    // ... create Money and call gateway
}

Anti-Pattern Umum dalam Dependency Injection

Service Locator adalah anti-pattern karena menyembunyikan dependensi. Value object seharusnya tidak diinject. Constructor bloat menunjukkan pelanggaran Single Responsibility Principle.
