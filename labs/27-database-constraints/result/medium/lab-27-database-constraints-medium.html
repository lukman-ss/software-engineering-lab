Validasi Aplikasi Runtuh di Bawah Beban Konkuren

Pola check-then-act yang memeriksa ketersediaan data via SELECT sebelum melakukan INSERT selalu tampak berhasil pada pengujian sekuensial. Namun di bawah beban konkuren, dua thread membaca kondisi yang sama sebelum salah satunya menulis. Kegagalan ini bukan berarti kode if-check rusak, melainkan akibat ketiadaan isolasi atomik pada titik penyimpanan.

Mengapa Review Manual dan Pengecekan Memori Gagal?

Review manual sering melewatkan celah integritas karena kode validasi tampak sangat rapi dan logis di editor. Unit test sekuensial selalu memberikan status hijau karena tidak ada kompetisi thread. Menjalankan validasi di lapisan aplikasi tidak otomatis melindungi sistem jika engine penyimpanan tidak menegakkan kunci eksklusif pada saat penulisan.

Model Mental Dua Lapis: Kolaborasi Aplikasi dan Database

Arsitektur modern membagi tanggung jawab menjadi dua lapis: aplikasi melayani keramahan pesan pengguna, sedangkan database menjaga kebenaran data absolut. Validasi aplikasi menyaring input yang salah format dengan cepat. Hanya pada jalur ini, ketika terjadi tabrakan konkuren, database constraint menolak pelanggaran secara atomik dan mengembalikan kode SQLSTATE terstandar.

Urutan Evaluasi Constraint: Alur Validasi Internal Mesin

Storage engine mengevaluasi batasan data dalam urutan deterministik: NOT NULL diperiksa lebih dulu, disusul ekspresi boolean CHECK, lalu penelusuran UNIQUE index, dan terakhir FOREIGN KEY. Jika salah satu tahap gagal, operasi dibatalkan seketika tanpa ada baris data atau indeks yang tertulis. Lab ini memodelkan alur sekuensial tersebut secara atomik di dalam satu critical section.

Evaluasi Atomik Constraint di Bawah Mutex Lock

Metode InsertUser menjalankan seluruh pengecekan di dalam satu blok mutex lock yang merepresentasikan ROW EXCLUSIVE lock pada PostgreSQL. Mengunci seluruh proses bukan berarti implementasi ini memakai latch halaman B-tree yang kompleks, melainkan memodelkan jaminan atomisitas agar tidak ada goroutine lain yang dapat menyisipkan email serupa.

func (e *Engine) InsertUser(u model.User, usePartial bool) (model.User, error) {
    e.mu.Lock()
    defer e.mu.Unlock()
    if u.Email == "" { return model.User{}, dberr.NewNotNullViolation("users", "email", "users_email_not_null") }
    if u.Age < 18 { return model.User{}, dberr.NewCheckViolation("users", "users_age_check", "age >= 18") }
    if exists := e.emailIndex[u.Email]; exists {
        return model.User{}, dberr.NewUniqueViolation("users", "users_email_key", "duplicate email")
    }
    u.ID = e.userSeq.Add(1); e.users[u.ID] = u; e.emailIndex[u.Email] = u.ID
    return u, nil
}

Kronologi Tabrakan: Dua Goroutine pada Validasi Naif

Ketika dua goroutine mengeksekusi UnsafeStore.RegisterUser secara paralel, keduanya sama-sama menemukan bahwa email belum terdaftar di database. Jeda scheduling CPU mengekspos race window sehingga kedua proses sama-sama melanjutkan ke langkah INSERT. Hanya pada jalur ini duplikasi data berhasil lolos ke penyimpanan, membuktikan bahwa pengecekan memori tanpa constraint tidak berdaya.

Tiga Keputusan Kunci Merancang Integritas Skema

Desain skema yang tangguh dimulai dari mendefinisikan kolom wajib dengan NOT NULL dan batasan nilai dengan CHECK. Ketika mengelola entitas unik yang mendukung soft-delete, gunakan partial unique index agar email lama dapat didaftarkan kembali. Memasang foreign key bukan berarti pekerjaan selesai; kolom referensi tetap wajib dibuatkan indeks terpisah agar performa query tetap optimal.

Kompromi Rekayasa: Constraints vs Fleksibilitas Skema

Menerapkan database constraints menambahkan sedikit biaya komputasi pada saat INSERT karena engine harus memeriksa B-tree index dan tabel induk. Selain itu, menambahkan constraint pada tabel miliaran baris di produksi memerlukan strategi khusus agar tidak mengunci tabel terlalu lama. Namun, overhead tersebut tidak otomatis memperlambat sistem jika dibandingkan biaya besar rekonsiliasi data rusak.

Pipeline Validasi Konkuren: Goroutine vs Mutex Lock

Diagram ini memvisualisasikan penanganan 50 goroutine konkuren yang mencoba menulis email yang sama persis. Antrean mutex memaksa eksekusi berjalan serial pada saat penulisan, sehingga goroutine pemenang pertama berhasil mendaftarkan data. Seluruh goroutine berikutnya secara deterministik ditolak oleh pemeriksaan indeks unik, membuktikan bahwa isolasi atomik memotong habis celah race condition.

Transformasi: Dari UnsafeStore ke SafeStore

Sebelum menerapkan database constraints, UnsafeStore mengandalkan pemindaian memori yang mudah ditembus oleh 20 goroutine konkuren hingga menghasilkan baris duplikat. Setelah beralih ke SafeStore, delegasi ke engine database menjamin tepat satu pemenang dari 50 request paralel. Mempertahankan validasi aplikasi di depan bukan berarti redundan, melainkan jembatan penting untuk menyajikan pesan error yang informatif.

Verifikasi Test: Membuktikan Kebocoran Data pada UnsafeStore

Unit test ini membuktikan secara empiris bahwa pendekatan validasi di aplikasi gagal total di bawah konkurensi. Dua puluh goroutine yang mendaftarkan email yang sama menghasilkan lebih dari satu entri di tabel data. Kegagalan ini cakupannya mengikuti test lab, mengonfirmasi secara faktual bahwa sistem tanpa constraint penyimpanan pasti mengalami korupsi data saat menerima lonjakan request.

func TestConcurrentRegistration_Unsafe_SuffersRaceCondition(t *testing.T) {
    eng := engine.NewEngine(); s := store.NewUnsafeStore(eng)
    goroutines := 20; var wg sync.WaitGroup; wg.Add(goroutines)
    for i := 0; i < goroutines; i++ {
        go func(idx int) {
            defer wg.Done()
            _, _ = s.RegisterUser(ctx, model.User{Email: "unsafe@example.com", Username: fmt.Sprintf("u_%d", idx)})
        }(i)
    }
    wg.Wait()
    if eng.GetUsersCount() <= 1 { t.Errorf("expected race condition causing >1 user entries, got %d", eng.GetUsersCount()) }
}

Verifikasi Test: SafeStore Menjamin Tepat Satu Pemenang

Pengujian ini membuktikan ketangguhan SafeStore yang mengandalkan constraint engine. Dari 20 goroutine yang dijalankan serentak, tepat satu pendaftaran yang berhasil ditulis ke penyimpanan, sementara 19 goroutine lainnya menerima penolakan. Hanya pada jalur ini integritas tabel tetap terjaga pada angka tepat 1 baris, membuktikan keampuhan proteksi level database.

func TestConcurrentRegistration_Safe_EnforcesUniqueness(t *testing.T) {
    eng := engine.NewEngine(); s := store.NewSafeStore(eng)
    goroutines := 20; var wg sync.WaitGroup; wg.Add(goroutines)
    successCount, errorCount := 0, 0; var mu sync.Mutex
    for i := 0; i < goroutines; i++ {
        go func(idx int) {
            defer wg.Done()
            _, err := s.RegisterUser(ctx, model.User{Email: "safe@example.com", Username: fmt.Sprintf("u_%d", idx), Age: 25, Status: "active"})
            mu.Lock(); defer mu.Unlock()
            if err == nil { successCount++ } else { errorCount++ }
        }(i)
    }
    wg.Wait()
    if successCount != 1 || errorCount != 19 || eng.GetUsersCount() != 1 { t.Fatalf("integrity violated!") }
}

Solusi Soft-Delete: Partial Unique Index WHERE deleted_at IS NULL

Penerapan UNIQUE biasa pada tabel dengan soft-delete menimbulkan masalah: email pengguna yang sudah dihapus tidak akan pernah bisa didaftarkan kembali. Dengan Partial Unique Index bersyarat WHERE deleted_at IS NULL, hanya akun aktif yang diperiksa keunikannya. Pengguna yang sudah soft-delete dikeluarkan dari indeks, sehingga email yang sama dapat dipakai ulang oleh pendaftar baru.

// PARTIAL UNIQUE: CREATE UNIQUE INDEX users_active_email_idx ON users (email) WHERE deleted_at IS NULL;
if usePartialUniqueIndex {
    if u.DeletedAt == nil {
        if existingID, exists := e.activeEmails[u.Email]; exists {
            return model.User{}, dberr.NewUniqueViolation("users", "users_active_email_idx", "duplicate active email")
        }
    }
}

Mencegah Data Yatim Piatu dengan Foreign Key Constraint

Fungsi InsertOrder mengevaluasi tiga batasan secara berurutan: NOT NULL pada UserID, CHECK pada TotalCents, dan verifikasi relasional FOREIGN KEY. Jika UserID bernilai 99999 yang tidak tercatat di tabel users, sistem mengembalikan SQLSTATE 23503. Mekanisme ini mencegah terciptanya order yatim piatu yang dapat merusak rekonsiliasi keuangan sistem.

func (e *Engine) InsertOrder(o model.Order) (model.Order, error) {
    e.mu.Lock(); defer e.mu.Unlock()
    if o.UserID == 0 { return model.Order{}, dberr.NewNotNullViolation("orders", "user_id", "orders_user_id_not_null") }
    if o.TotalCents <= 0 { return model.Order{}, dberr.NewCheckViolation("orders", "orders_total_cents_check", "total > 0") }
    // FOREIGN KEY: CONSTRAINT fk_orders_user FOREIGN KEY (user_id) REFERENCES users(id)
    if _, exists := e.users[o.UserID]; !exists {
        return model.Order{}, dberr.NewForeignKeyViolation("orders", "fk_orders_user", fmt.Sprintf("key (user_id)=(%d) not present", o.UserID))
    }
    o.ID = e.orderSeq.Add(1); e.orders[o.ID] = o; return o, nil
}

Inspeksi SQLSTATE: Mengubah Error Database Menjadi Domain Error

Banyak pengembang melakukan parsing string error seperti duplicate key yang sangat rapuh terhadap pergantian bahasa basis data. Kode SQLSTATE Class 23 bersifat universal dan terstandarisasi. Menggunakan MapToDomainError memungkinkan aplikasi mengubah kode mesin menjadi pesan domain yang bersih tanpa mengekspos struktur internal database ke publik.

func MapToDomainError(err error) error {
    var cErr *ConstraintError
    if errors.As(err, &cErr) {
        switch cErr.Code {
        case SQLStateUniqueViolation: // 23505
            return fmt.Errorf("conflict: resource with this unique attribute already exists (rule: %s)", cErr.ConstraintName)
        case SQLStateNotNullViolation: // 23502
            return fmt.Errorf("invalid input: mandatory field is missing (rule: %s)", cErr.ConstraintName)
        case SQLStateCheckViolation: // 23514
            return fmt.Errorf("validation failed: value outside boundary (rule: %s)", cErr.ConstraintName)
        case SQLStateForeignKeyViolation: // 23503
            return fmt.Errorf("reference error: referenced entity does not exist (rule: %s)", cErr.ConstraintName)
        }
    }
    return err
}

Checklist Penerapan Database Constraints di Produksi

Checklist ini merangkum langkah-langkah praktis sebelum merilis skema ke produksi: penetapan NOT NULL pada kolom wajib, penerapan UNIQUE untuk proteksi race condition, pemanfaatan partial index untuk soft-delete, pemasangan CHECK untuk validasi baris, penambahan indeks pada foreign key, serta inspeksi SQLSTATE pada layer error handling.

Anti-Pattern Umum dalam Menjaga Integritas Data

Anti-pattern paling fatal adalah merasa aman dengan pola SELECT sebelum INSERT pada aplikasi. Kesalahan lainnya mencakup parsing teks error alih-alih membaca SQLSTATE, serta berasumsi bahwa foreign key secara otomatis membuatkan indeks pada kolom anak. Mengabaikan aspek ini bukan berarti sistem rusak hari ini, melainkan menanam bom waktu performa di masa depan.

Prinsip Inti: Database Adalah Benteng Terakhir Kebenaran

Aplikasi backend akan terus ditulis ulang, microservices akan terus bertambah, namun data di database akan bertahan melampaui siklus hidup kode tersebut. Menyerahkan integritas data hanya pada kode aplikasi adalah perjudian berisiko tinggi. Database constraints memastikan bahwa apa pun bug yang terjadi di lapisan aplikasi, integritas data penyimpanan tidak akan pernah ternoda.
