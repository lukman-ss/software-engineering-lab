Database Constraints: Benteng Terakhir Integritas Data

Mencegah Race Condition, Menjaga Invarian Skema, dan Menolak Duplikasi Atomik di Go

Lukman / lukman-ss · Software Engineering Lab 27

Database constraints provide declarative, ACID-guaranteed enforcement that eliminates check-then-act vulnerabilities.

Masalah Nyata: Validasi Aplikasi Runtuh di Bawah Beban Konkuren

Pola check-then-act yang memeriksa ketersediaan data via SELECT sebelum melakukan INSERT selalu tampak berhasil pada pengujian sekuensial. Namun di bawah beban konkuren, dua thread membaca kondisi yang sama sebelum salah satunya menulis. Kegagalan ini bukan berarti logika if/else salah, melainkan akibat ketiadaan isolasi atomik pada titik penyimpanan.

Duplikasi yang terdeteksi lewat pengecekan memori aplikasi membuka celah race condition yang dapat dieksploitasi oleh CPU scheduler. Deduplikasi pasca-fakta di produksi membutuhkan rekonsiliasi manual, migration rumit, dan downtime. Unit test sekuensial tanpa goroutine selalu menghasilkan pass rate 100%, menciptakan ilusi keamanan palsu.

Mengapa Review Manual dan Pengecekan Memori Gagal?

Review manual sering melewatkan celah integritas karena kode validasi tampak sangat rapi dan logis di editor. Unit test sekuensial selalu memberikan status hijau karena tidak ada kompetisi thread. Menjalankan validasi di lapisan aplikasi tidak otomatis melindungi sistem jika engine penyimpanan tidak menegakkan kunci eksklusif pada saat penulisan.

Tiga kelemahan utama pendekatan naif:

  1. Interleaving CPU Scheduling — Jeda milidetik antara query SELECT dan INSERT cukup bagi thread lain untuk menyisipkan operasinya.
  2. Unit Test Sekuensial Menipu — Test standar tanpa konkurensi goroutine selalu pass 100%, menciptakan ilusi keamanan.
  3. Tidak Otomatis Terlindungi — Menjalankan validasi di microservice terpisah tidak otomatis menjamin keunikan tanpa koordinasi locking atomik.

Arsitektur modern membagi tanggung jawab menjadi dua lapis: aplikasi melayani keramahan pesan pengguna, sedangkan database menjaga kebenaran data absolut. Validasi aplikasi menyaring input yang salah format dengan cepat.

Urutan Evaluasi Constraint: Alur Validasi Internal Mesin

Storage engine mengevaluasi batasan data dalam urutan deterministik yang telah ditetapkan:

NOT NULL (23502) → CHECK (23514) → UNIQUE / PARTIAL (23505) → FOREIGN KEY (23503) → ATOMIC COMMIT
  1. NOT NULL — Memeriksa kekosongan nilai field wajib; gagal seketika jika kolom mandatori kosong.
  2. CHECK — Mengevaluasi ekspresi boolean pada baris (misalnya age >= 18 atau status valid).
  3. UNIQUE / PARTIAL — Memeriksa tabrakan nilai pada B-tree index aktif di bawah proteksi lock eksklusif.
  4. FOREIGN KEY — Memverifikasi keberadaan ID induk pada tabel referensi sebelum commit data.
  5. ATOMIC COMMIT — Baris data dan entri index ditulis bersamaan; belum membuktikan engine multi-node di lab ini.

Jika salah satu tahap gagal, operasi dibatalkan seketika tanpa ada baris data atau indeks yang tertulis. Lab ini memodelkan alur sekuensial tersebut secara atomik di dalam satu critical section.

Evaluasi Atomik Constraint di Bawah Mutex Lock

Metode InsertUser menjalankan seluruh pengecekan di dalam satu blok mutex lock yang merepresentasikan ROW EXCLUSIVE lock pada PostgreSQL:

func (e *Engine) InsertUser(u model.User, usePartial bool) (model.User, error) {
    e.mu.Lock()
    defer e.mu.Unlock()
    if u.Email == "" { return model.User{}, dberr.NewNotNullViolation("users", "email", "users_email_not_null") }
    if u.Age < 18 { return model.User{}, dberr.NewCheckViolation("users", "users_age_check", "age >= 18") }
    if exists := e.emailIndex[u.Email]; exists {
        return model.User{}, dberr.NewUniqueViolation("users", "users_email_key", "duplicate email")
    }
    u.ID = e.userSeq.Add(1); e.users[u.ID] = u; e.emailIndex[u.Email] = u.ID
    return u, nil
}

Mengunci seluruh proses bukan berarti implementasi ini memakai latch halaman B-tree yang kompleks, melainkan memodelkan jaminan atomisitas agar tidak ada goroutine lain yang dapat menyisipkan email serupa.

Kronologi Tabrakan: Dua Goroutine pada Validasi Naif

Ketika dua goroutine mengeksekusi UnsafeStore.RegisterUser secara paralel, keduanya sama-sama menemukan bahwa email belum terdaftar di database. Jeda scheduling CPU mengekspos race window sehingga kedua proses sama-sama melanjutkan ke langkah INSERT.

Urutan terjadinya duplikasi:

  1. Pengecekan Bersamaan — Goroutine A dan B sama-sama memindai tabel dan membaca bahwa email target belum terdaftar.
  2. Jeda Penjadwalan CPU — Keduanya memasuki jeda scheduling (time.Sleep) yang membuka race window di memori aplikasi.
  3. Penulisan Ganda Sukses — Goroutine A menulis row; Goroutine B langsung menyusul menulis row dengan email yang sama persis.
  4. Integritas Runtuh — Hanya pada jalur ini tabel memuat 2 baris dengan email sama, merusak invarian keunikan sistem.

Hanya pada jalur ini duplikasi data berhasil lolos ke penyimpanan, membuktikan bahwa pengecekan memori tanpa constraint tidak berdaya di bawah konkurensi.

Tiga Keputusan Kunci Merancang Integritas Skema

Desain skema yang tangguh dimulai dari mendefinisikan kolom wajib dengan NOT NULL dan batasan nilai dengan CHECK. Ketika mengelola entitas unik yang mendukung soft-delete, gunakan partial unique index agar email lama dapat didaftarkan kembali.

  1. Mandatori & Predikat Baris — Terapkan NOT NULL dan CHECK pada setiap kolom yang memiliki batasan domain eksplisit.
  2. Keunikan & Pola Penghapusan — Pilih UNIQUE biasa untuk entitas permanen, atau Partial Index jika sistem menerapkan soft-delete.
  3. Integritas Relasional & Index — Pasang FOREIGN KEY untuk mencegah orphan row; bukan berarti cukup, kolom relasi wajib di-index manual.

Memasang foreign key bukan berarti pekerjaan selesai; kolom referensi tetap wajib dibuatkan indeks terpisah agar performa query tetap optimal.

Batasan Bukti Lab: Yang Dibuktikan vs Belum

Lab ini membuktikan semantik SQLSTATE, keefektifan atomic locking, dan mekanisme partial index menggunakan simulator in-memory Go murni. Pengujian ini belum membuktikan constraint pada database terdistribusi multi-node atau penggunaan operator eksklusi GiST.

Yang Dibuktikan: Semantik SQLSTATE 23xxx, pencegahan race condition via atomic lock, dan siklus hidup partial index.

Yang Tidak Dibuktikan: Constraint terdistribusi multi-node, isolasi SERIALIZABLE, operator GiST, dan B-tree latch riil.

Batas Klaim Empiris: Lab belum membuktikan teknik migrasi ALTER TABLE ADD CONSTRAINT NOT VALID pada tabel produksi raksasa. Delineasi antara simulasi edukasi dan kompleksitas operasional engine produksi perlu dipertahankan.

Kompromi Rekayasa: Constraints vs Fleksibilitas Skema

Menerapkan database constraints menambahkan sedikit biaya komputasi pada saat INSERT karena engine harus memeriksa B-tree index dan tabel induk. Selain itu, menambahkan constraint pada tabel miliaran baris di produksi memerlukan strategi khusus agar tidak mengunci tabel terlalu lama.

Namun, overhead tersebut tidak otomatis memperlambat sistem jika dibandingkan biaya besar rekonsiliasi data rusak. Pertukaran utamanya adalah menerima latensi tulis yang minor demi menghapus biaya katastrofik rekonsiliasi data secara permanen.

Pipeline Validasi Konkuren: Goroutine vs Mutex Lock

Diagram ini memvisualisasikan penanganan 50 goroutine konkuren yang mencoba menulis email yang sama persis. Antrean mutex memaksa eksekusi berjalan serial pada saat penulisan:

  1. 50 Goroutines Spawn — 50 worker dijalankan serentak mencoba mendaftarkan race-target@domain.com.
  2. Mutex Lock Serialization — Goroutine pertama memperoleh lock eksklusif; 49 worker lainnya mengantre tertib.
  3. First Insert Success — Worker 1 lolos pengecekan, mencatatkan email ke tabel dan map index, lalu melepas lock.
  4. 49 Abort SQLSTATE 23505 — Worker 2–50 bergantian masuk lock, mendeteksi email sudah ada, dan langsung menerima error 23505.

Isolasi atomik memotong habis celah race condition. Setiap worker berikutnya secara deterministik ditolak oleh pemeriksaan indeks unik.

Transformasi: Dari UnsafeStore ke SafeStore

Sebelum menerapkan database constraints, UnsafeStore mengandalkan pemindaian memori yang mudah ditembus oleh 20 goroutine konkuren hingga menghasilkan baris duplikat. Setelah beralih ke SafeStore, delegasi ke engine database menjamin tepat satu pemenang dari 50 request paralel.

Verifikasi Test: Membuktikan Kebocoran Data pada UnsafeStore

Unit test ini membuktikan secara empiris bahwa pendekatan validasi di aplikasi gagal total di bawah konkurensi:

func TestConcurrentRegistration_Unsafe_SuffersRaceCondition(t *testing.T) {
    eng := engine.NewEngine(); s := store.NewUnsafeStore(eng)
    goroutines := 20; var wg sync.WaitGroup; wg.Add(goroutines)
    for i := 0; i < goroutines; i++ {
        go func(idx int) {
            defer wg.Done()
            _, _ = s.RegisterUser(ctx, model.User{Email: "unsafe@example.com", Username: fmt.Sprintf("u_%d", idx)})
        }(i)
    }
    wg.Wait()
    if eng.GetUsersCount() <= 1 { t.Errorf("expected race condition causing >1 user entries, got %d", eng.GetUsersCount()) }
}

Dua puluh goroutine yang mendaftarkan email yang sama menghasilkan lebih dari satu entri di tabel data. Kegagalan ini cakupannya mengikuti test lab, mengonfirmasi secara faktual bahwa sistem tanpa constraint penyimpanan pasti mengalami korupsi data saat menerima lonjakan request.

Verifikasi Test: SafeStore Menjamin Tepat Satu Pemenang

Pengujian ini membuktikan ketangguhan SafeStore yang mengandalkan constraint engine:

func TestConcurrentRegistration_Safe_EnforcesUniqueness(t *testing.T) {
    eng := engine.NewEngine(); s := store.NewSafeStore(eng)
    goroutines := 20; var wg sync.WaitGroup; wg.Add(goroutines)
    successCount, errorCount := 0, 0; var mu sync.Mutex
    for i := 0; i < goroutines; i++ {
        go func(idx int) {
            defer wg.Done()
            _, err := s.RegisterUser(ctx, model.User{Email: "safe@example.com", Username: fmt.Sprintf("u_%d", idx), Age: 25, Status: "active"})
            mu.Lock(); defer mu.Unlock()
            if err == nil { successCount++ } else { errorCount++ }
        }(i)
    }
    wg.Wait()
    if successCount != 1 || errorCount != 19 || eng.GetUsersCount() != 1 { t.Fatalf("integrity violated!") }
}

Dari 20 goroutine yang dijalankan serentak, tepat satu pendaftaran yang berhasil ditulis ke penyimpanan, sementara 19 goroutine lainnya menerima penolakan. Integritas tabel tetap terjaga pada angka tepat 1 baris.

Solusi Soft-Delete: Partial Unique Index WHERE deleted_at IS NULL

Penerapan UNIQUE biasa pada tabel dengan soft-delete menimbulkan masalah: email pengguna yang sudah dihapus tidak akan pernah bisa didaftarkan kembali. Dengan Partial Unique Index bersyarat WHERE deleted_at IS NULL, hanya akun aktif yang diperiksa keunikannya.

// PARTIAL UNIQUE: CREATE UNIQUE INDEX users_active_email_idx ON users (email) WHERE deleted_at IS NULL;
if usePartialUniqueIndex {
    if u.DeletedAt == nil {
        if existingID, exists := e.activeEmails[u.Email]; exists {
            return model.User{}, dberr.NewUniqueViolation("users", "users_active_email_idx", "duplicate active email")
        }
    }
}
// Saat soft delete: delete(e.activeEmails, u.Email) -> email langsung dapat didaftarkan kembali
// Baris dengan deleted_at != nil tidak diindeks, sehingga multi-duplikat soft-delete tetap valid.

Pengguna yang sudah soft-delete dikeluarkan dari indeks, sehingga email yang sama dapat dipakai ulang oleh pendaftar baru tanpa konflik.

Mencegah Data Yatim Piatu dengan Foreign Key Constraint

Fungsi InsertOrder mengevaluasi tiga batasan secara berurutan:

func (e *Engine) InsertOrder(o model.Order) (model.Order, error) {
    e.mu.Lock(); defer e.mu.Unlock()
    if o.UserID == 0 { return model.Order{}, dberr.NewNotNullViolation("orders", "user_id", "orders_user_id_not_null") }
    if o.TotalCents <= 0 { return model.Order{}, dberr.NewCheckViolation("orders", "orders_total_cents_check", "total > 0") }
    // FOREIGN KEY: CONSTRAINT fk_orders_user FOREIGN KEY (user_id) REFERENCES users(id)
    if _, exists := e.users[o.UserID]; !exists {
        return model.Order{}, dberr.NewForeignKeyViolation("orders", "fk_orders_user", fmt.Sprintf("key (user_id)=(%d) not present", o.UserID))
    }
    o.ID = e.orderSeq.Add(1); e.orders[o.ID] = o; return o, nil
}

Jika UserID bernilai 99999 yang tidak tercatat di tabel users, sistem mengembalikan SQLSTATE 23503. Mekanisme ini mencegah terciptanya order yatim piatu yang dapat merusak rekonsiliasi keuangan sistem.

Inspeksi SQLSTATE: Mengubah Error Database Menjadi Domain Error

Banyak pengembang melakukan parsing string error seperti "duplicate key" yang sangat rapuh terhadap pergantian bahasa basis data. Kode SQLSTATE Class 23 bersifat universal dan terstandarisasi:

func MapToDomainError(err error) error {
    var cErr *ConstraintError
    if errors.As(err, &cErr) {
        switch cErr.Code {
        case SQLStateUniqueViolation: // 23505
            return fmt.Errorf("conflict: resource with this unique attribute already exists (rule: %s)", cErr.ConstraintName)
        case SQLStateNotNullViolation: // 23502
            return fmt.Errorf("invalid input: mandatory field is missing (rule: %s)", cErr.ConstraintName)
        case SQLStateCheckViolation: // 23514
            return fmt.Errorf("validation failed: value outside boundary (rule: %s)", cErr.ConstraintName)
        case SQLStateForeignKeyViolation: // 23503
            return fmt.Errorf("reference error: referenced entity does not exist (rule: %s)", cErr.ConstraintName)
        }
    }
    return err
}

Menggunakan MapToDomainError memungkinkan aplikasi mengubah kode mesin menjadi pesan domain yang bersih tanpa mengekspos struktur internal database ke publik.

Checklist Penerapan Database Constraints di Produksi

Langkah-langkah praktis sebelum merilis skema ke produksi:

  • Tandai seluruh kolom mandatori dengan NOT NULL, jangan hanya mengandalkan validasi form.
  • Terapkan UNIQUE constraint pada atribut unik alih-alih melakukan SELECT sebelum INSERT.
  • Gunakan Partial Unique Index (WHERE deleted_at IS NULL) untuk entitas yang mendukung soft-delete.
  • Definisikan CHECK constraint untuk membatasi rentang nilai angka dan enum status kolom.
  • Pasang indeks eksplisit pada kolom referencing FOREIGN KEY demi mencegah full table scan saat DELETE parent.
  • Periksa kode SQLSTATE Class 23 (23502, 23505, 23514, 23503) pada error handler aplikasi.

Anti-Pattern Umum dalam Menjaga Integritas Data

Anti-pattern paling fatal adalah merasa aman dengan pola SELECT sebelum INSERT pada aplikasi. Kesalahan lainnya mencakup parsing teks error alih-alih membaca SQLSTATE, serta berasumsi bahwa foreign key secara otomatis membuatkan indeks pada kolom anak.

Anti-PatternRisiko
Check-Then-Act di AplikasiSELECT sebelum INSERT pasti bocor di bawah beban konkuren
Menebak String ErrorRegex matching pada teks error database yang dapat berubah sewaktu-waktu
Bukan Berarti Ter-IndexFOREIGN KEY bukan berarti kolom otomatis terindeks; ketiadaan indeks manual merusak performa query DELETE

Mengabaikan aspek ini bukan berarti sistem rusak hari ini, melainkan menanam bom waktu performa di masa depan.

Prinsip Inti: Database Adalah Benteng Terakhir Kebenaran

Aplikasi backend akan terus ditulis ulang, microservices akan terus bertambah, namun data di database akan bertahan melampaui siklus hidup kode tersebut. Menyerahkan integritas data hanya pada kode aplikasi adalah perjudian berisiko tinggi.

PilarDeskripsi
Deklaratif di Titik TulisLetakkan aturan keabsahan data sedekat mungkin dengan media penyimpanan agar terlindungi secara atomik
Pemisahan Peran yang JelasAplikasi melayani kenyamanan interaksi pengguna; database constraints menjamin kebenaran absolut
Tidak Otomatis LambatMemasang constraint tidak otomatis menyelesaikan aturan lintas tabel; pahami batas row-scoped versus triggers

Database constraints memastikan bahwa apa pun bug yang terjadi di lapisan aplikasi, integritas data penyimpanan tidak akan pernah ternoda.

Jangan pernah percayakan integritas data hanya pada application code; database constraint adalah benteng terakhir kebenaran absolut.
