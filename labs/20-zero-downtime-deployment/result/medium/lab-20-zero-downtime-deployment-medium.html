Zero-Downtime Deployment: Shutdown Graceful, Draining, & Expand–Contract DB

Koordinasi health probe, preStop hook, connection draining, dan migrasi database tanpa menghentikan layanan.

Lukman / lukman-ss · Software Engineering Lab 20

Problem: Dampak Tanpa Draining

Mematikan instance secara tiba-tiba tanpa koordinasi menyebabkan tiga dampak langsung: request HTTP yang sedang berjalan terputus, job background berhenti dan meninggalkan state parsial, serta skema database yang berubah tidak kompatibel antara versi aplikasi lama dan baru. Pengguna menerima error 502/504; job terhenti dengan state terpotong; versi baru tidak dapat membaca data yang ditulis versi lama.

Mental Model: Mulai Baru Sebelum Hentikan yang Lama

Prinsip inti zero-downtime deployment adalah koeksistensi. Versi dua (v2) dan versi satu (v1) harus berjalan bersamaan pada infrastruktur yang sama, mengakses database yang sama, dan berbagi load balancer yang sama. Ketiga mekanisme utama yang mengatur koeksistensi ini adalah: health probe untuk routing traffic, graceful shutdown untuk penutupan koneksi, dan expand–contract untuk evolusi schema database.

Komponen Arsitektur

Lab ini terbagi menjadi tiga modul independen:

  • internal/db: Penyimpanan in-memory yang mengimplementasikan pola expand–contract untuk migrasi schema.
  • internal/server: Server HTTP dengan endpoint liveness dan readiness, delay preStop yang dapat dikonfigurasi, dan mekanisme connection draining.
  • internal/worker: Background queue worker yang memproses job secara kooperatif saat menerima sinyal berhenti.

Health Probe: Liveness vs Readiness

Liveness probe (/healthz/live) hanya memeriksa apakah proses berjalan. Readiness probe (/healthz/ready) menentukan apakah instance siap menerima lalu lintas jaringan dari load balancer. Server memulai dengan readiness false (mengembalikan HTTP 503), kemudian beralih ke true (HTTP 200) setelah inisialisasi selesai.

mux.HandleFunc("/healthz/ready", func(w http.ResponseWriter, r *http.Request) {
    if s.ready.Load() {
        w.WriteHeader(http.StatusOK)
        w.Write([]byte("READY"))
    } else {
        w.WriteHeader(http.StatusServiceUnavailable)
        w.Write([]byte("NOT READY"))
    }
})

Pemisahan liveness dan readiness penting: proses bisa hidup tetapi belum siap (misalnya sedang melakukan cache warming atau koneksi database timeout). Load balancer hanya mengirim traffic ke instance yang readiness-nya true.

PreStop Hook: Jembatan Routing Asinkron

Pada orchestrator seperti Kubernetes, pengiriman SIGTERM dan pembaruan EndpointSlice atau kube-proxy berlangsung asinkron. Jika pod mati sebelum routing table eksternal diperbarui, klien tetap dikirim ke pod yang sudah dalam proses penghentian dan menerima HTTP 502/504.

Lab mengimplementasikan preStop delay menggunakan select pada time.After atau ctx.Done(). Ini memungkinkan context cancellation untuk membatalkan jeda jika deadline habis, menghindari deadlocks saat caller timeout.

if s.preStop > 0 {
    select {
    case <-time.After(s.preStop):
    case <-ctx.Done():
        return ctx.Err()
    }
}

Nilai preStop produksi harus melebihi latensi propagasi routing eksternal (kube-proxy, cloud LB). Estimasi terlalu rendah menyebabkan HTTP 502/504 saat routing masih mengarah ke pod yang terminasi.

Graceful Shutdown: Connection Draining

Metode Server.Shutdown menjalankan tiga langkah berurutan:

  1. Menetapkan readiness false, mengisolasi instance dari load balancer.
  2. Mengeksekusi preStop delay.
  3. Menelepon srv.Shutdown(ctx) untuk menolak koneksi baru, lalu menunggu semua request aktif selesai melalui wg.Wait().
s.SetReady(false)
if s.preStop > 0 {
    select { case <-time.After(s.preStop): case <-ctx.Done(): return ctx.Err() }
}
err := s.srv.Shutdown(ctx)
s.wg.Wait()

wg.Wait() menunda eksekusi sampai activeCount nol — setiap request in-flight selesai sebelum proses keluar. Request baru yang masuk selama shutting down ditolak oleh handler http.Server.

Worker: Drain Kooperatif dengan Timeout

Worker menjalankan beberapa goroutine yang menarik job dari channel. Saat Stop(timeout) dipanggil:

  • Flag stopped diset, channel ditutup — tidak ada job baru yang diterima.
  • wg.Wait() menunggu goroutine aktif selesai.
  • Jika timeout tercapai, w.cancel() membatalkan context untuk menghentikan job yang berjalan.
func (w *Worker) Stop(timeout time.Duration) {
    w.enqueueMu.Lock()
    w.stopped.Store(true)
    close(w.jobChan)
    w.enqueueMu.Unlock()

    done := make(chan struct{})
    go func() { w.wg.Wait(); close(done) }()

    select {
    case <-done:
    case <-time.After(timeout):
        w.cancel()
        <-done
    }
}

Job yang sedang aktif diselesaikan; job yang tertunda di channel dibuang saat timeout. Implementasi produksi memerlukan job-level preemption atau hard deadline escalation untuk runtime yang tidak terbatas.

Pola Expand–Contract Database

Migrasi schema database dibagi menjadi fase bertahap:

  • Expand: Tambahkan kolom baru (first_name, last_name) tanpa menghapus kolom lama (name). Aplikasi mendukung kedua format baca/tulis.
  • Migrate: Backfill data historis, dual-write untuk record baru.
  • Contract: Hapus kolom lama (name) hanya setelah seluruh instance menjalankan versi baru.
type UserRecord struct {
    ID        string
    Name      string
    FirstName string
    LastName  string
}

Logika read otomatis mengonversi format legacy: jika FirstName dan LastName kosong, parser Name diisi terpisah. Write menyimpan kedua representasi untuk kompatibilitas silang.

Langkah Checklist Produksi

  1. Implementasi readiness probe mengembalikan 503 sampai warmup selesai.
  2. Konfigurasi preStop hook >= latensi propagasi routing eksternal.
  3. Pola expand–contract DB dengan backward-compatible reads dan writes.
  4. Worker drain dengan timeout dan context cancellation.
  5. Dead letter queue untuk job yang gagal setelah timeout.

Kapan Menggunakan Pola Ini

Pilih zero-downtime deployment ketika SLA mensyaratkan nol detik unavailable, job background harus selesai atau gagal secara eksplisit, dan schema database berevolusi melintasi versi yang koeksis.

Jangan gunakan untuk:

  • Monolit dengan satu database: transaksi ACID lokal sudah cukup.
  • Layanan non-kritis di mana downtime singkat dapat ditoleransi.
  • Transformasi schema destructif yang tidak memerlukan backward compatibility.
