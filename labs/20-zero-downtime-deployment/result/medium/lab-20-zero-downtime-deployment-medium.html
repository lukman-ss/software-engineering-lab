Membedah propagasi routing asinkron, penundaan terminasi pod, connection draining HTTP, cooperative queue worker, dan evolusi skema database paralel.

Lukman / lukman-ss · Software Engineering Lab 20

Masalah penghentian instan pada deployment produksi

Setiap kali versi baru aplikasi didistribusikan ke lingkungan produksi, penghentian instance lama secara mendadak menimbulkan tiga kategori kegagalan sistem:

  1. Koneksi HTTP Terputus: Permintaan pengguna yang sedang diproses di tengah jalan (in-flight requests) langsung dijatuhkan, menghasilkan galat HTTP 502 Bad Gateway atau Connection Reset By Peer.
  2. Kerusakan Status Pekerjaan Asinkron: Worker antrean background yang dimatikan paksa di tengah eksekusi meninggalkan data dalam kondisi inkonsisten atau memicu duplikasi pekerjaan saat mekanisme at-least-once dijalankan ulang.
  3. Konflik Skema Database: Perubahan kolom yang merusak kompatibilitas (breaking change) menyebabkan aplikasi versi lama mengalami crash akibat query SQL yang mendadak tidak valid.
Zero-downtime deployment requires version coexistence. Start new instances before stopping old ones, decouple readiness from process liveness, and maintain database backward compatibility across version boundaries.

Di dalam Software Engineering Lab 20, kita membedah dan mengimplementasikan seluruh mekanisme penunjang Zero-Downtime Deployment (ZDD) menggunakan Go: pemisahan liveness dan readiness probe, penanganan jeda propagasi routing jaringan melalui preStop hook, graceful shutdown HTTP listener, terminasi kooperatif background worker, dan pola database Expand and Contract.

Mental model utama: Jalankan yang baru sebelum mematikan yang lama

Prinsip dasar zero-downtime deployment adalah koeksistensi versi. Versi aplikasi baru (Versi N) dan versi lama (Versi N-1) harus dapat berjalan berdampingan pada infrastruktur fisik yang sama, berbagi cluster database yang sama, dan melayani lalu lintas pengguna secara simultan selama proses peluncuran berlangsung.

PreStop Hook Menunda terminasi pod agar tabel routing jaringan sempat diperbarui Lonjakan galat HTTP 502 selama jeda propagasi EndpointSlice

Pemisahan Liveness Probe dan Readiness Probe

Pada orkestrator kontainer modern seperti Kubernetes, pemeriksaan kesehatan dibagi menjadi dua probe independen:

  • Liveness Probe (/healthz/live): Menjawab pertanyaan "Apakah proses aplikasi masih hidup dan tidak mengalami deadlock internal?". Jika probe ini gagal, orkestrator langsung me-restart kontainer.
  • Readiness Probe (/healthz/ready): Menjawab pertanyaan "Apakah instance ini siap menerima lalu lintas jaringan dari load balancer?". Jika probe ini gagal, orkestrator hanya mencabut pod dari daftar endpoint load balancer tanpa mematikan proses.

Menyatukan kedua probe ini adalah kesalahan fatal. Ketika sebuah service sedang melakukan pemanasan cache memori internal atau menunggu koneksi database, ia harus mengembalikan status tidak siap (HTTP 503) pada readiness probe, namun tetap mempertahankan liveness probe pada status sehat (HTTP 200). Pada internal/server/server.go, status kesiapan dikontrol melalui atomic mutex state:

func (s *Server) SetReady(ready bool) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.ready = ready
}

func (s *Server) liveHandler(w http.ResponseWriter, r *http.Request) {
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte("OK"))
}

func (s *Server) readyHandler(w http.ResponseWriter, r *http.Request) {
	s.mu.RLock()
	ready := s.ready
	s.mu.RUnlock()

	if !ready {
		w.WriteHeader(http.StatusServiceUnavailable)
		_, _ = w.Write([]byte("UNREADY"))
		return
	}
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte("READY"))
}

Celah propagasi routing asinkron dan kebutuhan PreStop Hook

Banyak pengembang berasumsi bahwa saat proses menerima sinyal SIGTERM dari orkestrator, load balancer atau ingress controller sudah selesai mencabut pod dari daftar routing. Asumsi ini keliru secara arsitektural.

Pada Kubernetes, siklus terminasi pod dan propagasi endpoint berjalan pada dua jalur kontrol yang terpisah dan asinkron:

  • Jalur Terminasi Pod (Control Plane): API Server mengubah status Pod menjadi Terminating → Kubelet langsung mengeksekusi sinyal SIGTERM ke proses di dalam kontainer.
  • Jalur Pembaruan Jaringan (Data Plane): API Server memberitahu Endpoints/EndpointSlice Controller → Controller memperbarui daftar IP → Agen jaringan (Kube-proxy, CNI, Ingress Gateway, Cloud Load Balancer) mendownload pembaruan → Aturan iptables/IPVS atau tabel upstream proxy dirombak.

Karena jalur data plane melintasi banyak hop jaringan dan pembaruan controller berkala, terdapat jeda propagasi selama ratusan milidetik hingga beberapa detik. Selama jeda ini, load balancer masih terus mengirimkan request pengguna baru ke pod lama. Jika server HTTP langsung menutup listener soket seketika saat menerima SIGTERM, seluruh request baru tersebut akan ditolak mentah-mentah (Connection Refused / HTTP 502).

Solusinya adalah menerapkan preStop hook delay. Begitu sinyal shutdown diterima, server menandai dirinya unready pada readiness probe, lalu menahan diri (delay) selama durasi tertentu agar tabel routing di luar sempat terbarui sebelum listener HTTP mulai ditutup:

func (s *Server) Shutdown(ctx context.Context) error {
	log.Println("Server received shutdown request")

	s.SetReady(false)
	log.Println("Server marked unready, detached from load balancer")

	if s.preStop > 0 {
		log.Printf("Executing preStop sleep for %v to allow routing table updates...", s.preStop)
		select {
		case <-time.After(s.preStop):
		case <-ctx.Done():
			log.Println("preStop sleep interrupted by context cancellation")
			return ctx.Err()
		}
	}

	log.Println("Initiating graceful shutdown of HTTP listeners...")
	err := s.srv.Shutdown(ctx)
	if err != nil {
		return fmt.Errorf("shutdown error: %w", err)
	}

	s.wg.Wait()
	log.Println("All in-flight requests completed. Server stopped gracefully.")
	return nil
}

Perhatikan bahwa implementasi di atas tidak menggunakan time.Sleep telanjang. Jeda dikelola menggunakan konstruksi select antara time.After dan ctx.Done(). Jika context dibatalkan karena batas waktu timeout orkestrator habis, jeda langsung terhenti secara kooperatif tanpa membuat proses menggantung sebagai zombie.

Graceful HTTP connection draining

Setelah jeda preStop terlampaui dan lalu lintas baru dipastikan berhenti mengalir, server memanggil srv.Shutdown(ctx) bawaan paket net/http Go. Fungsi ini menutup listener port agar tidak ada koneksi TCP baru yang diterima, namun membiarkan koneksi aktif yang sedang berjalan menyelesaikan pemrosesannya.

Untuk memastikan goroutine internal pelayan request terpantau sempurna, handler /work memanfaatkan sync.WaitGroup:

func (s *Server) workHandler(w http.ResponseWriter, r *http.Request) {
	s.wg.Add(1)
	defer s.wg.Done()

	durationStr := r.URL.Query().Get("duration")
	d, err := time.ParseDuration(durationStr)
	if err != nil {
		d = 50 * time.Millisecond
	}

	select {
	case <-time.After(d):
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("WORK_DONE"))
	case <-r.Context().Done():
		http.Error(w, "Request cancelled", http.StatusRequestTimeout)
	}
}

Database Parallel Change: Pola Expand and Contract

Hambatan paling berat dalam arsitektur zero-downtime adalah skema database relasional. Jika sebuah tabel memiliki kolom name dan tim ingin memecahnya menjadi first_name dan last_name, mengubah skema tabel secara langsung dalam satu langkah deployment akan menghancurkan sistem. Pod versi lama yang masih berjalan akan gagal mengeksekusi query SQL karena kolom name mendadak hilang.

Pola Expand and Contract (disebut juga Parallel Change) membagi evolusi skema ke dalam empat tahap terpisah:

Tahapan Perubahan Skema Database Perilaku Aplikasi (Kode)
1. Baseline Kolom lama name aktif Aplikasi Versi N-1 membaca dan menulis name
2. Expand Tambah kolom nullable first_name dan last_name Aplikasi Versi N dideploy: Dual-write dan Fallback-read
3. Migrate Skema tetap berisi kolom lama dan baru Background script melakukan backfill baris lama ke kolom baru
4. Contract Hapus kolom lama name (DROP COLUMN) Seluruh instance Versi N-1 sudah mati; Versi N murni membaca kolom baru

Pada internal/db/db.go, mesin penyimpanan memodelkan logika fallback transparan saat membaca data pengguna:

type UserRecord struct {
	ID        string
	Name      string // Format lama
	FirstName string // Format baru
	LastName  string // Format baru
}

func (s *UserStore) GetUser(id string) (UserRecord, error) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	rec, ok := s.records[id]
	if !ok {
		return UserRecord{}, ErrNotFound
	}

	if rec.FirstName == "" && rec.LastName == "" && rec.Name != "" {
		parts := strings.SplitN(rec.Name, " ", 2)
		rec.FirstName = parts[0]
		if len(parts) > 1 {
			rec.LastName = parts[1]
		}
	} else if rec.Name == "" {
		rec.Name = strings.TrimSpace(rec.FirstName + " " + rec.LastName)
	}

	return rec, nil
}

Bahaya lock contention DDL di PostgreSQL

Dalam database produksi berskala besar (seperti PostgreSQL), mengeksekusi DDL pada fase Expand memerlukan kehati-hatian tinggi terhadap penguncian tabel:

  • Constant Default vs Volatile Default: Sejak PostgreSQL 11, menambahkan kolom baru dengan nilai default konstan (seperti DEFAULT 'active' atau DEFAULT NULL) hanyalah operasi metadata tanpa menulis ulang tabel fisik (zero-rewrite). Namun, jika nilai default bersifat volatil (seperti DEFAULT clock_timestamp() atau gen_random_uuid()), PostgreSQL dipaksa menulis ulang seluruh tabel pada disk dan mengunci tabel secara eksklusif.
  • Antrean Lock ACCESS EXCLUSIVE: Perintah DDL ALTER TABLE selalu meminta lock ACCESS EXCLUSIVE. Jika terdapat transaksi analitik atau query transaksi lambat yang sedang membaca tabel tersebut, DDL akan mengantre di belakangnya. Yang berbahaya, seluruh query SELECT baru berikutnya akan ikut tertahan di belakang antrean DDL, menyebabkan koneksi database aplikasi menumpuk seketika dan memicu mati total sistem.

Untuk mencegah bencana ini, migrasi DDL di produksi wajib menetapkan batasan timeout penguncian:

SET lock_timeout = '2s';
ALTER TABLE users ADD COLUMN first_name VARCHAR(100);

Penghentian kooperatif pada background queue worker

Berbeda dengan server HTTP yang siklus request-responsenya berdurasi milidetik, background queue worker dapat mengeksekusi pekerjaan komputasi atau pengiriman data yang berlangsung selama hitungan detik hingga menit. Menghentikan worker secara tiba-tiba akan menghasilkan pekerjaan berstatus setengah selesai atau memicu eksekusi ganda yang melanggar integritas bisnis.

Pada internal/worker/worker.go, siklus hidup goroutine pekerja dikelola secara kooperatif:

func (w *Worker) Start(concurrency int) {
	for i := 0; i < concurrency; i++ {
		w.wg.Add(1)
		go func(workerID int) {
			defer w.wg.Done()
			for {
				select {
				case <-w.ctx.Done():
					return
				case job, ok := <-w.jobChan:
					if !ok {
						return
					}
					select {
					case <-w.ctx.Done():
						log.Printf("Worker %d dropping job %s due to shutdown context cancellation", workerID, job.ID)
						return
					default:
					}

					log.Printf("Worker %d starting job %s", workerID, job.ID)
					select {
					case <-time.After(job.Duration):
						w.completedMu.Lock()
						w.completed = append(w.completed, job.ID)
						w.completedMu.Unlock()
						log.Printf("Worker %d finished job %s", workerID, job.ID)
					case <-w.ctx.Done():
						log.Printf("Worker %d aborted job %s due to shutdown timeout", workerID, job.ID)
						return
					}
				}
			}
		}(i)
	}
}

Ketika fungsi w.Stop(timeout) dieksekusi:

  1. Worker mengubah status internal dan menutup intake channel, sehingga pemanggilan Enqueue baru langsung ditolak dengan aman.
  2. Goroutine pekerja menyelesaikan satu pekerjaan yang sedang aktif berada di tangannya.
  3. Jika seluruh pekerjaan aktif selesai sebelum durasi timeout habis, worker berhenti secara bersih.
  4. Jika durasi batas waktu pengurasan (drain timeout) terlampaui sebelum pekerjaan selesai, konteks dibatalkan (cancel()), pekerjaan yang sedang berjalan dihentikan, dan sisa buffer antrean dibuang.

Batas implementasi lab dan pertimbangan produksi

Kejujuran teknis mewajibkan penegasan batasan pengujian: Lab 20 memodelkan simulasi in-memory Go untuk siklus hidup HTTP draining, jeda propagasi routing, dan fallback skema database. Lab ini tidak menjalankan cluster Kubernetes fisik, cloud load balancer eksternal, atau proses database PostgreSQL nyata.
