Load Testing: Saat Booking Berhasil tetapi Antrean Membesar

Membaca VU, RPS, P95, dan P99 melalui server Go dengan lima slot database simulasi.

Lukman / lukman-ss · Software Engineering Lab 15

Booking cepat saat sepi, antre saat ramai

Satu booking yang berhasil belum menjelaskan perilaku endpoint ketika banyak pengguna datang bersama. Lab 15 mengirim HTTP POST ke /booking pada server lokal. Perbandingan beban rendah dan tinggi membantu melihat perubahan latency ketika slot kerja terbatas. Fokusnya adalah antrean dan distribusi waktu respons, bukan integrasi database production atau pembuktian bahwa aplikasi siap melayani semua pola traffic.

Dua skenario dengan server yang sama

Demo memakai lima slot simulasi database dan query dasar 20 ms. Smoke menjalankan dua virtual user, sedangkan stress menjalankan 50 virtual user. Keduanya berdurasi dua detik, dijalankan berurutan, memakai endpoint dan body booking yang sama. Angka tersebut merupakan konfigurasi eksperimen kecil untuk memperlihatkan saturasi; jumlah VU tidak otomatis menjadi target pengguna bisnis atau kapasitas maksimum layanan.

VU mengirim request secara berurutan

Runner membuat satu goroutine untuk setiap VU. Di dalamnya, request berikutnya dikirim setelah request sebelumnya selesai atau gagal. Tidak ada think time, ramp-up, atau penjadwal arrival rate. Ini menghasilkan pola closed loop: ketika respons melambat, setiap VU mengirim lebih sedikit request dalam satu detik. Karena itu, menaikkan VU dan menetapkan RPS adalah dua eksperimen yang berbeda.

Batas kerja memakai buffered channel

Server membuat semaphore berupa buffered channel dengan kapasitas MaxDBConnections. Handler harus memasukkan token sebelum melanjutkan simulasi query. Ketika channel penuh, handler menunggu token lain dilepas. Defer mengembalikan slot saat handler keluar. Mekanisme ini membatasi pekerjaan yang sedang memegang slot, tetapi tidak menyediakan antrean eksplisit dengan batas panjang atau kebijakan penolakan ketika antrean terlalu besar.

select {
case s.semaphore <- struct{}{}:
case <-r.Context().Done():
    return
}
defer func() { <-s.semaphore }()

Slot database adalah simulasi

Nama MaxDBConnections menggambarkan resource yang disimulasikan. Tidak ada driver SQL, query nyata, tabel booking, atau transaksi database pada implementasi ini. Timer mewakili durasi kerja. ActiveConnections mengembalikan len(semaphore), yaitu jumlah slot yang telah diakuisisi. Nilai itu bukan ukuran panjang antrean, bukan jumlah koneksi TCP, dan bukan telemetry dari database sebenarnya. Interpretasi metrik harus mengikuti objek yang diukur.

Antrean ditambah tail spike acak

Handler menambah activeReq sebelum memperoleh slot, sehingga counter mencakup handler POST yang sedang menunggu maupun bekerja. Setelah slot diperoleh, jika activeReq melebihi kapasitas, ada peluang sepuluh persen durasi query menjadi 25 kali durasi dasar. Pada konfigurasi demo, itu berarti 500 ms. Spike ini sengaja dimasukkan ke model; hasil stress tidak berasal dari antrean murni dengan service time konstan.

if atomic.LoadInt64(&s.activeReq) >
    int64(s.cfg.MaxDBConnections) {
    if rand.Float32() < 0.10 {
        dur = s.cfg.DBQueryDuration * 25
    }
}

Context membatasi waktu hidup tes

Run membungkus context caller dengan context.WithTimeout menggunakan Duration. Context tersebut dipasang pada setiap request HTTP. Client juga memiliki timeout lima detik, sehingga batas caller atau durasi tes dapat mengakhiri request lebih dulu. Handler server memeriksa cancellation saat menunggu slot dan saat menunggu timer. Ini memberi jalur keluar dari penantian, tetapi tidak mengubah cancellation menjadi respons overload dengan status khusus.

Cancellation tidak seluruhnya masuk total

Ketika pembuatan request atau client.Do gagal, runner hanya menambah error jika ctx.Err masih nil. Jadi request yang dibatalkan karena durasi tes habis dapat dikeluarkan dari hitungan. TotalRequests adalah jumlah latency sukses ditambah error yang tercatat, bukan penghitung seluruh request yang pernah dimulai. Perbedaan ini penting ketika membandingkan jumlah attempt, throughput selesai, dan jumlah request yang tertinggal di akhir eksperimen.

if err != nil {
    if ctx.Err() == nil {
        errs++
    }
    continue
}

Definisi sukses mengikuti status HTTP

Setelah memperoleh respons, runner membaca body sampai selesai lalu menutupnya. Status minimal 400 menambah error; status di bawah 400 masuk latency sukses. Artinya aturan kode lebih luas daripada hanya 2xx, walaupun handler booking normal menghasilkan 201. Runner tidak memvalidasi JSON status confirmed atau booking_id. Body read error juga diabaikan. Label SuccessCount perlu dipahami sebagai hasil aturan teknis runner, bukan validasi transaksi booking.

Latency berakhir setelah body dibaca

reqStart dicatat sebelum client.Do. Untuk respons yang dianggap sukses, time.Since dicatat sesudah body didrain dan ditutup. Angka ini mencakup jalur HTTP client sampai konsumsi body, bukan durasi timer query saja. Runner tidak memisahkan DNS, dial, TLS, time to first byte, pool wait, atau transfer body. Karena itu, kenaikan latency agregat belum langsung menentukan lapisan mana yang memakan waktu.

Percentile memakai subset sukses

Respons error dan transport error menambah counter tanpa menyimpan latency. CalculateMetrics menerima slice latency sukses dan jumlah error terpisah. P50, P90, P95, P99, min, max, dan average dihitung dari slice tersebut saja. Jika semua request gagal, statistik latency tetap nol walaupun mungkin ada waktu tunggu panjang. Nol pada P95 saat SuccessCount nol tidak boleh dibaca sebagai layanan yang sangat cepat.

KondisiInterpretasi
SuccessCount > 0Percentile subset sukses

P95 = 0 tanpa suksesBukan bukti layanan cepat

RPS mencakup error yang tercatat

CalculateMetrics menetapkan total sebagai len(latencies) ditambah errors. RPS membagi total itu dengan durasi aktual Run, yang dicatat setelah semua goroutine selesai. Maka RPS lab bukan success-only throughput. Bila tidak ada total request, fungsi mengembalikan Result kosong, termasuk Duration nol. Formula tersebut menjelaskan apa yang dilaporkan, tetapi tidak menyediakan target arrival rate maupun statistik request yang dibatalkan pada akhir tes.

total := len(latencies) + errors
res.RPS = float64(total) /
    totalDuration.Seconds()

Percentile memilih indeks tanpa interpolasi

Calculator menyalin slice lalu mengurutkannya, sehingga input tidak diubah. Percentile memilih indeks int((n-1) × p/100), dengan konversi integer membuang pecahan positif. Tidak ada interpolasi antara dua sampel. Untuk dataset test 1 sampai 100 ms, P50 menjadi 50 ms, P95 95 ms, dan P99 99 ms. Hasil ini sesuai algoritme lab, bukan klaim semua tool memakai definisi percentile yang sama.

idx := int(float64(len(sorted)-1) *
    (pct / 100.0))
return sorted[idx]

Fixture menjelaskan angka secara pasti

Seratus sampel 1 sampai 100 ms pada unit test menghasilkan minimum 1 ms, maksimum 100 ms, dan average 50,5 ms. time.Duration menyimpan unit nanosecond, sehingga pembagian tidak otomatis membulatkan ke millisecond utuh. Nilai fixture ini dapat dihitung langsung dari kode dan data test. Berbeda dengan output demo berbasis HTTP, ia bukan pengukuran performa mesin atau kapasitas endpoint booking.

Sampel kecil membuat tail kasar

Pada satu sampel 42 ms, seluruh percentile bernilai 42 ms. Pada jumlah sampel kecil, P95 atau P99 dapat menunjuk sampel yang sama dan bahkan tidak menunjuk maksimum karena rumus memakai n-1 lalu floor. Jadi label percentile tinggi tidak otomatis membuat estimasi tail stabil. Catat jumlah sukses, durasi, dan metode perhitungan agar pembaca tidak memberikan ketepatan lebih besar daripada data yang tersedia.

Average dan tail menjawab hal berbeda

Average merangkum seluruh latency sukses dalam satu nilai. P95 memilih bagian atas distribusi menurut rumus calculator. Unit test invariant memeriksa urutan min, P50, P90, P95, P99, dan max pada data yang mengandung spike. Integration test secara terpisah membandingkan P95 stress dengan average stress. Kedua bentuk assertion ini berbeda: urutan percentile tidak mengharuskan P95 selalu lebih besar daripada average untuk semua distribusi.

Angka demo adalah catatan run

engineering/03-execution-result.md menyimpan contoh smoke P95 sekitar 21,37 ms dan stress P95 sekitar 1,357 detik, dengan error tercatat nol. Itu adalah hasil run yang dicatat repository, bukan pengukuran baru di sini. Random spike, scheduling, dan batas context membuat run dapat berubah. Error nol juga tidak berarti semua attempt selesai: cancellation menjelang akhir tes dapat tidak masuk ErrorCount maupun TotalRequests.

Transport besar belum menjamin generator bebas bottleneck

Runner memakai MaxIdleConns dan MaxIdleConnsPerHost bernilai 1000. Kedua field mengatur koneksi idle yang dapat disimpan; keduanya bukan bukti bahwa seluruh batas client atau mesin generator hilang. Lab tidak mengukur CPU generator, resource jaringan, atau overhead alokasi. Setiap VU menyimpan semua latency sukses dalam slice, kemudian data digabung dan disalin untuk sorting. Kebutuhan memori bertambah bersama jumlah sampel yang terkumpul.

Booking response belum menjadi transaksi nyata

Server menolak metode selain POST dengan 405. Untuk POST yang selesai, ia mengirim 201 dengan status confirmed dan booking_id tetap BK-1001. Body request tidak didecode menjadi BookingRequest dan tidak divalidasi. Tidak ada penyimpanan booking, autentikasi, idempotency, atau unique booking ID. Ini cukup untuk demonstrasi HTTP dan antrean, tetapi workload transaksi nyata perlu karakter data dan jalur kerja yang lebih representatif.

Test memeriksa perilaku yang spesifik

Lima unit test metrics memeriksa fixture, input kosong, satu sampel, RPS, dan urutan statistik. Tujuh integration test memeriksa smoke versus stress, HTTP 500, metode salah, dial error, context cancellation, batas slot, dan invariant total. Test batas slot mem-poll ActiveConnections selama request concurrent serta memeriksa peak positif dan tidak melebihi kapasitas. Test tidak membuktikan fairness antrean atau menentukan kapasitas maksimum sistem.

Bottleneck lab diketahui dari desain

Di lab ini, bottleneck slot sengaja dibangun di server. Dalam layanan nyata, kenaikan P95 saja belum memisahkan antrean aplikasi, database, jaringan, atau dependency eksternal. Materi lanjutan repository membahas korelasi metrik komponen dan target performa, tetapi runtime tidak memasang exporter, tracing, atau threshold SLA otomatis. Demo hanya mencetak ringkasan hasil. Diagnosis dan keputusan pass atau fail membutuhkan observasi serta kriteria tambahan.

Jalankan ulang, lalu baca hasil dalam konteks

Modul menyatakan Go 1.22 dan menggunakan standard library. Perintah test, race detector, serta demo tersedia untuk dijalankan dari folder lab. Go belum tersedia di lingkungan penyusunan paket ini; source dan assertion dibaca tanpa menjalankan ulang test. Catatan passing test repository merupakan bukti run terdahulu. Mental model yang dibawa pulang: Load testing reveals how latency changes when demand competes for limited resources.

cd labs/15-load-testing
go test -v ./...
go test -race ./...
go run ./cmd/demo
