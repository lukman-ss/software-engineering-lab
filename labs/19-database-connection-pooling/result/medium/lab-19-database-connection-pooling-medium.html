Software Engineering Lab 19 — Database Connection Pooling, Overhead, dan Mitigasi Kebocoran
Mental Model Inti: Connection capacity is dictated by database hardware constraints, not by client concurrency. Keep pools lean, reuse connections, and never hold sockets during external I/O.

Masalah: Error Koneksi di Bawah Beban Konkuren

Ketika aplikasi berbasis backend menghadapi lonjakan lalu lintas, basis data relasional seperti PostgreSQL sering kali menolak permintaan dengan galat fatal: FATAL: sorry, too many clients already. Respons spontan yang kerap diambil oleh tim perekayasa adalah memperbesar ukuran connection pool pada aplikasi atau menaikkan parameter max_connections pada server database.

Tindakan tersebut keliru. Menaikkan batas koneksi secara serampangan justru memperburuk latensi transaksi dan membebani memori kerja database engine. Koneksi database bukanlah objek murah yang dapat dibuat tanpa batas; setiap koneksi menuntut alokasi memori internal, proses worker independen, serta menimbulkan kontensi lock dan context switching pada CPU server.

Dalam Software Engineering Lab 19, kita membedah mekanisme kerja connection pool pada Go menggunakan pustaka bawaan database/sql dan mock driver deterministik. Lab ini menguji overhead koneksi langsung, bahaya konfigurasi pool yang melebihi kapasitas server, efek pembekuan sistem akibat connection leak, serta formula kalkulasi ukuran pool yang aman.

Mengapa Koneksi Database Berbiaya Mahal?

Setiap pembukaan koneksi baru ke database engine menuntut serangkaian operasi jaringan dan sistem operasi:

  • Three-way TCP handshake melintasi jaringan.
  • Negosiasi enkripsi TLS/SSL.
  • Otentikasi kredensial pengguna dan pemilihan skema.
  • Inisialisasi proses backend database (misalnya proses dedicated worker pada arsitektur PostgreSQL).

Dokumentasi resmi PostgreSQL Wiki merinci bahwa melampaui ambang batas jenuh (saturation knee) akan menurunkan performa sistem akibat enam faktor: kontensi disk I/O, tekanan RAM (akibat alokasi work_mem per koneksi aktif), kontensi lock internal, lonjakan context switching pada CPU, cache line bouncing, serta struktur data internal database yang berskala O(N²).

1. Overhead Koneksi Baru: Pooled vs Unpooled

Untuk mensimulasikan latensi inisialisasi soket tanpa dependensi infrastruktur fisik luar, lab ini mengimplementasikan MockDriver pada internal/pool/mockdb.go dengan menyuntikkan connectDelay: 

type MockDriver struct {
	mu             sync.Mutex
	activeConns    int32
	maxConnections int32
	connectDelay   time.Duration
	totalCreated   int32
}

func (d *MockDriver) Open(name string) (driver.Conn, error) {
	if d.connectDelay > 0 {
		time.Sleep(d.connectDelay)
	}

	d.mu.Lock()
	defer d.mu.Unlock()

	if d.activeConns >= d.maxConnections {
		return nil, ErrServerOverloaded
	}

	d.activeConns++
	d.totalCreated++
	return &mockConn{driver: d}, nil
}

Pada pengujian perbandingan, mode unpooled dikonfigurasi dengan menyetel db.SetMaxIdleConns(0), sehingga Go segera memutus soket setiap kali sebuah kueri selesai dieksekusi. Sebaliknya, mode pooled menyetel db.SetMaxIdleConns(5) untuk mempertahankan koneksi terbuka.

Hasil pengujian interaktif pada CLI demo memperlihatkan perbedaan dramatis:

  • Unpooled (5 request berurutan): Menghabiskan waktu 54,59 ms karena menempuh 5 kali handshake.
  • Pooled (5 request berurutan): Menghabiskan waktu 6,33 µs karena koneksi yang telah terbuka digunakan kembali secara langsung.

Uji otomatis TestDirectConnectionOverhead dan TestTotalCreatedPoolReuse membuktikan bahwa pola pooling memangkas overhead inisialisasi dan meminimalkan pembuatan objek koneksi baru.

2. Formula Ukuran Kapasitas dan Multiplikasi Instance

Penetapan ukuran pool yang tepat tidak ditentukan oleh jumlah goroutine di aplikasi, melainkan oleh kapabilitas perangkat keras basis data. Formula dasar yang dirumuskan oleh PostgreSQL Wiki dan dokumentasi HikariCP adalah: 

connections = ((core_count * 2) + effective_spindle_count)

Variabel core_count mengacu pada inti CPU fisik server database (tidak menghitung thread hyperthreading). Sementara effective_spindle_count merepresentasikan jumlah piringan disk berputar yang aktif melayani I/O; nilainya mendekati 0 jika seluruh dataset aktif tersimpan di RAM cache.

Batasan Realistis: Formula ini divalidasi pada era storage HDD konvensional. Media penyimpanan NVMe modern memiliki karakteristik seek paralel yang berbeda. Oleh karena itu, formula ini berfungsi sebagai titik awal kalkulasi sebelum dilanjutkan dengan load testing empiris.

Dalam arsitektur komputasi modern yang mendistribusikan layanan ke banyak kontainer, ukuran pool harus dihitung secara global di level kluster: 

Total Potensi Koneksi = Jumlah Instance Pod x Ukuran Pool per Instance

Bila Anda menggelar 10 instance mikroservis dengan masing-masing pool berukuran 20 koneksi, total beban puncak mencapai 200 koneksi. Apabila basis data memiliki konfigurasi max_connections = 100, separuh dari permintaan aplikasi dipastikan gagal ditolak server saat traffic tinggi.

3. Skenario Kegagalan: Server Exhaustion dan Connection Leak

Lab 19 menyimulasikan dua bentuk kegagalan sistemik yang sering melumpuhkan infrastruktur produksi:

A. Oversized Pool Melampaui Batas Server

Pengujian TestOversizedPoolExhaustsServerConnections menetapkan batas keras server sebanyak 10 koneksi, namun mengizinkan aplikasi membuka hingga 20 koneksi. Ketika 20 kueri diluncurkan bersamaan, driver menolak kelebihan koneksi dengan ErrServerOverloaded. Menambah kapasitas pool aplikasi tanpa ruang cadangan di server berujung pada penolakan mentah dari database engine.

B. Connection Starvation Akibat Kebocoran I/O Eksternal

Bentuk kebocoran koneksi paling berbahaya terjadi saat kode aplikasi meminjam koneksi database lalu menahannya saat melakukan panggilan I/O jaringan pihak ketiga. Pada internal/pool/service.go, fungsi ProcessOrderUnsafeLeak meminjam koneksi, menjalankan pembaruan status awal, lalu memanggil API eksternal selama 100 ms sebelum akhirnya merilis koneksi. 

// ANTI-PATTERN: Menahan koneksi saat memanggil externalCall
func (s *OrderService) ProcessOrderUnsafeLeak(ctx context.Context, orderID string, externalCall func() error) error {
	conn, err := s.db.Conn(ctx)
	if err != nil {
		return err
	}
	defer conn.Close()

	if _, err := conn.ExecContext(ctx, "UPDATE orders SET status = 'pending' WHERE id = ?", orderID); err != nil {
		return err
	}

	// KONEKSI DATABASE TERTANDANDANG DI SINI:
	if err := externalCall(); err != nil {
		return err
	}

	_, err = conn.ExecContext(ctx, "UPDATE orders SET status = 'completed' WHERE id = ?", orderID)
	return err
}

Pada pengujian TestConnectionStarvationDueToLeak dengan ukuran pool dibatasi 1 koneksi, eksekusi unsafe order di atas langsung menghabiskan ketersediaan pool. Permintaan kedua yang menggunakan pola penulisan aman sekalipun dipaksa mengantre hingga akhirnya gagal dengan galat context deadline exceeded. Satu pola kode ceroboh melumpuhkan seluruh antrean permintaan aplikasi.

4. Solusi Pola Aman dan Formula Anti-Deadlock

Pola pencegahan baku yang diterapkan pada ProcessOrderSafe adalah menyelesaikan seluruh I/O non-database sebelum meminjam koneksi: 

// POLA AMAN: Selesaikan I/O eksternal SEBELUM meminjam koneksi database
func (s *OrderService) ProcessOrderSafe(ctx context.Context, orderID string, externalCall func() error) error {
	if err := externalCall(); err != nil {
		return err
	}

	conn, err := s.db.Conn(ctx)
	if err != nil {
		return err
	}
	defer conn.Close()

	_, err = conn.ExecContext(ctx, "UPDATE orders SET status = 'completed' WHERE id = ?", orderID)
	return err
}

Selain itu, saat sebuah alur kerja membutuhkan lebih dari satu koneksi serentak pada thread atau goroutine yang sama, risiko pool-locking deadlock dapat terjadi. Formula batas bawah untuk mencegah kebuntuan tersebut adalah: 

pool_size = Tn * (Cm - 1) + 1

Di mana Tn adalah jumlah thread konkuren maksimum, dan Cm adalah jumlah koneksi maksimum yang ditahan serentak oleh satu thread. Pengujian TestPoolLockingDeadlock membuktikan bahwa menahan koneksi pertama sembari meminta koneksi kedua pada pool berukuran 1 akan memicu deadlock seketika.

Panduan Rekayasa Produksi (Checklist Praktis)

  1. Tetapkan Ukuran Pool Ringkas: Awali konfigurasi dari formula ((core * 2) + spindle), lalu validasi dengan load test. Jangan pernah menaikkan pool size secara spontan untuk mengatasi latensi.
  2. Jangan Pernah Tahan Koneksi saat I/O Eksternal: Jauhkan panggilan API HTTP, manipulasi berkas disk, dan komputasi CPU berat dari blok transaksi database.
  3. Hitung Kapasitas Global Deployment: Pastikan perkalian replika x pool_size tidak melebihi max_connections server database setelah dikurangi slot cadangan monitoring.
  4. Gunakan Dedicated Proxy di Skala Besar: Untuk arsitektur multi-pod masif, pasang PgBouncer (pada transaction mode) atau AWS RDS Proxy untuk mengonsolidasikan ribuan koneksi aplikasi menjadi puluhan koneksi database yang stabil.
  5. Pantau Metrik Pool: Jangan hanya mengandalkan utilisasi CPU database. Amati metrik wait time akuisisi koneksi, rasio koneksi aktif versus idle, serta transaksi yang berstatus idle in transaction.
