SLO, SLI & Error Budget: Mengubah "Harus Stabil" Menjadi Angka yang Bisa Dideploy

Kerangka kerja Google SRE dalam Go murni — sliding window, evaluasi SLI/SLO, alert burn rate multi-jendela, dan gate deploy otomatis.

Layanan pembayaran mengalami degradasi. CPU berada di 30%, memory nominal, dan dashboard infrastruktur tetap hijau — namun 5% permintaan pengguna mengembalikan error 5xx. Lab 24 mengganti kepercayaan palsu tersebut dengan kerangka kerja SLO/SLI/Error Budget berbasis Google SRE yang ditulis dalam Go murni.

Metrik infrastruktur melacak mesin. Metrik SLO melacak pengguna. Selalu ukur apa yang dialami pelanggan.

Masalah Inti: Server Sehat, Pengalaman Pengguna Rusak

Tim keandalan secara historis memonitor CPU, RAM, dan disk — sinyal tingkat mesin yang tidak berkorelasi dengan error lapisan aplikasi. Dashboard infrastruktur yang selalu hijau bisa menyembunyikan error rate 5% pada endpoint utama. Tanpa kerangka SLO objektif, setiap release menjadi tebak-tebakan risiko dan keandalan berubah menjadi opini bukan keputusan berbasis data.

Dwell time memperparah masalah. Tanpa pelacakan error budget, tim baru menyadari insiden setelah complain massal dari pengguna. Satu regresi bisa menghabiskan anggaran uptime setahun dalam hitungan menit.

Mengapa Threshold Statis Gagal

Threshold alert tunggal tidak bisa membedakan spike transient dari insiden sistemik. Sepuluh error dari 100 request terlihat kritis (10%), tetapi sepuluh error dari satu juta request hampir tidak bermakna (0,001%). Threshold statis menghasilkan false positive berlebihan atau false negative berbahaya tergantung volume traffic.

Metrik infrastruktur memperburuk buta huruf ini. Spike CPU tidak sama dengan error rate; memory leak terjadi tanpa tekanan CPU; latency P99 bisa memburuk mientras error rate tampak stabil. Alerting threshold tunggal pada metrik mesin bersifat reaktif sejak awal.

Model Mental: Keandalan Bukan 100%

SLO menetapkan target realistis — 99,9% untuk layanan kritis, bukan 100%. Selisih antara target dan aktual adalah error budget. Setiap event buruk menghabiskan budget tersebut:

Error Budget = 1 - SLO
SLI = good_events / total_events
Burn Rate = actual_error_rate / allowed_error_rate

Burn rate 14,4× berarti budget akan habis dalam 2% dari waktunya. Burn rate 6,0× menunjukkan pembakaran lambat selama 5% window. Budget adalah modal risiko yang bisa dibelanjakan — ketika habis, inovasi berhenti sampai keandalan pulih.

Arsitektur Pipeline: Event ke Alert

Tiga komponen modular membentuk pipeline:

Event{Timestamp, Duration, StatusCode, Endpoint}
  ↓ WindowTracker.Record()        (RWMutex + bucket eviction)
  ↓ Summary(now)                  → (total, good, bad)
  ↓ Evaluator.Evaluate()          → SLI, Budget Remaining, CanDeploy
  ↓ AlertEngine.Check()           → Multi-window Burn Rate Alerts
  • metrics.WindowTracker — agregasi sliding window, query O(bucket_count)
  • slo.Evaluator — kalkulasi SLI, matematika budget, logika gate deploy
  • alerting.AlertEngine — pengecekan threshold burn rate dual-window

Window waktu: tracker SLO menggunakan 30 hari (dikompresi menjadi 30 menit di demo); alert short tracker 5 menit; alert long tracker 60 menit.

WindowTracker: Sliding Window dengan Dukungan Out-of-Order

WindowTracker menggunakan sync.RWMutex untuk thread-safety saat ratusan goroutine merekam event secara konkuren. Metode Record() mengakuisisi write lock, mengevict bucket kadaluarsa melewati windowSize, lalu mencari atau membuat bucket baru untuk timestamp yang di-truncate ke bucketSize.

// internal/metrics/tracker.go:46
func (w *WindowTracker) Record(e Event) {
    w.mu.Lock()
    defer w.mu.Unlock()

    w.evictStaleLocked(e.Timestamp)

    bucketStart := e.Timestamp.Truncate(w.bucketSize)
    // ... linear search insert atau append ...
}

func (w *WindowTracker) evictStaleLocked(now time.Time) {
    cutoff := now.Add(-w.windowSize)
    idx := 0
    for idx < len(w.buckets) && w.buckets[idx].StartTime.Before(cutoff) {
        idx++
    }
    if idx > 0 {
        w.buckets = w.buckets[idx:]
    }
}

Jika timestamp datang out-of-order, bucket disisipkan di posisi kronologis yang benar melalui linear search, memastikan slice tetap terurut untuk eviction efisien. Ini menangani clock skew dan network reordering yang umum terjadi di distributed systems.

Jalur Kegagalan: Regresi Latency Menghabiskan Budget

Sebuah deployment memperkenalkan regresi latency: P95 bergerak dari 50ms ke 500ms. Predicate isGood mensyaratkan StatusCode < 500 && Duration <= 200ms. Setiap request baru sekarang dihitung bad.

Dengan SLO 99,9% (allowed error rate = 0,1%) dan error rate 10% dari regresi, burn rate mencapai 100×. Budget 30 hari habis dalam sekitar 43 menit. Alert engine membandingkan burn rate short dan long window; ketika keduanya melewati 6,0×, alert TICKETterpicu dan CanDeployberubah false — menghentikan semua deployment non-P0 secara otomatis.

Tiga Keputusan Kritis dalam Error Budgeting

  1. Definisi SLI: Pilih metrik yang mencerminkan pengalaman pengguna, bukan kondisi server. Tentukan closure isGood — biasanya kombinasi status code dan latency threshold.
  2. Target SLO: Tetapkan target realistis (99,9% untuk layanan kritis). Hindari 100% — error network dan device di luar kendali Anda. Endpoint berbeda bisa memiliki SLO berbeda berdasarkan criticality.
  3. Kebijakan CanDeploy: CanDeploy = false saat budge tRemaining <= 0 (dan total > 0). Halt semua deployment non-P0 sampai budget pulih. Wajibkan postmortem jika satu insiden消耗 > 20% budget.

Transparansi Batasan: Apa yang Tidak Dibuktikan

Integritas rekayasa memerlukan pernyataan batasan eksplisit:

  • ❌ Tidak ada persistensi metrics: Semua data in-memory; hilang saat process restart.
  • ❌ Tidak ada histogram latency: Hanya predicate boolean good/bad — tidak ada distribusi P50/P95/P99.
  • ❌ Window waktu terkompresi: Demo menggunakan window 30 menit mewakili periode 30 hari.
  • ❌ Threshold burn rate adalah rekomendasi: 14,4×/6,0× mengikuti panduan Google SRE, bukan standar industri mutlak.
  • ❌ Field mati: LatencyThresholdada di Evaluator.Configtetapi tidak dibaca oleh Evaluate().
  • ❌ Tidak ada simulasi recovery: Budget tidak mengisi ulang setelah insiden berakhir di demo.
  • ❌ Lingkup endpoint terbatas: Demo menggunakan 2 endpoint; ratusan endpoint konkuren belum diuji.

Trade-off Arsitektur: In-Memory vs TSDB

Demo mengutamakan correctness dan zero-dependency di atas durabilitas produksi:

SIM (Demo):

  • + Zero-dependency: Go standard library saja
  • + Thread-safe: sync.RWMutexterbukti dengan race detector
  • + Out-of-order safe: bucket insertion menjaga urutan kronologis
  • - Tidak ada persistensi: data loss saat restart
  • - Tidak ada horizontal scaling: bottleneck single-process

Produksi (Rekomendasi):

  • + Prometheus/Grafana untuk time-series persistence
  • + Horizontal scaling via distributed TSDB cluster
  • + Native SLO query language (Prometheus recording rules)
  • - Kompleksitas infrastruktur tambahan
  • - Beban integration testing untuk data pipeline

Pola dual-window burn rate yang sama dapat direplikasi menggunakan Prometheus recording rules dan alerting expressions.

Konkurensi: Pipeline Rekaman Aman Goroutine

Test konkurensi mengeksekusi 20 goroutine, masing-masing merekam 100 request secara simultan ke WindowTrackeryang sama:

// tests/slo_test.go:200
func TestConcurrencyMetrics(t *testing.T) {
    var wg sync.WaitGroup
    numGoroutines := 20
    requestsPerGoroutine := 100
    for g := 0; g < numGoroutines; g++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            for i := 0; i < requestsPerGoroutine; i++ {
                tracker.Record(metrics.Event{...}) // RWMutex protects
            }
        }(g)
    }
    wg.Wait()
}

Hasil: 2.000 event tercatat dengan benar, good + bad == totalterverifikasi, dan go test -racemeng报告 nol data race. Granularitas lock cukup untuk workload throughput tinggi.

Evaluator: Matematika SLI dan Error Budget

Evaluatormenghitung tiga nilai: rasio SLI, total error budget, dan remaining budget:

// internal/slo/evaluator.go:41
func (e *Evaluator) Evaluate(now time.Time) Status {
    total, good, bad := e.tracker.Summary(now)

    var sli float64 = 1.0
    if total > 0 {
        sli = float64(good) / float64(total)
    }

    totalErrorBudget := (1.0 - e.config.TargetUptime) * float64(total)
    budgetRemaining := totalErrorBudget - float64(bad)
    canDeploy := total == 0 || budgetRemaining > 0
    // ...
}

Traffic nol mengembalikan SLI = 1,0 dan CanDeploy = trueuntuk mencegah false freeze pada service baru. Rumusnya sederhana: SLI = good/total, budget = (1 - SLO) × N, dan gate deploy aktif saat budgetRemaining ≤ 0dengan traffic aktif.

Alert engine menghitung burn rate untuk dua window secara paralel:

// internal/alerting/engine.go:51
func (a *AlertEngine) CalculateBurnRate(total, bad int64) float64 {
    if total == 0 { return 0.0 }
    actualErrorRate := float64(bad) / float64(total)
    allowedErrorRate := 1.0 - a.targetSLO
    return actualErrorRate / allowedErrorRate
}

Alert hanya terpicu jika keduanya window melewati threshold — kondisi AND yang menyaring spike transient:

// internal/alerting/engine.go:73
triggered := shortBurn >= rule.BurnRateFactor && longBurn >= rule.BurnRateFactor

Bukti spike transient: Short window menunjukkan burn rate 100× (10% error dalam 5 menit), long window menunjukkan 0,1× (0,01% dalam 60 menit). Hasil: tidak ada alert — spike bersifat sementara, bukan sistemik.

Bukti Test: Sustained vs Transient Burn

// Sustained burn: 98 OK + 2 error di KEDUA short dan long window
// → 20× burn rate, kedua window >= 14,4x → PAGE alert terpicu

// Transient spike: 90 OK + 10 error di short (100x),
//                  9999 OK + 1 error di long (0,1x)
// → short >= 14,4x ✓, long >= 14,4x ✗
// → 0 alerts — spike berhasil disaring

Jika hanya satu window berteriak, itu mungkin noise. Keduanya harus setuju untuk bertindak.

Verifikasi Out-of-Order dan Eviction

// Record event t+5s PERTAMA, lalu event t+2s KEDUA
// → Bucket di t+2s disisipkan sebelum bucket t+5s
// → Summary(t+6s): total=3, good=2, bad=1 ✓

// Maju ke t+13s → cutoff = t+3s
// → Bucket di t+2s di-evict, t+5s tetap
// → Summary(t+13s): total=1, good=1, bad=0 ✓

Bucket insertion terurut dengan eviction berbasis waktu menangani clock skew distributed dengan anggun tanpa koordinasi eksternal.

Trade-off Arsitektur: Pedagogis vs Produksi

Lab memilih in-memory untuk kejelasan pedagogis dan proof zero-dependency. Pola AlertEnginedual-tracker dan matematika burn rate portable ke database time-series apapun. Sistem produksi akan mengganti slice in-memory dengan metrik Prometheus, mengekspor pada interval pendek, dan mengevaluasi burn rate via recording rules.

Invariant inti — SLI = good/total, budget = (1-SLO)×N, gate deploy pada exhaustion — tetap identik terlepas dari backend penyimpanan.

Transformasi: Sebelum vs Sesudah Observability

Sebelum (Tanpa SLO):

  • Dashboard: CPU 30%, Memory 60%, Disk I/O normal
  • Alert: "CPU high" saat load test — pengalaman pengguna tidak terukur
  • Keputusan: Deploy berdasarkan intuisi, tanpa data budget
  • Respons: Reaktif, dwell time diukur dalam jam

Sesudah (Dengan SLO):

  • Dashboard: SLI 99,09%, Budget Remaining -8,90, CanDeploy=false
  • Alert: "Slow burn 9,09x" — kedua window terdeteksi
  • Keputusan: Auto-halt deployment, fokus postmortem
  • Respons: Proaktif, laju consumption budget terukur

Dashboard SLO menunjukkan realita pengguna; dashboard infrastruktur menunjukkan keadaan mesin.

Checklist Implementasi

Fundamental:

  • □ Definisi SLI mengukur pengalaman pengguna (rasio good/total)
  • □ Pilih SLO realistis ≤ 99,99% — hindari perfeksionisme 100%
  • □ Definisi closure isGood: status code + latency threshold
  • □ Implementasikan WindowTrackerdengan sliding window + bucket eviction

Alerting:

  • □ Setup dual tracker: short (5–15m) dan long (1–6h) window
  • □ Pilih threshold burn rate: 14,4× (PAGE) dan 6,0× (TICKET)
  • □ Implementasikan AND logic: alert hanya jika kedua window melebihi threshold
  • □ Integrasi dengan notification system (PagerDuty, Slack, email)

Policy:

  • □ CanDeploy gate: auto-halt saat budgetRemaining <= 0
  • □ Policy exception: P0/security hotfix tetap deploy dengan approval
  • □ Postmortem requirement: wajib jika single incident消耗 > 20% budget
  • □ Dashboard SLO: real-time SLI, budget gauge, burn rate trend

Measurement tanpa policy adalah vanity. Policy tanpa measurement adalah opinion.

Anti-Pattern dan Cara Reproduksinya

  1. SLO 100%: Menetapkan TargetUptime=0,999999membuat budget hampir nol. Satu error memicu CanDeploy=false.
    Reproduksi:Set SLO ekstrem, record satu bad event.
  2. Alert Single-Window: Alert hanya berdasarkan short window.
    Reproduksi:10 error di short window, 0 di long → alert false positive.
  3. SLI Infrastruktur: Menggunakan CPU/memory sebagai SLI utama.
    Reproduksi:CPU 30% dengan error rate 10% → tidak ada alert, keluhan pengguna naik.
  4. Tidak Ada Policy Deploy: Budget habis tapi tidak ada mekanisme auto-halt.
    Reproduksi:Set budgetRemaining=-5, lewati CanDeploy check → deployment jalan terus.

SLO terbaik adalah yang tertinggi yang pengguna Anda terima — bukan angka tertinggi yang bisa Anda tulis.

Prinsip Arsitektural Jangka Panjang

  1. Reliability Is a Feature: SLO bukan meta-metric — ia adalah user-facing quality contract. Setiap percentage point bernilai uang dan trust pengguna nyata.
  2. Automate the Halt: CanDeploy=falseharus memblokir pipeline CI/CD secara otomatis. Manual override hanya untuk P0/security dengan audit trail.
  3. Measure User Experience: CPU 30% tidak berarti apa-apa jika error rate 5%. CPU 90% oke jika SLI 99,99%. Dashboard harus menjawab: "Apakah pengguna kami bahagia?"

Automate the guardrails. Measure the user. Spend the budget wisely.
