SOFTWARE ENGINEERING LAB • LAB 24

SLI, SLO, dan Error Budget di Go: Multi-Window Multi-Burn-Rate Alerting

Implementasi time-bucketed sliding window, kalkulasi error budget deterministik, dan dual-window burn rate alert engine berbasis prinsip Google SRE.

Masalah Pengukuran Keandalan Tradisional

Tim keandalan sering mengukur stabilitas layanan menggunakan metrik infrastruktur seperti utilisasi CPU, konsumsi memori host, atau panjang antrean disk. Metrik ini tidak mencerminkan pengalaman nyata pengguna yang mengakses aplikasi. Server dapat beroperasi pada beban CPU rendah 10% namun gagal memproses transaksi karena kegagalan database pool. Sebaliknya, mesin yang berjalan pada utilisasi CPU 90% dapat melayani 100% permintaan pengguna secara sukses tanpa penurunan performa.

Mengukur kesehatan sistem menggunakan metrik yang keliru menimbulkan dua kendala operasional:

  • False Sense of Safety: Dasbor infrastruktur berwarna hijau padahal pengguna menghadapi error HTTP 500 secara masif.
  • Deployment Chaos: Tim pengembang tidak memiliki standar numerik objektif untuk menentukan kapan rilis fitur baru harus dihentikan demi stabilisasi sistem.

Dalam Software Engineering Lab 24, kita membedah dan mengimplementasikan kerangka kerja Service Level Indicators (SLI), Service Level Objectives (SLO), kalkulasi Error Budget matematis, dan mesin peringatan Multi-Window Multi-Burn-Rate berbasis prinsip Google SRE di Go.

Keandalan bukanlah target 100%. Target 100% adalah target yang salah, memboroskan biaya rekayasa, dan melampaui keandalan jaringan pengguna. Error budget menyediakan batas toleransi kesalahan yang dapat dibelanjakan untuk rilis fitur secara terukur.

Mental Model: Error Budget Sebagai Kuota Risiko

Prinsip keandalan modern menetapkan target ketersediaan layanan secara realistis di bawah 100%. Batas selisih antara target layanan dengan batas sempurna merupakan kuota kesalahan yang diizinkan:

SLO Target    : 99.9% (Uptime yang dijanjikan)
Error Budget  : 1.0 - 0.999 = 0.001 (0.1% request diizinkan gagal)
Total Trafik  : 1.000 request
Kuota Gagal   : 1.000 × 0.1% = 1 request

Error budget berfungsi sebagai penyeimbang antara kecepatan rilis fitur dan stabilitas layanan. Selama error budget tersisa bernilai positif, pengembang bebas merilis pembaruan perangkat lunak. Ketika insiden atau regresi performa menghabiskan budget hingga minus, kebijakan deployment freeze langsung diberlakukan.

Pilar 1: Service Level Indicator (SLI)

SLI didefinisikan sebagai rasio kuantitatif antara kejadian sukses (good events) terhadap seluruh kejadian valid (total events):

SLI = Kejadian Sukses / Total Kejadian

Pada implementasi internal/metrics/tracker.go, kualifikasi kejadian sukses ditentukan langsung oleh pemanggil melalui fungsi predikat closure isGood:

type Event struct {
	Timestamp  time.Time
	Duration   time.Duration
	StatusCode int
	Endpoint   string
}

// Caller mendefinisikan kriteria kejadian sukses:
isGood := func(e metrics.Event) bool {
	return e.StatusCode < 500 && e.Duration <= latencyThreshold
}

Pemisahan logika kualifikasi ini menjaga komponen agregator metrik tetap agnostik terhadap format protokol atau status kode spesifik.

Pilar 2: Agregasi Time-Bucketed Sliding Window

Melacak metrik pada jendela waktu berjalan (rolling window) seperti 30 hari atau 1 jam membutuhkan struktur data yang efisien. Menyimpan jutaan struct request di dalam memori memicu lonjakan garbage collection. Lab ini menerapkan WindowTracker yang mengelompokkan request ke dalam bucket interval waktu deterministik:

type Bucket struct {
	StartTime  time.Time
	TotalCount int64
	GoodCount  int64
	BadCount   int64
}

type WindowTracker struct {
	mu         sync.RWMutex
	windowSize time.Duration
	bucketSize time.Duration
	buckets    []*Bucket
}

Setiap kali event dicatat melalui Record(), tracker mengunci mutex, memangkas bucket kadaluarsa di luar jendela waktu (eviction), lalu menambahkan pencacah ke bucket yang sesuai berdasarkan timestamp terpotong (truncated timestamp):

func (w *WindowTracker) Record(e Event, isGood bool) {
	w.mu.Lock()
	defer w.mu.Unlock()

	w.evict(e.Timestamp)

	bucketStart := e.Timestamp.Truncate(w.bucketSize)
	b := w.getOrCreateBucket(bucketStart)

	b.TotalCount++
	if isGood {
		b.GoodCount++
	} else {
		b.BadCount++
	}
}

Pilar 3: Evaluator SLO dan Penegakan Deployment Freeze

Komponen Evaluator di internal/slo/evaluator.go membaca ringkasan metrik dari window tracker dan menghitung sisa error budget secara absolut:

func (e *Evaluator) Evaluate(now time.Time) Status {
	total, good, bad := e.tracker.Summary(now)

	if total == 0 {
		return Status{
			TargetSLO:       e.config.TargetUptime,
			CurrentSLI:      1.0,
			BudgetRemaining: 0,
			CanDeploy:       true,
		}
	}

	sli := float64(good) / float64(total)
	totalErrorBudget := (1.0 - e.config.TargetUptime) * float64(total)
	budgetRemaining := totalErrorBudget - float64(bad)
	canDeploy := budgetRemaining > 0

	return Status{
		TargetSLO:       e.config.TargetUptime,
		CurrentSLI:      sli,
		TotalRequests:   total,
		GoodRequests:    good,
		BadRequests:     bad,
		BudgetRemaining: budgetRemaining,
		CanDeploy:       canDeploy,
	}
}

Ketika volume trafik nol, evaluator mengembalikan CurrentSLI: 1.0 dan CanDeploy: true. Penanganan kondisi batas ini mencegah pemblokiran rilis palsu saat layanan baru pertama kali dinyalakan.

Pilar 4: Multi-Window Multi-Burn-Rate Alerting

Peringatan berbasis satu jendela waktu memiliki kelemahan mendasar: jendela pendek (5 menit) memicu false alarm akibat lonjakan galat sesaat, sedangkan jendela panjang (24 jam) terlambat memberitahu insiden kritis. Kerangka Google SRE menyelesaikan dilema ini dengan mengevaluasi laju pembakaran budget (Burn Rate) secara simultan pada dua jendela waktu.

Burn Rate merefleksikan kecepatan penghabisan budget dibandingkan tingkat kegagalan yang diizinkan:

Burn Rate = Tingkat Galat Nyata / Tingkat Galat Diizinkan
          = (Bad / Total) / (1.0 - TargetSLO)

Tabel konfigurasi ambang batas burn rate yang diterapkan pada lab:

Tingkat Peringatan Keparahan Ambang Burn Rate Jendela Pendek Jendela Panjang Budget Terbakar
Page Fast PAGE 14.4× 5 Menit 1 Jam 2% dalam 1 Jam
Ticket Slow TICKET 6.0× 30 Menit 6 Jam 5% dalam 6 Jam

Pada internal/alerting/engine.go, peringatan hanya diaktifkan jika laju pembakaran pada jendela pendek DAN jendela panjang secara simultan melampaui batas ambang:

for _, rule := range e.rules {
	if sBurn >= rule.BurnRateThreshold && lBurn >= rule.BurnRateThreshold {
		alerts = append(alerts, Alert{
			RuleName:      rule.Name,
			Severity:      rule.Severity,
			ShortBurnRate: sBurn,
			LongBurnRate:  lBurn,
			FiredAt:       now,
		})
	}
}

Lonjakan galat sementara yang menaikkan jendela pendek hingga 100x tidak akan membunyikan alarm jika jendela panjang tetap bersih.

Batasan Implementasi Laboratorium

Implementasi pada lab ini dirancang untuk mendemonstrasikan algoritma inti dalam lingkungan terisolasi. Dalam lingkungan produksi skala besar, terdapat beberapa batasan yang harus disesuaikan:

  • Penyimpanan In-Memory: Metrik disimpan dalam slice RAM lokal. Restart pod akan menghapus histori jendela. Produksi memerlukan TSDB terdistribusi seperti Prometheus atau VictoriaMetrics.
  • Kompresi Waktu Simulasi: Demo mengompresi jendela jam menjadi hitungan menit agar dapat diverifikasi secara instan.
  • Kualifikasi Boolean: SLI dihitung berdasarkan predikat benar/salah pada closure, bukan agregasi kuantil histogram latency lengkap (P95/P99).

Kesimpulan

Penerapan SLI, SLO, dan Error Budget mengubah perdebatan subjektif mengenai stabilitas sistem menjadi keputusan matematis yang dapat diverifikasi. Dengan melacak laju konsumsi budget menggunakan peringatan multi-jendela, tim rekayasa perangkat lunak dapat merilis fitur secara agresif tanpa mengorbankan keandalan yang menjadi hak pengguna.
