Deadlock pada Sistem Konkuren: Mekanisme Terjadinya, Penanganan Database, dan Strategi Pencegahan Tingkat Aplikasi

Membedah dinamika circular wait, tindakan terminasi deadlock victim oleh database engine, pencegahan deterministik melalui lock ordering, dan pemulihan transaksi menggunakan application retry di Go.

Software Engineering Lab 18 — Deadlock Simulation, Lock Ordering, & Application Retry

Masalah: Kondisi Saling Menunggu Tanpa Akhir

Pada arsitektur perangkat lunak yang melayani ribuan transaksi konkuren per detik, berbagai proses komputasi saling memperebutkan akses eksklusif terhadap entitas bersama, seperti baris data pada tabel database relasional. Masalah timbul saat dua transaksi berusaha mengunci dua sumber daya yang sama tetapi menggunakan urutan yang bertolak belakang.

Kondisi ini menciptakan deadlock (dikenal juga sebagai deadly embrace). Masing-masing transaksi telah mengunci satu sumber daya dan menolak melepaskannya sebelum mendapatkan sumber daya kedua. Akibatnya, kedua proses terhenti selamanya dalam kondisi saling menunggu. Tanpa campur tangan pengawas eksternal, transaksi yang membeku ini akan menyandera koneksi database pool, menaikkan latensi sistem secara drastis, hingga membuat seluruh server kehabisan sumber daya.

Mental Model: Deadlock is a circular dependency. The database aborts one transaction as a victim. Lock ordering prevents cycles from forming. Application retry recovers aborted victims.

Mengapa Isu Ini Sangat Berdampak

Banyak pengembang keliru menganggap deadlock sebagai kerusakan internal pada mesin basis data. Faktanya, database engine dirancang untuk mendeteksi siklus dan mengorbankan salah satu transaksi secara sepihak. Dampak sistemik yang ditimbulkan antara lain:

  • Lonjakan Latensi Antrean: Transaksi yang tertahan memblokir transaksi lain yang mengantre pada baris data terkait, melipatgandakan waktu respons aplikasi.
  • Peningkatan Tingkat Kegagalan (Aborted Transactions): Database engine membatalkan transaksi korban secara paksa. Bila aplikasi tidak siap menangani pembatalan ini, pengguna langsung menerima pesan error 500.
  • Pemborosan Siklus Komputasi: Sumber daya komputasi yang telah dialokasikan untuk memproses transaksi yang dibatalkan terbuang sia-sia karena seluruh statusnya harus di-rollback.

Anatomi Siklus Tunggu (Circular Wait)

Berdasarkan formulasi teoretis Coffman Conditions, deadlock hanya dapat terbentuk jika empat kondisi terpenuhi bersamaan: mutual exclusion, hold and wait, no preemption, dan circular wait. Pola circular wait pada transaksi transfer dana dua arah dapat digambarkan sebagai berikut:

Transaksi 1 memegang Lock A ---> Transaksi 1 membutuhkan Lock B
                ^                                      |
                |                                      v
Transaksi 2 membutuhkan Lock A <--- Transaksi 2 memegang Lock B

Skenario kegagalan berlangsung melalui tahapan konkurensi berikut:

  1. Transaksi 1 mengeksekusi transfer dari Akun A ke Akun B. Transaksi 1 berhasil mengakuisisi lock pada Akun A.
  2. Transaksi 2 secara paralel mengeksekusi transfer dari Akun B ke Akun A. Transaksi 2 berhasil mengakuisisi lock pada Akun B.
  3. Transaksi 1 meminta lock pada Akun B, namun terblokir karena Akun B sedang ditahan oleh Transaksi 2.
  4. Transaksi 2 meminta lock pada Akun A, namun terblokir karena Akun A sedang ditahan oleh Transaksi 1.
  5. Kedua transaksi terjebak dalam siklus ketergantungan tertutup.

Bagaimana Database Engine Menangani Deadlock

Database engine relasional modern (seperti PostgreSQL, MySQL InnoDB, dan SQL Server) menerapkan mekanisme penanganan otomatis berbasis graf:

  • Wait-For Graph (WFG): Database memelihara graf berarah di memori, di mana simpul merepresentasikan transaksi aktif dan busur berarah merepresentasikan relasi tunggu.
  • Deadlock Detection Thread: Thread latar belakang memeriksa keberadaan siklus pada graf secara berkala setelah jeda konfigurasi tertentu (misalnya nilai deadlock_timeout di PostgreSQL).
  • Pemilihan Korban (Deadlock Victim): Saat siklus terdeteksi, engine memilih salah satu transaksi untuk dibatalkan (abort). Engine me-rollback transaksi korban, melepas kuncinya, dan mengembalikan error kode spesifik ke klien (misalnya PostgreSQL SQLSTATE 40P01 atau SQL Server Error 1205).

Implementasi Pembuktian di Software Engineering Lab 18

Laboratorium ini mengisolasi fenomena deadlock ke dalam kode Go standar tanpa dependensi eksternal, memodelkan row-level lock menggunakan buffer channel berkapasitas 1 slot dengan batasan context timeout.

1. Model Akun dan Akuisisi Lock Berbatas Waktu

package bank

import (
	"context"
	"errors"
)

var ErrDeadlock = errors.New("deadlock victim")

type Account struct {
	ID      string
	Balance int
	ch      chan struct{}
}

func NewAccount(id string, bal int) *Account {
	ch := make(chan struct{}, 1)
	ch <- struct{}{}
	return &Account{ID: id, Balance: bal, ch: ch}
}

func (a *Account) Lock(ctx context.Context) error {
	select {
	case <-a.ch:
		return nil
	case <-ctx.Done():
		return ErrDeadlock
	}
}

func (a *Account) Unlock() {
	a.ch <- struct{}{}
}

Ketika channel kosong (lock sedang dipegang oleh goroutine lain), pemanggil akan menunggu hingga channel kembali terisi atau waktu context habis (ctx.Done()), yang memicu kembalian ErrDeadlock sebagai representasi transaksi korban.

2. Pola Naif: Pemicu Deadlock

func TransferNaive(ctx context.Context, from, to *bank.Account, amount int, delay time.Duration) error {
	if err := from.Lock(ctx); err != nil {
		return err
	}
	defer from.Unlock()

	time.Sleep(delay) // simulasi durasi pemrosesan transaksi

	if err := to.Lock(ctx); err != nil {
		return err
	}
	defer to.Unlock()

	from.Balance -= amount
	to.Balance += amount
	return nil
}

Urutan penguncian ditentukan langsung oleh parameter pemanggil (from lalu to). Parameter delay memperlebar jendela kompetisi konkurensi. Dua pemanggilan simultan dengan arah berlawanan terbukti memicu kegagalan deadlock.

3. Solusi Pencegahan: Deterministic Lock Ordering

func TransferOrdered(ctx context.Context, acc1, acc2 *bank.Account, amount int, delay time.Duration) error {
	first, second := acc1, acc2
	if acc1.ID > acc2.ID {
		first, second = acc2, acc1
	}

	if err := first.Lock(ctx); err != nil {
		return err
	}
	defer first.Unlock()

	time.Sleep(delay)

	if err := second.Lock(ctx); err != nil {
		return err
	}
	defer second.Unlock()

	acc1.Balance -= amount
	acc2.Balance += amount
	return nil
}

Fungsi TransferOrdered membandingkan nilai string acc1.ID dan acc2.ID. Akun dengan identifier lebih kecil selalu dikunci terlebih dahulu. Kedua transaksi konkuren akan bersaing memperebutkan lock pertama yang sama, sehingga salah satu transaksi mengantre secara tertib tanpa pernah membentuk siklus tunggu.

4. Solusi Pemulihan: Application-Level Retry

func TransferWithRetry(ctx context.Context, from, to *bank.Account, amount int, delay time.Duration, maxRetries int) error {
	for i := 0; i < maxRetries; i++ {
		attemptCtx, cancel := context.WithTimeout(ctx, 10*time.Millisecond)
		err := TransferNaive(attemptCtx, from, to, amount, delay)
		cancel()

		if err == nil {
			return nil
		}
		if err != bank.ErrDeadlock && err != context.DeadlineExceeded {
			return err
		}

		time.Sleep(2 * time.Millisecond)
	}
	return bank.ErrDeadlock
}

Jika transaksi naif digugurkan sebagai korban deadlock, aplikasi menangkap error tersebut, melakukan jeda waktu (backoff), lalu mengeksekusi ulang seluruh transaksi dari awal.

Panduan Arsitektur untuk Sistem Produksi

  1. Terapkan Urutan Penguncian Universal: Pastikan urutan penguncian entitas diterapkan seragam di semua endpoint, repositori, dan background worker. Mengurutkan ID di satu fungsi tidak berguna bila ada query lain yang mengakses data tanpa urutan.
  2. Minimalkan Durasi Transaksi Database: Jangan pernah meletakkan panggilan jaringan (seperti pemanggilan payment gateway eksternal atau pengiriman email) di dalam blok transaksi aktif database.
  3. Gunakan Klausa Pengurutan pada Operasi Batch: Saat melakukan mutasi massal (misalnya UPDATE ... WHERE id IN (...)), selalu urutkan kumpulan identifier secara menaik (ORDER BY id ASC) sebelum eksekusi.
  4. Wajibkan Idempotensi pada Transaksi yang Di-retry: Pastikan logika yang diulang tidak mengeksekusi efek samping non-idempotent tanpa mekanisme dedup.

Batasan Implementasi Lab

Laboratorium ini merupakan simulasi di tingkat aplikasi menggunakan channel Go dan context timeout untuk memodelkan efek dari transaksi korban yang dibatalkan. Lab ini tidak mengimplementasikan algoritma traversal graf siklus penuh (Wait-For Graph) seperti yang ada pada storage engine internal DBMS. Selain itu, jeda retry pada lab menggunakan nilai tetap 2ms demi kecepatan eksekusi unit test; pada sistem produksi, pengembang wajib menggunakan exponential backoff dengan jitter.
