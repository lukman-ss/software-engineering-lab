Lonjakan Transaksi Konkuren Memicu Kemacetan Sistemik

Ketika volume transaksi tinggi mengakses baris data secara bersamaan, urutan akses yang tidak teratur memicu kebuntuan fatal. Munculnya galat pembatalan transaksi bukan berarti database mengalami kerusakan internal, melainkan sinyal bahwa lapisan aplikasi membiarkan pola penguncian saling silang.

Review Kode Manual Gagal Menangkap Siklus Tunggu Konkuren

Review manual dan unit test sekuensial tidak mampu mereproduksi deadlock karena eksekusi konkuren bergantung pada timing scheduler CPU. Menjalankan query di dalam transaksi ACID tidak otomatis melindungi sistem dari deadlock jika dua alur bisnis mengunci entitas dalam urutan berlawanan.

Anatomi Siklus Tunggu: Deadly Embrace Dua Transaksi

Deadlock terjadi ketika empat syarat Coffman hadir bersamaan: eksklusivitas, menahan lock lama, tanpa perebutan paksa, dan siklus tunggu melingkar. Hanya pada jalur ini kondisi saling sandera terkunci permanen, menuntut adanya intervensi eksternal seperti pembatalan paksa oleh database engine.

Alur Deteksi Mesin Basis Data: Dari Wait-For Graph ke Abort

Basis data tidak memeriksa deadlock secara terus-menerus demi menghemat CPU, melainkan menunggu jeda timeout tertentu sebelum menelusuri Wait-For Graph. Simulasi lab membatalkan transaksi via context timeout, tetapi belum membuktikan algoritma pemilihan korban berbasis biaya modifikasi terkecil seperti MySQL InnoDB.

Pola Penguncian Naif yang Menimbulkan Deadlock

Fungsi TransferNaive mengunci akun pengirim lalu akun penerima sesuai urutan parameter pemanggilan. Menambahkan jeda waktu eksekusi bukan berarti memperlambat kode secara sengaja, melainkan memodelkan latensi query nyata yang membuka celah tabrakan bagi transaksi berlawanan arah.

func TransferNaive(ctx context.Context, from, to *bank.Account, amount int, delay time.Duration) error {
    if err := from.Lock(ctx); err != nil { return err }
    defer from.Unlock()
    time.Sleep(delay) // simulasi durasi transaksi internal
    if err := to.Lock(ctx); err != nil { return err }
    defer to.Unlock()
    from.Balance -= amount
    to.Balance += amount
    return nil
}

Kronologi Tabrakan: Goroutine A vs Goroutine B

Ketika dua transfer berjalan simultan dengan arah berlawanan, masing-masing berhasil mendapatkan kunci pertama namun gagal memperoleh kunci kedua. Hanya pada jalur ini kebuntuan absolut terjadi, memaksa timer pembatalan mengorbankan salah satu transaksi agar yang lain dapat selesai.

Batasan Bukti Lab: Yang Dibuktikan vs Belum

Lab ini membuktikan mekanika dasar deadlock dan validitas teknik pengurutan kunci menggunakan channel in-memory. Pengujian ini belum membuktikan fenomena kompleks seperti gap locking pada indeks database riil atau perilaku sistem pada beban puluhan ribu TPS.

Kompromi Rekayasa: Lock Ordering vs Application Retry

Penerapan lock ordering memberikan kepastian absolut namun menuntut disiplin penulisan query yang seragam di seluruh repository. Menambahkan retry logic tidak otomatis membuat sistem berkinerja tinggi jika sumber daya yang diperebutkan mengalami saturasi ekstrem.

Model Sinkronisasi Akun Berbasis Channel dan Timeout

Model Account memanfaatkan buffered channel 1 slot untuk mengendalikan hak akses mutasi saldo. Simulasi ini tidak sama dengan locking row-level di PostgreSQL yang memiliki status lock modes bertingkat, namun secara elegan merefleksikan pembatalan transaksi akibat timeout eksternal.

type Account struct {
    ID      string
    Balance int
    ch      chan struct{} // channel buffer 1 sebagai token lock
}
func (a *Account) Lock(ctx context.Context) error {
    select {
    case <-a.ch: return nil
    case <-ctx.Done(): return ErrDeadlock // representasi deadlock abort
    }
}

Transformasi: Dari Tabrakan Acak ke Eksekusi Teratur

Sebelum standarisasi urutan, dua transaksi yang bersilangan akan saling menunggu dan berujung pada pembatalan sepihak. Mengantrekan transaksi pada kunci pertama bukan berarti memperlambat sistem, melainkan menyelamatkan CPU dari pemborosan rollback dan retry.

Pencegahan Deterministik: Pengurutan Kunci Berdasarkan ID

Dengan membandingkan identifier string secara leksikografis, entitas dengan ID lebih kecil selalu dikunci terlebih dahulu. Logika pencegahan ini cakupannya mengikuti test konkurensi lab, menjamin bahwa circular wait mustahil terbentuk karena seluruh goroutine mengantre pada kunci pertama yang sama.

func TransferOrdered(ctx context.Context, acc1, acc2 *bank.Account, amount int, delay time.Duration) error {
    first, second := acc1, acc2
    if acc1.ID > acc2.ID { first, second = acc2, acc1 }
    if err := first.Lock(ctx); err != nil { return err }
    defer first.Unlock()
    time.Sleep(delay)
    if err := second.Lock(ctx); err != nil { return err }
    defer second.Unlock()
    acc1.Balance -= amount; acc2.Balance += amount
    return nil
}

Verifikasi Test: Membuktikan Terjadinya Deadlock Victim

Unit test membuktikan secara deterministik bahwa transfer silang tanpa pengurutan selalu mengorbankan minimal satu transaksi. Menjalankan dua goroutine paralel tidak otomatis memicu deadlock tanpa delay internal yang memadai untuk membuka jendela kontensi.

func TestDeadlockOccurrence(t *testing.T) {
    // Goroutine 1 mentransfer A -> B (delay 10ms, timeout 20ms)
    go func() { errs[0] = transfer.TransferNaive(ctx1, accA, accB, 10, 10*time.Millisecond) }()
    // Goroutine 2 bersamaan mentransfer B -> A (delay 10ms, timeout 20ms)
    go func() { errs[1] = transfer.TransferNaive(ctx2, accB, accA, 10, 10*time.Millisecond) }()
    wg.Wait()
    hasDeadlock := (errs[0] == bank.ErrDeadlock) || (errs[1] == bank.ErrDeadlock)
    if !hasDeadlock { t.Fatalf("expected at least one deadlock victim") }

Verifikasi Test: Lock Ordering Menuntaskan Semua Transaksi

Pengujian membuktikan bahwa kedua transaksi bolak-balik berhasil dieksekusi tanpa error sama sekali saat menggunakan TransferOrdered. Hanya pada jalur ini konsistensi saldo terjaga utuh (100 dan 100) karena transaksi saling mengantre secara tertib alih-alih saling mematikan.

func TestLockOrderingPreventsDeadlock(t *testing.T) {
    go func() { errs[0] = transfer.TransferOrdered(ctx1, accA, accB, 10, 5*time.Millisecond) }()
    go func() { errs[1] = transfer.TransferOrdered(ctx2, accB, accA, 10, 5*time.Millisecond) }()
    wg.Wait()
    if errs[0] != nil || errs[1] != nil { t.Fatalf("expected both to succeed") }
    if accA.Balance != 100 || accB.Balance != 100 {
        t.Fatalf("unexpected balance: A=%d, B=%d", accA.Balance, accB.Balance)
    }
}

Pemulihan Transparan: Penanganan Abort dengan Retry

Fungsi TransferWithRetry menangkap galat pembatalan deadlock dan mencoba kembali transaksi secara transparan hingga batas maksimal. Menggunakan fixed backoff 2ms bukan berarti pola ini ideal untuk produksi; implementasi ini adalah penyederhanaan terencana yang membutuhkan jitter pada skala besar.

func TransferWithRetry(ctx context.Context, from, to *bank.Account, amount int, delay time.Duration, maxRetries int) error {
    for i := 0; i < maxRetries; i++ {
        attemptCtx, cancel := context.WithTimeout(ctx, 10*time.Millisecond)
        err := TransferNaive(attemptCtx, from, to, amount, delay)
        cancel()
        if err == nil { return nil }
        if err != bank.ErrDeadlock && err != context.DeadlineExceeded { return err }
        time.Sleep(2 * time.Millisecond) // backoff sebelum mencoba kembali
    }
    return bank.ErrDeadlock
}

Dampak Durasi: Transaksi Panjang Memperbesar Risiko

Pengujian empiris membuktikan bahwa transaksi yang menahan lock selama 5 milidetik menghasilkan frekuensi deadlock yang lebih tinggi atau sama dibandingkan transaksi tanpa delay. Pengamatan ini cakupannya mengikuti test lab, memvalidasi prinsip bahwa memperpanjang waktu penahanan lock memperbesar kemungkinan tabrakan.

func TestTransactionDurationImpact(t *testing.T) {
    longDeadlocks := countDeadlocks(5*time.Millisecond, 10)
    shortDeadlocks := countDeadlocks(0, 10)
    if longDeadlocks < shortDeadlocks {
        t.Fatalf("expected long duration to have >= deadlocks: long=%d, short=%d",
                 longDeadlocks, shortDeadlocks)
    }
}

Checklist Proteksi Deadlock di Lingkungan Produksi

Checklist ini merangkum langkah mitigasi wajib: urutan penguncian global yang seragam, pengurutan kunci pada update massal, pembebasan transaksi dari panggilan eksternal, penangkapan kode galat vendor spesifik, retry berbasis jitter, serta jaminan idempotensi.

Anti-Pattern Umum dalam Penanganan Transaksi

Menahan koneksi transaksi database sambil menunggu respons API pihak ketiga adalah penyebab paling umum lonjakan deadlock di produksi. Memasang wrapper retry tanpa memastikan idempotensi mutasi bukan berarti sistem menjadi andal, melainkan berisiko mencatatkan perubahan saldo ganda.

Prinsip Inti: Deadlock adalah Keniscayaan Konkurensi

Deadlock tidak boleh dipandang sebagai aib atau bug fatal, melainkan mekanisme perlindungan integritas data dari basis data. Merancang sistem transaksional tidak otomatis membebaskan kita dari kontensi; sistem yang tangguh mencegah siklus sedini mungkin dan memulihkan korban dengan anggun.
