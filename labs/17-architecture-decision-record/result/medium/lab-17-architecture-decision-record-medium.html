Architecture Decision Record: Mengunci Silsilah Keputusan Arsitektur di Git

Menjaga konteks teknis di repositori: parsing Markdown, penomoran monotonik, validasi timbal-balik supersedes, dan siklus rejected.

Lukman / lukman-ss · Software Engineering Lab 17

Keputusan arsitektur sebagai kode dan dokumen Git

Ketika basis kode bertumbuh dan insinyur berganti, pertanyaan historis muncul ke permukaan: mengapa subsistem ini memakai modular monolith? Mengapa relational database dipilih daripada document store? Ketika dokumentasi arsitektur disimpan terpisah pada wiki internal, dokumen tersebut cepat mengalami documentation drift—ketinggalan zaman dan terputus dari commit aktual. Michael Nygard (2011) memperkenalkan Architecture Decision Record (ADR) untuk menyimpan rekaman keputusan langsung di dalam direktori Git bersama kode aplikasi, ditinjau melalui pull request, dan diperlakukan sebagai artefak perangkat lunak yang dapat diverifikasi secara terprogram.

Anatomi lima seksi wajib: Title, Status, Context, Decision, Consequences

Sebuah berkas ADR yang sehat mengikuti struktur terstandarisasi (format MADR). Berkas diawali dengan nomor urut dan judul singkat, diikuti status siklus hidup terkini. Bagian Context menguraikan gaya dorong (forces), batasan bisnis, dan kendala teknis saat keputusan diambil. Bagian Decision menegaskan perubahan desain yang disepakati dengan kalimat aktif. Terakhir, Consequences mendokumentasikan dampak positif, trade-off negatif, dan risiko netral yang harus ditanggung tim. Ketiadaan salah satu dari seksi ini menandakan catatan yang tidak lengkap.

Model data Record dan konstanta Status diskret

Pada internal/adr/models.go, status ADR didefinisikan sebagai tipe custom berbasis string dengan lima nilai diskret yang diizinkan. Struct Record merepresentasikan dokumen ADR di dalam memori setelah melalui proses parsing:

type Status string

const (
    StatusProposed   Status = "Proposed"
    StatusAccepted   Status = "Accepted"
    StatusSuperseded Status = "Superseded"
    StatusDeprecated Status = "Deprecated"
    StatusRejected   Status = "Rejected"
)

type Record struct {
    ID           int
    Title        string
    Status       Status
    SupersededBy int // 0 jika tidak ada
    Supersedes   int // 0 jika tidak ada
    Content      string
}

State machine lima status: Proposed, Accepted, Rejected, Superseded, Deprecated

Status ADR tidak boleh diisi dengan teks bebas sembarangan (seperti "Draft" atau "In Progress"). Setiap status merepresentasikan kondisi formal dalam siklus hidup arsitektur:

ADR tidak dibuat untuk mencatat setiap refaktorisasi rutin atau perubahan nama variabel. Berdasarkan taksonomi Zimmermann (2020), ADR hanya dicadangkan untuk keputusan yang berdampak luas:

Implementasi pada internal/adr/parser.go menggunakan bufio.Scanner untuk memindai dokumen Markdown secara linier baris demi baris. Regex ekstraksi metadata judul dan nomor ID

Header utama dokumen diekstraksi menggunakan ekspresi reguler ^#\s+(\d+)\.\s+(.+)$. Pola ini memastikan bahwa setiap dokumen ADR memiliki judul tingkat satu (H1) yang diawali oleh nomor bulat positif dan titik, diikuti oleh nama keputusan arsitektural. Jika judul tidak cocok dengan pola tersebut, parser mengembalikan error spesifik bahwa format judul tidak valid.

var titleRegex = regexp.MustCompile(`^#\s+(\d+)\.\s+(.+)$`)
matches := titleRegex.FindStringSubmatch(line)
if matches != nil {
    id, _ := strconv.Atoi(matches[1])
    record.ID = id
    record.Title = matches[2]
}

Parsing silsilah: Superseded by dan Supersedes

Ketika sebuah keputusan mengalami evolusi, parser mengekstraksi hubungan silsilah penggantian melalui regex status. Jika sebuah baris status menyatakan Status: Superseded by 2, parser menetapkan record.Status = StatusSuperseded dan record.SupersededBy = 2. Begitu pula jika terdapat baris Supersedes: 1, parser menetapkan record.Supersedes = 1.

var supersededRegex = regexp.MustCompile(
    `(?i)superseded\s+by\s+(\d+)`)
var supersedesRegex = regexp.MustCompile(
    `(?i)supersedes[:\s]+(\d+)`)

Model linier versus directed acyclic graph (DAG)

Kumpulan ADR dalam satu repositori tidak sekadar daftar linier berurutan, melainkan membentuk Directed Acyclic Graph (DAG). Sebuah keputusan di masa lalu dapat digantikan oleh keputusan baru, yang di kemudian hari dapat digantikan lagi oleh keputusan ketiga (ADR 1 → ADR 5 → ADR 12). Pohon silsilah ini memungkinkan insinyur baru menelusuri rantai evolusi arsitektur dari keputusan fondasi hingga kondisi operasional saat ini.

Linter memvalidasi urutan penomoran monotonik

Pada internal/adr/linter.go, fungsi Linter.Lint(records []*Record) memeriksa keutuhan urutan penomoran ID. Linter mengurutkan seluruh ID yang terdaftar dan memverifikasi bahwa urutan dimulai tepat dari 1 dan bertambah satu demi satu tanpa celah (1, 2, 3, ... N). Jika terdapat ID duplikat atau nomor yang hilang, linter mengembalikan error penomoran non-monotonik.

sort.Slice(records, func(i, j int) bool {
    return records[i].ID < records[j].ID
})
for i, r := range records {
    expectedID := i + 1
    if r.ID != expectedID {
        errs = append(errs, fmt.Errorf(
            "non-monotonic ID: expected %d, got %d",
            expectedID, r.ID))
    }
}

Validasi timbal-balik (Bidirectional Lineage Check)

Integritas silsilah diperiksa melalui validasi dua arah (bidirectional reciprocal check). Jika Record A berstatus SupersededBy: B, linter mencari Record B di dalam repositori dan menegaskan bahwa Record B benar-benar mendeklarasikan Supersedes: A. Sebaliknya, jika Record B mengklaim Supersedes: A, linter memverifikasi bahwa Record A berstatus Superseded dan menunjuk balik ke Record B. Jika salah satu sisi hilang, linter melaporkan inkonsistensi silsilah.

Goroutine konkuren memvalidasi graf referensi

Untuk mendemonstrasikan efisiensi konkurensi di Go, linter membagi pemeriksaan simpul graf ADR ke dalam goroutine terpisah menggunakan sync.WaitGroup. Setiap goroutine memvalidasi satu dokumen ADR terhadap peta memori (recordsMap) secara paralel, menghasilkan waktu validasi mendekati instan bahkan pada repositori dengan ratusan berkas ADR.

var wg sync.WaitGroup
for _, r := range records {
    wg.Add(1)
    go func(rec *Record) {
        defer wg.Done()
        // Validasi reciprocal timbal-balik
    }(r)
}
wg.Wait()

Mutex mengunci agregasi slice error validasi

Karena banyak goroutine dapat menemukan pelanggaran aturan secara bersamaan, penulisan ke slice errs dilindungi oleh sync.Mutex. Setiap kali goroutine menemukan tautan patah atau ketidaksesuaian status, ia mengunci mutex sebelum menambahkan error ke koleksi bersama. Mekanisme ini memastikan validasi konkurensi bebas dari data race saat diuji dengan flag -race.

var mu sync.Mutex
// Di dalam goroutine validasi:
if invalid {
    mu.Lock()
    errs = append(errs, err)
    mu.Unlock()
}

Pemisahan parser murni dari rule-checking linter

Lab memisahkan secara tegas tanggung jawab pemindaian teks (Parser) dari penegakan aturan arsitektur (Linter). Parser murni memetakan Markdown menjadi struct data tanpa menghakimi validitas hubungan antardokumen. Linter menerima slice []*Record dan menerapkan aturan bisnis agregat. Pemisahan ini mencerminkan prinsip Single Responsibility dan mempermudah pengujian modular.

Pencatatan status Rejected mencegah debat berulang

Salah satu nilai terbesar ADR adalah mencatat opsi yang ditolak (Rejected). Dalam banyak organisasi, ide teknis yang sama (seperti "mari migrasi ke NoSQL") diusulkan berulang kali setiap beberapa bulan oleh anggota tim yang berbeda. Dengan adanya ADR berstatus Rejected yang mendokumentasikan alasan kegagalan evaluasi, tim dapat menghemat ratusan jam diskusi dan langsung merujuk pada bukti yang telah diuji.

Invarian Git: ADR bersifat append-only dan immutable

Aturan dasar pengelolaan ADR adalah immutability. Sekali sebuah ADR disetujui (Accepted), isinya tidak boleh diedit secara retroaktif untuk mengubah substansi keputusan. Jika arah arsitektur berubah karena kebutuhan skala baru, tim wajib membuat ADR baru yang menggantikannya. ADR lama tetap ada di repositori dengan status Superseded, menjaga integritas riwayat evolusi sistem sebagaimana log transaksi akuntansi.

CLI demo mendemonstrasikan validasi direktori riil

File cmd/demo/main.go mengintegrasikan parser dan linter untuk memeriksa direktori Markdown secara nyata:

func main() {
    files, _ := filepath.Glob("docs/adr/*.md")
    var records []*adr.Record
    for _, f := range files {
        content, _ := os.ReadFile(f)
        rec, err := adr.Parse(string(content))
        if err != nil {
            log.Fatalf("Parse error %s: %v", f, err)
        }
        records = append(records, rec)
    }

    linter := adr.NewLinter()
    if errs := linter.Lint(records); len(errs) > 0 {
        for _, err := range errs {
            fmt.Printf("[LINT ERROR] %v\n", err)
        }
        os.Exit(1)
    }
    fmt.Println("[ADR LINTER PASS] All 3 ADRs valid and lineage verified.")
}
