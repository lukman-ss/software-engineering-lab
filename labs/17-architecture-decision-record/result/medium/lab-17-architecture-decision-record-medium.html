Architecture Decision Record: Mengunci Silsilah Keputusan Arsitektur di Git

Menjaga konteks teknis di repositori: parsing Markdown, penomoran monotonik, validasi timbal-balik supersedes, dan siklus rejected.

Lukman / lukman-ss · Software Engineering Lab 17

Ketika basis kode bertumbuh dan insinyur berganti, pertanyaan historis muncul ke permukaan: mengapa modul notifikasi dipisahkan menjadi microservice? Mengapa event sourcing ditolak untuk manajemen pesanan? Ketika dokumen desain tersimpan terpisah pada wiki eksternal, dokumentasi tersebut cepat usang dan terputus dari commit aktual.

Hilangnya konteks keputusan memicu dua jebakan tim rekayasa:

  1. Membatalkan pola masa lalu secara terburu-buru tanpa memahami batasan awal yang memicunya.
  2. Mempertahankan arsitektur lama secara kaku meski skala beban dan ukuran tim sudah jauh melampaui kapasitas desain awal.
Architecture decisions must form an immutable, verifiable directed acyclic graph. Once accepted, records are never edited retroactively; they are superseded through explicit bidirectional lineage.

Lab 17 mendemonstrasikan implementasi validator dan linter struktural di Go untuk Architecture Decision Records (ADR). ADR disimpan bersama kode sumber dalam format Markdown, bernomor urut monotonik, dan memiliki silsilah penggantian timbal-balik yang diperiksa otomatis pada pipeline pengujian.

Batasan Keputusan yang Signifikan Secara Arsitektur

ADR tidak dirancang untuk mencatat setiap refaktorisasi metode atau perbaikan bug lokal. Sesuai prinsip Michael Nygard (2011) dan Olaf Zimmermann (2020), ADR dicadangkan khusus untuk keputusan bernilai arsitektural (Architecturally Significant Requirements):

Kategori Cakupan Keputusan Contoh Nyata
Struktur Pemisahan subsistem dan batasan modularitas Modular Monolith vs Microservices
Non-Fungsional (NFR) Skalabilitas, toleransi kesalahan, dan latensi Isolasi antrean asinkron untuk lonjakan trafik
Dependensi Pemilihan basis data dan pustaka inti Relational DB vs Document DB
Antarmuka Kontrak komunikasi antarlayanan Protokol REST vs gRPC vs Message Broker
Konstruksi Standar integritas dan transaksi Tabel audit relasional vs Event Sourcing

Siklus Hidup Status ADR

Keputusan arsitektur dimodelkan melalui status diskret pada berkas internal/adr/models.go:

type Status string

const (
	StatusProposed   Status = "Proposed"
	StatusAccepted   Status = "Accepted"
	StatusSuperseded Status = "Superseded"
	StatusDeprecated Status = "Deprecated"
	StatusRejected   Status = "Rejected"
)

type Record struct {
	ID           int
	Title        string
	Status       Status
	SupersededBy int // 0 jika tidak digantikan
	Supersedes   int // 0 jika tidak menggantikan
	Content      string
}

Setiap status memiliki peran semantik eksplisit:

  • Proposed: Usulan arsitektur yang sedang ditinjau tim sebelum disetujui.
  • Accepted: Keputusan resmi yang aktif mengikat desain sistem saat ini.
  • Superseded: Keputusan yang tidak lagi aktif karena digantikan oleh ADR baru.
  • Deprecated: Keputusan yang ditinggalkan tanpa ada pengganti langsung.
  • Rejected: Usulan yang ditolak secara formal. Mencatat usulan yang ditolak mencegah perdebatan teknis berulang di kemudian hari tanpa adanya bukti atau data beban baru.

Skenario Kerusakan Dokumen Markdown Manual

Memelihara berkas ADR tanpa linter otomatis menimbulkan risiko inkonsistensi data:

  • Tautan Penggantian Patah: Berkas lama mencatat Status: Superseded by 99, tetapi ADR 99 tidak ada di repositori.
  • Tautan Sepihak: ADR baru mencantumkan Supersedes: 1, namun ADR 1 masih berstatus Accepted tanpa referensi Superseded by 2.
  • Penomoran Loncat: Penomoran melompat dari ADR 1 langsung ke ADR 3, menimbulkan ketidakpastian apakah berkas ADR 2 terhapus atau tertinggal dalam konflik merge Git.
  • Self-Supersession dan Siklus: ADR menyatakan menggantikan dirinya sendiri (ID 1 menggantikan ID 1) atau terjadi siklus tak berujung (1 → 2 → 3 → 1).
  • Bagian Wajib Kosong: Pengembang menghapus heading Context, Decision, atau Consequences sehingga ADR kehilangan alasan rasionalnya.

Mekanisme Parsing Teks ke Struktur Invarian

Modul internal/adr/parser.go memindai berkas Markdown baris demi baris menggunakan ekspresi reguler terarah:

var (
	titleRegex        = regexp.MustCompile(`^#\s+(\d+)\.\s+(.+)$`)
	statusRegex       = regexp.MustCompile(`(?i)^Status:\s*([A-Za-z]+)(?:\s+by\s+(\d+))?`)
	supersedesRegex   = regexp.MustCompile(`(?i)^Supersedes:\s*(\d+)`)
	contextRegex      = regexp.MustCompile(`(?i)^##\s+Context`)
	decisionRegex     = regexp.MustCompile(`(?i)^##\s+Decision`)
	consequencesRegex = regexp.MustCompile(`(?i)^##\s+Consequences`)
)

Fungsi Parse memeriksa keberadaan teks non-kosong di dalam setiap bagian wajib:

if !foundContext || !contextHasContent {
	return nil, fmt.Errorf("context section missing or empty")
}
if !foundDecision || !decisionHasContent {
	return nil, fmt.Errorf("decision section missing or empty")
}
if !foundConsequences || !consequencesHasContent {
	return nil, fmt.Errorf("consequences section missing or empty")
}

Validasi Monotonik dan Silsilah Timbal-Balik

Modul internal/adr/linter.go menjalankan tiga lapis pemeriksaan integritas:

1. Pemeriksaan Urutan Monotonik

Seluruh identitas ID dikumpulkan ke dalam slice dan diurutkan. Algoritma memastikan penomoran dimulai dari 1 hingga N tanpa jeda:

sort.Ints(ids)
for i := 0; i < len(ids); i++ {
	if ids[i] != i+1 {
		errs = append(errs, fmt.Errorf("non-monotonic numbering, expected %d but got %d", i+1, ids[i]))
		break
	}
}

2. Deteksi Siklus Supersession

Linter menggunakan penelusuran graf (Depth-First Search) tiga warna (unvisited, visiting, visited) untuk mendeteksi siklus berarah pada rantai SupersededBy:

state := make(map[int]int)
var detectCycle func(id int)
detectCycle = func(id int) {
	state[id] = 1
	rec, exists := recordMap[id]
	if exists && rec.SupersededBy != 0 && rec.SupersededBy != rec.ID {
		nextID := rec.SupersededBy
		if state[nextID] == 1 {
			errs = append(errs, fmt.Errorf("cyclical supersession detected involving ADR %d", nextID))
		} else if state[nextID] == 0 {
			detectCycle(nextID)
		}
	}
	state[id] = 2
}

3. Validasi Timbal-Balik Konkuren

Setiap node divalidasi secara paralel melalui goroutine dengan sinkronisasi sync.Mutex:

if rec.Status == StatusSuperseded {
	if rec.SupersededBy == rec.ID {
		localErrs = append(localErrs, fmt.Errorf("ADR %d cannot supersede itself", rec.ID))
	} else if rec.SupersededBy == 0 {
		localErrs = append(localErrs, fmt.Errorf("ADR %d is superseded but missing superseded_by reference", rec.ID))
	} else {
		replacement, exists := recordMap[rec.SupersededBy]
		if !exists {
			localErrs = append(localErrs, fmt.Errorf("ADR %d superseded by non-existent ADR %d", rec.ID, rec.SupersededBy))
		} else if replacement.Supersedes != rec.ID {
			localErrs = append(localErrs, fmt.Errorf("ADR %d superseded by ADR %d, but ADR %d does not declare it supersedes ADR %d", rec.ID, rec.SupersededBy, rec.SupersededBy, rec.ID))
		}
	}
}

Studi Kasus: Evolusi Arsitektur SaaS ERP

Program percontohan cmd/demo/main.go memodelkan evolusi arsitektur SaaS ERP melalui tiga ADR konkret:

  1. ADR 0001 (Modular Monolith): Dipilih saat tim berjumlah 5 insinyur dengan tenggat 3 bulan. Memprioritaskan iterasi cepat, satu basis data bersama, dan integritas transaksi ACID lokal. Menyertakan pemicu peninjauan ketika tim melampaui 20 insinyur.
  2. ADR 0002 (Ekstraksi Microservice Notifikasi): Diterbitkan ketika tim mencapai 25 insinyur dan mesin notifikasi mengalami lonjakan beban tinggi yang mengganggu inti ERP. ADR 0001 ditandai Superseded by 2, sementara ADR 0002 mencantumkan Supersedes: 1. Modul notifikasi dipisahkan menjadi layanan independen berbasis antrean pesan asinkron.
  3. ADR 0003 (Penolakan Event Sourcing): Usulan merombak modul pesanan menjadi event sourcing ditolak (Status: Rejected). Tabel catatan audit relasional dinilai mencukupi kebutuhan kepatuhan hukum tanpa menanggung kerumitan migrasi skema event dan konsistensi eventual.

Eksekusi demo memvalidasi ketiga dokumen tersebut dan memastikan seluruh rantai silsilah terikat sempurna tanpa pelanggaran aturan linter:

Batas Implementasi dan Pertimbangan Produksi

Untuk adopsi di lingkungan produksi, pahami batas lingkup lab ini:

  • Parser Berbasis Pola Regex: Parser bergantung pada format heading Markdown spesifik (# 1. Judul dan ## Context). Belum menggunakan parser AST Markdown umum.
  • Pemrosesan In-Memory: Demo dan suite pengujian memvalidasi string memori; pembacaan rekursif dari direktori disk lokal atau commit Git belum diimplementasikan di layer CLI.
  • Integrasi CI dan Pre-commit: Linter dirancang dipanggil pada pipeline pengujian lokal atau CI; instalasi hook otomatis pada .git/hooks belum disertakan.
  • Validasi Semantik: Linter memastikan struktur, ID, dan tautan silsilah valid. Penilaian apakah keputusan arsitektural tersebut benar tetap menjadi tanggung jawab manusia melalui peninjauan rekan kerja (peer review).
