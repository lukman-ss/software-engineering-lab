Konteks Keputusan Arsitektur Hilang Tanpa Jejak

Dalam praktik engineering sehari-hari, keputusan arsitektur sering kali diambil secara informal—lewat chat, voice note, atau diskusi meeting. Ketika engineer baru bergabung atau sistem mengalami pivot strategis, konteks historis mengapa pilihan tertentu dibuat hilang. Tim kemudian terjebak debat berulang tentang keputusan yang sebenarnya sudah pernah diverifikasi dan ditolak. Ini bukan masalah dokumentasi biasa; ini adalah kehilangan kapabilitas keputusan yang berharga.

Review Markdown Manual Lupa Relasi Penggantian

Ketika tim mengandalkan review manual terhadap dokumen Markdown ADR, pola kegagalan yang paling sering muncul adalah tautan supersesi yang tidak sinkron. Engineer bisa jadi memperbarui isi keputusan pada ADR baru namun lupa mengembalikan marker pada ADR lama. Atau sebaliknya: ADR baru mengklanimsupersedes_ADR lama, tapi ADR lama tidak pernah mengubah statusnya menjadi Superseded. Review manual juga sulit mendeteksi loncatan nomor urut karena tidak ada mekanisme enforcement struktural.

ADR Bukan Dokumen, Tapi Record yang Bisa Dicek

Inti dari pendekatan lab ini adalah memandang Architecture Decision Record bukan sebagai dokumen naratif yang perlu dibaca manusia secara manual, melainkan sebagai record terstruktur yang bisa diparse dan divalidasi oleh mesin. Parser membaca Markdown, mengekstrak field-field kunci menjadi struct Record, dan linter kemudian menjalankan serangkaian aturan struktural. Nilai utama bukan pada otomasi pengambilan keputusan, melainkan pada kemampuan mendeteksi anomali struktural yang sering luput dari review manual.

Pipeline: Markdown → Parser → Records → Linter

Arsitektur sistem validasi ADR pada lab ini dibangun sebagai pipeline tiga tahap. Tahap pertama, parser membaca Markdown baris demi baris menggunakan regex dan mengekstrak field-field kunci. Hasilnya adalah slice struct Record yang berisi metadata keputusan. Tahap kedua, linter menjalankan validasi urutan ID monotonik dan deteksi siklus melalui depth-first search. Tahap ketiga, validasi graf silsilah dilakukan secara paralel menggunakan goroutine dengan mutex untuk agregasi error, memastikan setiap tautan SupersededBy dan Supersedes saling konsisten.

Struct Record: Definisi Inti ADR

Struktur data Record pada models.go merupakan fondasi seluruh sistem validasi. Field Status menggunakan enum string yang hanya mengakui lima nilai resmi: Proposed, Accepted, Superseded, Deprecated, dan Rejected. Field SupersededBy mereferensikan ADR pengganti, sedangkan Supersedes mereferensikan ADR yang digantikan. Keduanya bernilai 0 (nol) ketika tidak ada relasi. Dengan representasi terstruktur ini, linter tidak perlu menebak-tebak — ia hanya memeriksa konsistensi integer dan string.

type Status string

const (
    StatusProposed   Status = "Proposed"
    StatusAccepted   Status = "Accepted"
    StatusSuperseded Status = "Superseded"
    StatusDeprecated Status = "Deprecated"
    StatusRejected   Status = "Rejected"
)

type Record struct {
    ID           int
    Title        string
    Status       Status
    SupersededBy int // 0 if not superseded
    Supersedes   int // 0 if does not supersede
    Content      string
}

Supersesi Patah: ADR 1 Merujuk ke ADR 99

Skenario kegagalan paling umum pada pemeliharaan ADR manual adalah tautan supersesi yang merujuk ke nomor ADR yang belum ada atau sudah dihapus. Linter menangkap kasus ini dengan memverifikasi keberadaan setiap ID referensi di dalam recordMap. Jika ADR 1 menyatakan Superseded by 99 namun tidak ada Record dengan ID 99, pesan error spesifik langsung dihasilkan. Bukti ini berasal dari test case TestLinter_BrokenReferences yang dijalankan secara deterministik.

superseded points to non-existent:
  ADR 1: Status Superseded by 99
  → Error: superseded by non-existent ADR 99

supersedes points to non-existent:
  ADR 1: Status Accepted, Supersedes: 99
  → Error: supersedes non-existent ADR 99

Biaya Tersembunyi: Lineage Drift Tanpa Deteksi

Biaya tersembunyi dari ketiadaan validasi otomatis bukan hanya waktu deteksi, tetapi akumulasi kepercayaan palsu bahwa dokumentasi ADR masih akurat. Setiap kali engineer menambahkan ADR baru tanpa memutakhirkan ADR lama, tercipta discrepancy yang hanya akan terdeteksi saat inspeksi manual. Pada tim kecil, hal ini mungkin tidak terasa. Namun begitu skala tim bertambah, waktu yang terbuang untuk mencari konsistensi manual berlipat ganda tanpa bound yang jelas.

Setup Eksperimen: 3 ADR Evolusi Arsitektur

Eksperimen lab ini memodelkan tiga skenario ADR yang merepresentasikan evolusi arsitektur nyata. ADR 1 merekam keputusan awal menggunakan Modular Monolith. ADR 2 menggantikan ADR 1 setelah tim tumbuh melebihi 20 engineer dan membutuhkan scaling independen untuk notification service. ADR 3 menolak usulan Event Sourcing karena kebutuhan audit trail masih terpenuhi oleh relational log table standar. Ketiganya divalidasi bersama melalui linter untuk memastikan konsistensi lineagenya.

Output demo CLI membuktikan bahwa ketiga ADR berhasil diparse dari string Markdown dan diterjemahkan menjadi struct Record. Lineage chain ADR 1 → ADR 2 terdeteksi sebagai valid: ADR 1 berstatus Superseded dengan reference ke 2, dan ADR 2 berstatus Accepted dengan klaim Supersedes: 1. Apa Artinya Linter Passed di Lab Ini?

Hasil linter yang passing adalah bukti kondisi necessary, bukan sufficient. Ia membuktikan bahwa ketiga ADR memenuhi invariant struktural: format parsable, nomor urut monotonik, dan tautan supersesi timbal-balik utuh. Namun, linter tidak menilai apakah keputusan Modular Monolith memang tepat, atau apakah penolakan Event Sourcing didasarkan pada analisis yang komprehensif. Kualitas substansi keputusan tetap tanggung jawab review manusia.

Trade-off: Enforced Structure vs Dokumentasi Fleksibel

Validasi struktural ADR membawa trade-off mendasar: semakin ketat format yang dipaksakan, semakin rendah fleksibilitas penulisan konteks arsitektur. Lab ini memilih path enforceable machine-checkable, artinya parser akan menolak ADR yang tidak mengikuti skema tetap. Di sisi lain, pendekatan ini memungkinkan CI/CD gate yang andal. Tim yang membutuhkan nuansa lebih kaya bisa menambahkan section tambahan di luar yang diparsing, selama tiga section wajib tetap ada.

Validasi Paralel: Goroutine + Mutex untuk Agregasi Error

Pola validasi konkuren pada linter menunjukkan praktik Go yang tepat untuk parallel error aggregation. Setiap Record divalidasi dalam goroutine terpisah, menghasilkan slice error lokal yang hanyadigabungkan ke global errs slice setelah acquire mutex. Pola ini menghindari race condition pada write ke shared error slice. Meskipun validasi pada 3 record tidak memberikan gain performa signifikan, pola ini dapat diskalakan untuk hundred-an ADR tanpa perubahan struktur kode.

Before vs After: Otomasi Linter Menghilangkan Human Error

Perbandingan before-after menunjukkan bahwa automasi linter menutup celah deteksi yang secara konsisten terlewatkan pada review manual. Empat skenario failure yang tercatat dalam test suite—dangling reference, mismatched link, non-monotonic ID, dan self-supersession—semuanya lolos dari radar reviewer manusia tetapi langsung tertangkap oleh automated check. Ini bukan berarti linter menggantikan peran arsitek, melainkan mengurangi beban kognitif pada hal-hal yang bersifat mekanis.

Batasan Lab: Validasi Format, Bukan Kualitas Keputusan

Batasan paling penting dari lab ini adalah ia hanya memeriksa kepatuhan format, bukan kebenaran konten. Parser tidak tahu apakah keputusan 'Extract Notification Service to Microservice' adalah keputusan yang tepat—ia hanya memverifikasi bahwa keputusan tersebut ditulis dalam format yang benar dengan relasi supersesi yang konsisten. Klaim validasi otomatis ini berlaku pada jalur yang diuji, bukan jaminan bahwa seluruh ekosistem dokumentasi arsitektur tim sudah bersih.

Edge Case: Keputusan Dibatalkan Tanpa ADR Baru

Kasus tepi yang tidak ditangani oleh linter saat ini adalah penghentian keputusan tanpa dokumentasi formal. Ketika engineer secara diametral menghentikan fitur yang sebelumnya di-accept via ADR, status dokumen tetap Accepted meskipun praktik aktual sudah berubah. Ini menciptakan gap antara dokumentasi dan realitas sistem. Solusi yang direkomendasikan adalah policy tim yang mewajibkan ADR Deprecated sebagai pengganti, bukan penghapusan file.

Apa yang Dibuktikan Oleh Test Suite

Suite pengujian lab ini mencakup 10 test function dengan 18 sub-case yang membuktikan seluruh invariant struktural yang didefinisikan. Parser menangani 6 kasus validasi format (termasuk 9 sub-case invalid). Linter menangani 8 skenario integritas graf (valid sequence, 7 broken reference types). Race detector pada go test -race juga lulus tanpa warning. Bukti ini cakupannya mengikuti skenario test yang didefinisikan — bukan klaim bahwa seluruh kemungkinan edge case production tertutup.

Apa yang Tidak Dibuktikan Oleh Test Suite

Penting untuk mengenali batas bukti dari test suite ini. Test tidak menilai kebenaran substansi keputusan arsitektur yang terdapat di dalam field Content. Test juga tidak membuktikan bahwa linter akan bekerja dengan baik ketika diterapkan pada ratusan file ADR di repositori production. Simulasi berjalan pada string literal di dalam kode, bukan pada file system I/O aktual. Klaim validasi struktural yang dihasilkan test berlaku pada jalur yang diuji, bukan generalisasi ke seluruh spektrum kemungkinan error di lapangan.

Risiko Produksi: False Confidence dari Linter Hijau

Risiko terbesar dari automasi validasi adalah false confidence. Ketika linter menghasilkan output hijau tanpa error, tim cenderung menganggap seluruh aspek dokumentasi arsitektur sudah OK. Padahal, Content field bisa saja berisi penjelasan yang sangat minim atau bahkan placeholder. Linter passing bukan berarti keputusan arsitektur tersebut berkualitas tinggi — ia hanya berarti formatnya konsisten secara struktural. Mitigasi utamanya adalah mempertahankan human review sebagai gate tambahan.

Implementation Checklist: Menerapkan ADR Linter di Tim

Implementasi ADR linter di lingkungan production memerlukan enam langkah praktis. Dimulai dari definisi template Markdown standar yang disepakati tim, dilanjutkan implementasi parser dan linter sesuai pola yang divalidasi di lab. Integrasi CI/CD memastikan violation langsung ditolak pada PR. Langkah terakhir — yang paling sering terlewat — adalah policy enforcement: mengubah budaya tim agar setiap perubahan keputusan arsitektur dicatat sebagai ADR baru, bukan suntingan retroaktif pada ADR lama.

Anti-Pattern: 5 Kebiasaan Buruk Saat Mengadopsi ADR

Lima anti-pattern ini sering muncul saat tim pertama kali mengadopsi ADR. Pola yang paling merusak adalah retroactive edit — suntingan diametral pada ADR yang sudah Accepted. Ini menghancurkan jejak keputusan dan membuat engineer berikutnya membaca konteks yang sudah tidak relevan. ADR linter lab ini dirancang untuk mencegah sebagian besar anti-pattern tersebut secara struktural, meskipun tidak menutupi masalah adopsi budaya tim.

ADR Diubah Jadi Data yang Bisa Dicek, Bukan Hanya Dokumen

Pelajaran rekayasa perangkat lunak utama dari lab ini adalah pergeseran perspektif: dari ADR sebagai dokumen naratif statis menjadi ADR sebagai record terstruktur yang dapat diverifikasi mesin. Parser dan linter tidak menggantikan judgment arsitek, tetapi mereka menutupi gap mekanisme yang konsisten terlewat oleh review manual. Pola validasi konkuren yang diterapkan di linter juga bersifat generik dan dapat diadaptasi untuk validasi dokumen struktural lain di luar konteks ADR.
