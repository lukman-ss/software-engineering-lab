WebSocket vs Server-Sent Events: Panduan Arsitektur Real-Time Berdasarkan Directionality dan Kompleksitas Protokol

Penulis: Lukman / lukman-ss  |  Seri: Software Engineering Lab 35  |  Topik: Networking & Real-Time Web Architecture
Mental Model Inti: Directionality dictates the protocol: server-push belongs to SSE, bidirectional belongs to WebSocket. Jangan bayar pajak koneksi dua arah jika trafik hanya mengalir satu arah.

1. Pendahuluan / Latar Belakang

Dalam lanskap rekayasa sistem modern, interaktivitas real-time telah bergeser dari sekadar fitur pelengkap menjadi tuntutan mendasar. Pengguna menuntut agar perubahan data, notifikasi transaksi, pergerakan kursor kolaboratif, hingga streaming respons Large Language Model (LLM) dapat tersaji seketika di layar peramban tanpa perlu memicu penyegaran halaman manual.

Namun, antusiasme untuk menghadirkan pengalaman real-time sering kali diiringi oleh keputusan arsitektur yang seragam dan tidak teruji: mengasumsikan bahwa WebSocket adalah satu-satunya protokol standar untuk semua interaksi langsung antara server dan client. Pola pikir default ini menyebabkan banyak arsitek perangkat lunak secara refleks memasang WebSocket bahkan untuk fitur yang murni bersifat satu arah (unidirectional push), seperti notifikasi lonceng pada aplikasi web atau pembaruan metrik pada live dashboard pemantauan server.

Pilihan ini membawa beban operasional yang nyata. Menggunakan WebSocket berarti menukar kesederhanaan model request-response HTTP dengan koneksi TCP persisten non-HTTP yang memerlukan penanganan siklus hidup koneksi secara eksplisit, framing biner kustom, mekanisme heartbeat aplikasi mandiri, serta penyesuaian khusus pada lapisan proxy dan load balancer. Sebaliknya, ekosistem web modern menyediakan Server-Sent Events (SSE) yang berjalan di atas protokol HTTP standar, dirancang khusus untuk mendorong data satu arah dari server ke client dengan keandalan pemulihan koneksi otomatis bawaan browser.

Artikel ini mengkaji secara komprehensif perbedaan mekanistik antara WebSocket (RFC 6455) dan Server-Sent Events (WHATWG SSE) melalui implementasi murni bahasa Go tanpa ketergantungan pada library pihak ketiga. Eksperimen ini dirancang untuk membuktikan batas kapabilitas, trade-off arsitektural, dan determinisme perilaku kedua protokol pada tingkat byte dan frame jaringan.

2. Masalah yang Diselesaikan

Tantangan rekayasa mendasar yang dihadapi para developer adalah menentukan batas trade-off antara kapabilitas protokol dan biaya operasional. Ketika arsitektur salah dalam memilih protokol transport, tim pengembang akan berhadapan dengan salah satu dari dua kegagalan ekstrem:

  • Over-Engineering via WebSocket untuk Use Case Satu Arah: Mengharuskan pengelolaan state koneksi yang sangat rentan di memori instance aplikasi, membutuhkan konfigurasi routing sticky session pada load balancer, dan memaksa penulisan ratusan baris kode client-side untuk menangani rekoneksi manual serta sinkronisasi offset data yang hilang saat koneksi terputus sesaat.
  • Under-Engineering via HTTP Polling: Melakukan request HTTP berulang setiap beberapa detik (short polling) yang menghabiskan bandwidth jaringan dengan overhead header HTTP redundan, membebani database backend, serta menghasilkan latensi semu yang bergantung pada interval polling.

Skenario Nyata: Ledakan Rekoneksi Gateway Notifikasi

Mari telaah studi kasus konkret pada sistem notifikasi perbankan digital. Sistem ini dirancang untuk melayani 50.000 pengguna aktif bersamaan. Arsitek awal memilih WebSocket dengan asumsi fleksibilitas masa depan. Karena WebSocket adalah koneksi raw TCP berstatus stateful, status socket tersimpan di memori instance server tertentu.

Ketika instans gateway di-deploy ulang (rolling restart) untuk pembaruan sistem, 25.000 koneksi WebSocket yang terhubung ke instans tersebut putus secara mendadak. Karena spesifikasi RFC 6455 tidak mendefinisikan mekanisme rekoneksi otomatis, pustaka JavaScript di peramban segera memicu loop rekoneksi manual. Hasilnya adalah badai rekoneksi (thundering herd) yang melumpuhkan gateway baru karena harus memproses puluhan ribu jabat tangan HTTP Upgrade secara simultan. Lebih buruk lagi, event notifikasi yang terkirim selama periode pemutusan koneksi hilang sepenuhnya karena protokol tidak menyediakan offset pelacakan event.

Sebaliknya, jika sistem menggunakan Server-Sent Events (SSE), load balancer dapat mendistribusikan koneksi streaming ke sembarang node tanpa sticky session. Saat satu node restart, API EventSource di peramban secara otomatis menyambung kembali dengan jeda backoff bawaan dan menyertakan header Last-Event-ID. Server baru membaca header tersebut, memutar ulang notifikasi yang terlewat dari buffer penyimpanan, dan menyambungkan kembali client ke stream utama tanpa kehilangan data sama sekali.

Komponen utama sistem terbagi menjadi tiga modul yang saling terisolasi namun diorkestrasi di bawah satu http.ServeMux terpadu:

  1. SSE Hub (internal/sse): Mengelola siklus hidup koneksi peramban yang berlangganan stream. Menyimpan riwayat event dengan sequence ID monotonik, menangani pemutaran ulang (replay) berdasarkan offset Last-Event-ID, dan menyalurkan broadcast secara non-blocking melalui buffer Go channel untuk melindungi stabilitas server saat menghadapi client lambat (slow consumer).
  2. WebSocket Engine (internal/ws): Mengelola transisi dari request HTTP menjadi koneksi raw TCP melalui interface http.Hijacker. Bertanggung jawab atas kalkulasi kriptografi jabat tangan (handshake challenge), penyusunan frame biner, pemrosesan panjang payload adaptif (7-bit, 16-bit, 64-bit), dan bitwise XOR unmasking.
  3. Unified Server Router (internal/server): Menyatukan endpoint /sse, /ws, dan /publish untuk mendemonstrasikan bahwa sebuah aplikasi Go dapat melayani kedua paradigma secara berdampingan tanpa konflik alokasi port.

Langkah 1: Formatting Frame Teks SSE Sesuai Spesifikasi WHATWG

Spesifikasi WHATWG menetapkan format baris teks ketat untuk SSE. Setiap field diberi prefiks nama field, diikuti titik dua dan spasi. Jika payload data memiliki beberapa baris (multi-line), setiap baris harus diawali prefiks data: secara terpisah sebelum diakhiri dengan delimiter ganda \n\n. 

// internal/sse/sse.go:19-36
func (e Event) Format() []byte {
    var sb strings.Builder
    if e.ID > 0 {
        fmt.Fprintf(&sb, "id: %d\n", e.ID)
    }
    if e.Event != "" {
        fmt.Fprintf(&sb, "event: %s\n", e.Event)
    }
    if e.Retry > 0 {
        fmt.Fprintf(&sb, "retry: %d\n", e.Retry)
    }
    lines := strings.Split(e.Data, "\n")
    for _, l := range lines {
        fmt.Fprintf(&sb, "data: %s\n", l)
    }
    sb.WriteString("\n")
    return []byte(sb.String())
}

Langkah 2: Mekanisme Resumption dan Broadcast pada SSE Hub

Hub bertindak sebagai broker in-memory. Ketika client baru terhubung, Hub memeriksa parameter lastID. Semua event di riwayat yang memiliki sequence ID lebih besar dari lastID dikumpulkan ke dalam slice replay. Channel client dibuat dengan kapasitas buffer 64. Saat broadcast dipicu, select non-blocking memastikan subscriber yang macet tidak menahan pengiriman pesan ke subscriber lainnya. 

// internal/sse/sse.go:52-96
func (h *Hub) Broadcast(eventType, data string) Event {
    h.mu.Lock()
    defer h.mu.Unlock()

    evt := Event{
        ID:    h.nextID,
        Event: eventType,
        Data:  data,
        Retry: 2000,
    }
    h.nextID++
    h.history = append(h.history, evt)

    for ch := range h.clients {
        select {
        case ch <- evt:
        default: // Lindungi server dari slow consumer
        }
    }
    return evt
}

func (h *Hub) Subscribe(lastID int) (chan Event, []Event, func()) {
    h.mu.Lock()
    defer h.mu.Unlock()

    var replay []Event
    for _, evt := range h.history {
        if evt.ID > lastID {
            replay = append(replay, evt)
        }
    }

    ch := make(chan Event, 64)
    h.clients[ch] = struct{}{}

    unsubscribe := func() {
        h.mu.Lock()
        defer h.mu.Unlock()
        delete(h.clients, ch)
        close(ch)
    }

    return ch, replay, unsubscribe
}

Langkah 3: Streaming HTTP dengan Flusher dan Keep-Alive Heartbeat

Di lapisan HTTP handler, server memastikan respons tidak tertahan di buffer Go runtime dengan memanfaatkan http.Flusher. Header X-Accel-Buffering: no secara eksplisit ditambahkan untuk menginstruksikan reverse proxy Nginx agar segera menyalurkan setiap byte data ke client. Ticker 15 detik mengirim komentar baris keep-alive (: keep-alive\n\n) agar socket tidak ditutup oleh timeout firewall jaringan. 

// internal/sse/sse.go:98-151
func (h *Hub) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    flusher, ok := w.(http.Flusher)
    if !ok {
        http.Error(w, "Streaming unsupported", http.StatusInternalServerError)
        return
    }

    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Cache-Control", "no-cache")
    w.Header().Set("Connection", "keep-alive")
    w.Header().Set("X-Accel-Buffering", "no")

    lastID := 0
    if idHeader := r.Header.Get("Last-Event-ID"); idHeader != "" {
        if id, err := strconv.Atoi(idHeader); err == nil {
            lastID = id
        }
    }

    ch, replay, unsub := h.Subscribe(lastID)
    defer unsub()

    for _, evt := range replay {
        w.Write(evt.Format())
    }
    flusher.Flush()

    ctx := r.Context()
    ticker := time.NewTicker(15 * time.Second)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            return
        case evt, ok := <-ch:
            if !ok { return }
            w.Write(evt.Format())
            flusher.Flush()
        case <-ticker.C:
            w.Write([]byte(": keep-alive\n\n"))
            flusher.Flush()
        }
    }
}

Langkah 4: WebSocket Handshake Kriptografis dan Hijacking TCP

Pada sisi WebSocket, proses jabat tangan RFC 6455 diawali dengan memvalidasi keberadaan header Upgrade: websocket dan membaca nilai Sec-WebSocket-Key. Kunci ini digabungkan dengan GUID standar 258EAFA5-E914-47DA-95CA-C5AB0DC85B11, di-hash menggunakan SHA-1, dan dikonversi ke Base64 untuk membentuk header Sec-WebSocket-Accept. Interface http.Hijacker kemudian dipanggil untuk memutuskan koneksi dari siklus hidup HTTP normal. 

// internal/ws/ws.go:31-76
func Upgrade(w http.ResponseWriter, r *http.Request) (*Conn, error) {
    key := r.Header.Get("Sec-WebSocket-Key")
    h := sha1.New()
    h.Write([]byte(key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))
    accept := base64.StdEncoding.EncodeToString(h.Sum(nil))

    hj, ok := w.(http.Hijacker)
    if !ok {
        return nil, errors.New("cannot hijack connection")
    }

    netConn, bufrw, err := hj.Hijack()
    if err != nil {
        return nil, err
    }

    resp := "HTTP/1.1 101 Switching Protocols\r\n" +
        "Upgrade: websocket\r\n" +
        "Connection: Upgrade\r\n" +
        "Sec-WebSocket-Accept: " + accept + "\r\n\r\n"

    bufrw.WriteString(resp)
    bufrw.Flush()

    return &Conn{rw: bufrw, closer: netConn}, nil
}

Langkah 5: Decoding Frame Biner RFC 6455 dan Bitwise XOR Unmasking

Setelah pembajakan soket selesai, parsing data dilakukan pada tingkat bit. Dua byte pertama frame menentukan Opcode dan panjang payload. Jika bit MASK menyala (wajib untuk pesan dari client ke server sesuai RFC 6455 Section 5.1), 4 byte berikutnya adalah masking key. Payload data kemudian dipulihkan menggunakan operasi bitwise XOR: data[i] ^= mask[i % 4]. 

// internal/ws/ws.go:84-127
func (c *Conn) ReadFrame() (opcode byte, payload []byte, err error) {
    var head [2]byte
    io.ReadFull(c.rw, head[:])

    opcode = head[0] & 0x0F
    masked := (head[1] & 0x80) != 0
    length := uint64(head[1] & 0x7F)

    if length == 126 {
        var ext [2]byte
        io.ReadFull(c.rw, ext[:])
        length = uint64(binary.BigEndian.Uint16(ext[:]))
    } else if length == 127 {
        var ext [8]byte
        io.ReadFull(c.rw, ext[:])
        length = binary.BigEndian.Uint64(ext[:])
    }

    var mask [4]byte
    if masked {
        io.ReadFull(c.rw, mask[:])
    }

    data := make([]byte, length)
    io.ReadFull(c.rw, data)

    if masked {
        for i := range data {
            data[i] ^= mask[i%4] // Pemulihan payload asli via XOR
        }
    }

    return opcode, data, nil
}

7. Trade-off & Batasan Implementasi

Meskipun Server-Sent Events menawarkan banyak keunggulan dalam kesederhanaan, protokol ini memiliki batasan yang tidak dapat dikompromikan. Memahami trade-off ini sangat krusial bagi arsitek perangkat lunak sebelum mengambil keputusan final:

  • Keterbatasan Tipe Payload pada SSE: Spesifikasi WHATWG membatasi SSE secara eksklusif untuk payload teks UTF-8. Jika aplikasi harus mengirim data biner terkompresi (seperti format Protobuf atau audio PCM mentah), data harus di-encode ke Base64 terlebih dahulu. Hal ini menghasilkan penambahan ukuran payload sekitar 33%. Sebaliknya, WebSocket mendukung frame biner asli (Opcode 0x2) tanpa overhead encoding.
  • Batas Koneksi HTTP/1.1: Pada lingkungan yang masih menggunakan HTTP/1.1, peramban membatasi koneksi maksimal 6 socket persisten per domain host. Jika pengguna membuka beberapa tab browser secara bersamaan, saluran SSE akan mengalami starvation. Masalah ini sepenuhnya terselesaikan saat beralih ke HTTP/2 atau HTTP/3 berkat fitur stream multiplexing.
  • Batasan Khusus Lab 35: Implementasi pada repositori ini dirancang untuk tujuan pedagogis dengan isolasi mekanika protokol. Masking key pada WebSocket dialer menggunakan nilai konstan (bukan random cryptographically secure), parser frame belum mendukung fragmented continuation (Opcode 0x0), dan buffer riwayat SSE disimpan dalam slice memori tak terbatas (unbounded) yang membutuhkan penggusuran (eviction ring buffer) untuk penggunaan produksi.

8. Kapan Menggunakan Pattern Ini

Gunakan panduan keputusan berikut untuk menentukan protokol transport real-time pada arsitektur Anda:

Pilih Server-Sent Events (SSE) Jika:

  • Karakteristik Trafik Unidirectional: Aliran data murni bergerak dari server ke client. Contoh ideal mencakup: sistem notifikasi aktivitas pengguna, live update skor pertandingan olahraga, pembaruan harga bursa saham (ticker), dan streaming respons kata-demi-kata pada aplikasi berbasis Generative AI / Large Language Models (sebagaimana diterapkan oleh OpenAI API dan Anthropic Claude).
  • Mengutamakan Kemudahan Operasional: Arsitektur sistem mengandalkan infrastruktur cloud standar dengan lapisan reverse proxy (Nginx, Envoy, Cloudflare) dan tidak menginginkan kompleksitas konfigurasi sticky session.
  • Kebutuhan Auto-Healing Tinggi: Aplikasi berjalan pada jaringan mobile yang sering mengalami pemutusan koneksi sesaat, di mana pemulihan posisi data otomatis via Last-Event-ID sangat krusial.

Pilih WebSocket Jika:

  • Karakteristik Trafik True Full-Duplex: Client harus terus-menerus mengirimkan data masukan ke server dengan latensi serendah mungkin pada saluran yang sama. Contoh: kanvas kolaboratif real-time (seperti Figma), game multiplayer, aplikasi trading finansial frekuensi tinggi dengan eksekusi instan, atau aplikasi video/audio conferencing signaling.
  • Payload Biner Murni: Sistem mentransmisikan data audio, video chunking, atau format serialisasi biner bervolume tinggi di mana overhead encoding Base64 tidak dapat ditoleransi.
