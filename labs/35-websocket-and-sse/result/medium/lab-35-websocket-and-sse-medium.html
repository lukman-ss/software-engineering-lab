WebSocket vs Server-Sent Events: Memilih Protokol Real-Time Berdasarkan Directionality dan Kompleksitas

Memilih Protokol Real-Time Berdasarkan Directionality dan Kompleksitas

Dilema Protokol Real-Time Modern

Banyak tim rekayasa perangkat lunak menganggap WebSocket sebagai standar de facto untuk semua kebutuhan real-time. Padahal, memasang WebSocket untuk use case satu arah seperti notifikasi atau live dashboard memperkenalkan overhead operasional yang tidak perlu. SSE menyediakan mekanisme server push berbasis HTTP murni yang jauh lebih ramah proxy dan hemat resource.

Mental Model: Directionality Rule

Keputusan arsitektural dapat disederhanakan melalui satu pertanyaan fundamental: apakah client perlu mengirim pesan ke server secara independen pada saluran yang sama? Jika komunikasi hanya satu arah dari server ke client, SSE memberikan solusi paling bersih. WebSocket hanya diwajibkan ketika komunikasi dua arah berlatensi rendah mutlak diperlukan.

Topologi Arsitektur Lab 35

Lab 35 mendemonstrasikan kedua protokol di bawah satu HTTP ServeMux di internal/server/server.go. Pendekatan zero external dependencies membongkar bagaimana Go standard library mampu menangani streaming HTTP (SSE) melalui http.Flusher sekaligus protokol non-HTTP (WebSocket) melalui interface http.Hijacker.

Anatomi Server-Sent Events (SSE)

Spesifikasi WHATWG mendefinisikan SSE sebagai respons HTTP berdurasi panjang dengan format text/event-stream. Setiap event terdiri dari field id, event, retry, dan data yang diakhiri oleh double newline. Karena berbasis HTTP murni, SSE langsung kompatibel dengan infrastruktur web yang ada seperti TLS termination dan monitoring.

Format Event SSE: Multi-Line Framing

Method Format() pada struct Event mematuhi aturan WHATWG secara ketat. Jika payload mengandung baris baru, setiap baris harus diawali prefiks 'data: '. Kegagalan memecah baris baru akan merusak parsing client EventSource di browser. Karakter double newline di akhir menjadi sinyal bahwa frame event telah lengkap.

func (e Event) Format() []byte {
    var sb strings.Builder
    if e.ID > 0 { fmt.Fprintf(&sb, "id: %d\n", e.ID) }
    if e.Event != "" { fmt.Fprintf(&sb, "event: %s\n", e.Event) }
    if e.Retry > 0 { fmt.Fprintf(&sb, "retry: %d\n", e.Retry) }
    lines := strings.Split(e.Data, "\n")
    for _, l := range lines {
        fmt.Fprintf(&sb, "data: %s\n", l)
    }
    sb.WriteString("\n")
    return []byte(sb.String())
}

SSE Hub: Resumption via Last-Event-ID

Fitur paling unggul dari SSE adalah kemampuan auto-reconnect bawaan yang dipadukan dengan header Last-Event-ID. Ketika koneksi putus, browser secara otomatis mengirimkan ID terakhir yang diterimanya. Hub di backend menyaring riwayat in-memory dan langsung memutar ulang event yang terlewat sebelum menyambungkan client ke antrean live.

func (h *Hub) Subscribe(lastID int) (chan Event, []Event, func()) {
    h.mu.Lock(); defer h.mu.Unlock()
    var replay []Event
    for _, evt := range h.history {
        if evt.ID > lastID { replay = append(replay, evt) }
    }
    ch := make(chan Event, 64)
    h.clients[ch] = struct{}{}
    return ch, replay, func() { ... }
}

Loop Streaming HTTP & Heartbeat

Koneksi SSE memerlukan http.Flusher agar frame teks terkirim ke client seketika tanpa tertahan di buffer Go runtime. Loop select memantau tiga hal: sinyal pemutusan dari context request, event baru dari broadcast channel, dan ticker 15 detik yang mengirim komentar ': keep-alive' untuk mencegah proxy memutus koneksi akibat idle timeout.

flusher, ok := w.(http.Flusher)
for {
    select {
    case <-ctx.Done(): return
    case evt, ok := <-ch:
        if !ok { return }
        w.Write(evt.Format())
        flusher.Flush()
    case <-ticker.C:
        w.Write([]byte(": keep-alive\n\n"))
        flusher.Flush()
    }
}

Anatomi Protokol WebSocket (RFC 6455)

WebSocket dirancang oleh IETF RFC 6455 untuk menghadirkan kanal dua arah berlatensi rendah. Koneksi diawali dengan request HTTP biasa yang meminta Upgrade. Server merespons dengan 101 Switching Protocols dan menghitung Sec-WebSocket-Accept menggunakan GUID standar. Setelah itu, socket sepenuhnya beralih ke parsing frame biner.

Handshake Upgrade & Connection Hijacking

Fungsi Upgrade() mendemonstrasikan kalkulasi kriptografis Sec-WebSocket-Accept sesuai RFC 6455. Dengan memanggil w.(http.Hijacker).Hijack(), Go melepaskan kendali socket TCP dari net/http runtime. Server menulis respons 101 Switching Protocols secara langsung ke buffer TCP dan membungkus socket ke dalam struct Conn kustom.

h := sha1.New()
h.Write([]byte(key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))
accept := base64.StdEncoding.EncodeToString(h.Sum(nil))

hj, ok := w.(http.Hijacker)
netConn, bufrw, err := hj.Hijack()
resp := "HTTP/1.1 101 Switching Protocols\r\n" +
    "Upgrade: websocket\r\nConnection: Upgrade\r\n" +
    "Sec-WebSocket-Accept: " + accept + "\r\n\r\n"
bufrw.WriteString(resp); bufrw.Flush()

Struktur Frame Biner RFC 6455

Struktur frame RFC 6455 dirancang sangat efisien. Header terkecil hanya membutuhkan 2 byte. Panjang payload dikodekan secara adaptif: 7 bit untuk pesan kecil, 16 bit untuk ukuran menengah, dan 64 bit untuk data raksasa. Mekanisme masking wajib diterapkan oleh client untuk mencegah eksploitasi cache poisoning pada proxy perantara.

Parsing Frame & Operasi XOR Masking

Method ReadFrame() mengekstrak header biner dari stream TCP. Jika bit MASK aktif, server membaca 4 byte masking key. Setiap byte payload kemudian di-XOR dengan mask[i % 4] untuk membuka enkripsi transport. Sifat simetris XOR memungkinkan decoding langsung di memori secara cepat tanpa alokasi buffer sekunder.

var head [2]byte
io.ReadFull(c.rw, head[:])
opcode = head[0] & 0x0F
masked := (head[1] & 0x80) != 0
length := uint64(head[1] & 0x7F)
// ... handle extended length ...
if masked {
    io.ReadFull(c.rw, mask[:])
    io.ReadFull(c.rw, data)
    for i := range data {
        data[i] ^= mask[i%4] // Bitwise XOR unmasking
    }
}

WriteFrame: Konstruksi Frame Outbound

Method WriteFrame() menyusun paket biner untuk dikirim ke socket. Mutex c.mu menjamin bahwa penulisan frame bersifat atomic sehingga dua goroutine tidak mencampur aduk byte frame di TCP stream. Bit FIN diset ke 1 untuk menandakan pesan mandiri tanpa fragmentasi lanjutan.

func (c *Conn) WriteFrame(opcode byte, payload []byte, mask bool) error {
    c.mu.Lock(); defer c.mu.Unlock()

    b0 := byte(0x80) | (opcode & 0x0F) // FIN=1

Server Loop: Echo Teks & Reversal Biner

Loop pemrosesan WebSocket di server menangani berbagai tipe frame kontrol dan data. Untuk teks, server menambahkan prefiks 'echo: '. Untuk biner, payload dibalik urutan byte-nya sebelum dikirim kembali. Reversal ini memberikan bukti deterministik bahwa protokol mampu mentransfer biner murni tanpa kompromi.

switch op {
case ws.OpClose:
    conn.WriteFrame(ws.OpClose, nil, false); return
case ws.OpPing:
    conn.WriteFrame(ws.OpPong, data, false)
case ws.OpText:
    conn.WriteFrame(ws.OpText, append([]byte("echo: "), data...), false)
case ws.OpBinary:
    rev := make([]byte, len(data))
    for i := range data { rev[i] = data[len(data)-1-i] }
    conn.WriteFrame(ws.OpBinary, rev, false)
}

Matriks Evaluasi: WebSocket vs SSE

Matriks perbandingan memperjelas trade-off arsitektural. WebSocket menawarkan kemampuan full-duplex dan dukungan biner dengan kompensasi hilangnya auto-reconnect bawaan dan meningkatnya kerumitan proxy. SSE memberikan ketahanan jaringan otomatis dan dukungan native HTTP/2 stream multiplexing.

Tantangan Proxy, Firewall & Gateway

Koneksi jangka panjang rentan terhadap timeout dan pemotongan oleh proxy perantara. WebSocket kerap terhambat oleh firewall korporat yang mencurigai protokol non-HTTP. SSE menghadapi risiko proxy buffering di Nginx, yang dapat diselesaikan dengan menyetel X-Accel-Buffering: no atau menonaktifkan proxy_buffering.

Dampak HTTP/2 & Multiplexing Aliran

Revolusi HTTP/2 secara dramatis meningkatkan daya tarik SSE. Melalui stream multiplexing, puluhan saluran SSE dapat berbagi satu koneksi TCP tanpa batasan 6 koneksi per domain. Sebaliknya, WebSocket memerlukan implementasi RFC 8441 yang rumit karena HTTP/2 melarang mekanisme connection upgrade tradisional.

Studi Kasus Nyata: Notifikasi & AI Tokens

Tren modern membuktikan penerapan aturan directionality. Layanan AI generative seperti OpenAI ChatGPT memilih SSE untuk men-stream token kata demi kata ke browser karena request prompt sudah selesai di awal. Sebaliknya, aplikasi seperti Figma atau multiplayer gaming mengandalkan WebSocket karena user terus-menerus mengirimkan data interaktif.

Checklist Keputusan Arsitektur Real-Time

Gunakan checklist ini dalam tahap perancangan sistem real-time. Jika komunikasi upstream dapat dipenuhi melalui HTTP POST standar dan client hanya mendengarkan event, SSE adalah pilihan terbaik. Pastikan konfigurasi reverse proxy telah disesuaikan dan kapasitas file descriptor sistem operasi memadai.

Tiga Prinsip Inti Komunikasi Real-Time

Sistem real-time yang elegan memilih protokol berdasarkan karakteristik data transport. Hindari godaan over-engineering dengan memasang WebSocket di setiap use case. Dengan memilih SSE untuk pola satu arah dan WebSocket untuk pola interaktif dua arah, sistem tetap efisien, mudah di-scale, dan tahan banting.
