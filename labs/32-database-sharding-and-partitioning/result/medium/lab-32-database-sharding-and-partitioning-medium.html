Masalah Nyata: Batasan Skala Database Monolitik

Dalam arsitektur backend skala hiper, mesin database monolitik pada akhirnya akan membentur batasan fisik perangkat keras vertikal. Ketika kapasitas working set memori terlewati, operasi degrade menjadi siklus latensi disk-bound sambil pemeliharaan administratif seperti VACUUM atau DDL migrations mengunci throughput produksi secara parah. Lebih buruk lagi, ketika tim rekayasa beralih ke sharding horizontal menggunakan kunci timestamp sekuensial, trafik tulis justru terjebak total pada satu shard aktif. Sementara itu, pencarian sekunder tanpa shard key memicu badai broadcast scatter-gather yang jenuhkan CPU di seluruh node.

Mengapa Hash Modulo Sederhana & Shard Monotonik Gagal?

Pendekatan naif kerap mengimplementasikan sharding menggunakan operator modulo sederhana hash(key) % N. Ketika sistem perlu menambah node ke-5 untuk mengatasi lonjakan beban, rumus modulo berubah seketika dan memaksa hampir 80 persen data berpindah antar server di jaringan. Proses resharding ini menyebabkan lonjakan transfer data yang menghabiskan bandwidth, invalidasi cache masif, dan sering memicu outage kaskade yang catastrophik. Selain itu, penggunaan auto-increment lokal di masing-masing shard mengakibatkan bentrokan primary key, sedangkan query tanpa shard key membebani seluruh server secara bersamaan.

Mental Model: Logical Partitioning vs Physical Sharding

Mental model sistem data terdistribusi bertumpu pada pemisahan konsep yang tegas antara partisi logis dan sharding fisik. Logical Partitioning adalah fitur mesin database tunggal (seperti declarative partitioning di PostgreSQL) yang membagi file fisik tabel berdasarkan rentang waktu untuk mempercepat query pruning dan pembuangan data historis tanpa beban garbage collection. Sebaliknya, Physical Sharding adalah arsitektur shared-nothing di mana setiap shard merupakan instance database mandiri dengan CPU, RAM, dan storage terisolasi, diperintah oleh cluster router dan Global Secondary Indexes.

type PartitionRange struct {
    Name  string; Start time.Time; End time.Time // Range [Start, End)
}
type Table struct { // Single Engine Logical Partitioning
    Name string; partitions []*Partition // Pruning lokal via overlap check
}
type Cluster struct { // Multi-Node Physical Sharding
    shards map[string]*Shard // Server fisik independen
    router Router            // Consistent Hash Ring dengan Virtual Nodes
    gsi    *GlobalSecondaryIndex // Lookup Vindex mapping non-shard keys
}

Pipeline End-to-End: Routing, Pruning, & GSI Resolution

Pipeline eksekusi ini menggambarkan bagaimana database menangani berbagai pola akses data secara efisien. Pada operasi temporal di single node, query planner langsung memangkas (pruning) partisi yang tidak relevan sehingga I/O disk berkurang drastis. Pada cluster sharded, operasi write dan read yang menyertakan sharding key diarahkan secara presisi ke satu node spesifik via consistent hash ring. Ketika client mencari data berdasarkan atribut non-shard key seperti email, Global Secondary Index memetakan email ke shard key terkait sehingga kueri tetap menjadi point-lookup 1-node dan menghindari bencana broadcast paralel.

Implementasi Inti: Consistent Hashing Ring dengan Virtual Nodes

Potongan kode ini merupakan mesin pengarah utama dalam modul internal/sharding/sharding.go. Struktur ConsistentHashRouter merepresentasikan ruang cincin 64-bit yang dipetakan oleh ribuan virtual nodes (misal 100 vnodes per physical shard). Saat kunci data masuk, fungsi hashKey menghitung nilai FNV-1a 64-bit, lalu fungsi sort.Search mengeksekusi binary search dalam waktu logaritmik O(log V) untuk menemukan virtual node pertama yang memiliki nilai hash lebih besar atau sama. Jika nilai hash melewati batas maksimum ring, pencarian wrap-around kembali ke indeks 0, menjamin distribusi seragam.

func (ch *ConsistentHashRouter) GetShard(key string) (string, error) {
    ch.mu.RLock(); defer ch.mu.RUnlock()
    if len(ch.ring) == 0 { return "", ErrShardNotFound }
    h := hashKey(key)
    // Binary search vnode pertama dengan hash >= h
    idx := sort.Search(len(ch.ring), func(i int) bool {
        return ch.ring[i].hash >= h
    })
    if idx == len(ch.ring) { idx = 0 } // Wrap-around ke awal ring
    return ch.ring[idx].shardID, nil
}

Failure Path: Bencana Shard Key Monotonik & Resharding Modulo

Bukti failure path ini diambil langsung dari hasil eksekusi program demo cmd/demo/main.go. Pada Skenario A, penggunaan kunci sharding monotonik berbasis tanggal kalender menyebabkan 1.000 dari 1.000 data masuk ke satu node shard-2, membuktikan bagaimana shard key yang salah memusatkan beban 100 persen dan melumpuhkan kapasitas I/O satu server. Pada Skenario C, saat cluster melakukan scale-out dari 4 menjadi 5 node, algoritma hash modulo memindahkan 7.984 dari 10.000 key (79.84 persen). Sebaliknya, consistent hashing hanya memindahkan 1.200 key (12.00 persen), membuktikan keunggulan arsitekturalnya.

Mekanisme vs Gejala: Evaluasi Strategi Partisi & Sharding

Tabel ini mengevaluasi spektrum lengkap solusi skalabilitas database. Logical partitioning sangat ampuh untuk mengelola siklus hidup data besar pada satu mesin (seperti membuang data lama secara instan tanpa operasi DELETE/VACUUM yang lambat), namun tidak mampu mengatasi keterbatasan memori dan CPU server tunggal. Untuk arsitektur multi-node, modulo hashing terbukti berbahaya saat cluster bertumbuh karena merombak mayoritas lokasi data. Consistent hashing dengan virtual nodes menjadi standar emas karena meminimalkan migrasi, sementara Global Secondary Index menghilangkan ketergantungan pada scatter-gather broadcast yang boros sumber daya.

3 Keputusan Desain Kritis Arsitektur Sharding

Tiga keputusan arsitektural ini menentukan keberhasilan transisi dari database monolitik ke sistem terdistribusi. Pertama, pemilihan sharding key harus memprioritaskan atribut dengan sebaran nilai yang sangat beragam (high cardinality) seperti tenant ID atau user ID guna mendistribusikan data secara seimbang ke seluruh node. Kedua, router wajib menerapkan consistent hashing dengan virtual nodes yang cukup (50 hingga 150 vnodes) agar penambahan node baru tidak memicu perombakan data global. Ketiga, query non-shard key harus dilayani oleh Global Secondary Index untuk mencegah broadcast paralel yang menghancurkan throughput cluster.

Trade-off Arsitektur: Sharding vs Kompleksitas Terdistribusi

Keputusan mengadopsi physical sharding selalu membawa kompromi teknik yang signifikan. Di satu sisi, sistem memperoleh skalabilitas linear dan isolasi kegagalan di mana matinya satu server tidak melumpuhkan seluruh aplikasi. Namun di sisi lain, pengembang harus membayar harga arsitektural yang mahal: hilangnya kapabilitas SQL JOIN antar tabel yang berbeda shard, tingginya latensi koordinasi transaksi Two-Phase Commit, serta keharusan mengelola overhead double-write untuk menjaga konsistensi Global Secondary Index.

Validasi Konkurensi: 200 Worker Simultan pada Sharded Cluster

Uji konkurensi TestConcurrentClusterAccess memverifikasi ketahanan cluster saat diserbu oleh 200 goroutine simultan yang melakukan insert, pembacaan berbasis shard key, dan point-lookup via GSI. Karena setiap instance Shard dan struktur GlobalSecondaryIndex memiliki sync.RWMutex masing-masing, penguncian data bersifat granular sehingga operasi pada shard-1 tidak menghalangi operasi pada shard-2. Pengujian dengan flag -race membuktikan ketiadaan memory race condition dan menegaskan integritas data tersimpan secara utuh tepat 200 record.

func TestConcurrentClusterAccess(t *testing.T) {
    router := sharding.NewConsistentHashRouter(50, []string{"s1", "s2", "s3", "s4"})
    cluster := sharding.NewCluster(router)
    var wg sync.WaitGroup; numOps := 200
    for i := 0; i < numOps; i++ {
        wg.Add(1)
        go func(idx int) {
            defer wg.Done()
            sk := fmt.Sprintf("tenant-%d", idx%10)
            recID := fmt.Sprintf("id-%d", idx)
            email := fmt.Sprintf("user-%d@test.com", idx)
            _ = cluster.Insert(sharding.Record{ID: recID, ShardKey: sk, Email: email, Data: "concurrent-test"})
            _, _ = cluster.GetByShardKey(sk, recID)
            _, _ = cluster.GetByEmailUsingGSI(email, recID)
        }(i)
    }
    wg.Wait()
    // Assert: total seluruh record di seluruh shard == 200 (Zero Data Loss)
}

Test 1: Validasi Query Pruning pada Range Partitioning

Unit test pertama memvalidasi mekanisme pemangkasan partisi pada internal/partitioning/table.go. Tabel orders dikonfigurasikan dengan tiga rentang partisi bulanan. Saat kueri range dieksekusi khusus untuk bulan Februari 2026, sistem secara cerdas mengevaluasi batasan waktu partisi dan hanya memindai partisi p2026_02 (PartitionsScanned=1 dari 3). Selain itu, pengujian membuktikan bahwa method DropPartition menghapus seluruh data bulan Januari seketika secara O(1) tanpa perlu memindai dan menghapus baris satu per satu.

func TestPartitionPruning(t *testing.T) {

    tbl := partitioning.NewTable("orders", ranges)

Test 2: Evaluasi Relokasi Data Scale-Out (5.000 Keys)

Pengujian kedua membandingkan dampak scale-out cluster dari 3 node menjadi 4 node terhadap 5.000 kunci data unik. Algoritma modulo hashing terbukti merelokasi 3.756 kunci (75.12 persen), memvalidasi model matematika di mana penambahan node ke-4 mengacak ulang tiga perempat penempatan data. Sebaliknya, router consistent hashing dengan 150 virtual nodes hanya memindahkan 800 kunci (16.00 persen). Data yang tersisa (84 persen) tetap berada di shard aslinya tanpa perlu dipindahkan sama sekali melalui jaringan.

func TestRoutingAndConsistentHashRelocation(t *testing.T) {
    numKeys := 5000
    modRouter := sharding.NewModuloRouter([]string{"shard-1", "shard-2", "shard-3"})
    modRouter.AddShard("shard-4") // Scale-out 3 -> 4
    // Hash Modulo memindahkan 3756 / 5000 keys (75.12%)
    chRouter := sharding.NewConsistentHashRouter(150, []string{"shard-1", "shard-2", "shard-3"})
    chRouter.AddShard("shard-4") // Scale-out 3 -> 4
    // Consistent Hash memindahkan 800 / 5000 keys (16.00%)
}

Test 3: Eliminasi Broadcast via Global Secondary Index

Unit test ketiga menguji arsitektur pencarian atribut sekunder yang tidak dijadikan sharding key. Fungsi GetByEmailUsingGSI membuktikan bahwa pemetaan Global Secondary Index memungkinkan sistem menemukan data hanya dengan mengakses 1 shard spesifik tanpa membroadcast ke shard lain. Ketika pencarian dilakukan tanpa bantuan GSI melalui ScatterGatherBroadcast, seluruh 3 shard terpaksa dipindai secara paralel. Pengujian juga memvalidasi bahwa jika klien membatalkan request melalui context.Context, seluruh goroutine broadcast langsung berhenti bekerja dengan aman.

// 1. Direct Point-Lookup menggunakan ShardKey
rec, err := cluster.GetByShardKey("tenant-A", "rec-1") // Langsung ke Shard 0
// 2. Lookup via Global Secondary Index (GSI)
recGSI, err := cluster.GetByEmailUsingGSI("bob@example.com", "rec-2")
// Assert: recGSI.Data == "Bob Data" (Tepat 1 shard dihubungi, 0 broadcast overhead)
// 3. Fallback Scatter-Gather Broadcast
sgRes := cluster.ScatterGatherBroadcast(func(r sharding.Record) bool { return r.Email == "carol@example.com" })
// Assert: sgRes.ShardsQueried == 3 (Broadcast menembus seluruh 3 shard)

Analisis Teknis: Solusi Primary Key Terdistribusi

Dalam database terdistribusi, fitur auto-increment bawaan satu mesin tidak dapat digunakan karena akan menimbulkan tabrakan primary key antar shard. Lab ini menguji dua solusi standar industri. Pertama, RFC 9562 UUIDv7 menghasilkan ID 128-bit independen yang menyematkan 48-bit timestamp pada bit awal, menjamin sifat time-ordered yang ramah indeks B-tree tanpa koordinasi jaringan. Kedua, Sequence Block Allocation meminta jatah alokasi blok angka (misal blok 1.000 ID) ke server sentral, memungkinkan worker menerbitkan ID integer berurutan secara cepat di memori lokal.

Anti-Pattern: Kesalahan Desain Sharding & Reproduksi Lab

Mengabaikan prinsip dasar partisi database dapat melumpuhkan seluruh infrastruktur backend. Anti-pattern paling umum adalah memilih sharding key monotonik seperti tanggal transaksi yang memusatkan seluruh write traffic pada satu mesin database yang malang. Kesalahan fatal lainnya adalah menggunakan rumus hash modulo sederhana yang memicu banjir data saat menambah kapasitas server. Pengembang dapat mereproduksi skenario kegagalan ini secara langsung di lab melalui fungsi demo dan unit test yang telah disediakan.
