Rate Limiting dan Backpressure di Go: Melindungi Sistem Terdistribusi dari Kelebihan Beban

Implementasi Token Bucket, Leaky Bucket, bounded queue backpressure, RFC 6585 HTTP 429, dan AWS Full Jitter di Go murni.
Karya: Lukman / lukman-ss • Software Engineering Lab Seri 25

Sistem terdistribusi modern menghadapi tantangan struktural yang tidak terhindarkan: volume request masuk sering kali melampaui kapasitas pemrosesan downstream worker. Tanpa pertahanan sistematis, ketidakseimbangan beban memicu pembengkakan antrean memori, degradasi latensi dramatis, memory exhaustion (OOM), dan kegagalan bertingkat (cascading failure). Perlindungan terhadap kelebihan beban menuntut kombinasi dua lapis arsitektur: rate limiting di gerbang masuk sistem dan backpressure di aliran pemrosesan internal.

Dalam Software Engineering Lab 25, kami membangun implementasi komprehensif menggunakan pustaka standar Go 1.22+. Proyek ini mengintegrasikan algoritma Token Bucket dan Leaky Bucket, bounded queue backpressure berbasis unbuffered/buffered channel dengan fast rejection, middleware HTTP 429 berbasis RFC 6585, dan algoritma exponential backoff AWS Full Jitter untuk meredam badai percobaan ulang (retry storm).

Mental Model: Penjaga Gerbang vs. Katup Tekanan Internal

Banyak pengembang menganggap penerapan rate limiting saja sudah cukup untuk mengamankan sistem. Anggapan ini keliru. Rate limiting mengontrol akses pada lapisan batas (boundary), sedangkan backpressure mengendalikan aliran internal saat proses downstream melambat.

Mental model inti: Rate limiting adalah penjaga batas yang menentukan apakah klien berhak masuk berdasarkan kuota waktu. Bounded queue backpressure adalah katup internal yang melindungi worker dari antrean tak terbatas. Full jitter retry memecah sinkronisasi klien agar sistem tidak dihantam badai pengulangan saat proses pemulihan berlangsung.

Alur permintaan diproses melalui empat lapisan proteksi berurutan:

[Incoming Request]
        │
        ▼
[HTTP Middleware / Tenant Extractor] ── (RFC 6598 Tenant Key via X-API-Key)
        │
        ▼
[Token Bucket / Rate Limiter] ── (Exceeded? → HTTP 429 + Retry-After)
        │ (Passed)
        ▼
[Bounded Queue / Backpressure Channel] ── (Queue Full? → ErrQueueFull)
        │ (Enqueued)
        ▼
[Worker Pool / Consumer] ── (Little's Law L = λW steady state)
        │
        ▼
[Client with Full Jitter Retry] ── (AWS Jitter Backoff)

Komparasi: Token Bucket vs. Leaky Bucket

Pemilihan algoritma rate limiting harus disesuaikan dengan karakteristik beban kerja sistem:

Dimensi Arsitektur Token Bucket Leaky Bucket
Karakteristik Utama Mengizinkan lonjakan burst hingga kapasitas batas B Menegakkan laju pengeluaran konstan R (traffic smoothing)
Penanganan Lonjakan Menerima request selama token tersedia di wadah Menolak request saat air di wadah telah mencapai kapasitas penuh
Pola Keluaran Trafik Bervariasi mengikuti kedatangan burst yang valid Stabil dan terpola secara periodik
Skenario Penggunaan API Gateway pengguna (Stripe, GitHub, REST public) Egress traffic shaping, NGINX limit_req_module
Dualitas Matematis Token terisi pada laju R; berkurang saat ada request masuk Air bertambah saat ada request masuk; bocor pada laju konstan R

Implementasi Token Bucket di Go

Algoritma TokenBucket menggunakan penghitungan waktu monotonik untuk mengisi ulang token secara proporsional terhadap selang waktu berlalu tanpa memerlukan timer latar belakang:

type TokenBucket struct {
	mu         sync.Mutex
	capacity   float64
	tokens     float64
	refillRate float64
	lastRefill time.Time
}

func (tb *TokenBucket) AllowN(now time.Time, n float64) bool {
	tb.mu.Lock()
	defer tb.mu.Unlock()

	elapsed := now.Sub(tb.lastRefill).Seconds()
	tb.tokens = math.Min(tb.capacity, tb.tokens+elapsed*tb.refillRate)
	tb.lastRefill = now

	if tb.tokens >= n {
		tb.tokens -= n
		return true
	}
	return false
}

Ketika kuota habis, fungsi RetryAfterSeconds menghitung durasi tunggu eksak hingga token yang dibutuhkan terisi kembali, menghasilkan nilai header Retry-After yang deterministik bagi klien.

Bounded Queue Backpressure dan Hukum Little

Teori antrean menegaskan bahwa waktu tunda pengeringan antrean diatur oleh Hukum Little (L = λW). Bila laju kedatangan melebihi kapasitas pemrosesan (λ > μ), kedalaman antrean L akan membesar tanpa batas:

Bila 5.000.000 antrean menumpuk dengan laju konsumsi worker 2.000 item/detik, durasi pengosongan membutuhkan 2.500 detik atau setara 41 menit 40 detik. Selama rentang waktu ini, memori server terkuras dan timeout bertingkat menghantam klien pemanggil.

Implementasi BoundedQueue mencegah penumpukan liar ini menggunakan Go channel berkapasitas tetap yang dipadukan dengan idiom non-blocking select-default:

func (bq *BoundedQueue) TrySubmit(job Job) error {
	bq.mu.Lock()
	if bq.stopped {
		bq.mu.Unlock()
		return ErrQueueStopped
	}
	bq.mu.Unlock()

	select {
	case bq.jobs <- job:
		bq.mu.Lock()
		bq.stats.Accepted++
		bq.mu.Unlock()
		return nil
	default:
		bq.mu.Lock()
		bq.stats.Rejected++
		bq.mu.Unlock()
		return ErrQueueFull
	}
}

Penolakan cepat (fast rejection) ini menghentikan alokasi memori liar dan segera memberitahu upstream caller bahwa sistem sedang mengalami saturasi beban.

Middleware HTTP 429 dan Isolasi Tenant RFC 6598

Pembatasan laju berbasis alamat IP mentah (client IP) berbahaya pada arsitektur Carrier-Grade NAT (RFC 6598, blok alamat 100.64.0.0/10). Dalam skenario ini, ratusan pengguna berada di balik satu gateway publik. Jika satu pengguna melakukan flooding, seluruh pengguna lain di balik IP tersebut akan terblokir secara tidak adil.

Middleware Lab 25 mengekstrak identitas penyewa melalui header X-API-Key (dengan fallback anonymous) dan menerapkan respon standar RFC 6585:

func RateLimitMiddleware(reg *ratelimit.Registry, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		tenant := r.Header.Get("X-API-Key")
		if tenant == "" {
			tenant = "anonymous"
		}

		limiter := reg.Get(tenant)
		if !limiter.Allow() {
			retryAfter := int(limiter.RetryAfterSeconds(1))
			if retryAfter < 1 {
				retryAfter = 1
			}

			w.Header().Set("Retry-After", strconv.Itoa(retryAfter))
			w.Header().Set("Content-Type", "application/json")
			w.WriteHeader(http.StatusTooManyRequests) // RFC 6585: 429
			_ = json.NewEncoder(w).Encode(map[string]interface{}{
				"error":       "rate_limit_exceeded",
				"retry_after": retryAfter,
			})
			return
		}

		next.ServeHTTP(w, r)
	})
}

Sesuai spesifikasi RFC 6585 Bagian 4, respon berstatus 429 MUST NOT disimpan ke dalam cache oleh perantara (reverse proxy atau CDN).

Penanganan Badai Pengulangan via AWS Full Jitter

Ketika ratusan klien menerima galat penolakan dan mengulang request pada interval eksponensial deterministik tanpa keacakan, waktu pengulangan mereka akan jatuh pada detik yang sama. Fenomena thundering herd ini melipatgandakan beban puncak dan menghancurkan proses pemulihan downstream.

Formula AWS Full Jitter yang dirumuskan Marc Brooker mengatasi persoalan ini dengan menyebarkan durasi jeda secara merata di seluruh rentang backoff:

sleep = random(0, min(cap, base * 2^attempt))
func ComputeBackoff(strategy JitterStrategy, attempt int, base, cap time.Duration, prev time.Duration) time.Duration {
	maxSleep := float64(base) * math.Pow(2, float64(attempt))
	if maxSleep > float64(cap) {
		maxSleep = float64(cap)
	}

	switch strategy {
	case FullJitter:
		return time.Duration(rand.Float64() * maxSleep)
	case EqualJitter:
		half := maxSleep / 2
		return time.Duration(half + rand.Float64()*half)
	case DecorrelatedJitter:
		var p float64
		if prev == 0 {
			p = float64(base)
		} else {
			p = float64(prev)
		}
		sleep := float64(base) + rand.Float64()*(p*3-float64(base))
		if sleep > float64(cap) {
			sleep = float64(cap)
		}
		return time.Duration(sleep)
	default:
		return time.Duration(maxSleep)
	}
}

Full Jitter meminimalkan total konsumsi waktu komputasi server saat pemulihan berlangsung dengan menghancurkan keselarasan fasa request ulang klien.

Verifikasi dan Batasan Produksi

Seluruh modul diuji dengan pendeteksi race condition Go untuk memastikan kekokohan konkurensi di bawah beban goroutine simultan:

go test -race -v ./...
# 16/16 PASS (0 data race terdeteksi)

Untuk adopsi skala perusahaan (enterprise production), terdapat tiga batasan implementasi yang perlu dicatat:

  1. Penyimpanan In-Memory Terisolasi: Wadah token disimpan dalam memori RAM instans Go lokal. Arsitektur multi-node membutuhkan Redis cluster dengan script Lua atomik atau sorted sets sliding window.
  2. Backpressure Lingkup Proses: Buffer channel Go beroperasi di dalam satu proses. Backpressure lintas armada membutuhkan perantara pesan terdistribusi (partisi Apache Kafka atau kontrol prefetch RabbitMQ).
  3. Kalibrasi Konstanta: Nilai dasar jeda dan batas maksimum retry wajib dikalibrasi terhadap SLA dan profil latensi downstream layanan target.
